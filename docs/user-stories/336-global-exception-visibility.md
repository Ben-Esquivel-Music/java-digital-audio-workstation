# Global Exception Visibility: Handlers, Log Sink, Notification Bridge

## Motivation

A repo-wide grep for `UncaughtExceptionHandler` over all main source returns **zero matches**. `DawApplication.start` (`DawApplication.java:56` onward) installs the dispatcher, bus, and theme/density/motion managers — but no FX-thread handler; `DawLauncher.main` (`DawLauncher.java:56-64`) installs the GC profile and launches — no default handler either. Every exception escaping an FX event handler falls through to the toolkit's stderr print, and in a jpackaged windowed app **stderr does not exist**. Any handler exception, anywhere, reads as a dead control — the silent "button does nothing" failure class.

The same grep story for logging: no `LogManager`, `FileHandler`, or `readConfiguration` exists in any module's main source, and no `logging.properties` ships beyond the JDK-default console configuration. Every one of the hundreds of `catch`-and-`LOG.log` sites in the tree is therefore **catch-and-discard** in the packaged app. Two examples of the compounding cost (book §1.2):

- The command palette catches a handler's `RuntimeException`, logs a WARNING nobody can read, and **rethrows onto the FX thread where no handler exists** (`CommandPaletteView.java:292-308`) — a failed palette command fails in silence.
- `SettingsDialog.applyKeyBindings` throws mid-apply on the FX thread, uncaught by its caller — a perfectly good conflict message evaporates (its specific rollback-and-surface fix is story 339; the *generic* catch-all that would at least have shown *something* is this story).

For a studio engineer the impact is that failure is indistinguishable from absence: a control that throws looks identical to a control wired to nothing, "it failed yesterday" is unanswerable because no log survives the session, and the audit's hollowness went unnoticed for so long precisely because nothing ever surfaced (book §1 preamble). This is the foundation stage of `docs/design/FAILURE_SURFACING_DESIGN_BOOK.md`: every later failure surface needs somewhere to land.

## Goals

- A **default uncaught-exception handler** (process-wide) installed in `DawLauncher.main` *before* `Application.launch`, so toolkit-startup and background/virtual-thread failures are caught from the first instruction (book §4.1).
- An **FX-thread handler** installed in `DawApplication.start` — FX event-dispatch exceptions are delivered to the thread's own handler, not the default one.
- Both route to one funnel: build a failure fact (book §3.1 — origin, severity, category, fingerprint, message, count, first/last) → write the full stack to the log sink → marshal via `FxDispatcher` to a `NotificationBar` ERROR toast naming the failed action when derivable, the fingerprint's category otherwise. Toast, not modal dialog: a modal raised from an arbitrary failure point can re-enter broken state and block a live audio session; FATAL severity may *offer* a dialog from a clean pulse (book §4.1).
- The funnel is **fingerprint rate-limited** (book §6.2): first occurrence surfaces immediately; repeats within the window (~30 s, the track-budget precedent) are counted silently; a repeat after the window re-surfaces with the accumulated count; each fingerprint's occurrences are accounted for in the story-273 history: the first notice, each re-show carrying the running total since the first occurrence, and a history-only tail entry counting the occurrences after the last notice. The newest notice's running total plus the counts of the tail entries after it equals the number of occurrences. That holds for a fingerprint only while its notices and tails reach the history and are still in it (the history keeps the newest 100 entries). Among the cases where they do not: its notice came before the toasts were armed and the arm-time summary or a FATAL fact's toast stands in for it, or it was only counted beyond the 16 facts kept until arming; its fingerprint was evicted; or the toasts were disarmed while it owed a tail, or before a notice of it ran on the FX thread. An evicted fingerprint's tail and a tail owed at the disarming go to the log file only. Occurrences counted after the disarming are written to the log file when it closes, only on a launch whose session banner says "Exit hold: active", and only those counted before that last write. Counts not yet written when the process ends without the JDK's shutdown reset, such as a crash, are in neither the history nor the log; per fingerprint they are at most one 30 s window of occurrences (`FingerprintRateLimiter`'s class Javadoc, "Accounting"). Counting replaces one history entry per occurrence, which would push every other notification out of the 100-entry history within seconds of a per-frame failure; the alternative "first 5 per window, then counting" was rejected too (studio-engineer ruling, story 336).
- The funnel is **reentrant-safe**: a throw inside the funnel itself is written with a last-resort plain print and never re-enters the funnel.
- A **rotating file log sink**: `java.util.logging` configured programmatically at launch — a rotating `FileHandler` under the per-user settings directory (the root the launcher already writes its GC profile into), bounded size and file count, INFO and above, compact single-line format with thread and logger names (book §4.2). Programmatic, not a bundled properties file the jlink image build could drop.
- A **Help ▸ "Open Log Folder"** menu item makes the sink discoverable (book §2.8).
- Startup ordering per book §6.4: log sink before handlers can fire; handlers before launch; the funnel logs immediately and upgrades to toasts once the dispatcher exists; the first-run wizard shows only after the spine is live.
- **The log sink outlives the JDK's shutdown reset until story 331's exit wait has returned** (story 331, ruling N1).
  - `LogManager`'s own shutdown hook resets (removes and closes) every handler as the exit begins, so a line that another shutdown hook logs reaches no handler today. That covers `ProjectManager.awaitWritesBeforeExit`'s INFO "Waiting up to 30 s for the saves and checkpoints still being written before the application exits" and its WARNING "Saves or checkpoints were still being written 30 s after the application began to exit; the application exits without them, and project.daw holds the last save that finished" (story 331, rulings M1 and N1).
  - The sink holds off that reset while the `daw-exit-write-wait` hook is registered, until its method returns. Then the funnel's default handler writes the tail lines it still owes for the occurrences counted so far, the log manager writes its closing line, and the handlers are flushed and closed; an occurrence counted after that is not written. The hold is bounded at the exit wait's limit plus 5 s. An exit with no exit wait registered skips the hold, but not the tail lines or the closing line. A launch path whose session banner says "Exit hold: inactive" has none of this: the JDK resets at once.

## Goals — Tests

- The book §6.3 gate-4 wiring test (in-process, headless, the repo's established `MainController`-substitute pattern): asserts both handlers are installed at startup, and a deliberately thrown FX-handler exception produces a SEVERE record with full stack in the log file **and** an ERROR toast.
- A background/virtual-thread throw funnels identically through the default handler.
- The log file exists under the user settings directory, records INFO and above, and rotates at its size cap.
- A rate-limiting test: the same fingerprint thrown repeatedly yields at most one toast per window with the count carried on re-show, while the history accounts for every occurrence (the newest notice's running total plus any later tail counts equals the occurrences thrown).
- A reentrancy test: an exception thrown from inside the funnel (e.g. a throwing notification consumer) does not recurse or deadlock — the last-resort print path runs and the app continues.
- A palette regression test: the rethrow at `CommandPaletteView.java:302-306` now lands visibly as an ERROR toast (the *named-command* copy is story 339's refinement; this stage guarantees visibility).
- Help ▸ "Open Log Folder" resolves to the directory the `FileHandler` writes into.
- The exit wait's lines (story 331, ruling N1), binding: a child JVM sets up logging exactly as the packaged launcher does. With a save held past a shortened exit-wait bound, it exits, and its log file holds both lines verbatim.

- **The RT audio path.** Audio-thread code may not log or notify (book §2.3); callback guards, the RT health record/ring, and the pulse drain are story 337 (Stage 3). This spine deliberately excludes the render callback.
- **Engine health surfaces** — watchdog, xrun counter, engine-state cell, clock indicator — story 338 (Stage 5).
- **Constructor injection of the real notification sink** into `DefaultAudioEngineController`/`MixerView`, the keybinding-conflict rollback, and the named palette-failure copy — story 339 (Stage 4).
- **Dialog dismissibility** — story 313 (pattern) and 339 (gate).
- **A logging-façade migration** (SLF4J or similar): explicitly rejected by book §4.2 — the tree has hundreds of existing `Logger.getLogger` sites; the sink upgrades every one of them in a single change, and a façade stays possible later.
- **Dead-wire controls** (a button wired to *nothing*): `INTERACTION_COMPLETENESS_DESIGN_BOOK.md` (stories 341-347). Per book §2.2, "button does nothing" is three defects; this story kills the uncaught-exception and swallowed-validation kinds, the dead-wire kind belongs there.

## Known limits

- **JavaFX's own prints to standard error.** A failure on JavaFX's render thread (`QuantumRenderer` sets a handler of its own that prints, `QuantumRenderer.java:137-140`), in a snapshot callback (`Scene.snapshot`, `Node.snapshot`) or in `PlatformImpl.runAndWait` run on the FX thread is printed to standard error only. Neither handler sees it, and the packaged app has no standard error: a render-thread failure looks like a frozen or black window. This is a JavaFX-internal gap.
- **Failures held in futures, `Task`s and executors.** A failure captured in a `CompletableFuture`, a JavaFX `Task`, an executor's `submit`, a `SubmissionPublisher` or a `ScheduledThreadPoolExecutor` never reaches a thread's top, so neither handler sees it and this story does not cover it. Example: `MainController.retirePluginProject`'s disposal failure now reaches the log file, through that method's own WARNING, but shows nothing. Owner: future story 443.
- **Render-path log-once sites.** The render path's existing log-once sites (among them `EngineStreamPump`'s render loop at `:363`, `:383` and `:407`, `RenderPipeline#renderBlock`'s once-only notice, allow-listed in `RealTimeSafeContractTest`, and `PluginInvocationSupervisor`'s SEVERE record of an `Error` a plugin throws, after which its slot is bypassed until it is re-enabled) now format a record and write it to disk under the file handler's lock at a first fault, which can cost one extra dropout. Owner: story 337, which moves them to its RT channel. No new render-path logging may be added. If one of these records is the session's first write to the log file to fail, the same render thread also runs the sink's write-failure notice, once per session: `LogSink`'s error manager takes its monitor and prints one line to standard error, the sink takes its own monitor, and `FailureFunnel.onSinkWriteFailure` takes `armLock` and, while the toasts are armed, formats the WARNING and posts it through `Platform.runLater`; if formatting or posting it throws, the same thread writes the last-resort record, printing it to standard error and appending it under the last resort's append lock; story 337's move takes this off the render thread too.
- **Palette double logging.** A failed palette command is logged twice: `CommandPaletteView.executeSelected` logs a WARNING and rethrows (`CommandPaletteView.java:303-305`), and the funnel logs the same failure at SEVERE. Owner: story 339.
- **Sustained-failure escalation.** Book §6.2's escalation of a sustained failure (WARNING → a persistent fault cell with an action) is not part of this story's funnel, which counts and re-shows. Owners: stories 337 and 338.
- **Windows rotation and the roaming profile.** On Windows, a log viewer that holds the current file open during rotation can make the JDK `FileHandler` truncate it: `rotate()` ignores a failed rename and reopens `daw-0.log` with truncation (`FileHandler.java:714-725`, JDK 27). This is a `java.util.logging` limitation. The log folder sits under `%APPDATA%`, which is the roaming profile; the 25 MiB cap (5 files of 5 MiB) bounds the cost.
- **How an FX-thread exception reaches a handler (clarification).** Goals bullet 2 says FX event-dispatch exceptions go to "the thread's own handler, not the default one". JavaFX reports them through the FX thread's `getUncaughtExceptionHandler()` (`com/sun/glass/ui/Application.java:448-453`). With no handler set, that call returns the thread's `ThreadGroup`, which delegates to the default handler, so the default handler alone would already see them. The FX handler exists to label the origin `ui.handler`, and the gate-4 test asserts by identity that the FX thread's handler is the funnel's own. The Goal's text stays as written; this bullet records the mechanism.
- **Launchers and crash evidence.** Story 336's review found the launchers and the crash evidence uneven. Among the gaps: the jlink launcher scripts `bin/daw` and `bin/daw.bat` pass no `--enable-native-access`; no launcher passes `@<settings>/zgc.conf`, though `DawLauncher`'s class Javadoc says the shipped launcher script does; a native crash report (`hs_err_pid*.log`) is written outside the log folder; the installer's version that the exe's banner labels is jpackage's literal `1.0.0`; and "Log closed at application exit." also ends an exit through `System.exit`, such as the JDK's own exit when an FFM upcall throws, so it is not proof of a clean exit. Owner: future story 444.
- **What the bar shows, and for how long.** The bar shows one toast at a time for a flat 5 s, whatever its level, and every toast is also recorded in the history. Among the cases this leaves: a routine toast posted after an ERROR toast replaces it; a toast the pointer is on still dismisses itself after 5 s, and its tooltip goes with it; an ERROR toast can run out unseen behind an owned window, such as the Welcome window or the first-run wizard at startup; a click on a history pill's button leaves that button with keyboard focus, so the next Space activates it instead of Play/Pause; and while project actions are fenced, a click on Help ▸ Open Log Folder, like one on Help…, does nothing. Owner: future story 445.
- **The render pump's death is logged, not shown.** `EngineStreamPump` sets its own uncaught-exception handler on the `engine-render-pump` thread, which pre-empts the default handler, so the pump's death reaches the log file but no toast. Owner: story 338 (its Note from Story 336).
- **A pulse storm past JavaFX's cap.** JavaFX hands the FX thread's handler only the first 100 throwables that leave the dispatcher's pulse timer and drops the rest, so a long pulse storm stops reaching the funnel, and its tail reads as if the failure stopped. Owner: story 337 (its Note from Story 336).
- **Dispose sites that declare no plugin.** `unpublished-plugin-dispose` (`PluginInstallPanel`) and `daw-plugin-registry-dispose` (`PluginManagerDialog`) declare no subject. What escapes them reaches the funnel under the background-task copy, which names the thread instead of the plugin. Owner: future story 443.
- **Control characters in logged names and messages.** Story 336 escapes only line breaks. Another character, such as ESC, in a thread's, logger's or plugin's name or in a message reaches `daw-*.log`, the console and the last-resort record as it is, and a terminal that shows the file can interpret it. The header's own delimiters, such as `]` in a thread's name or `: ` in a logger's name, make its fields ambiguous to a parser. A line break inside a background thread's name reaches the toast's copy and its history entry. Owner: future story 446.

## Note from Story 334

- **A plugin the insert rack or the plugin menu discards after it loaded.** It is disposed on a virtual thread with nothing to catch what its `dispose()` throws: the insert rack's `cancelled-plugin-dispose`, `refused-plugin-dispose` and `failed-plugin-dispose` threads (`InsertEffectRack.completeExternalInsert`), and the plugin menu's discards in `PluginViewController.loadForInsertion`, on the `plugin-activate` worker `MainController` gives it. A plugin loaded from a JAR still has its class loader closed, since its disposal closes it in a `finally` (a built-in plugin the menu discards has none of its own), but the failure reaches only the thread group's print to standard error, with no log record and nothing shown. The review of story 334's pull request left it to this story's default handler, and this story's background-thread test covers it: a plugin the insert rack discards whose `dispose()` throws reaches the funnel once, with that exception.
- **A log record whose plugin exception cannot be formatted.** A log handler formats a record's exception by running whatever of the plugin's own code that formatting reaches — for example the exception's `printStackTrace(PrintWriter)`, and the `toString()`, `getMessage()` and `getCause()` of it, its causes and its suppressed exceptions — and once the plugin's class loader is closed, an exception whose message needs a class only the plugin's JAR holds, and that was never loaded, throws `NoClassDefFoundError` there. The JDK's `StreamHandler` catches only an `Exception` its formatter throws, so that error leaves `Logger.log` and no record is written; the thread group's print of such an exception, uncaught, shows the thread's name and nothing else. Story 334's pull request logs a plugin's failure at WARNING after its class loader is closed in the insert rack's and the plugin menu's load workers, the install panel's install worker and its release of the plugins it does not keep, and the Manage Plugins dialog's release of a removed plugin; `MainController.retirePluginProject` logs a retired plugin's disposal failure the same way, and that record is lost without a trace, since the failure stays in a future nothing reads. Story 334 makes the rack, the menu and the install panel recover whatever that logging throws, and leaves the record to this story: the sink and the funnel write a record whatever formatting its exception throws, naming at least the exception's class, and the background-thread test also throws an exception that only its closed class loader's JAR can format, since a host-made one passes while a plugin's is lost. Reading the exception before the class loader closes, as story 334's loader does for the name of what a plugin's constructor threw, is one way to keep the plugin's own message too. The insert rack, the plugin menu and the install panel leave what such a handler throws to reach the top of the thread that logged; story 334's tests check that for the plugin menu's load worker, and this story's background-thread test also checks it for the insert rack's load worker and the install panel's install worker.

## Resolution

A failure that reaches either of the application's uncaught-exception handlers is no longer silent. It is written, with its whole stack, to a rotating log file under the user settings folder, and, unless it is a launch failure (`app.launch`, logged only) or its toast has not run on the FX thread when `DawApplication.stop()` begins, it shows as an ERROR toast in the main window's notification bar, with an Open Log Folder action, and as an entry in the Notifications history; the failures from before the toasts are armed, just before the window first shows, get one toast between them. The Known limits name the failures that never reach the handlers. The same failure repeated is shown at most once every 30 s and counted, not listed. Help ▸ Open Log Folder opens the folder. A support reader gets a file in which a session's lines begin with a line naming the build's version, the session's start and its process, followed at launch by a banner naming Java, the operating system, the heap and whether the exit hold is active. Every record is one header line with its following lines tab-indented, and, on every launch path that names the application's log manager, the exit wait's own lines and a closing line reach the file at exit. Every bullet of the Goals — Tests is met as follows.

**The two handlers and their install order.** `DawLauncher.main` calls `prepareLaunch(userSettingsDirectory())` before `Application.launch`. `prepareLaunch` first names the application's log manager (`selectExitHoldingLogManager`, unless the launch line already named one), then runs `installDiagnostics`: an oversized last-resort file is moved aside (`LastResortLog.moveOversizedAtLaunch`), `LogSink.install` opens the log file, `logSessionStart` writes the banner, and `FailureFunnel.forLaunch(sink, Thread.currentThread())` is installed as the process-wide default handler (`installAsDefaultHandler`). Only then is `zgc.conf` installed; its failure is now the WARNING `Could not install zgc.conf; the application runs without the tuned garbage-collector profile`, written to the log as well as to standard error. `DawApplication.start` installs the funnel's FX-thread handler (`installOnCurrentFxThread`) right after `FxDispatcher.installDefault`, before the event bus is built and the FXML is loaded. `DawLauncher.failureFunnel()` hands it the funnel `main` installed, or installs one with no launch thread when the application starts without `main`. A failure on the FX thread is `ui.handler`; one that reaches the default handler on the launch thread is `app.launch` and is logged only; one on any other thread is `thread.uncaught`. The book §6.3 gate-4 test is `FailureSpineStartupWiringTest.bothHandlersAreInstalledAndAnFxFailureIsLoggedWithItsStackAndShownAsAnErrorToast`: it asserts the default handler, and the FX thread's own handler by identity, and that an exception thrown on the FX thread gives a SEVERE record with its whole stack in the log file and an ERROR toast. `BackgroundFailureReachesTheFunnelTest.aVirtualThreadsUncaughtFailureIsLoggedAndShown` meets the background-thread test, and `FailureSpineWiringSourceTest` pins the order in `DawLauncher` and `DawApplication`.

**`FailureFunnel`.** For each failure, `FailureFunnel` unwraps the throwable's carriers (`CompletionException`, `ExecutionException`, `InvocationTargetException`, `UndeclaredThrowableException`, `ExceptionInInitializerError`, and on `app.launch` JavaFX's launcher wrapper; at most 8, `GuardedThrowables.unwrapCarriers`), takes its `Fingerprint`, and lets the `FingerprintRateLimiter` decide on the failing thread. A surfaced occurrence gets its severity (`severityOf`), its base sentence (`FailureCopy.base`), one SEVERE record with the original throwable's whole chain (`logFact`), and then its toast, posted un-keyed through `FxDispatcher.onFx`, so that `NotificationBar.show` runs on the FX thread, with the Open Log Folder action. A record that cannot be written does not cost the failure its toast: what writing it threw goes to the last resort, and the toast is still posted. The record's header and a tail's line are each one line: a line break anywhere in them, a thread's name or a fingerprint included, is written as its escape (ruling R992-3).
- **Severity.** A `VirtualMachineError` is FATAL. An `ExceptionInInitializerError` or `UnsatisfiedLinkError` is FATAL unless its anchor is plugin code. An `app.launch` failure is FATAL unless JavaFX's wrapper says the application's or the preloader's `stop()` threw. Everything else is ERROR. FATAL is an ERROR-level toast with its own copy, `Serious internal error: the application may not work correctly from now on. When you can, save a copy with File ▸ Save As… and restart. Reason: {0}.`, or for an `OutOfMemoryError` `The application ran out of memory. When you can, save a copy with File ▸ Save As… and restart.`, which is resolved before any failure. The funnel never opens a dialog, exits, halts, saves, or touches the transport, the engine or monitoring.
- **What the toast names.** Only a site that knows what failed names it (`DeclaredSubject`); the copy is never inferred from stack frames, the focus owner or the last event. Otherwise an FX-thread failure reads `Internal error in the user interface: {0}. Check that your last change took effect.`, and a background failure names the task its thread's name states, `Internal error in the background task “{0}”: {1}. Its work may be incomplete.`, or `Internal error in a background task: {0}. Its work may be incomplete.` for a generic thread name. The reason is the unwrapped exception's first line, named by `PluginResolution.FailedToLoad.messageOrName` and read guardedly, with one trailing full stop dropped and at most 120 characters. `failure.ui.named` is defined for story 339, which declares palette commands.
- **Reentrancy.** While it handles a failure, the funnel binds a `ScopedValue` (`IN_FUNNEL`; JEP 506, final in Java 25). A failure that arrives while it is bound goes to the last resort, and so does anything the funnel itself throws. Every runnable the funnel posts to the FX thread runs inside the same binding and its own `catch (Throwable)`, so a history listener that throws cannot loop through the toast that notified it. `FailureFunnelReentrancyTest` meets the reentrancy test: a throwing history listener, a log handler that hands the funnel another failure on the same thread, a log handler that throws an `Error` on the FX thread, a throwing listener on the toast's label and one that throws while a tail is recorded.

`CommandPaletteFailureIsVisibleTest.aPaletteCommandThatThrowsIsAnErrorToastAndASevereRecord` meets the palette test.

**`Fingerprint` and `FingerprintRateLimiter`.** `Fingerprint.key()` is `category|subject|exceptionClass` when the site declared a subject, else `category|exceptionClass|anchor`. The anchor is `class.method:line` of the first frame, counting from the throw site, that is host code (`com.benesquivelmusic.`) or plugin code (a frame with no module name), else frame 0, else `-`, so that two unrelated `Objects.requireNonNull` failures are not counted as one. That holds in the installed application because its runtime image keeps the class files' line numbers (ruling R992-1); a stripped image reads every frame of a class it holds as line -1, which would merge two throw sites of one method. `FingerprintRateLimiter.occur` decides on the failing thread, before anything is posted to the FX thread:
- **The window.** 30 s (`WINDOW_NANOS`) on a monotonic clock, fixed and anchored at the last notice shown, never sliding, so a failure thrown every frame still re-surfaces every 30 s.
- **Counting.** An occurrence inside the window is counted, not listed: no toast, no history entry and no log record of its own. A re-show reads `{0} It has happened {1} times since {2}.`, the total since the first occurrence and when that was, and its record says how many occurrences since the previous notice were not logged individually.
- **The tails.** A fingerprint with occurrences counted since its notice, whose last occurrence is a window old, owes one tail. The pulse participant (`postTailsIfDue`, a field read) posts the keyed `flushDueTails`, which records one history-only entry (`{0} It happened {1,choice,1#once more|1<{2} more times} after that notice, the last time at {3}.`) and one SEVERE line without a stack (`Failure <category> repeated <n> more times between … and …, not logged individually (fingerprint …); last message: …`).
- **The LRU.** At most 256 fingerprints are kept (`MAX_FINGERPRINTS`), the least recently seen evicted. An evicted fingerprint's owed tail goes to the log only, written after the limiter's monitor is released.
- **The accounting.** It is stated once, in the "Accounting" paragraph of `FingerprintRateLimiter`'s class Javadoc, and Goals bullet 4 states its scope. Each occurrence counted before the log's last write is in exactly one tail line or in the next surfaced record's count of occurrences not logged individually. The newest notice's running total plus the tail counts after it equals the occurrences, while a fingerprint's notices and tails reach the history and are still in it. A tail line that cannot be written goes to the last resort with its fingerprint and count, and costs neither the failure being handled nor the tails taken after it anything.

`FailureRateLimitTest.oneToastPerWindowAndTheHistoryAccountsForEveryOccurrence` meets the rate-limiting test. The rest of `FailureRateLimitTest` (the drains at the disarming and at the log's close, eviction, and tails that cannot be written or named), `FingerprintRateLimiterTest` and `FingerprintTest` cover the rest.

**Arming and the hold before it.** `DawApplication.start` calls `MainController.attachFailureFunnel` right after `setFxDispatcher`, before `primaryStage.show()` and before `showWelcomeIfNoProjectOpen()`, which can open the first-run wizard. It calls `FailureFunnel.armToasts(fxDispatcher, notificationBar)`, which registers the tail check as a pulse participant and posts, once, what is owed from before: the sink's WARNINGs first, then the first FATAL failure's toast if there was one, else the one failure's own toast, else one summary toast with the action, `{0} internal errors occurred while the application was starting, so some features may not work.` Until then the funnel logs every surfaced failure at once, keeps the first 16 toasts (`PRE_ARM_CAPACITY`), counts the rest, and keeps the first FATAL one whichever it was. With no notification bar or dispatcher, `attachFailureFunnel` logs one WARNING, `The window has no notification bar or FX dispatcher yet, so failure toasts stay off; failures are logged only`. `DawApplication.stop()` calls `disarmToasts()` as its first statement: from then on failures are logged only, the pulse participant is removed, and every tail still owed is written to the log at once. A failure's toast posted before the disarming that has not yet run on the FX thread is dropped there, since `postOnFx` runs a body only while its target is still armed; its failure's record is already in the log, written before the toast was posted (ruling R992-5). The default handler is never removed. `FailureSpineStartupWiringTest` covers one, two, more than sixteen and FATAL failures before arming, the disarming, an unavailable log file, write failures before and while armed, and the controller without a bar.

**`LogSink` and `LogLineFormatter`.**
- **The file.** `LogSink.install` creates `<settings>/logs` (`%APPDATA%\java-daw\logs` on Windows) and adds a `FileHandler` to the root logger with the pattern `daw-%g.log` (the folder's own `%` escaped), 5 MiB per file (`FILE_LIMIT_BYTES`) and 5 files (`FILE_COUNT`), appended across sessions. The root logger and the handler are at INFO, the encoding is UTF-8, and `FileHandler` flushes every record.
- **The format.** Every root handler formats with `LogLineFormatter`, the console handler included, whether or not the file could be opened. A record is one header line, `<timestamp with offset> <level padded to 7> [<thread>] <logger>: <message>`, and every following line of it begins with a tab, so `grep -E '^[0-9]{4}-'` lists the records. Each line keeps its values on it: a line break inside a value, such as a thread's or logger's name, a level, a class or a frame, or in a message any line break but CR, LF and CRLF, which still begin tab-indented continuation lines, is written as its escape, `\u000A` for LF and `\u2028` for the line separator, so a Linux file name such as `mix\npart.zip` in a thread's name cannot split a record or forge one (ruling R992-2). A throwable's chain is read with guarded calls (`GuardedThrowables.appendChain`; cycles stop the walk, at most 16 deep), so a plugin exception that only its closed JAR could format is written by its class name, followed by `<the message could not be read: java.lang.NoClassDefFoundError>`.
- **The session line.** The file's formatter has a head (`LogLineFormatter.getHead`), which `StreamHandler` writes before the first record of every stream it opens, at launch and after each rotation: `Lines from here on belong to the session of Digital Audio Workstation <version> that started at <time> as process <pid>` (`LogSink.sessionLine`).
- **The banner.** At launch `logSessionStart` follows it with two INFO lines: `Session started: Digital Audio Workstation <version>, Java <runtime version> (<vendor>), <OS name> <OS version> (<architecture>), process <pid>, maximum heap <n> MiB`, and `Exit hold: active` or `Exit hold: inactive (java.util.logging.manager does not name the application's log manager on this launch path); lines logged while the application exits may be lost`.
- **The version.** The `daw.app` module's version (`0.1.0-SNAPSHOT` today), followed in the installed application by the installer's, labelled: `0.1.0-SNAPSHOT (installer 1.0.0)` (`LogSink.applicationVersion`).
- **The sink's own failures.** A log file that cannot be opened prints one line to standard error and, once the toasts are armed, shows a WARNING without the action: `The log file could not be opened in {0}: {1}. This session is not logged to a file.` The first failed write shows once as a WARNING with the action: `The log file could not be written: {0}. Lines from this session may be missing from it.`

`LogSinkTest` meets the log-file test: the file is `daw-0.log` in the settings folder's `logs` and holds INFO and above only, it rotates at its production cap with each new file beginning with the session line, and at most five files are kept. `LogLineFormatterTest` covers the format.

**`LastResortLog`.** When the funnel itself throws, or a failure re-enters it, `LastResortLog.write` writes one record to standard error and appends it to `<settings>/logs/daw-last-resort.log`, opening and closing the file for every append. It never appends to a `daw-N.log`, whose `FileHandler` writes at its own offset. The record holds the time, the thread, the failure being handled or what the funnel was doing, and what the funnel hit, each by class name, guarded message and guarded frames; it uses no `java.util.logging`, formatter or resource bundle, and no `toString()` or `printStackTrace()` of the throwables. A line break inside any of them, the message's included, is written as its escape (ruling R992-2). Within a session appends stop once the file reaches 1 MiB (`MAX_BYTES`): the size check and the append are made together under one lock for every writer in the process, so this process's writers leave the file at most one record past that size in a session; the record goes to standard error before the lock is taken (ruling R992-4). A writer whose interrupt flag is set still appends its record and keeps the flag: the size is read with a stat and the record appended through `Files.newOutputStream`, whose channel an interrupt does not close (ruling R992-4). At launch a file that size or larger is moved to `daw-last-resort-previous.log` (`moveOversizedAtLaunch`), so one bad session cannot disable it for every later one. `LastResortLogTest` covers it.

**`ExitHoldingLogManager`.** `MainController.registerExitWriteWait` hands the `daw-exit-write-wait` hook to `ExitHoldingLogManager.holdShutdownResetFor(hook, ProjectManager.EXIT_WRITE_WAIT)` right after `addShutdownHook`; a refused registration registers no hold. Its `reset()` holds only the JDK's shutdown reset, which it recognizes by its thread's class, `java.util.logging.LogManager$Cleaner`; any other reset runs at once. On the shutdown reset it:
1. waits until the hook has returned, at most the exit wait's 30 s plus `HOLD_MARGIN` (5 s), so `awaitWritesBeforeExit`'s lines and the records of writers that fail during the wait reach the file;
2. asks the default handler, through `ExitHoldingLogManager.OwedLines`, to write the tail lines the funnel still owes;
3. writes `Log closed at application exit.`, or, when the hold ran out, `The log is closing 35 s after the application began to exit, and the wait for saves and checkpoints has not returned; anything it logs after this line is lost.`;
4. always ends in `super.reset()`.

With no exit wait registered it skips the hold and still writes the owed lines and the closing line. `ExitWaitLinesReachTheLogTest.aSaveHeldPastTheShortenedBoundLeavesBothLinesThenTheClosingLine` meets the binding exit-wait test: a child JVM, launched `-m daw.app/…` with the jpackage `-D` value read from `daw-app/pom.xml`, holds a save past a 2 s bound and exits, and its log holds both lines verbatim, then the closing line. The class's other cases cover the JDK's own manager (the deadline WARNING is lost), a hold that runs out, no exit wait, and occurrences counted after the disarming, written before the closing line. `ExitHoldAwaitsTheExitWaitTest` and `ExitWaitIsHandedToTheLogManagerTest` cover the rest.

**Accepted as built.** These are recorded so that nobody "fixes" them:
- The message tooltip is built when the pointer first enters the label, not with the pill, because the inspector rebuilds up to 100 history pills on every toast. The first hover still shows it: JavaFX delivers the entry before the move that starts the show delay.
- Every toast is un-keyed `FxDispatcher.onFx` work, which is `Platform.runLater`: it does not wait for the dispatcher's pulse. The test asserts that the toast is recorded on the FX application thread, not that it waits for a pulse.
- On Windows, the javafx-maven-plugin's options patch writes the jlink image's `sh` script `bin/daw` with CRLF line endings; an image built on Windows carries Windows libraries and runs only there.
- A `VirtualMachineError` is FATAL: one SEVERE record, an ERROR-level toast with the FATAL copy, and nothing more — no dialog, exit, halt, save or engine stop (ruling E3). When the heap is truly exhausted, the funnel's own work may fail; that goes to the last resort, and when the last resort fails too, the record is dropped silently, the end of the line (ruling E11).
- A failure on the FX thread is formatted, written and flushed to the log file on the FX thread, and so is each tail line written when it falls due or at the disarming, at most one record and one tail line per fingerprint per 30 s; every other INFO-and-above record logged on the FX thread is a file write too, and a last-resort record written on the FX thread may wait for another thread's append under the last resort's append lock (ruling R992-4). - An interrupted hold writes no closing line (ruling R-V1); the last-resort record's labels are "Failure being handled" and "What the failure funnel hit while handling it" (ruling R-V2); a storm can cause at most one spurious keyed tail flush per window (ruling R-V5).
- The exit hold recognizes the JDK's shutdown reset by a private JDK class name, `java.util.logging.LogManager$Cleaner`; if a JDK renamed it, every reset would run at once, and `ExitWaitLinesReachTheLogTest` would fail.
- A reason cut at 120 characters ends with "…", and the sentence's own full stop follows it.
- The jlink image is linked without stripping debug attributes (no `--strip-debug`), so its `lib/modules` is about 6.6 MB (16.5 %) larger; stripping it would make every frame of a class it holds read `(Unknown Source)` and merge distinct throw sites of one method into one fingerprint (ruling R992-1).
- A line break inside a logged value is written as its escape, a visible marker, not a reversible encoding: a value that holds the six characters `\u000A` itself reads the same (ruling R992-2).
- Two processes writing one `daw-last-resort.log` can each append one record past 1 MiB: the append lock serializes one process's writers only, and no file lock is taken across processes, since a Windows file lock is mandatory and blocks readers (ruling R992-4).
