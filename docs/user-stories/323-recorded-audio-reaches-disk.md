# Recorded Audio Reaches Disk: Segment Flush and Project-Relative Storage

## Motivation

No recorded sample ever reaches disk. `RecordingSession` is the capture buffer and it is RAM only: `recordAudioData` appends frames into a growing in-memory `[channel][sample]` array (`RecordingSession.java:201-240`), and the class contains zero file I/O — a grep for file-writing calls across the recording package matches only the metronome settings JSON store (`MetronomeSettingsStore.java:155`). The class javadoc promises the opposite: *"Each segment is stored as a separate file … A crash only risks the current segment, not the entire session"* (`RecordingSession.java:20-25`). Both sentences are false:

- `startNewSegment` constructs only a `RecordingSegment` metadata record naming `segment-NNN.wav`; no file is ever created (`RecordingSession.java:395-405`).
- `finalizeCurrentSegment` marks the in-memory record complete with a **wall-clock-estimated** sample count (`RecordingSession.java:407-423`) — even the metadata is approximate.
- `RecordingPipeline.stop()` stamps each recorded clip's source path from `getSegments().getFirst()` — the path of a file that never existed, and only the *first* segment even when rotation produced several (`RecordingPipeline.java:306-308`). Playback after stop works only because the full take is attached to the clip in RAM (`RecordingPipeline.java:317-319`).
- `ProjectSerializer.buildClipElement` persists only the `source-file` attribute (`ProjectSerializer.java:376-378`); on reload the nonexistent path is flagged in `missingFiles` (`ProjectDeserializer.java:529-537`). A recorded take is unrecoverable after any restart.

And the fictional path is not even inside the project: `TransportController.onRecord` targets `Files.createTempDirectory("daw-recording-")` — the OS temp directory, wiped on cleanup or reboot (`TransportController.java:433`) — while the status bar claims *"auto-save active"* (`TransportController.java:484-485`). Meanwhile `ProjectManager` creates an `audio/` directory in every project, documented as *"recorded audio files"*, that nothing ever writes into (`ProjectManager.java:32,39,160`).

For a studio engineer the consequence is absolute: **every take of every session is unconditionally lost** — on a crash, on a device failure, on OS temp cleanup, or at the latest on project reload. This is THE data-loss story and the single highest-leverage change in `docs/design/RECORDING_RELIABILITY_DESIGN_BOOK.md`: the session invariant (book §2.1) — *everything the performer played is on disk, inside the project, within seconds of being played* — is currently inverted.

## Goals

- Introduce the capture-to-disk skeleton of book §4.1-4.4: a preallocated `CaptureRing` the recording callback hands raw device blocks to (with slot headers stamping start frame, transport beat position, and gate flags), a dedicated `capture-flush` platform thread (`CaptureFlushService`) that drains the ring strictly in order, routes per armed track (reusing the existing pipeline routing/gating logic as-is for this stage), and a `SegmentWriter` that streams real WAV segments to disk.
- Recorded audio lands under `<project>/audio/takes/<UTC-timestamp>_take-NNNN/<trackId>/segment-NNN.wav` per the book §3.3 layout — the `audio/` directory `ProjectManager` already creates. The OS temp-directory root (`TransportController.java:433`) is deleted; the OS temp directory never holds session audio (book §2.6).
- Each take directory carries a `take.manifest` sidecar written by the flush thread at take start and rewritten at each rotation/seal: format, start position, compensation frames, ordered per-track segment lists, seal status — so a recovery scan can rebuild a take without the project file (book §3.3).
- Segment lifecycle per book §3.4: segments stream as `segment-NNN.wav.part` with a provisional self-describing header (fixed 44-byte data offset; sample count derivable from file length), are force-flushed to storage every 5 seconds (configurable), and seal via patch-header + atomic rename — the rename is the commit point. Exact sample counts replace `finalizeCurrentSegment`'s wall-clock estimates.
- Stop finalizes atomically: seal all active segments, write the manifest's final seal status, then build clips that reference **every** segment of the take in manifest order — the `getFirst()`-only stamping (`RecordingPipeline.java:306-308`) is deleted.
- Serialized clip references are **project-relative** (`audio/takes/…/segment-NNN.wav`); absolute paths for anything under the project root are forbidden (book §9.5). The serialization schema change is coordinated with `PERSISTENCE_INTEGRITY_DESIGN_BOOK.md` (stories 329/334 own reload and take persistence).
- The existing 30-minute / 500 MB segment-rotation caps are retained; rotation becomes a flush-thread act producing real files (book §5.3).
- A disk-headroom watch on the flush thread (cached free-space figure, refreshed on a slow tick): crossing the low-water mark raises a warning, and exhaustion seals the take cleanly with everything captured so far intact — never a throw out of a write loop (book §4.3). Until the Book 4 notification stories land, warnings degrade to logging (book §6.3 ordering note).
- The transport status line during recording tells the truth: the §1.1 *"auto-save active"* claim becomes accurate, because audio is continuously flushed.
- Explicitly allowed this stage: the in-RAM `capturedAudio` growth may remain, since it feeds today's post-stop playback attach — story 324 (Stage 2) removes it and makes the callback side RT-safe.

## Goals — Tests

- A crash-durability test records ~2 minutes of simulated capture and hard-terminates the writer mid-take: the sealed and `.part` segments under `<project>/audio/takes/` contain the captured audio, and a reader using only the §3.4 grammar (sample count = (length − data offset) ÷ frame size) recovers playable audio.
- A rotation test records past a rotation boundary and asserts the finalized clip references **all** segments, in manifest order — never only `segment-000.wav`.
- A round-trip test saves and reopens a project with a recorded take: serialized clip references are project-relative, resolve inside the project directory, and are flagged missing only if the files were actually deleted.
- A filesystem-level test asserts the seal is atomic: no observable `.wav` ever has a provisional (streaming-sentinel) header — a `.wav` is either fully sealed or still a `.part`.
- A force-cadence test asserts un-forced data is bounded by the configured cadence (default 5 s) per active segment — the book §2.1 risk window.
- A manifest test asserts the sidecar carries the ordered segment list, format, start position, and seal status, and is rewritten at rotation and seal.
- A storage-location test asserts the record path roots at the project's `audio/` directory and that no capture-path code references `Files.createTempDirectory` (the temp-root call site is gone).
- A disk-exhaustion test simulates free-space exhaustion mid-take: the take seals cleanly with all previously flushed audio intact and readable.

Files to touch: `RecordingSession.java` (segment metadata gains real files; estimates → exact counts), `RecordingPipeline.java` (stop/finalize references every segment; `:306-308` deleted), `TransportController.java` (`:433` temp root deleted; project-rooted output; truthful status line), `ProjectSerializer.java`/`ProjectDeserializer.java` (project-relative references), `ProjectManager.java` (the existing `audio/` directory becomes real).

## Resolution

Every recorded sample now reaches disk, inside the project, within the force cadence of being played. The recording callback no longer grows a RAM buffer: `RecordingPipeline.onAudioCaptured` (audio thread) claims one preallocated slot of a `CaptureRing`, copies the device block into source 0 and each armed graph-instrument track's `AudioEngine.graphInstrumentRecordingBuffer` into sources 1…n (that engine buffer is valid only inside the callback), stamps the slot header with `transport.getPositionInBeats()`, the start frame derived from it, the punch snapshot (`isPunchEnabled()` and the `PunchRegion`'s start/end frames) and `isLoopEnabled()`, publishes, and unparks the flush thread (`CaptureFlushService.signal()`). One platform daemon thread named `capture-flush` (`CaptureFlushService`, built with `Thread.ofPlatform().name(THREAD_NAME).daemon(true).unstarted(this::runLoop)`) drains the ring strictly in order (`peek`/`release`), parks with a 50 ms backstop (`PARK_BACKSTOP`) when dry, and per block — in this order — detects a loop-lap wrap from the header (loop-record on, `loopEnabled`, beat lower than the previous block's) and seals the lane, stacks the lap as a `Take` and opens the next lane; ticks the `DiskHeadroomWatch`; applies the punch gating the callback used to run (`captureWithTransportPunch` with its sample-accurate slicing, 5 ms cosine fades and `wasInsidePunchRegion` re-entry rule, or the legacy beat-based `PunchRange` gate) from the header's frames and beat, never re-reading the transport; routes the sources into each `TrackCapture`'s preallocated scratch block per the `InputRouting` snapshot taken at `start()` (every row of the routed block the source did not provide is zeroed, never stale — including the rows beyond an instrument source narrower than the routed width); hands the routed block to that track's lane `RecordingSession.recordAudioData`, which appends to a `SegmentWriter` and to the RAM mirror; notes a truncation when the block was longer than its ring slot; and rewrites the manifest if a segment opened, sealed or was discarded or a truncation episode began. One writer per byte (book §2.3): the callback writes ring slots only; while it runs the flush thread is the only writer of segment files, `take.manifest`, the RAM mirrors, the loop-take stacks and the ring's read index (the caller thread creates each track's first segment file and the first manifest before it starts the thread, and deletes them again if the start fails); the flush thread never touches a `Track` (`TrackCapture` snapshots id, name, routing and compensation on the caller thread); the caller thread (FX in the app) calls `RecordingPipeline.start()`/`stop()` and mutates `Track`s (`addClip`, `putTakeGroup`) only after `stop()` has joined the flush thread. `start()` is all-or-nothing: anchor, recording flags, compensation, ring, one `TrackCapture` per armed track, `CaptureFlushService.start()` — which starts every lane-0 session (each creating `<take>/<trackId>/segment-000.wav.part`) and writes the initial manifest on the caller thread before the thread is started — then the callback install, `audioEngine.start()` and `transport.record()`; any failure after `active = true` rolls back in reverse (`rollbackFailedStart(cause)`: callback removed, `CaptureFlushService.abortStart()` joins the thread and deletes every segment file this take opened and the manifest if this take wrote one, `track.setRecording(false)`, and `active = false` in a `finally`; every step runs even if an earlier one throws, and whatever a step throws is attached to the original failure as suppressed) and rethrows, leaving a fresh take directory empty — a `SegmentWriter.open` whose header write fails deletes the `.part` it had just created. `doStart` clears the previous take's flush service, ring and instrument-track array before it allocates anything, so a failed restart of a reused pipeline rolls back only what that start created and never the previous take's sealed files; and the callback returns at once when the pipeline holds no ring or no flush service, so a callback the audio thread had already loaded is harmless after a failed restart. `RecordingSession` listeners now fire on the flush thread (lane 0's start notification on the caller thread, inside `CaptureFlushService.start()`; its Javadoc says so); `capturedSampleCount`, `active` and `paused` are volatile and `totalSamplesRecorded` atomic. `RecordingPipeline.awaitFlushed()` (bounded, 10 s by default) is the fence tests and diagnostics use: it returns once every block published before the call has been applied and every overflow counted before the call has its `gap=` line recorded — the manifest rewrite attempted, or — while an earlier manifest failure is still being retried — deferred to the next retry slot; a rewrite that failed is retried later and is not part of the fence. It may be called from any thread but the flush thread.

`CaptureRing` follows the `AudioBlockRing` discipline: `AtomicLong head`/`tail` with `lazySet` release stores; slot count `slotCountFor(sampleRate, blockFrames, DEFAULT_HANDOFF_TOLERANCE)` — enough blocks to cover 250 ms, never fewer than `MIN_SLOTS` = 8, rounded up to a power of two so the wrap is a mask (the constructor refuses a request above `MAX_SLOTS` = 2^30, the largest power of two an `int` holds, with `IllegalArgumentException`, and `slotCountFor` refuses a tolerance that covers more than `MAX_SLOTS` blocks the same way: rounding either up would never terminate); slot payload `sourceCount × channelsPerSource` rows of `format.bufferSize()` frames, where the row count is `max(format.channels(), max over armed routings of firstChannel + channelCount)` so a device that delivers more input rows than the format's width loses none of them; and a primitives-only header. `claim()` → fill → `publish()` on the producer, `peek()` → `release()` on the consumer; the `Slot` setters that take counts clamp rather than throw, so no exception path is reachable from the callback for a source index within `sourceCount()` and a block whose rows are non-null (source indices are not clamped; an index outside that range or a `null` row throws). `CaptureRing.claim/publish/overflowCount/droppedAfterSequence/noteTruncatedFrames/truncatedFrames/size/isEmpty` are `@RealTimeSafe` under `RealTimeSafeContractTest`'s bytecode rules; `Slot` is annotated at type level but is a nested class, which that test's `ModuleClassScanner` skips (it filters `$` names), so the reflection-visible rules — no `synchronized` modifier, no varargs, no boxed parameter or return type on any public method — are pinned for `Slot` by `CaptureRingTest.slotsRealTimeSafeSurfaceObeysTheRulesTheModuleScannerCannotReach`, with `theSlotPinWouldRejectEachForbiddenShape` as its non-vacuity fixture; the bytecode half of the `synchronized` rule — no monitor instruction in any public method, which a `synchronized` block leaves behind with no modifier for reflection to see — is pinned by `CaptureRingTest.slotsPublicMethodsHoldNoMonitorInstruction`, which parses `CaptureRing$Slot` with the Class-File API, with `theMonitorScanWouldRejectASynchronizedBlock` as its fixture. **Binding decision — overflow policy (a deliberate deviation from book §4.2):** when the ring is full the *incoming* block is dropped — `claim()` returns `null`, having first stored the drop marker (`droppedAfterSequence`, the sequence number of the last block published before the drop) with a `lazySet` and then advanced the overflow counter by a plain load and a `lazySet` (no read-modify-write on the callback), and `onAudioCaptured` returns at once. The book's "drops the oldest unwritten block" was not implemented because overwriting the oldest slot is not single-producer-safe while the consumer may be copying out of exactly that slot — the reason `AudioBlockRing.write` gives. The loss is bounded and honestly recorded: after each drain pass the flush thread compares `overflowCount()` with the value it last saw and appends one `gap=*|<startFrame>|<droppedBlocks>` line per noticed episode, positioned at the end of the last block accepted before the drop: the drain pass remembers the end frame of the block the drop marker names when it applies that block, so blocks published after the drop and applied in the same pass do not move the position. Drops at different points that one pass notices together share one line, at the most recent marked block; and when the marked block's end was not captured — the marker was not yet visible when that block was applied, or the drop happened after the pass's last look at the ring — the line falls back to the end of the last block applied. The flush thread keeps `overflow-blocks=` current, rewrites the manifest and warns through the sink. The callback never blocks (book §9.14). **Over-long blocks are counted, never cut off silently:** a ring slot holds `format.bufferSize()` frames, the size the pipeline was constructed with, and nothing guarantees the engine delivers no more; a longer block keeps its first `format.bufferSize()` frames, the callback stamps the excess on the slot and adds it to the ring's `truncatedFrames` counter (`RecordingPipeline.getTruncatedFrames()`), and the flush thread records the first over-long block of a run as one `gap=*|<end of its kept frames>|0` line with one warning and one manifest rewrite — one line per episode, not per block — and carries the running total in `truncated-frames=` with every later manifest write, exact at the seal.

A segment is a real WAV file streamed by `SegmentWriter`: `append` and `seal()` run on the flush thread; `open` runs on the caller thread for a track's first segment (before the flush thread is started) and on the flush thread for every later one; one thread at a time writes a file. While streaming it is `<take>/<trackId>/segment-NNN.wav.part`: a 44-byte canonical header (`RIFF`/`WAVE`/`fmt ` of 16 bytes/`data`; `DATA_OFFSET` = 44), format code 1 (PCM) for 16 and 24 bit and 3 (IEEE float) for 32 bit — the rule `WavExporter` applies with `DitherType.NONE` — with the RIFF-size and data-size fields (offsets 4 and 40) holding `PROVISIONAL_SIZE` (`0xFFFFFFFF`). Appends go straight through positional `FileChannel` writes with no Java-side buffering; after every append the channel is `force(false)`d when `now − lastForce ≥ cadence` on the injected `nanoClock` (`DEFAULT_FORCE_CADENCE` = 5 s; `RecordingPipeline.setForceCadence` before `start()`), so the un-forced tail of every active segment is bounded by the cadence (book §2.1). `seal()` is `force(true)` → patch both size fields with the exact values → `force(true)` → close → `Files.move(part, wav, ATOMIC_MOVE)`; the rename is the commit point, an existing `.wav` is never overwritten (`FileAlreadyExistsException` before the file is touched, and `open` already refuses when the sealed `.wav` exists so a lane fails at its open rather than at its seal; the guarantee rests on that existence check, not on the move — `ATOMIC_MOVE` replaces an existing target on POSIX file systems — and covers what the design itself can produce, one writer per segment), and `close()` on an unsealed writer abandons it — the seal is never a side effect of try-with-resources. If the rename itself fails the writer ends abandoned with the `.part` in place, its exact sizes already patched in and still readable by the streaming grammar (`SegmentWriter.failNextRename()` is the test seam that pins patch-before-rename). A segment's data chunk is at most `SegmentWriter.MAX_DATA_BYTES` = `Integer.MAX_VALUE − 44`, so a whole segment file never exceeds `Integer.MAX_VALUE` bytes and both size fields of a sealed segment are positive signed 32-bit values (the house `WavFileReader` reads the data size as a signed `int`). Bit depths 16, 24 and 32 are accepted; any other `AudioFormat.bitDepth()` fails at `RecordingSession.start()` with `IllegalArgumentException` (8-bit capture is not a take format). The PCM quantiser lives in one place, `core.export.PcmSampleEncoding`, which `WavExporter` now delegates to as well, so a sealed segment's data chunk is byte-identical to an export of the same frames with `DitherType.NONE` at the same bit depth (a dithered export differs by design: capture never dithers). `SegmentFile` is the §3.4 reader a recovery scan needs and uses nothing but the bytes and the name: `describe(Path)` takes the frame count from the file length for a `.part` (`(length − 44) / (channels × bytesPerSample)`, floored to whole frames) and from the data-size field for a sealed `.wav` (rejecting a sealed name that still carries the sentinel, or a data size the file cannot hold); `readFrames(Path)` decodes at `WavFileReader`'s scale. `TakeManifest` is the `take.manifest` sidecar — line-oriented UTF-8, `key=value`, `#` comments, `|`-separated fields, unknown keys ignored: `manifest-version=1`, `take`, `started-at`, `sample-rate`, `bit-depth`, `stream-channels`, `start-beat`, `start-frame`, `force-cadence-millis`, `ring-slots`, `ring-frames`; one `track=<trackId>|<channels>|<compensation-frames>` per armed track in armed order; one `segment=<trackId>|<lane>|<index>|<path relative to the take dir, '/'>|<frames or -1 while streaming>|<streaming|sealed>` per segment; `gap=<trackId or *>|<startFrame>|<dropped-blocks>` lines (one per overflow episode; `dropped-blocks` 0 marks the start of a truncation episode); `overflow-blocks`; `truncated-frames` (absent in files written before this key existed: reads as 0); `seal-status=streaming|sealed|aborted`; and `sealed-by=stop|disk-exhaustion|write-failure|start-failure`, present iff the status is not streaming. Segment order in the manifest *is* the clip's segment order: `segments()` is canonicalised at construction (track order, then lane, then index), a backslash in a relative path is rejected, and `read(Path)` parses exactly what `write(Path)` emits (and ignores one leading U+FEFF, so a manifest re-saved by a BOM-writing editor still reads). Every write is atomic and durable before it is visible — `take.manifest.tmp` in the take directory is written through a `FileChannel`, forced to storage (`force(true)`) and closed, and only then moved: `Files.move(tmp, manifest, REPLACE_EXISTING, ATOMIC_MOVE)` with a `REPLACE_EXISTING`-only fallback on `AtomicMoveNotSupportedException` (the Persistence book §4.1 idiom — same-directory sibling → fsync → atomic move — implemented locally until story 331 centralises it). It is written at take start on the caller thread (from `CaptureFlushService.start()`, before the flush thread is started) and thereafter by the flush thread whenever a segment opens, seals or is discarded (rotation, lane seal), on every overflow episode, at the start of every truncation episode, and at the final seal. Deviation from the Goals wording: the first manifest write happens on the caller thread inside `CaptureFlushService.start()` (so a failed start can roll back before the flush thread is started — there is no running thread to stop); every later write is the flush thread's. **The manifest is a sidecar, so a manifest write that fails never ends the take:** on the flush thread one write is attempted up to `MANIFEST_WRITE_ATTEMPTS` = 5 times, `MANIFEST_RETRY_PAUSE` = 20 ms apart (on Windows a target held open by another process without delete sharing fails the move with a `FileSystemException`, which the `AtomicMoveNotSupportedException` fallback does not catch, and is usually that short-lived); if every attempt fails — an `IOException` or a `RuntimeException` — the failure is recorded (`lastFailure()`), the sink is warned once per failure episode, capture continues, and the write is retried with later blocks and idle passes, one attempt at most once per `MANIFEST_RETRY_INTERVAL` = 1 s of the take's clock so that an unwritable manifest costs the drain one retry cycle (4 × 20 ms) per failure episode and one attempt a second after that, until it lands. The same holds for the final seal: the segments are sealed whether or not the manifest can say so, and the manifest on disk is then the last one written. Only the initial write in `start()` is a single attempt, and its failure fails the start.

**Binding decision — rotation on exact counts (D4):** the 30 min / 500 MB caps stay (`RecordingSession.DEFAULT_MAX_SEGMENT_DURATION`/`DEFAULT_MAX_SEGMENT_BYTES`; `RecordingPipeline.setSegmentLimits` before `start()`), but rotation is decided on the flush thread from exact counts — after each append from `writer.frameCount() / sampleRate ≥ maxSegmentDuration` or `writer.dataBytes() ≥ maxSegmentBytes`, and before an append that would take a segment already holding audio past the byte cap, so no sealed segment exceeds the cap (the one exception is a single block larger than the cap, which lands in an empty segment that then rotates) — and no wall-clock read decides it; the `Instant`s in `RecordingSegment.startTime`/`endTime` are metadata only. A byte cap the writer could not honour is refused up front: `RecordingSession.requireSegmentByteCap` (the session constructors and `RecordingPipeline.setSegmentLimits`) rejects a cap above `SegmentWriter.MAX_DATA_BYTES` with `IllegalArgumentException`, because such a cap could never rotate a segment before the writer refused the append and ended the take instead. `RecordingSegment` keeps its shape with `sampleCount`/`sizeBytes` now exact (frames appended, data-chunk bytes) and gains `streamingPath()` (`filePath()` + `.part`). `getSegments()` never lists a segment without a file on disk (book §9.3): a segment is added when its `.part` is created, replaced by its sealed record when the `.wav` lands, and a zero-frame tail at `stop()` is deleted and dropped from the list (its index reused by the next open) rather than sealed into an empty file — a take with no audio leaves no segment. Disk first: `recordAudioData` appends to the writer before `capturedSampleCount` and `totalSamplesRecorded` advance, so a failed write leaves the session reporting exactly what the file holds. `finalizeCurrentSegment`'s wall-clock estimate, `estimateSegmentSamples` and the test-only `recordSamples(long, long)` are gone.

`RecordingPipeline.stop()` removes the callback, clears the recording flags, stops the transport, then calls `flush.stopAndSeal(STOP)`: the stop flag is set, the thread unparked and joined for at most `STOP_JOIN_TIMEOUT` (30 s; on expiry it logs SEVERE, warns through the sink and continues with whatever is sealed — the caller is never hung forever); the thread's final sweep drains the ring, stops every lane's session (exact-count seal; in loop-record the in-flight lap becomes the last take) and writes the manifest `seal-status=sealed`/`sealed-by=stop` — unless a lane's seal threw, in which case that `.part` stays for recovery and the manifest reads `aborted`/`write-failure` even on a Stop, because the record must not claim more than the disk holds. Only after the join does the caller thread build clips: on the normal path one `AudioClip` per track whose `setSourceSegmentPaths(capture.sealedSegmentPaths())` carries every sealed segment, absolute, in manifest order, with the RAM audio attached as before; in loop-record the lap takes were built on the flush thread (each take's clip carrying its own lane's segment list; segment numbering continues across lanes inside `<trackId>/`) and are applied with `addClip`/`putTakeGroup` after the join. The take ends in the mode it began in: loop-record is part of the take's configuration, `setLoopRecord` refuses a change while recording (`IllegalStateException`, like the other pre-start seams), and `stop()` reads the snapshot the flush thread worked from (`flush.config().loopRecord()`), not the live field. A lane is finalized once: `TrackCapture.finalizeLane` marks the lane's session before anything in it can throw, so the early seal that answers a seal failure at a loop wrap neither stacks the lap a second time nor lists a sealed segment twice. `sealAll` is safe to re-enter in two independent halves — the lanes are sealed by the first call only and its reason sticks, the final manifest is written by whichever call finds it not yet on disk — so a throw inside the first call's manifest step still leaves a manifest whose `seal-status` is not `streaming`. Every lane gets its seal attempt, and a lane that threw makes the seal a failed one: `TrackCapture.finalizeLane` catches an `Error` as well as a `RuntimeException` around the session's `stop()`, so the bookkeeping of a segment that did seal still runs before the throw goes on; `sealAll` catches both per lane, goes on to the remaining lanes, writes the manifest `aborted`/`write-failure` — never `sealed`/`stop` — and only then rethrows the first `Error`, which on a Stop the flush loop logs SEVERE and reports through the sink. The `getFirst()`-only stamping, the `takeFinalizationExecutor` no-op executor and the on-callback `previousBeatPosition` are deleted. **Binding decision — clip references and the head invariant (D5):** `AudioClip` gains an ordered, immutable `getSourceSegmentPaths()` (empty for a single-file clip); when it is non-empty the list is the authority and `getSourceFilePath()` equals its first element — `setSourceSegmentPaths` derives the head, `setSourceFilePath` throws `IllegalArgumentException` for any other value while a list is present, an empty list leaves `sourceFilePath` untouched, and `duplicate()`/`splitAt()` propagate the list.

**Every caller that reads or re-points a clip's source is segment-aware.** Every recorded clip carries a segment list — one element for a take that never rotated — so a caller that knew only `getSourceFilePath()` would either be refused by the head invariant or silently use a fraction of the take. `ProjectArchiver.collectRefs` emits one `AudioClipSegmentRef(clip, index)` per element of a non-empty list and no head-only `AudioClipRef` for that clip (`update` rebuilds the list with that one element replaced through `setSourceSegmentPaths`, so the head follows element 0); Archive Project therefore copies every segment of a rotated take (SHA-deduplicated, one `assets/…` entry each), `openArchive` restores the list in order as absolute paths under the extract directory and reports each unresolvable segment once, and `consolidateInPlace` and `previewAssetSizes` follow through the same walk. `saveAsArchive` now rewrites the references inside the `try` whose `finally` restores them, recording each original before its reference is touched, so a rewrite that throws part-way through leaves the in-memory project as it was (no production reference throws from its update any more, so the package-private fault seam `ProjectArchiver.failRewriteAfter(int)` injects that failure for the test that pins it). `ProjectLifecycleController.collectMissingAssetPaths` (the pre-archive dialog) walks the same elements. `ClipProcessingService` (Reverse, Normalize) refuses a clip of more than one segment with `IllegalStateException` before anything is rendered — no file written, nothing recorded in the `ClipAssetHistory` — because its render reads one file; the batch factories (`reverse(List)`, `normalize(List, double)`) check every clip of the selection before they build an action, so a batch holding such a clip is refused as a whole, at the factory, and the clips ahead of it are not processed (the check when the action runs stays); for a one-segment clip it clears the list and then sets the rendered file, undo restores the list (and with it the head), redo collapses again. `GlueClipsAction` compares the two clips' segment lists as well as their heads and carries the list onto the merged clip; `TakeComping.compile` carries the take clip's list onto each comp clip. `AafExportService.composeTimeline` refuses an included clip of more than one segment with an `IllegalStateException` naming the clip, its id and its track, and writes nothing; `SessionInterchangeController.exportSession` keeps the head reference and adds one warning per such clip to the `SessionExportResult`, which the export surface already shows.

Persisted references follow one rule, `ProjectPaths` (package-private, shared by the serializer and the deserializer so the two cannot drift). Write side — `relativize(root, reference)` rewrites a reference only when the root is known, the reference parses as a `Path`, is absolute and lies strictly under the normalised root, as the root-relative path joined with `/` (`audio/takes/<take>/<trackId>/segment-000.wav`); an already-relative reference, an absolute reference outside the root, the root itself or an unparseable string is written verbatim, so an outside asset stays absolute (book §9.5; Persistence book §3.3). `ProjectSerializer.buildClipElement` passes `source-file` through it and writes one `<source-segment path="…"/>` child per element of `getSourceSegmentPaths()`, in order, none for a single-file clip; the root is `project.getMetadata().projectPath()`, which `ProjectManager.saveDawProject` sets before serialising. Read side — the new `ProjectDeserializer.deserialize(String xml, Path projectDirectory)` resolves a reference only when it has no root component (`Path.getRoot() == null`) to the absolute normalised path under the directory; references that have a root component on the platform reading them (a legacy file's absolute path, or an outside asset) are kept verbatim — a legacy Windows-absolute reference (`C:\…`) read on Linux has no root component there, so it is rebased under the project directory and reported missing under that path rather than kept verbatim; the missing-file check runs on the resolved paths, each segment once and the head not reported a second time through `source-file`; a `<source-segment>` whose `path` is empty or missing is skipped with a WARNING that names the clip; the 1-arg `deserialize(String)` delegates with `null` and keeps today's semantics. `ProjectManager.openProject` passes its `projectDirectory`, `JournalReplayer.loadCheckpoint` passes `ctx.projectDirectory()`, and `SnapshotsController.loadFromEntry` passes the open project's path (null-safe); each of the three also stamps that directory on the loaded project's metadata (`getMetadata().withPath(…)`), because the references are absolute in memory and can only be written project-relative again by a project that knows its directory — without it a restored snapshot was refused by Record's no-directory gate and serialized absolute paths into every later checkpoint, and the `project.daw` that journal recovery rewrites held absolute paths. **Binding decision — schema:** `<source-segment>` is version-neutral — an optional child absent from files written before this story and ignored by older readers, landed without a `MigrationRegistry` bump the way `<midi-effect-chain>` and `<layout>` were; `ReferenceTrack.source-file` is untouched (story 329).

**Binding decision — the take's home and the no-directory refusal (D6):** a take lives in the project, never in the OS temp directory. `ProjectManager.AUDIO_DIR_NAME` (`"audio"`) is public and `ProjectManager.audioDirectory(Path)` returns `<project>/audio`, which `createProject` creates; `TakeDirectories.allocate(audioDirectory, now)` creates `<audio>/takes/<yyyy-MM-dd'T'HH-mm-ss>_take-NNNN` — a UTC stamp plus `1 + the highest ordinal already present under takes/`, zero-padded to four ASCII digits whatever the default locale (formatted with `Locale.ROOT`; a locale with its own digits would otherwise produce a name the take-name grammar does not recognise), claimed with `Files.createDirectory` in a loop that bumps the ordinal on `FileAlreadyExistsException`. `TransportController.onRecord()` reads `project.getMetadata().projectPath()`; when audio tracks are armed and the project has no directory it refuses before the engine, the pipeline or any `MidiRecorder` is touched — `LOG.warning`, status text and an ERROR toast both reading `NO_PROJECT_FOLDER_MESSAGE` ("Recording needs a project folder — save the project first"), REC indicator hidden, transport still STOPPED; a MIDI-only take writes no audio files and is not gated. Otherwise it allocates the take directory (a failure there is its own SEVERE log plus an ERROR toast naming `audio/takes`), constructs the pipeline over it, and opens the device and calls `recordingPipeline.start()` inside the same `try`, so a device-open failure and a pipeline-start failure both reach `abortRecordingTake(outputDir, e)`, which deletes the take directory — empty again after D11's rollback. `Files.createTempDirectory` no longer appears in code under `daw-app/src/main/java` or the daw-core `core.recording` package (`ProjectLifecycleController` names it in comments only).

`DiskHeadroomWatch` runs on the flush thread once per applied block, before the write, from a cached figure refreshed on a slow tick (`DEFAULT_REFRESH` 2 s; the production probe is `Files.getFileStore(root).getUsableSpace()` on the take directory, rethrown as `UncheckedIOException`): OK at or above the low-water mark, LOW below it (`DEFAULT_LOW_WATER_BYTES` 1 GiB; the sink is warned once per crossing), EXHAUSTED below the floor (`DEFAULT_FLOOR_BYTES` 64 MiB) or after `FAILURES_BEFORE_EXHAUSTED` = 2 consecutive probe failures (a single failure keeps the last figure). EXHAUSTED seals the take before the block is written: `sealAll(DISK_EXHAUSTION)` stops every lane with its exact counts and writes `seal-status=aborted`/`sealed-by=disk-exhaustion`; the thread stays alive, every later block is drained and discarded (`discardedBlocks()`) so the callback side never notices, and a later `stop()` keeps the early reason. An `UncheckedIOException` from a session or any other `Throwable` while a block is applied is logged SEVERE, reported through the sink ("Recording stopped early — …; everything captured so far is sealed under …") and answered by the same clean seal with `sealed-by=write-failure`; a throwable that escapes the drain loop itself is logged SEVERE and reported through the sink the same way ("Recording stopped unexpectedly — …") and ends the thread after the seal; a manifest write that fails is neither — it never ends the take (above). Nothing throws out of the loop (book §4.3). Warnings go to the `Consumer<String>` injected through `RecordingPipeline.setWarningSink`, or to `java.util.logging` WARNING when none is injected (story 339 injects the production seam). The sink is foreign code: a `RuntimeException` it throws is logged at WARNING with the message it was given and ignored, in the headroom watch as in the flush service, so a warning that could not be delivered neither ends a take nor changes the reason one ended.

The status line tells the truth (D12): during an audio take `TransportController` shows `Recording — N track(s) armed — streaming to audio/takes/<take-dir-name>`; a MIDI-only take shows `Recording — N track(s) armed`; nothing claims an "auto-save". The INFO toast ("Recording started — N track(s) armed") is unchanged, and `abortRecordingTake`/`deleteEmptyTakeDirectory` document the take directory under the project's `audio/takes` rather than a temp directory.

**Known limitations / deferred (in scope of later stories)**

- **RT-safety of the callback (story 324).** `RecordingPipeline.onAudioCaptured` allocates nothing by construction — `CaptureRing.claim/copySource/publish` are bounded copies and scalar stores, the only loop is over the preallocated `Track[] instrumentTracks`, `AudioEngine.graphInstrumentRecordingBuffer` is a linear scan of `RenderPipeline.instrumentRecordingTracks`, and `publish()`'s only throw is the programming-error `IllegalStateException` no well-formed claim → fill → publish sequence reaches — but no bytecode sentinel proves it: the method is not `@RealTimeSafe`, of this story's code `RealTimeSafeContractTest` reaches only the ring's annotated surface (its outer methods; the nested `Slot` is pinned by `CaptureRingTest`), and the `RealTimeSafeContractTest`-pattern walk over the whole capture path is story 324's proof. It still reads three plain (non-volatile) `RecordingPipeline` fields — `ring`, `flush`, `instrumentTracks` — whose visibility to the audio thread rests on the volatile `AudioEngine.recordingCallback` install happening after they are written, and it still calls into `Transport` per block — `getPositionInBeats()`, `isPunchEnabled()`/`getPunchRegion()` and `isLoopEnabled()` (volatile fields) and `getTempo()`, which is `TempoMap.getTempoChanges().get(0).bpm()`, a fixed view over a plain `ArrayList` — rather than reading a snapshot the transport stamps.
- **The in-RAM mirror is retained (story 324).** `RecordingSession.capturedAudio` still grows without bound on the flush thread (`ensureMirrorCapacity` doubles it), `getCapturedAudio()` copies the whole take, and `RecordingPipeline.stop()` / `TrackCapture.finalizeLane` attach it through `AudioClip.setAudioData`; post-stop playback is from RAM, and nothing reloads a clip from its segment list yet (story 329). Mirror and segments both carry the stream width (`format.channels()`) for every track, unrouted rows silent — today's routing shape; story 326 narrows capture to the routed width.
- **`ReferenceTrack.source-file` stays absolute (story 329).** `ProjectSerializer` writes `ref.getSourceFilePath()` verbatim (`ProjectSerializer.java:776`) and `ProjectDeserializer` reads it without `ProjectPaths` (`ProjectDeserializer.java:1281`); only clip references (`source-file` and `<source-segment>`) go through the rule, which story 329 extends to imported assets and relinked paths.
- **A legacy Windows-absolute reference is rebased when read on another platform (story 329).** `ProjectPaths.resolve` decides "has a root component" on the platform reading the file: `C:\…` read on Linux has none, so it resolves under the project directory and is reported missing under that path instead of being kept verbatim — equally missing either way; only the reported text differs.
- **Recovery scan invocation (story 332).** `SegmentFile` and `TakeManifest.read` define and read the on-disk grammar, but nothing walks `audio/takes` for a `seal-status=streaming` manifest or a `.part` on any open path; an orphaned `.part` is readable, not yet sealed or offered.
- **`IncompleteTakeStore` is still rooted under the OS temp directory** (`DefaultAudioEngineController.java:441` passes `java.io.tmpdir`; `IncompleteTakeStore.java:148` appends `.daw/incomplete-takes/`) and unconnected to the flush service's early seal; story 327 re-roots it at the project and repurposes it as the rescued-take registry.
- **A processed recorded clip's file lands inside the take's track directory (unowned).** The callers that read or re-point a clip's source are segment-aware now (Resolution above): the archiver copies every segment, clip processing refuses a clip of more than one segment before rendering and collapses a one-segment list, glue and comp propagate the list, AAF export refuses a multi-segment clip and session export warns about it. What remains is where Reverse/Normalize writes: `ClipProcessingService.produceProcessedFile` puts `Reversed-<uuid>.wav`/`Normalized-<uuid>.wav` beside the source, which for a recorded clip is `<take>/<trackId>/` — a file the take's manifest does not list, in a directory story 332's recovery scan will read. A multi-segment take cannot be reversed, normalized or AAF-exported until something consolidates it into one file; no filed story owns that consolidation. `ProjectArchiver.openArchive` deliberately stays on the 1-arg `deserialize` because its own asset relocation keys on the stored `assets/…` form. `AafExportService` refuses a multi-segment clip whether or not media is embedded, although an embedded export also carries the clip's in-RAM audio. Neither service has a production caller in this tree yet; the guarantees are API-level.
- **Track ids do not survive a reopen (unowned; story 334's take-stack persistence will need it).** `ProjectDeserializer` creates `new Track(name, type)` (`ProjectDeserializer.java:459`), so a reopened project's in-memory track id no longer equals the `<trackId>` directory name under the take; the string references still resolve.
- **Abort after a successful device open (story 325).** When the device opened and `RecordingPipeline.start()` then threw and rolled back, `abortRecordingTake` leaves the device stream open; the next Stop closes it through `stopAudioOutputWhenIdle()` — the pre-existing abort shape, not widened here.
- **Bounded waits and synchronous I/O on the FX thread.** `RecordingPipeline.stop()` joins the flush thread for up to `STOP_JOIN_TIMEOUT` (30 s) on the FX thread; on expiry it logs SEVERE, warns and continues with whatever is sealed (javafx-application-design §11: bounded, never indefinite). On that expiry path the flush thread may still be running while `stop()` builds the clips, so the RAM audio attached to a clip (`RecordingSession.getCapturedAudio()`) and its segment list may be partial. Record start does synchronous file I/O in the record handler as well — `TakeDirectories.allocate` ensures `audio/takes` exists, lists it and creates the take directory, then `RecordingPipeline.start()` opens one segment file per armed track and writes the first manifest (the manifest write includes one `force(true)` of its staging file): small and bounded, but a deviation from javafx-application-design §11 ("never perform synchronous I/O from a UI event handler"), the same class as the temp-directory call it replaces.
- **One block can be in flight at Stop (story 325).** Removing the recording callback does not wait for the audio thread: a block whose callback was already running when `stop()` removed it may be published after the flush thread's final sweep. It stays in the ring and is not part of the take — the loss is bounded to the single block in flight, the block the code before this story also dropped; a drained-callback handshake belongs to story 325's stop fence.
- **A failed start does not restore the monitoring mode (pre-existing).** `start()` applies the pipeline's monitoring mode to every armed track still at `InputMonitoringMode.OFF`; the rollback clears the recording flags but leaves that mode in place, as the code before this story did.
- **Warnings degrade to logging (story 339).** Ring overflow, block truncation, low disk, exhaustion, early seals, a segment that could not be sealed, an unwritable manifest, a flush-loop failure and a slow finalisation reach the `Consumer<String>` from `RecordingPipeline.setWarningSink`; the app injects none yet, so they land in `java.util.logging` WARNING. A sink that throws a `RuntimeException` is logged and ignored; it can never end a take. `DiskHeadroomWatch.forDirectory` watches the take directory's file store with the default thresholds.
- **Unsupported capture bit depth.** A project format whose bit depth is not 16, 24 or 32 fails at record start (`IllegalArgumentException` from `SegmentWriter.open`, surfaced by `abortRecordingTake`); 8-bit capture is not a take format.
- **Smaller facts worth knowing.** A pipeline restarted over the take directory of a take that recorded audio cannot start — `segment-000.wav` exists and `SegmentWriter.open` never overwrites — and fails cleanly, leaving that take's segments and manifest as they were (the app constructs a fresh pipeline over a fresh take directory for every take); `getSession(track)` after `stop()` returns the last lane's inactive session rather than `null`; lap-take clip durations use the tempo snapshotted at `start()` (`TrackCapture.tempoBpm`) while the normal-path clip built in `stop()` uses the live `transport.getTempo()`, as before; `awaitFlushed` also fences on the overflow bookkeeping observed at call time; a lane whose seal throws leaves its `.part` and turns the manifest `aborted`/`write-failure` even on a Stop; an `Error` out of one lane's seal does not cost the lanes after it theirs — every lane gets its seal attempt, the manifest is written `aborted`/`write-failure`, and the first such `Error` is rethrown after that, so on a Stop the flush loop still logs it SEVERE and reports it through the sink; and test pipelines that never call `stop()` (e.g. `PerTrackMonitoringTest`) leave a parked `capture-flush` daemon for the JVM's life (pre-existing test shape, harmless).
