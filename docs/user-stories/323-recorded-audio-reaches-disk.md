# Recorded Audio Reaches Disk: Segment Flush and Project-Relative Storage

## Motivation

No recorded sample ever reaches disk. `RecordingSession` is the capture buffer and it is RAM only: `recordAudioData` appends frames into a growing in-memory `[channel][sample]` array (`RecordingSession.java:201-240`), and the class contains zero file I/O — a grep for file-writing calls across the recording package matches only the metronome settings JSON store (`MetronomeSettingsStore.java:155`). The class javadoc promises the opposite: *"Each segment is stored as a separate file … A crash only risks the current segment, not the entire session"* (`RecordingSession.java:20-25`). Both sentences are false:

- `startNewSegment` constructs only a `RecordingSegment` metadata record naming `segment-NNN.wav`; no file is ever created (`RecordingSession.java:395-405`).
- `finalizeCurrentSegment` marks the in-memory record complete with a **wall-clock-estimated** sample count (`RecordingSession.java:407-423`) — even the metadata is approximate.
- `RecordingPipeline.stop()` stamps each recorded clip's source path from `getSegments().getFirst()` — the path of a file that never existed, and only the *first* segment even when rotation produced several (`RecordingPipeline.java:306-308`). Playback after stop works only because the full take is attached to the clip in RAM (`RecordingPipeline.java:317-319`).
- `ProjectSerializer.buildClipElement` persists only the `source-file` attribute (`ProjectSerializer.java:376-378`); on reload the nonexistent path is flagged in `missingFiles` (`ProjectDeserializer.java:529-537`). A recorded take is unrecoverable after any restart.

And the fictional path is not even inside the project: `TransportController.onRecord` targets `Files.createTempDirectory("daw-recording-")` — the OS temp directory, wiped on cleanup or reboot (`TransportController.java:433`) — while the status bar claims *"auto-save active"* (`TransportController.java:484-485`). Meanwhile `ProjectManager` creates an `audio/` directory in every project, documented as *"recorded audio files"*, that nothing ever writes into (`ProjectManager.java:32,39,160`).

For a studio engineer the consequence is absolute: **every take of every session is unconditionally lost** — on a crash, on a device failure, on OS temp cleanup, or at the latest on project reload. This is THE data-loss story and the single highest-leverage change in `docs/design/RECORDING_RELIABILITY_DESIGN_BOOK.md`: the session invariant (book §2.1) — *everything the performer played is on disk, inside the project, within seconds of being played* — is currently inverted.

## Goals

- Introduce the capture-to-disk skeleton of book §4.1-4.4: a preallocated `CaptureRing` the recording callback hands raw device blocks to (with slot headers stamping start frame, transport beat position, and gate flags), a dedicated `capture-flush` platform thread (`CaptureFlushService`) that drains the ring strictly in order, routes per armed track (reusing the existing pipeline routing/gating logic as-is for this stage), and a `SegmentWriter` that streams real WAV segments to disk.
- Recorded audio lands under `<project>/audio/takes/<UTC-timestamp>_take-NNNN/<trackId>/segment-NNN.wav` per the book §3.3 layout — the `audio/` directory `ProjectManager` already creates. The OS temp-directory root (`TransportController.java:433`) is deleted; the OS temp directory never holds session audio (book §2.6).
- Each take directory carries a `take.manifest` sidecar written by the flush thread at take start and rewritten at each rotation/seal: format, start position, compensation frames, ordered per-track segment lists, seal status — so a recovery scan can rebuild a take without the project file (book §3.3).
- Segment lifecycle per book §3.4: segments stream as `segment-NNN.wav.part` with a provisional self-describing header (fixed 44-byte data offset; sample count derivable from file length), are force-flushed to storage every 5 seconds (configurable), and seal via patch-header + atomic rename — the rename is the commit point. Exact sample counts replace `finalizeCurrentSegment`'s wall-clock estimates.
- Stop finalizes atomically: seal all active segments, write the manifest's final seal status, then build clips that reference **every** segment of the take in manifest order — the `getFirst()`-only stamping (`RecordingPipeline.java:306-308`) is deleted.
- Serialized clip references are **project-relative** (`audio/takes/…/segment-NNN.wav`); absolute paths for anything under the project root are forbidden (book §9.5). The serialization schema change is coordinated with `PERSISTENCE_INTEGRITY_DESIGN_BOOK.md` (stories 329/334 own reload and take persistence).
- The existing 30-minute / 500 MB segment-rotation caps are retained; rotation becomes a flush-thread act producing real files (book §5.3).
- A disk-headroom watch on the flush thread (cached free-space figure, refreshed on a slow tick): crossing the low-water mark raises a warning, and exhaustion seals the take cleanly with everything captured so far intact — never a throw out of a write loop (book §4.3). Until the Book 4 notification stories land, warnings degrade to logging (book §6.3 ordering note).
- The transport status line during recording tells the truth: the §1.1 *"auto-save active"* claim becomes accurate, because audio is continuously flushed.
- Explicitly allowed this stage: the in-RAM `capturedAudio` growth may remain, since it feeds today's post-stop playback attach — story 324 (Stage 2) removes it and makes the callback side RT-safe.

## Goals — Tests

- A crash-durability test records ~2 minutes of simulated capture and hard-terminates the writer mid-take: the sealed and `.part` segments under `<project>/audio/takes/` contain the captured audio, and a reader using only the §3.4 grammar (sample count = (length − data offset) ÷ frame size) recovers playable audio.
- A rotation test records past a rotation boundary and asserts the finalized clip references **all** segments, in manifest order — never only `segment-000.wav`.
- A round-trip test saves and reopens a project with a recorded take: serialized clip references are project-relative, resolve inside the project directory, and are flagged missing only if the files were actually deleted.
- A filesystem-level test asserts the seal is atomic: no observable `.wav` ever has a provisional (streaming-sentinel) header — a `.wav` is either fully sealed or still a `.part`.
- A force-cadence test asserts un-forced data is bounded by the configured cadence (default 5 s) per active segment — the book §2.1 risk window.
- A manifest test asserts the sidecar carries the ordered segment list, format, start position, and seal status, and is rewritten at rotation and seal.
- A storage-location test asserts the record path roots at the project's `audio/` directory and that no capture-path code references `Files.createTempDirectory` (the temp-root call site is gone).
- A disk-exhaustion test simulates free-space exhaustion mid-take: the take seals cleanly with all previously flushed audio intact and readable.

## Technical Notes

- Implements **Stage 1 — Recorded Audio Reaches Disk: Segment Flush and Project-Relative Storage** of `docs/design/RECORDING_RELIABILITY_DESIGN_BOOK.md` (§8). The behavioural contracts bound here: §3.3 (on-disk layout), §3.4 (segment lifecycle), §5.3 (segment lifecycle contract), §4.2-4.4 (ring, flush service, writer), §2.1/§2.5/§2.6 (principles).
- New classes in the `daw-core` recording package: `CaptureRing`, `CaptureFlushService`, `SegmentWriter`, `TakeManifest`, `TrackCapture` (book §3.1). Files to touch: `RecordingSession.java` (segment metadata gains real files; estimates → exact counts), `RecordingPipeline.java` (stop/finalize references every segment; `:306-308` deleted), `TransportController.java` (`:433` temp root deleted; project-rooted output; truthful status line), `ProjectSerializer.java`/`ProjectDeserializer.java` (project-relative references), `ProjectManager.java` (the existing `audio/` directory becomes real).
- Model `CaptureRing` on the proven house idiom `AudioBlockRing`, and the `capture-flush` thread on `AsioBufferSwitchShim`'s `asio-input-drain` thread (stories 311-312; book §1.9, Appendix A) — park when dry with a bounded backstop, drain strictly in order.
- `SegmentWriter` is a distinct class from `WavExporter`: export is one-shot known-length, capture is append-unknown-length with partial-file states (book §4.4's rejected alternative).
- Ring slot headers carry frame/beat/gate snapshots stamped on the callback so flush-side gating stays sample-accurate (book §4.2); per-track RT-side routing was explicitly rejected (book §9).
- Subsumes the write-to-disk goal of story **007** (Complete Recording Workflow with Monitoring and Count-In) and the capture-integration disk goal of story **060** (Complete Recording Pipeline with Audio Capture and Clip Creation) — cross-reference both rather than re-filing.
- Cross-refs: story **324** (RT-safe completion on this seam), **327** (rescue = this seal early), **329/332/334** (`PERSISTENCE_INTEGRITY_DESIGN_BOOK.md` hand-offs, book §6.4), **331** (shared temp-file + atomic-move idiom).
- Research backing: SKILL `research-daw` §3, whose primary source (`docs/research/open-source-daw-tools.md` §3, Real-Time Audio Processing) asks for a lock-free audio thread — "no allocations or locks on the audio thread" — and "Ring buffers: For communication between audio thread and UI thread". The dedicated `capture-flush` drain thread is the book's own design (§2.3, §4.3), modeled on the `AsioBufferSwitchShim` + `AudioBlockRing` drain-thread discipline its Appendix B lists.

## Resolution

Every recorded sample now reaches disk, inside the project, while the take streams: once the flush thread has drained its block from the ring and written it, it stays un-forced for at most the force cadence plus the wait for that thread's next cadence check (the segment paragraph below). The recording callback no longer grows a RAM buffer: `RecordingPipeline.onAudioCaptured` (audio thread) claims one preallocated slot of a `CaptureRing`, copies the device block into source 0 and each armed graph-instrument track's `AudioEngine.graphInstrumentRecordingBuffer` into sources 1…n (that engine buffer is valid only inside the callback), stamps the slot header with `transport.getPositionInBeats()`, the start frame derived from it, the punch snapshot (`isPunchEnabled()` and the `PunchRegion`'s start/end frames) and `isLoopEnabled()`, publishes, and unparks the flush thread (`CaptureFlushService.signal()`). One platform daemon thread named `capture-flush` (`CaptureFlushService`, built with `Thread.ofPlatform().name(THREAD_NAME).daemon(true).unstarted(this::runLoop)`) drains the ring strictly in order (`peek`/`release`), parks with a 50 ms backstop (`PARK_BACKSTOP`) when dry, and per block — in this order — detects a loop-lap wrap from the header (loop-record on, `loopEnabled`, beat lower than the previous block's) and seals the lane, stacks the lap as a `Take` and opens the next lane; ticks the `DiskHeadroomWatch`; applies the punch gating the callback used to run (`captureWithTransportPunch` with its sample-accurate slicing, 5 ms cosine fades and `wasInsidePunchRegion` re-entry rule, or the legacy beat-based `PunchRange` gate) from the header's frames and beat, never re-reading the transport; routes the sources into each `TrackCapture`'s preallocated scratch block per the `InputRouting` snapshot taken at `prepare()` (every row of the routed block the source did not provide is zeroed, never stale — including the rows beyond an instrument source narrower than the routed width); hands the routed block to that track's lane `RecordingSession.recordAudioData`, which appends to a `SegmentWriter` and to the RAM mirror; notes a truncation when the block was longer than its ring slot; rewrites the manifest if a segment opened, sealed or was discarded or a truncation episode began; and runs the cadence tick before the block is released and counted, as it does once more at the end of every pass (Copilot review round 2, below). One writer per byte (book §2.3): the callback writes ring slots only; the flush thread is the only writer of segment files, `take.manifest`, the RAM mirrors, the loop-take stacks and the ring's read index, and the only thread that creates or deletes a segment or manifest file of its take — each track's first segment and the first manifest included, which it creates as its first act, and the files of a start that failed or was cancelled, which it deletes before it terminates if it has not already ended on its own (Copilot review round 5, below); the flush thread never touches a `Track` (`TrackCapture` snapshots id, name, routing and compensation on the caller thread); the caller thread (FX in the app) runs the take's lifecycle — `RecordingPipeline.prepare()`, then `beginCapture()` or `cancelStart()`, then `requestStop()` and `completeStop()` — none of which touches storage or waits for the flush thread, and it mutates `Track`s (`addClip`, `putTakeGroup`) only in `completeStop()`, once the flush thread has terminated (`CaptureFlushService.isTerminated()`; before then `completeStop()` builds nothing and throws `IllegalStateException`, below). A start is all-or-nothing and comes in two halves, gated on the take's files (Copilot review round 5, below). `prepare()` reads the anchor, sets the recording flags, resolves compensation, allocates the ring and one `TrackCapture` per armed track (each with an unstarted lane-0 session), constructs and starts the `CaptureFlushService` — whose `start()` only starts the thread — and returns the take's readiness stage; the thread's first act is the take's initialisation: it creates the take directory if it is missing, starts every lane-0 session (each creating `<take>/<trackId>/segment-000.wav.part`) and writes the initial manifest, and only then completes readiness and begins draining. `beginCapture()`, once readiness has completed normally, puts the transport back at the position `prepare()` read if it has moved since — only when the transport is not rolling (STOPPED or PAUSED); a rolling transport is never sought there (Known limitations) — then installs the callback and calls `audioEngine.start()` and `transport.record()`; nothing is captured before that, because by default the ring holds only the blocks that cover `CaptureRing.DEFAULT_HANDOFF_TOLERANCE` (250 ms) of audio, rounded up to a power-of-two slot count of at least `CaptureRing.MIN_SLOTS` (8) — with 256-frame blocks at 48 kHz, 47 blocks rounded up to 64 slots, about 341 ms. No rollback waits for the flush thread. An initialisation that fails, or that an abort reaches, deletes on the flush thread every segment file this take opened and the manifest if this take attempted to write it; the thread then marks itself terminated, and only after that fails readiness. A `prepare()` or `beginCapture()` that throws rolls back in reverse (`beginCapture()` first removes the callback and stops a transport the failed step left recording; then `releaseFailedStart(cause)`: the take's flush service asked to discard the take with `CaptureFlushService.requestAbort()`, the captures dropped, `track.setRecording(false)`, and `preparing`/`active` cleared in a `finally`; every step runs even if an earlier one throws, and whatever a step throws is attached to the original failure as suppressed) and rethrows; `cancelStart()` asks the same discard for a take abandoned before capture began and returns the thread's `termination()` signal. Either way the flush thread deletes the take's segment and manifest files, and each track directory it created, if that leaves it empty, and then terminates, so a fresh take directory is empty once `termination()` has completed (the deletes are best-effort: a file the OS refuses to delete is logged and left) — unless that thread had already ended on its own before the discard was asked for (a throwable that escaped its drain loop sealed the take early), when the discard deletes nothing and the take stays in the directory as it was sealed early; a `SegmentWriter.open` whose header write fails closes and deletes the `.part` it had just created, best-effort: an `IOException` from that close or delete is attached as suppressed to the rethrown failure (`SegmentWriter` logs nothing), and a `.part` the delete could not remove is left. `doPrepare` clears the previous take's flush service, ring and instrument-track array before it allocates anything, so a failed restart of a reused pipeline rolls back only what that start created and never the previous take's sealed files (two exceptions, deferred to story 350: when the restart's first manifest write fails before its rename lands, the rollback deletes whatever is at `take.manifest`, such as the manifest the previous take left, and whatever file or empty directory is at `take.manifest.tmp` — Known limitations); after a `cancelStart()`, or a `beginCapture()` that failed and was rolled back, the next `prepare()` of the same pipeline is refused with `IllegalStateException`, touching nothing, until that take's flush thread has marked itself terminated (`CaptureFlushService.isTerminated()`; `termination()` completes right after), because that thread may still be creating or deleting that take's files in the same take directory (book §2.3: one writer per byte) — the app builds a fresh pipeline over a fresh take directory for every start, so it never meets the refusal; and the callback returns at once when the pipeline holds no ring or no flush service, so a callback the audio thread had already loaded is harmless after a failed restart. `RecordingSession` listeners now fire on the flush thread, lane 0's start notifications included (inside the take's initialisation; its Javadoc says so); `capturedSampleCount`, `active` and `paused` are volatile and `totalSamplesRecorded` atomic. `RecordingPipeline.awaitFlushed()` (bounded, 10 s by default) is the fence tests and diagnostics use: it returns once every block published before the call has been applied and every overflow counted before the call has its `gap=` line recorded — the manifest rewrite attempted, or — while an earlier manifest failure is still being retried — deferred to the next retry slot; a rewrite that failed is retried later and is not part of the fence. It may be called from any thread but the flush thread.

`CaptureRing` follows the `AudioBlockRing` discipline: `AtomicLong head`/`tail` with `lazySet` release stores; slot count `slotCountFor(sampleRate, blockFrames, DEFAULT_HANDOFF_TOLERANCE)` — enough blocks to cover 250 ms, never fewer than `MIN_SLOTS` = 8, rounded up to a power of two so the wrap is a mask (the constructor refuses a request above `MAX_SLOTS` = 2^30, the largest power of two an `int` holds, with `IllegalArgumentException`, and `slotCountFor` refuses a tolerance that covers more than `MAX_SLOTS` blocks the same way: rounding either up would never terminate); slot payload `sourceCount × channelsPerSource` rows of `format.bufferSize()` frames, where the row count is `max(format.channels(), max over armed routings of firstChannel + channelCount)` so a device that delivers more input rows than the format's width loses none of them; and a primitives-only header. `claim()` → fill → `publish()` on the producer, `peek()` → `release()` on the consumer; the `Slot` setters that take counts clamp rather than throw, so no exception path is reachable from the callback for a source index within `sourceCount()` and a block whose rows are non-null (source indices are not clamped; an index outside that range or a `null` row throws). `CaptureRing.claim/publish/overflowCount/droppedAfterSequence/noteTruncatedFrames/truncatedFrames/size/isEmpty` are `@RealTimeSafe` under `RealTimeSafeContractTest`'s bytecode rules; `Slot` is annotated at type level but is a nested class, which that test's `ModuleClassScanner` skips (it filters `$` names), so the reflection-visible rules — no `synchronized` modifier, no varargs, no boxed parameter or return type on any public method — are pinned for `Slot` by `CaptureRingTest.slotsRealTimeSafeSurfaceObeysTheRulesTheModuleScannerCannotReach`, with `theSlotPinWouldRejectEachForbiddenShape` as its non-vacuity fixture; the bytecode half of the `synchronized` rule — no monitor instruction in any public method, which a `synchronized` block leaves behind with no modifier for reflection to see — is pinned by `CaptureRingTest.slotsPublicMethodsHoldNoMonitorInstruction`, which parses `CaptureRing$Slot` with the Class-File API, with `theMonitorScanWouldRejectASynchronizedBlock` as its fixture. **Binding decision — overflow policy (a deliberate deviation from book §4.2):** when the ring is full the *incoming* block is dropped — `claim()` returns `null`, having first stored the drop marker (`droppedAfterSequence`, the sequence number of the last block published before the drop) with a `lazySet` and then advanced the overflow counter by a plain load and a `lazySet` (no read-modify-write on the callback), and `onAudioCaptured` returns at once. The book's "drops the oldest unwritten block" was not implemented because overwriting the oldest slot is not single-producer-safe while the consumer may be copying out of exactly that slot — the reason `AudioBlockRing.write` gives. The loss is bounded and honestly recorded: after each drain pass the flush thread compares `overflowCount()` with the value it last saw and appends one `gap=*|<startFrame>|<droppedBlocks>` line per noticed episode, positioned at the end of the last block accepted before the drop: the drain pass remembers the end frame of the block the drop marker names when it applies that block, so blocks published after the drop and applied in the same pass do not move the position. Drops at different points that one pass notices together share one line, at the most recent marked block; and when the marked block's end was not captured — the marker was not yet visible when that block was applied, or the drop happened after the pass's last look at the ring — the line falls back to the end of the last block applied. The flush thread keeps `overflow-blocks=` current, rewrites the manifest and warns through the sink. The callback never blocks (book §9.14). **Over-long blocks are counted, never cut off silently:** a ring slot holds `format.bufferSize()` frames, the size the pipeline was constructed with, and nothing guarantees the engine delivers no more; a longer block keeps its first `format.bufferSize()` frames, the callback stamps the excess on the slot and adds it to the ring's `truncatedFrames` counter (`RecordingPipeline.getTruncatedFrames()`), and the flush thread records the first over-long block of a run as one `gap=*|<end of its kept frames>|0` line with one warning and one manifest rewrite — one line per episode, not per block — and carries the running total in `truncated-frames=` with every later manifest write, exact at the seal.

A segment is a real WAV file streamed by `SegmentWriter`: `open`, `append`, `forceIfDue()` and `seal()` run on the flush thread — a track's first segment is opened in the take's initialisation, every later one at a rotation or a new loop lane — so in the pipeline one thread writes a file. While streaming it is `<take>/<trackId>/segment-NNN.wav.part`: a 44-byte canonical header (`RIFF`/`WAVE`/`fmt ` of 16 bytes/`data`; `DATA_OFFSET` = 44), format code 1 (PCM) for 16 and 24 bit and 3 (IEEE float) for 32 bit — the rule `WavExporter` applies with `DitherType.NONE` — with the RIFF-size and data-size fields (offsets 4 and 40) holding `PROVISIONAL_SIZE` (`0xFFFFFFFF`). Appends go straight through positional `FileChannel` writes with no Java-side buffering. The channel is `force(false)`d when bytes have been appended since its last force and `now − lastForce ≥ cadence` on the injected `nanoClock` (`lastForce` is the open time until the first force; `DEFAULT_FORCE_CADENCE` = 5 s; `RecordingPipeline.setForceCadence` before `prepare()`). That check runs after every append and in `SegmentWriter.forceIfDue()`, which the flush thread's cadence tick (`CaptureFlushService.forceDueSegments()`, through `RecordingSession.forceIfCadenceElapsed()`) calls for every track's current session, paused or not, after every block it applies and at the end of every drain pass — including the pass after each `PARK_BACKSTOP` park while the ring is dry — so bytes that nothing more is appended after (a punch-out, a block without the track's instrument source, a dry ring) are forced on cadence too (Copilot review round 2, below). While the take streams, a byte therefore stays un-forced for at most the cadence plus the wait for the flush thread's next check (book §2.1, §4.3). Nothing is forced when nothing is un-forced; the tick stands down once the take is sealed and during the final sweep, whose seal opens with a `force(true)` of every segment it seals; and a tick whose force throws ends the take as a failed append does, sealed `aborted`/`write-failure`. `seal()` is `force(true)` → patch both size fields with the exact values → `force(true)` → close → `Files.move(part, wav, ATOMIC_MOVE)`; the rename is the commit point, an existing `.wav` is never overwritten (`FileAlreadyExistsException` before the file is touched, and `open` already refuses when the sealed `.wav` exists so a lane fails at its open rather than at its seal; the guarantee rests on that existence check, not on the move — `ATOMIC_MOVE` replaces an existing target on POSIX file systems — and covers what the design itself can produce, one writer per segment), and `close()` on an unsealed writer abandons it — the seal is never a side effect of try-with-resources. If the rename itself fails the writer ends abandoned with the `.part` in place, its exact sizes already patched in and still readable by the streaming grammar (`SegmentWriter.failNextRename()` is the test seam that pins patch-before-rename). A segment's data chunk is at most `SegmentWriter.MAX_DATA_BYTES` = `Integer.MAX_VALUE − 44`, so a whole segment file never exceeds `Integer.MAX_VALUE` bytes and both size fields of a sealed segment are positive signed 32-bit values (the house `WavFileReader` reads the data size as a signed `int`). Bit depths 16, 24 and 32 are accepted; any other `AudioFormat.bitDepth()` fails at `RecordingSession.start()` with `IllegalArgumentException` (8-bit capture is not a take format). The PCM quantiser lives in one place, `core.export.PcmSampleEncoding`, which `WavExporter` now delegates to as well, so a sealed segment's data chunk is byte-identical to an export of the same frames with `DitherType.NONE` at the same bit depth (a dithered export differs by design: capture never dithers). `SegmentFile` is the §3.4 reader a recovery scan needs and uses nothing but the bytes and the name: `describe(Path)` takes the frame count from the file length for a `.part` (`(length − 44) / (channels × bytesPerSample)`, floored to whole frames) and from the data-size field for a sealed `.wav` (rejecting a sealed name that still carries the sentinel, or a data size the file cannot hold); `readFrames(Path)` decodes at `WavFileReader`'s scale. `TakeManifest` is the `take.manifest` sidecar — line-oriented UTF-8, `key=value`, `#` comments, `|`-separated fields, unknown keys ignored: `manifest-version=1`, `take`, `started-at`, `sample-rate`, `bit-depth`, `stream-channels`, `start-beat`, `start-frame`, `force-cadence-millis`, `ring-slots`, `ring-frames`; one `track=<trackId>|<channels>|<compensation-frames>` per armed track in armed order; one `segment=<trackId>|<lane>|<index>|<path relative to the take dir, '/'>|<frames or -1 while streaming>|<streaming|sealed>` per segment; `gap=<trackId or *>|<startFrame>|<dropped-blocks>` lines (one per overflow episode; `dropped-blocks` 0 marks the start of a truncation episode); `overflow-blocks`; `truncated-frames` (absent in files written before this key existed: reads as 0); `seal-status=streaming|sealed|aborted`; and `sealed-by=stop|disk-exhaustion|write-failure|start-failure`, present iff the status is not streaming. Segment order in the manifest *is* the clip's segment order: `segments()` is canonicalised at construction (track order, then lane, then index); a segment's relative path must be one or more `/`-separated names, each matching `[a-z0-9][a-z0-9._-]*`, none ending in `.`, and none whose stem — the part before its first `.` — is a Windows device name (`con`, `prn`, `aux`, `nul`, `com1`–`com9`, `lpt1`–`lpt9`) or `com0`/`lpt0`, so a backslash, a `:`, a space, a `~`, a capital or non-ASCII letter, a leading `.` or `-`, and an empty, `.` or `..` name are all refused — with an `IllegalArgumentException` at construction, which `read(Path)` reports as an `IOException` naming the file and the line (the Copilot review round, below); and `read(Path)` parses exactly what `write(Path)` emits (and ignores one leading U+FEFF, so a manifest re-saved by a BOM-writing editor still reads). Every write is atomic and durable before it is visible — `take.manifest.tmp` in the take directory is written through a `FileChannel`, forced to storage (`force(true)`) and closed, and only then moved: `Files.move(tmp, manifest, REPLACE_EXISTING, ATOMIC_MOVE)` with a `REPLACE_EXISTING`-only fallback on `AtomicMoveNotSupportedException` (the Persistence book §4.1 idiom — same-directory sibling → fsync → atomic move — implemented locally until story 331 centralises it). It is written by the flush thread: at take start, in the take's initialisation, and thereafter whenever a segment opens, seals or is discarded (rotation, lane seal), on every overflow episode, at the start of every truncation episode, and at the final seal. So the Goals wording — "written by the flush thread at take start" — holds: until Copilot review round 5 (below) the first write was made on the caller thread, a deviation that round removed. **The manifest is a sidecar, so a manifest write that fails never ends the take:** on the flush thread one write is attempted up to `MANIFEST_WRITE_ATTEMPTS` = 5 times, `MANIFEST_RETRY_PAUSE` = 20 ms apart (on Windows a target held open by another process without delete sharing fails the move with a `FileSystemException`, which the `AtomicMoveNotSupportedException` fallback does not catch, and is usually that short-lived); if every attempt fails — an `IOException` or a `RuntimeException` — the failure is recorded (`lastFailure()`), the sink is warned once per failure episode, capture continues, and the write is retried with later blocks and idle passes, one attempt at most once per `MANIFEST_RETRY_INTERVAL` = 1 s of the take's clock so that an unwritable manifest costs the drain one retry cycle (4 × 20 ms) per failure episode and one attempt a second after that, until it lands. The same holds for the final seal: the segments are sealed whether or not the manifest can say so, and the manifest on disk is then the last one written. Only the initial write, in the take's initialisation, is a single attempt, and its failure fails the take's readiness once the files the initialisation created have been deleted.

**Binding decision — rotation on exact counts (D4):** the 30 min / 500 MB caps stay (`RecordingSession.DEFAULT_MAX_SEGMENT_DURATION`/`DEFAULT_MAX_SEGMENT_BYTES`; `RecordingPipeline.setSegmentLimits` before `prepare()`), but rotation is decided on the flush thread from exact counts — after each append from `writer.frameCount() / sampleRate ≥ maxSegmentDuration` or `writer.dataBytes() ≥ maxSegmentBytes`, and before an append that would take a segment already holding audio past the byte cap, so no sealed segment exceeds the cap (the one exception is a single block larger than the cap, which lands in an empty segment that then rotates) — and no wall-clock read decides it; the `Instant`s in `RecordingSegment.startTime`/`endTime` are metadata only. A byte cap the writer could not honour is refused up front: `RecordingSession.requireSegmentByteCap` (the session constructors and `RecordingPipeline.setSegmentLimits`) rejects a cap above `SegmentWriter.MAX_DATA_BYTES` with `IllegalArgumentException`, because such a cap could never rotate a segment before the writer refused the append and ended the take instead. `RecordingSegment` keeps its shape with `sampleCount`/`sizeBytes` now exact (frames appended, data-chunk bytes) and gains `streamingPath()` (`filePath()` + `.part`). `getSegments()` never lists a segment without a file on disk (book §9.3): a segment is added when its `.part` is created, replaced by its sealed record when the `.wav` lands, and a zero-frame tail at `stop()` is deleted and dropped from the list (its index reused by the next open) rather than sealed into an empty file — a take with no audio leaves no segment. Disk first: `recordAudioData` advances `capturedSampleCount` and `totalSamplesRecorded` after the append, whether or not it throws, by exactly the frames the append added to the writer's `frameCount()` — the whole block when only the cadence force after its writes failed, none when it failed before writing — so the session's counters, its RAM mirror and the segments its writers seal hold the same frames (until the verification round of Copilot review round 2, below, a failed append-time force left the session and its clip one block short of their own sealed segment and manifest). `finalizeCurrentSegment`'s wall-clock estimate, `estimateSegmentSamples` and the test-only `recordSamples(long, long)` are gone.

A stop comes in two halves, and neither waits for the flush thread (Copilot review round 5, below). `RecordingPipeline.requestStop()` removes the callback, clears the recording flags and stops the transport, then asks the flush thread to seal (`CaptureFlushService.requestStop(STOP)`, in a `finally`, so the seal is requested even when one of those steps throws): the stop flag is set and the thread unparked, and `requestStop()` returns the thread's `termination()` signal at once; a further call while the take is finalising repeats none of those steps and returns the same signal. The thread's final sweep drains the ring, stops every lane's session (exact-count seal; in loop-record the in-flight lap becomes the last take) and writes the manifest `seal-status=sealed`/`sealed-by=stop` — unless a lane's seal threw, in which case that `.part` stays for recovery and the manifest reads `aborted`/`write-failure` even on a Stop, because the record must not claim more than the disk holds. Only once the thread has terminated does `RecordingPipeline.completeStop()` build clips, on the caller thread (called before then, it reads and builds nothing, throws `IllegalStateException` and leaves the take finalising): on the normal path one `AudioClip` per track whose `setSourceSegmentPaths(capture.sealedSegmentPaths())` carries every sealed segment, absolute, in manifest order, with the RAM audio attached as before; in loop-record the lap takes were built on the flush thread (each take's clip carrying its own lane's segment list; segment numbering continues across lanes inside `<trackId>/`) and are applied with `addClip`/`putTakeGroup` once the thread has terminated. The take ends in the mode it began in: loop-record is part of the take's configuration, `setLoopRecord` refuses a change while a take is being prepared or recording (`IllegalStateException`, like the other pre-start seams), and `completeStop()` reads the snapshot the flush thread worked from (`flush.config().loopRecord()`), not the live field. A lane is finalized once: `TrackCapture.finalizeLane` marks the lane's session before anything in it can throw, so the early seal that answers a seal failure at a loop wrap neither stacks the lap a second time nor lists a sealed segment twice. `sealAll` is safe to re-enter in two independent halves — the lanes are sealed by the first call only and its reason sticks, the final manifest is written by whichever call finds it not yet on disk — so a throw inside the first call's manifest step still leaves a manifest whose `seal-status` is not `streaming`. Every lane gets its seal attempt, and a lane that threw makes the seal a failed one: `TrackCapture.finalizeLane` catches an `Error` as well as a `RuntimeException` around the session's `stop()`, so the bookkeeping of a segment that did seal still runs before the throw goes on; `sealAll` catches both per lane, goes on to the remaining lanes, writes the manifest `aborted`/`write-failure` — never `sealed`/`stop` — and only then rethrows the first `Error`, which on a Stop the flush loop logs SEVERE and reports through the sink. The `getFirst()`-only stamping, the `takeFinalizationExecutor` no-op executor and the on-callback `previousBeatPosition` are deleted. **Binding decision — clip references and the head invariant (D5):** `AudioClip` gains an ordered, immutable `getSourceSegmentPaths()` (empty for a single-file clip); when it is non-empty the list is the authority and `getSourceFilePath()` equals its first element — `setSourceSegmentPaths` derives the head, `setSourceFilePath` throws `IllegalArgumentException` for any other value while a list is present, an empty list leaves `sourceFilePath` untouched, and `duplicate()`/`splitAt()` propagate the list.

**Every caller that reads or re-points a clip's source is segment-aware.** Every recorded clip carries a segment list — one element for a take that never rotated — so a caller that knew only `getSourceFilePath()` would either be refused by the head invariant or silently use a fraction of the take. `ProjectArchiver.collectRefs` emits one `AudioClipSegmentRef(clip, index)` per element of a non-empty list and no head-only `AudioClipRef` for that clip (`update` rebuilds the list with that one element replaced through `setSourceSegmentPaths`, so the head follows element 0); Archive Project therefore copies every segment of a rotated take (SHA-deduplicated, one `assets/…` entry each), `openArchive` restores the list in order as absolute paths under the extract directory and reports each unresolvable segment once, and `consolidateInPlace` and `previewAssetSizes` follow through the same walk. `saveAsArchive` now rewrites the references inside the `try` whose `finally` restores them, recording each original before its reference is touched, so a rewrite that throws part-way through leaves the in-memory project as it was (no production reference throws from its update any more, so the package-private fault seam `ProjectArchiver.failRewriteAfter(int)` injects that failure for the test that pins it). `ProjectLifecycleController.collectMissingAssetPaths` (the pre-archive dialog) walks the same elements. `ClipProcessingService` (Reverse, Normalize) refuses a clip of more than one segment with `IllegalStateException` before anything is rendered — no file written, nothing recorded in the `ClipAssetHistory` — because its render reads one file; the batch factories (`reverse(List)`, `normalize(List, double)`) check every clip of the selection before they build an action, so a batch holding such a clip is refused as a whole, at the factory, and the clips ahead of it are not processed (the check when the action runs stays); for a one-segment clip it clears the list and then sets the rendered file, undo restores the list (and with it the head), redo collapses again. `GlueClipsAction` compares the two clips' segment lists as well as their heads and carries the list onto the merged clip; `TakeComping.compile` carries the take clip's list onto each comp clip. `AafExportService.composeTimeline` refuses an included clip of more than one segment with an `IllegalStateException` naming the clip, its id and its track, and writes nothing; `SessionInterchangeController.exportSession` keeps the head reference and adds one warning per such clip to the `SessionExportResult`, which the export surface already shows.

Persisted references follow one rule, `ProjectPaths` (shared by the serializer and the deserializer so the two cannot drift; the class is public only for its in-memory predicate `isAbsoluteReference`, and `relativize`, `resolve` and the classification stay package-private). Write side — `relativize(root, reference)` rewrites a reference only when the root is known, the reference parses as a `Path`, is absolute and lies strictly under the normalised root, as the root-relative path joined with `/` (`audio/takes/<take>/<trackId>/segment-000.wav`); an already-relative reference, an absolute reference outside the root, the root itself or an unparseable string is written verbatim, so an outside asset stays absolute (book §9.5; Persistence book §3.3). `ProjectSerializer.buildClipElement` passes `source-file` through it and writes one `<source-segment path="…"/>` child per element of `getSourceSegmentPaths()`, in order, none for a single-file clip; the root is `project.getMetadata().projectPath()`, which `ProjectManager.saveDawProject` sets before serialising. Read side — the new `ProjectDeserializer.deserialize(String xml, Path projectDirectory)` puts every non-empty clip reference in exactly one of five classes, judged with the `Path` semantics of the platform reading the file by one private `ProjectPaths` method that `resolve` and the package-private `unresolvable` both call: (a) a *project-relative* reference — no root component (`Path.getRoot() == null`), and the directory joined with it, normalised, lies strictly under the directory (the containment test `relativize` applies, in one private helper both use) — becomes that absolute normalised path, containment being judged on the normalised target, not on the raw string, so `../<directory name>/audio/x.wav` is resolved; (b) a reference that is *absolute* on the reading platform (a legacy file's absolute path, or an outside asset) is kept verbatim; and (c) one that is *not a valid path* there, (d) one that is *drive- or root-relative* there (on Windows `C:x.wav`, `\x.wav` and `/x.wav`) and (e) one that *escapes* — no root component, and a normalised target outside the directory (`../outside.wav`, `audio/../../x.wav`, `..`) or the directory itself (`.`, `audio/..`) — are **unresolvable**. The deserializer does not resolve an unresolvable reference: it keeps it as written — so the next save writes it back unchanged and a segment list keeps its count, order and head — logs it once at WARNING naming the clip, the reference and the reason (`escapes the project directory`, `is the directory itself`, `is not a valid path on this platform` or `is drive- or root-relative on this platform`), and reports it missing whether or not a file exists anywhere it could name, never through the existence check, which would judge a relative, drive-relative or root-relative string from the JVM's working directory or the current drive. Every usable reference is reported missing only when no file exists at its in-memory path, each segment once, and a clip with segments is checked through its segments only (its `source-file` attribute is not resolved, checked, warned about or reported: `setSourceSegmentPaths` makes the first segment the head); a `<source-segment>` whose `path` is empty or missing is skipped with a WARNING that names the clip; the 1-arg `deserialize(String)` delegates with `null` and keeps today's semantics (with no directory, nothing is unresolvable). The classification follows the reading platform, and `ProjectPaths` states where that matters: containment follows the platform's `Path` equality, which is case-insensitive on Windows (for a directory named `Session`, `../SESSION/audio/x.wav` walks back in on Windows and escapes on Linux); a name Win32 trims (`...`, `a.`) is lexically a plain name, so it resolves under the directory — residue, not an escape, since no such name reaches outside it; a Windows device name (`NUL`, `CON`, `COM1`–`COM9`, `con.wav`, `audio/nul.wav`) is lexically a plain name as well, so it resolves under the directory, where on Windows it names a device rather than a file — the three consumers below require a regular file (`Files.isRegularFile` in the archiver and the pre-flight, `WavFileReader`'s `isRegularFile` check in clip processing), so none reads it as one; and `..\x.wav` is unresolvable on Windows but one in-root file name on Linux, where `C:x.wav` and `\x.wav` are single names under the directory too, a legacy Windows-absolute `C:\…` has no root component and is rebased under it (Known limitations), and `/x.wav` is absolute. After a load with a directory, every clip reference is therefore absolute or unresolvable, and **the code that opens clip references — `ProjectArchiver`, the Archive Project pre-flight and `ClipProcessingService` — treats one that is not an absolute path on this platform as naming no file, and never resolves it against the JVM's working directory; only a load with no project directory (the one-argument `deserialize(String)`) still checks a relative clip reference's existence there, for `getMissingFiles()`.** The three consumers share one public predicate, `ProjectPaths.isAbsoluteReference`: `ProjectArchiver` (Archive Project packs no file for such a reference and gives it the missing-asset treatment, `previewAssetSizes` leaves it out, and `consolidateInPlace` leaves it as it is), the Archive Project pre-flight `ProjectLifecycleController.collectMissingAssetPaths` (lists it as missing without touching the filesystem; a blank one is skipped — Known limitations) and `ClipProcessingService` (Reverse and Normalize refuse such a clip with an `IllegalStateException` before anything is rendered — naming the clip and the reference and saying to relink it, or, for a blank reference, that the clip has no source — and the batch factories refuse a batch holding one, blank or not, before any clip is processed). `AafExportService` and `SessionInterchangeController` write a clip reference as text and never open it, and are unchanged. `ProjectManager.openProject` passes its `projectDirectory`, `JournalReplayer.loadCheckpoint` passes `ctx.projectDirectory()`, and `SnapshotsController.loadFromEntry` passes the open project's path (null-safe); each of the three also stamps that directory on the loaded project's metadata (`getMetadata().withPath(…)`), because the references it resolved are absolute in memory and can only be written project-relative again by a project that knows its directory — without it a restored snapshot was refused by Record's no-directory gate and serialized absolute paths into every later checkpoint, and the `project.daw` that journal recovery rewrites held absolute paths. **Binding decision — schema:** `<source-segment>` is version-neutral — an optional child absent from files written before this story and ignored by older readers, landed without a `MigrationRegistry` bump the way `<midi-effect-chain>` and `<layout>` were; `ReferenceTrack.source-file` is untouched (story 329).

**Binding decision — the take's home and the no-directory refusal (D6):** a take lives in the project, never in the OS temp directory. `ProjectManager.AUDIO_DIR_NAME` (`"audio"`) is public and `ProjectManager.audioDirectory(Path)` returns `<project>/audio`, which `createProject` creates; `TakeDirectories.allocate(audioDirectory, now)` creates `<audio>/takes/<yyyy-MM-dd'T'HH-mm-ss>_take-NNNN` — a UTC stamp plus `1 + the highest ordinal already present under takes/`, zero-padded to four ASCII digits whatever the default locale (formatted with `Locale.ROOT`; a locale with its own digits would otherwise produce a name the take-name grammar does not recognise), claimed with `Files.createDirectory` in a loop that bumps the ordinal on `FileAlreadyExistsException`. `TransportController.onRecord()` reads `project.getMetadata().projectPath()`; when audio tracks are armed and the project has no directory it refuses before the engine, the pipeline or any `MidiRecorder` is touched — `LOG.warning`, status text and an ERROR toast both reading `NO_PROJECT_FOLDER_MESSAGE` ("Recording needs a project folder — save the project first"), REC indicator hidden, transport still STOPPED; a MIDI-only take writes no audio files and is not gated. Otherwise it opens the device first, on the FX thread — a refusal there reaches `abortRecordingTake(e)` before anything of the take is allocated — and then enters PREPARING (Copilot review round 5, below): it allocates the take directory on a storage executor, never on the FX thread (a failure there is its own SEVERE log plus an ERROR toast naming `audio/takes`); the FX turn the allocation posts constructs the pipeline over that directory and calls `prepare()`; and the FX turn the take's readiness posts calls `beginCapture()` when readiness completed normally and the start has not been cancelled meanwhile. A start that fails after the device opened — the pipeline cannot be built, `prepare()` throws, readiness fails or `beginCapture()` throws — reaches `abortRecordingTake(e)`, whose ERROR toast reads "Recording aborted — no take was started: …", and the removal of its files runs off the FX thread: the flush thread, if the start got one, deletes the segment and manifest files it created, and each track directory it created, if that leaves it empty (D11) — unless it had already ended on its own before the discard was asked for (a throwable that escaped its drain loop sealed the take early), when it deletes nothing — and once that thread has terminated, the take directory, if it is empty, is deleted on the storage executor; one still holding files is left in place. The turn that ends a start whose take directory could not be allocated, or whose pipeline could not be built, also calls `stopAudioOutputWhenIdle()` for the output stream Record opened, unless the transport is PLAYING or RECORDING (`stopAudioOutputUnlessRolling()`); after a failed `prepare()`, readiness or `beginCapture()` that stream stays open (Known limitations). `Files.createTempDirectory` no longer appears in code under `daw-app/src/main/java` or the daw-core `core.recording` package (`ProjectLifecycleController` names it in comments only); the storage-location sentinel pins that for the `core.recording` package and for the daw-app files on the record path, not for the rest of daw-app (Copilot review round 2, below).

`DiskHeadroomWatch` runs on the flush thread once per applied block, before the write, from a cached figure refreshed on a slow tick (`DEFAULT_REFRESH` 2 s; the production probe is `Files.getFileStore(root).getUsableSpace()` on the take directory, rethrown as `UncheckedIOException`): OK at or above the low-water mark, LOW below it (`DEFAULT_LOW_WATER_BYTES` 1 GiB; the sink is warned once per crossing), EXHAUSTED below the floor (`DEFAULT_FLOOR_BYTES` 64 MiB) or after `FAILURES_BEFORE_EXHAUSTED` = 2 consecutive probe failures (a single failure keeps the last figure). EXHAUSTED seals the take before the block is written: `sealAll(DISK_EXHAUSTION)` stops every lane with its exact counts and writes `seal-status=aborted`/`sealed-by=disk-exhaustion`; the thread stays alive, every later block is drained and discarded (`discardedBlocks()`) so the callback side never notices, and a later `requestStop()` keeps the early reason. An `UncheckedIOException` from a session or any other `Throwable` while a block is applied is logged SEVERE, reported through the sink ("Recording stopped early — …; everything captured so far is sealed under …") and answered by the same clean seal with `sealed-by=write-failure`; a throwable that escapes the drain loop itself is logged SEVERE and reported through the sink the same way ("Recording stopped unexpectedly — …") and ends the thread after the seal; a manifest write that fails is neither — it never ends the take (above). Nothing throws out of the loop (book §4.3). Warnings go to the `Consumer<String>` injected through `RecordingPipeline.setWarningSink`, or to `java.util.logging` WARNING when none is injected (story 339 injects the production seam). The sink is foreign code: a `RuntimeException` it throws is logged at WARNING with the message it was given and ignored, in the headroom watch as in the flush service, so a warning that could not be delivered neither ends a take nor changes the reason one ended.

The status line tells the truth (D12): during an audio take `TransportController` shows `Recording — N track(s) armed — streaming to audio/takes/<take-dir-name>`; a MIDI-only take shows `Recording — N track(s) armed`; nothing claims an "auto-save". The INFO toast ("Recording started — N track(s) armed") is unchanged, and `abortRecordingTake`/`deleteEmptyTakeDirectory` document the take directory under the project's `audio/takes` rather than a temp directory.

**Known limitations / deferred (in scope of later stories)**

- **RT-safety of the callback (story 324).** `RecordingPipeline.onAudioCaptured` allocates nothing by construction — `CaptureRing.claim/copySource/publish` are bounded copies and scalar stores, the only loop is over the preallocated `Track[] instrumentTracks`, `AudioEngine.graphInstrumentRecordingBuffer` is a linear scan of `RenderPipeline.instrumentRecordingTracks`, and `publish()`'s only throw is the programming-error `IllegalStateException` no well-formed claim → fill → publish sequence reaches — but no bytecode sentinel proves it: the method is not `@RealTimeSafe`, of this story's code `RealTimeSafeContractTest` reaches only the ring's annotated surface (its outer methods; the nested `Slot` is pinned by `CaptureRingTest`), and the `RealTimeSafeContractTest`-pattern walk over the whole capture path is story 324's proof. It still reads three plain (non-volatile) `RecordingPipeline` fields — `ring`, `flush`, `instrumentTracks` — whose visibility to the audio thread rests on the volatile `AudioEngine.recordingCallback` install happening after they are written, and it still calls into `Transport` per block — `getPositionInBeats()`, `isPunchEnabled()`/`getPunchRegion()` and `isLoopEnabled()` (volatile fields) and `getTempo()`, which is `TempoMap.getTempoChanges().get(0).bpm()`, a fixed view over a plain `ArrayList` — rather than reading a snapshot the transport stamps.
- **The in-RAM mirror is retained (story 324).** `RecordingSession.capturedAudio` still grows without bound on the flush thread (`ensureMirrorCapacity` doubles it), `getCapturedAudio()` copies the whole take, and `RecordingPipeline.completeStop()` / `TrackCapture.finalizeLane` attach it through `AudioClip.setAudioData`; post-stop playback is from RAM, and nothing reloads a clip from its segment list yet (story 329). Mirror and segments both carry the stream width (`format.channels()`) for every track, unrouted rows silent — today's routing shape; story 326 narrows capture to the routed width. *Superseded by story 324:* the in-memory copy is gone — `RecordingSession.capturedAudio`, `getCapturedAudio()`, `getCapturedSampleCount()` and `ensureMirrorCapacity` no longer exist, and no array the capture objects hold grows with the frames recorded (what still grows is one list entry per segment file and, in loop-record, one take per lap). A stopped take's clips get their audio by reading the sealed segments back (`SegmentFile.readFrames`) on the app's storage executor before the take is published (`RecordingPipeline.recordedSegmentPaths()`, `completeStop(Function)`), and a bounded peak mirror (`CapturePeakMirror`) stands in for the copy while the take is recorded. Reloading on project open is still story 329.
- **`ReferenceTrack.source-file` stays absolute (story 329).** `ProjectSerializer` writes `ref.getSourceFilePath()` verbatim (`ProjectSerializer.java:776`) and `ProjectDeserializer` reads it without `ProjectPaths` (`ProjectDeserializer.parseReferenceTrackManager`); only clip references (`source-file` and `<source-segment>`) go through the rule, which story 329 extends to the other asset references inside `project.daw` and to relinked paths.
- **A reference is classified on the platform reading the file.** `ProjectPaths` judges "has a root component", "is absolute" and containment with the reading platform's `Path` semantics. A legacy Windows-absolute `C:\…` read on Linux has no root component, so it resolves under the project directory and is reported missing under that path instead of being kept verbatim — equally missing either way; only the reported text differs (story 329). `..\x.wav`, `C:x.wav` and `\x.wav` are unresolvable on Windows (kept as written, a WARNING, reported missing) and single file names under the project directory on Linux (resolved, and reported missing only because no file is there, with no WARNING); `/x.wav` is root-relative, and so unresolvable, on Windows and absolute on Linux (unowned). A POSIX-absolute reference that reaches memory on Windows — from a DAWproject made on macOS or Linux, or from a project saved on Linux with an asset outside it — is root-relative there and names no file, so Archive Project lists it as missing where the code before the Copilot round looked it up at the root of the current drive; that follows from the owner's decision that a root-relative reference is unresolvable and names no file (unowned). Containment is case-insensitive on Windows, so a walk-back that differs from the directory's name only in case resolves there and escapes on Linux (unowned).
- **Other asset references still resolve a relative path against the working directory (story 329 for the persisted form of SoundFont and reference-track references and the reference-track existence check; the archive flow's SoundFont working-directory lookups are unowned).** Story 323's path rule covers clip references only. A SoundFont assignment goes through `ProjectArchiver`'s default `AssetRef.absolutePath()`, which resolves a relative path against the JVM's working directory, and the Archive Project pre-flight checks its path with `Files.isRegularFile` as it is; a reference track's `source-file` is existence-checked by `ProjectDeserializer.parseReferenceTrackManager` with `Files.exists(Path.of(sourceFile))`. Story 329 extends the rule to the other asset references inside `project.daw` and to relinked paths — its Goals: "Path semantics (design book §3.3): asset references inside `project.daw` normalise **project-relative** (forward-slash) on the next save; absolute paths remain accepted on read for backward compatibility; relinked paths are re-persisted project-relative when the asset lives under the project directory, and stay absolute when it does not (shared sample libraries)." The two archive-flow lookups are not 329's: its Non-Goals list "The archive consolidation flow itself — story 189 (landed); the relink surface links to it."
- **Hand-off to story 329: rehydration must follow the in-memory rule.** Story 329's rehydrator will be the next code to open clip references — its Goals: "every `AudioClip` that carries a source reference but no sample data is queued for rehydration on background virtual threads — decode the source file". Before decoding, it must call `ProjectPaths.isAbsoluteReference` and treat any other reference as missing, never resolving it against the JVM's working directory: after a directory-aware load such a reference is unresolvable, and a DAWproject import keeps its `<File path>` as written.
- **The Archive Project pre-flight does not list a blank clip reference (unowned).** A whitespace-only clip reference — `AudioClip.setSourceSegmentPaths` and the project reader keep one, and on Windows it loads as written because it is not a valid path there — names no file. `ProjectArchiver.collectRefs` collects it like any other, so it gets no payload and is written into an archive as it is, but the pre-flight (`ProjectLifecycleController.collectMissingAssetPaths`) skips it: `ArchiveSummaryDialog` turns every listed path into an `ArchiveAssetDecision`, whose constructor refuses a blank path with an `IllegalArgumentException`, so listing it would make the dialog's Archive button throw. Listing it needs that constructor to accept a whitespace-only path.
- **Recovery scan invocation (story 332).** `SegmentFile` and `TakeManifest.read` define and read the on-disk grammar, but nothing walks `audio/takes` for a `seal-status=streaming` manifest or a `.part` on any open path; an orphaned `.part` is readable, not yet sealed or offered.
- **`IncompleteTakeStore` is still rooted under the OS temp directory** (`DefaultAudioEngineController.java:441` passes `java.io.tmpdir`; `IncompleteTakeStore.java:148` appends `.daw/incomplete-takes/`) and unconnected to the flush service's early seal; story 327 re-roots it at the project and repurposes it as the rescued-take registry. Book §9 item 4 rejects the OS temp directory for rescue stores as well, but the storage-location sentinel does not cover this one: `IncompleteTakeStore` and `DefaultAudioEngineController` name no `core.recording` type, and the store reaches the temp directory through the `java.io.tmpdir` property, not `Files.createTempDirectory`.
- **Bundle export stages in the OS temp directory (unowned).** `BundleExportService` (daw-core `core.export`) stages a bundle's renders and metadata in `Files.createTempDirectory("daw-bundle-")` (`BundleExportService.java:132`), zips them to the bundle's `zipOutput()` and deletes the staging directory best-effort in a `finally` (`:277-280`). That is rendered output, not captured audio, and it is outside the storage-location sentinel, which pins the capture path only (the story's acceptance criterion; Copilot review round 2); whether book §9 item 4's "staging" extends to export staging is not decided here.
- **A manifest's track ids and `take=` name are not path-checked (story 327).** `TakeManifest` checks `trackId` (on `track=`, `segment=` and `gap=` lines) and the `take=` scalar only for blank values, `|` and line breaks; only a segment's `relativePath` is held to the name rule of the Copilot round, so a hand-edited or corrupted manifest can carry a `trackId` or `take=` such as `..`, `/abs` or `C:`. The reader story 327 adds — "a `.part` segment plus an unsealed manifest reconstructs a playable RESCUED take registered for review (book §4.7)" (story 327, Goals) — must therefore build every segment path through `SegmentEntry.resolve(takeDirectory)` and never from `trackId` or `take=`, and, because `resolve` judges lexically, check that the entry is a regular file and follow no links.
- **A processed recorded clip's file lands inside the take's track directory (unowned).** The callers that read or re-point a clip's source are segment-aware now (Resolution above): the archiver copies every segment, clip processing refuses a clip of more than one segment before rendering and collapses a one-segment list, glue and comp propagate the list, AAF export refuses a multi-segment clip and session export warns about it. What remains is where Reverse/Normalize writes: `ClipProcessingService.produceProcessedFile` puts `Reversed-<uuid>.wav`/`Normalized-<uuid>.wav` beside the source, which for a recorded clip is `<take>/<trackId>/` — a file the take's manifest does not list, in a directory story 332's recovery scan will read. A multi-segment take cannot be reversed, normalized or AAF-exported until something consolidates it into one file; no filed story owns that consolidation. `ProjectArchiver.openArchive` deliberately stays on the 1-arg `deserialize` because its own asset relocation keys on the stored `assets/…` form. `AafExportService` refuses a multi-segment clip whether or not media is embedded, although an embedded export also carries the clip's in-RAM audio. Neither service has a production caller in this tree yet; the guarantees are API-level.
- **Track ids do not survive a reopen (unowned; story 334's take-stack persistence will need it).** `ProjectDeserializer` creates `new Track(name, type)` (`ProjectDeserializer.parseTrack`), so a reopened project's in-memory track id no longer equals the `<trackId>` directory name under the take; the string references still resolve.
- **Abort after a successful device open (story 325).** When the device opened and the take then did not start because its `prepare()` threw, its readiness failed or its `beginCapture()` threw, the stream that open started stays open: `abortRecordingTake` does not close it — the pre-existing abort shape. A start whose take directory could not be allocated, or whose pipeline could not be built, ends otherwise: until Copilot review round 5 both failures came before the device open, and since that round's verification the turn that ends such a start (`onTakeDirectoryAllocated`) calls `stopAudioOutputWhenIdle()` unless the transport is PLAYING or RECORDING (`stopAudioOutputUnlessRolling()`). A user's cancel while the take is being prepared (Copilot review round 5) is not such an abort: a Stop over a STOPPED transport, and Record pressed again over a STOPPED or PAUSED transport, call `stopAudioOutputWhenIdle()` as every other Stop does; a Stop over a transport that was not STOPPED goes on as an ordinary Stop, which calls it once the transport has stopped — at once, or at the end of the post-roll it enters; Record pressed again over a PLAYING transport leaves the stream to the playback; the end of a post-roll that cancels it calls `stopAudioOutputWhenIdle()` once it has stopped the transport, as it does whenever it acts — its controller not retired and its transport still in that post-roll; and the cancel `retire()` makes touches no device. `TransportController` leaves a stream closed only through `stopAudioOutputWhenIdle()` (a later Record's `startAudioInputOutput()` also closes the open stream, but only to open a new full-duplex one), which a later Stop calls and which closes it only while `hasGraphInstruments()` is false: while a mixer channel, a return bus or the master channel holds an instrument insert, bypassed or not, the stream is kept open so the instrument can be auditioned while stopped. Closing it after a failed `prepare()`, readiness or `beginCapture()` belongs to story 325's rollback of everything already started, in reverse start order.
- **A MIDI-only Record whose MIDI inputs all fail to open still enters RECORDING (story 325).** With no audio track armed and the audio output started, `TransportController.onRecord` tries each armed MIDI track's input: one that is not found gets a WARNING toast, one whose device cannot be opened or has no transmitter available (`MidiUnavailableException`) an ERROR toast, and neither gets a recorder in `activeMidiRecorders`. When every one fails, `onRecord` still calls `project.getTransport().record()` and lights the REC indicator, so the transport is RECORDING and nothing is captured; `activeMidiRecorders` stays empty, so with no audio take in flight `isRecordingInFlight()` is false, and the in-app doors that replace the open project are not refused in that state. Book §5.2's row "MIDI device missing / open fail" makes a MIDI-only Record whose inputs all fail to open (no track opens) a Record guard failure, which leaves the transport STOPPED; that belongs to story 325's `RecordCoordinator`.
- **The device open stays on the FX thread at Record (story 325; pre-existing since story 316).** `TransportController.onRecord()` calls `AudioEngine.startAudioInputOutput()` — `startAudioOutput()` when every armed track records its graph instrument with no input routing — on the FX thread, before anything of the take is allocated, and the engine opens the driver and starts its stream before it returns, which takes as long as the driver takes: a deviation from javafx-application-design §11 ("The JavaFX Application Thread is sacred. Never block it.") that predates Copilot review round 5 and lies outside its findings. Moving the open off the FX thread belongs with story 325's `RecordCoordinator`. Since round 5, Record and Stop otherwise do no storage I/O on the FX thread and never wait for the capture-flush thread there; what else they do there is the engine's and the transport's own — `beginCapture()` calls `AudioEngine.start()`, which takes the engine's lifecycle lock (and, when an earlier stop left its render pump's teardown deferred, retries that pump's bounded join), and `requestStop()` calls `Transport.stop()`, which waits, spinning, for an in-flight real-time advance to retire — and neither bytecode walk of round 5 follows those calls.
- **A take is published after its Stop, never by it, and the project waits for it.** Since Copilot review round 5 every audio take is published on the FX turn its flush thread's termination posts (`finishWrittenTake`), never by the Stop itself, however fast the seal: the Stop shows `TAKE_FINISHING_MESSAGE`, and `TAKE_STILL_WRITING_MESSAGE` follows, as a WARNING toast and in place of that status text, if the take is still unpublished `TAKE_STILL_WRITING_DELAY` (2 s) after the Stop. Until that turn has run, Record is refused (`RECORD_WHILE_WRITING_MESSAGE`) — as it is while the files of a cancelled or failed start are being removed — and so are the in-app doors below, even for the FX turn or two that a fast seal takes. The Record Audio undo entry is pushed, and the project marked dirty, when the clips are published, not when Stop was pressed: the entry lands on top of any edit made while the take was being written, and `UndoManager.execute` clears the redo stack, as it does for every action. The take belongs to the project it was recorded in, so no in-app door replaces that project while the take is being written (Copilot review round 2, above): while `TransportController.isTakeBeingWritten()` — a take whose publishing turn has not run yet, or a cancelled or failed start whose files are still being removed — `ProjectLifecycleController` refuses New, Open, Import, Restore from Archive, a Project Hub or Welcome open and a snapshot restore in `confirmProjectMayClose()`, the gate those doors pass — first, before it asks `confirmDiscardUnsavedChanges()`, the unsaved-changes prompt, which asks only when the project is dirty, and a take being written has not marked it dirty: it is not in the project yet, and only the FX turn that publishes its clips marks the project dirty (Copilot review round 4) — refuses Recover and a migration roll-back at their start, and refuses again the loads that the recovery and archive-restore flows make after work off the FX thread; the user sees `PROJECT_CHANGE_WHILE_WRITING_MESSAGE` as a WARNING toast, and no dialog. A load refused after that work has written or deleted something — the archive extracted, the recovered changes written to `project.daw`, the journal discarded — or after a replay that failed shows instead one WARNING (`ProjectLifecycleController.lateLoadRefusalMessage`) that says what the work did and that the project can be opened once the take has been written. `MainController` answers the check from the transport controller that is current when it is asked. As a fallback for a replacement that bypasses the guard, `MainController.createTransportController()` retires the controller it replaces (`TransportController.retire()`): when a retired controller's take has been written, it does not complete the take and publishes nothing — no clip on the replaced project's tracks, no undo entry, no SUCCESS toast — and instead logs and shows a WARNING naming the project the take was recorded in and the take's directory (`TransportController.takeOfAReplacedProjectMessage`, which claims no order between the replacement and the end of the writing) and replaces a status bar still reading `TAKE_FINISHING_MESSAGE` or `TAKE_STILL_WRITING_MESSAGE` with `TAKE_OF_A_REPLACED_PROJECT_STATUS`; no project references such a take, and the book §4.7 recovery scan, which looks for `.part` segments and unsealed manifests, would not offer one that sealed normally. A take still being prepared when its controller is retired is cancelled, and its files are removed as for any cancel; that removal is owed by the retired controller, whose `isTakeBeingWritten()` the doors no longer ask. The same doors are refused, at the same points, while a recording is in flight (Copilot review round 3, above): while `TransportController.isRecordingInFlight()` — an audio take being prepared (Copilot review round 5) or whose pipeline is active, or a live MIDI recorder — the user sees `PROJECT_CHANGE_WHILE_RECORDING_MESSAGE`, which asks them to stop the recording first, or, for a late load, `lateLoadRefusalWhileRecordingMessage`, and the recording is left as it is.
- **Quitting the application is not guarded while a take is being prepared, recorded or written (story 333).** The primary stage has no close-request handler, and quitting replaces no transport controller, so nothing is retired or cancelled and no Stop runs; the capture-flush thread and the storage executor's virtual threads are daemons, so quitting can end their work part-way — while a take is being prepared (PREPARING), before all its files exist; while it records or is being written, before the seal, which leaves `.part` segments and a `seal-status=streaming` manifest, a take referenced by no project, to the book §4.7 recovery scan (story 332); and while the files of a cancelled or failed start are being removed (FINALIZING), before they are gone. `PROJECT_CHANGE_WHILE_WRITING_MESSAGE` asks the user to keep the application open until the take has been written. These exit cases are handed to story 333: its GUARD step carries the take rule — a take being prepared is a recording in flight to that rule's `isRecordingInFlight()` check, and a cancelled or failed start still removing its files is a take being written to its `isTakeBeingWritten()` check — and its Goals — Tests carry the recording and being-written cases.
- **Record over a rolling transport (stories 325, 328).** Record is accepted while the transport is PLAYING (punch-on-the-fly), and Copilot review round 5's readiness gate puts time between reading the take's anchor and beginning capture: `prepare()` reads the anchor on the FX turn after the take directory has been allocated, and `beginCapture()` runs on the readiness turn, once the capture thread has created the take's files. `beginCapture()` puts the transport back at the position `prepare()` read only when the transport is STOPPED or PAUSED; over a rolling transport it seeks nothing, so playback goes on without a jump. A take anchored at the transport's position and started over a rolling transport therefore keeps the anchor `prepare()` read, while capture begins where the transport has rolled to by `beginCapture()`: its clips are placed at, and its manifest anchored to, a position about the preparation time (from `prepare()` to the readiness turn) earlier than the transport's when the first block was captured, and Stop, with return-to-start on, returns the playhead to where `Transport.record()` anchored it rather than to the take's start. The synchronous start before round 5 had the same kind of difference, sized mostly by the storage I/O it ran on the FX thread between reading the anchor and `Transport.record()` (every armed track's first segment created, the initial manifest written, forced and renamed). Record is not refused over a rolling transport, which would remove punch-on-the-fly; story 328's transport-clocked capture-start gate owns the fix.
- **A post-roll tail that ends after capture began stops the transport under the take (story 325; pre-existing).** Record is accepted inside a post-roll's tail, where the transport is still PLAYING, and neither Record nor the start of capture stops the timer that ends the tail or takes the transport out of its post-roll (`Transport.record()` leaves `isInPostRoll()` set), so when the tail ends after capture began, `finishPostRoll()` — its controller not retired, and its transport still in that post-roll — finds no take being prepared, stops the transport under the recording take (`Transport.finishPostRoll()`), calls `stopAudioOutputWhenIdle()`, hides the REC indicator and shows "Stopped", while the take's pipeline stays active until a Stop requests its seal — as the code before Copilot review round 5 did; that round changes only a tail that ends while the take is still being prepared, which cancels it, and, in a later fix round, a timer whose tail had already ended another way, or whose controller was retired, which then does nothing when it fires (`retire()` also stops and drops it); story 325's `RecordCoordinator`, to be the only mutator of record state, owns the rest.
- **One block can be in flight at Stop (story 325).** Removing the recording callback does not wait for the audio thread: a block whose callback was already running when `requestStop()` removed it may be published after the flush thread's final sweep. It stays in the ring and is not part of the take — the loss is bounded to the single block in flight, the block the code before this story also dropped; a drained-callback handshake belongs to story 325's stop fence. *Superseded by story 324:* story 324 built the fence, not story 325 (whose Non-Goals leave the fence internals to story 324), and it is a producer gate on `CaptureRing`, not a handshake. `RecordingPipeline.requestStop()` closes the gate (`CaptureRing.closeProducer()`) before it removes the callback; a callback that was inside when the gate closed does not publish, so the block that straddles the stop is dropped whole; and the flush thread waits, for at most 200 ms (`CaptureFlushService.PRODUCER_QUIESCENCE_BOUND`), for a callback in flight to leave the gate before its final sweep. A block published behind the sweep — through the pipeline, possible only when that wait timed out — is recorded in the manifest as a gap, with a warning.
- **A clip of a take whose seal failed references only the sealed segments (stories 325, 332).** When a lane's segment could not be sealed — in the seal a Stop requested, or in an early seal — the FX turn that publishes a plain take still publishes that track's clip if it recorded audio (a later loop-record lap's clip goes only into the track's take group, whose active take stays the first lap and which `project.daw` does not hold yet — story 334), and the clip lists only sealed segments in its segment references (`AudioClip.setSourceSegmentPaths`): no clip references the `.part`, and the audio of that segment reaches the clip only through the clip's in-RAM audio data; a lane none of whose segments sealed gets a clip with no source file (`getSourceFilePath()` is `null`). Since publishing marks the project dirty (Copilot review round 4), the Save that the unsaved-changes prompt offers writes such a clip into `project.daw` without the segment that failed — with no source at all when none sealed — so a reopened project's clip references no file that holds that audio, which survives only in the `.part` left for recovery (nothing reloads a clip's audio on open yet — story 329). Whether such a lane publishes a clip, and whether it references the `.part`, belongs to story 325's FINALIZING row (`RecordCoordinator`); recovering the `.part` is the recovery-scan hand-off above (story 332).
- **A failed start does not restore the monitoring mode (pre-existing).** `prepare()` applies the pipeline's monitoring mode to every armed track still at `InputMonitoringMode.OFF`; the rollback of a failed `prepare()` or `beginCapture()`, and `cancelStart()`, clear the recording flags but leave that mode in place, as the code before this story did. (The app builds its pipeline with `InputMonitoringMode.OFF`, so no track's mode is changed there.)
- **Warnings degrade to logging (story 339).** Ring overflow, block truncation, low disk, a segment that could not be sealed, an unwritable manifest and a flush-loop failure after the take was sealed reach the `Consumer<String>` from `RecordingPipeline.setWarningSink` (a slow finalisation no longer does: since Copilot review round 5 no production code joins the flush thread, so no join runs out to warn about); the app injects none yet, so they land in `java.util.logging` WARNING. The warnings of an early seal — disk exhaustion, a write failure, a flush-loop failure that sealed the take — land there too, but an early seal is no longer surfaced by logging alone: the app stops the take itself unless a Stop got there first, and the FX turn that publishes the take shows one ERROR toast and status text naming the cause and what was kept or left, segment files that could not be finished included (Copilot review round 3; the auto-Stop and the publishing turn of a transport controller retired by a project change do neither). Nor is a segment that could not be sealed in the seal a Stop requested surfaced by logging alone any more: the FX turn that publishes the take shows one ERROR toast and status text for it (Copilot review round 4). A sink that throws a `RuntimeException` is logged and ignored; it can never end a take. `DiskHeadroomWatch.forDirectory` watches the take directory's file store with the default thresholds.
- **Unsupported capture bit depth.** A project format whose bit depth is not 16, 24 or 32 fails at record start (`IllegalArgumentException` from `SegmentWriter.open`, in the flush thread's initialisation of the take, which fails the take's readiness; surfaced by `abortRecordingTake`); 8-bit capture is not a take format.
- **A reused pipeline's failed first manifest write removes the earlier take's manifest (story 350).** `CaptureFlushService.writeManifestOnce` sets `manifestTouched` before it calls `TakeManifest.write`, and the rollback's `deleteManifestFiles()` deletes `take.manifest` and `take.manifest.tmp` whenever it is set; so when a take's first manifest write — its initialisation's single attempt — fails before its rename lands (the staging file cannot be opened, written, forced or closed, or the move fails), the rollback deletes whatever `take.manifest` the take directory holds, which is not this take's. `RecordingPipeline` records every take into the directory it was constructed with and arms the same tracks each time, so a pipeline started again over a take that sealed no segment — stopped, or sealed early, before any frame was written — reaches that write in the earlier take's directory, and deletes the earlier take's manifest if the write fails (if it lands, it replaces it); a restart over a take that sealed a segment is refused cleanly before then (Smaller facts, below). One cause of a failed move spares that manifest: on Windows, another process that holds `take.manifest` open without delete sharing fails the move and, while the hold lasts, the rollback's delete of `take.manifest` too (logged at WARNING), and the staging-file delete after it, in the same `try`, is skipped. The app is unaffected: `TransportController` builds a new pipeline over a freshly allocated take directory for every take and prepares it once. Story 350 makes the rollback delete only the manifest files the take wrote — `take.manifest` once one of its writes has landed, the staging file only if its write opened it — and makes a take directory hold one take, recommending that a start refuse a directory that already holds another take's manifest or segments.
- **Smaller facts worth knowing.** A pipeline restarted over the take directory of a take that recorded audio cannot start — `segment-000.wav` exists and `SegmentWriter.open` never overwrites, so the restart's readiness fails — and fails cleanly, leaving that take's segments and manifest as they were (the app constructs a fresh pipeline over a fresh take directory for every take); a restart of the same pipeline right after a `cancelStart()` or a rolled-back `beginCapture()` is refused by `prepare()` until that take's flush thread has terminated (Resolution above); `getSession(track)` after a stop returns the last lane's inactive session rather than `null`; lap-take clip durations use the tempo snapshotted at `prepare()` (`TrackCapture.tempoBpm`) while the normal-path clip built in `completeStop()` uses `transport.getTempo()` as read when the stop began (`RecordingPipeline.clipTempoBpm`, read by `requestStop()` before the transport stop, so that `completeStop()`, which runs once the flush thread has terminated, builds the clips of the take as it was stopped; Copilot review rounds 2 and 5); `awaitFlushed` also fences on the overflow bookkeeping observed at call time; a lane whose seal throws turns the manifest `aborted`/`write-failure` even on a Stop, and leaves its `.part` when the segment's own seal failed — and the FX turn that publishes the take, after its Stop, then reports it as an ERROR (Copilot review rounds 4 and 5); an `Error` out of one lane's seal does not cost the lanes after it theirs — every lane gets its seal attempt, the manifest is written `aborted`/`write-failure`, and the first such `Error` is rethrown after that, so on a Stop the flush loop still logs it SEVERE and reports it through the sink; and test pipelines that are never stopped (e.g. `PerTrackMonitoringTest`) leave a parked `capture-flush` daemon for the JVM's life (pre-existing test shape, harmless).
