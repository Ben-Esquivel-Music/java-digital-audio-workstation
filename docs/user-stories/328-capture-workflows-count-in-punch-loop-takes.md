# Capture Workflows: Count-In, Punch, Loop Takes, Comping

## Motivation

Every advertised capture workflow ships without capture behind it (book §1.8):

- **Count-in is a no-op for audio and destroys MIDI.** The mode is user-visible in the metronome popup and Settings (`MetronomeController.java:42,140`, `SettingsDialog.java:1267`) and passed to the pipeline (`TransportController.java:426,445`) — but `generateCountInAudio`, the only audio use of the mode, has zero production callers (`RecordingPipeline.java:516`), and `start()` calls `transport.record()` immediately with no click and no delay (`:162-247`). Worse, the MIDI count-in window is anchored to the **first MIDI message received** (`MidiRecorder.java:342-346`), then notes inside the window are discarded (`:366-372`) — a performer who waits through the silent "count-in" and then plays loses their first bars.
- **Punch-in/out cannot be created.** `SET_PUNCH_IN`/`SET_PUNCH_OUT`/`TOGGLE_PUNCH` are declared with default shortcuts and listed in the Key Bindings UI (`DawAction.java:32-36`), but `buildActionHandlers` registers none of them (`KeyboardShortcutController.java:185` ff.). The ruler *draws* the punch region and its handles (`TimelineRuler.java:403,422`) but its mouse handlers implement loop-region drag only (`:581-599`); the only production caller of `Transport.setPunchRegion` is the project deserializer (`ProjectDeserializer.java:385`). So the complete, tested gating engine with its cosine crossfades (`RecordingPipeline.java:724-755`) and `Transport.isInputCaptureGated` (`Transport.java:460`, zero production consumers) are unreachable. And what the ruler does draw is wrong: its frame→beat conversion uses a 44.1 kHz default (`TimelineRuler.java:105`; `setSampleRate` at `:253` has zero production callers), so against the 96 kHz project default a deserialized punch region draws ~2.18× too far right.
- **Loop-record and comping do not connect.** `setLoopRecord` has zero production callers (`RecordingPipeline.java:868`) — no toggle, no shortcut — so recording over a loop concatenates into one session instead of stacking takes. The COMP tool's press handler early-returns unless the track's comping is active (`ClipInteractionController.java:1083-1087`), and nothing ever activates it. `Track` carries **two** take models side by side (`Track.java:98-99`); the pipeline populates only `takeGroups` (`RecordingPipeline.java:294`) and no UI renders them.
- **The click cannot reach a cue bus.** Settings offers "Send click to" a cue bus (`MetronomeController.java:248`), but the render loop writes side-output/cue click buffers via `backend.writeToChannel(...)` on the SDK backend slot, which is null on the default legacy path (`RenderPipeline.java:670`), and the interface's default implementation drops the samples (`AudioBackend.java:150`) — a routed click can never sound.

For a studio engineer, this is the feature set the UI has promised since stories 131/132/249: they set a count-in and lose the first bars of a MIDI take; they reach for punch and the shortcuts do nothing; they loop-record a solo and get one long concatenated smear instead of takes to comp.

## Resolution

Every workflow is a gate on the one capture pipeline (book §2.10): the count-in holds the capture start gate, punch and loop-wrap gating are the flush-thread mechanisms stories 323/324 landed, and `SingleCapturePipelineScanTest` (`theWorkflowGatesDoNotNameACaptureBufferSessionOrWriter`) pins that none of the workflow code names a capture buffer, session or writer. Each paragraph below names the code as it is on disk.

### Count-in

`CountInSchedule` (daw-core `audio`) is a count-in on the engine's frame clock. `RecordCoordinator.countInScheduleFor` builds it with `CountInSchedule.forMode(mode, timeSignatureNumerator, tempo, engineFormat.sampleRate(), engineFormat.bufferSize(), masterLatencyFrames)` — the mixer's `getDelayCompensation().getMasterLatencySamples()` — and returns empty for a rolling transport, which records at once with no COUNT_IN phase. The frame math: `countInFrames = round(totalBeats × sampleRate × 60 / tempoBpm)`; the leading pad is the block alignment plus whole blocks until the pad is at least the master latency, so `totalFrames = pad + countInFrames` ends on a block boundary and click 1 — emitted `masterLatencyFrames` early, at `pad − masterLatencyFrames ≥ 0` — is never clamped; clicks are placed backwards from the end frame, the first beat of each bar accented. `AudioEngine.scheduleCountIn` refuses (`IllegalStateException`) a rolling transport, a second pending schedule, or a schedule whose block size or sample rate differ from the opened stream format; `cancelCountIn` and `pendingCountIn` are the caller-thread API, and the engine's stop and stream close cancel a pending schedule rather than strand it.

On the render thread `RenderPipeline.renderBlock` takes the pending schedule: while it is pending and the transport is not rolling, the playhead holds at the record position, `mixCountInClicks` sums `Metronome.generateClick(accent)` straight into the main mix at `clickFrame − masterLatency` — bypassing `MetronomeSideOutputRouter`, `Metronome.isClickEnabled()` and therefore `ClickOutput.mainMixEnabled()`: a count-in sounds whenever one is scheduled, metronome on or off — and the recording callback runs with its `CaptureCallback.StartGate` closed. Bar 1's downbeat is the count-in's too: `CountInSchedule.hasPendingDownbeat`/`downbeatFrame` (= `totalFrames`)/`consumeDownbeat` let `mixCountInClicks` emit one click at `totalFrames − masterLatency` from the count-in's last blocks — this one only when `metronome.isClickEnabled()`, because it stands in for the running click's first beat, which the running walk (starting at the record position plus the master latency) would otherwise never sound; it is accented by the running click's own rule, the project bar grid at the record position (`RenderPipeline.isProjectBarDownbeat(positionInBeats, timeSignatureNumerator)`: the floored beat modulo the bar length, a non-positive numerator read as 4/4), so a record position that is not bar-aligned gets an unaccented hand-off click, the same whether or not master latency made the click this path's; with no master latency the emission frame is the end frame itself, past every count-in block, so the running walk sounds it and there is never a double click. The schedule's cursor advances last of all in `renderBlock`; the block in which it reaches `totalFrames` ends with `CountInSchedule.fire()`, which stamps `fireNanos` (`System.nanoTime()`, volatile) before `fired` and runs the record start that `RecordingPipeline.beginCapture(Runnable, CountInSchedule)` set: `transport.record()` and the gate's opening (`positionSeek`, `seekPending`, `beat`, `active`). The next block is the first rendered — and captured — from the record position; nothing of the count-in is in the take. A cancel from the caller thread stores `CANCELLED` and re-reads `FIRED`; the verdict can be stale by one render-thread instruction, so both verdicts run the same cleanup and the verdict decides only what is announced. The fire path is render-thread code and is pinned as such: `Transport.record` and the schedule's render methods (`isPending`, `cursor`, `hasPendingClick`, `nextClickFrame`, `nextClickAccent`, `consumeClick`, `hasPendingDownbeat`, `downbeatFrame`, `consumeDownbeat`, `advance`, `fire`) carry `@RealTimeSafe`, and `RealTimeSafeContractTest`'s count-in fire walk group follows them plus the `lambda$beginCapture$N` that invokes `Transport#record` (found by content), tolerating exactly `System#nanoTime`, `Runnable#run`, `Consumer#accept` and `AtomicLong#get` (`COUNT_IN_FIRE_EXTERNAL_CALL_ALLOWLIST`, exact in both directions).

`RecordCoordinator` (FX thread) enters COUNT_IN through `observeCountIn`: the status "Count-in — N bars", a `FxDispatcher.ContinuousChannel<Transport.ChangeKind>` opened on the dispatcher (`countInFireChannel`, drained into `onCountInFired` by the dispatcher's pulse), a `Transport.ChangeKind.STATE` listener (`countInObserver`) that runs ON THE RENDER THREAD — the render thread's `record()` reaches it through the RT-safe `ChangeNotifier` — and does nothing but one wait-free `channel.publish(kind)` (`AtomicReference.lazySet` of an enum constant: no `Platform.runLater`, no allocation, no logging; `postFx` only when no dispatcher exists, the pure-unit case) and, for an audio take, the pipeline's `beginCapture(RecordCoordinator::refuseActivationDuringCountIn, schedule)` on the readiness turn; a MIDI-only take goes through `beginMidiOnlyCountIn` (`schedule.setRecordStart(transport::record)`, then `audioEngine.scheduleCountIn`). `TransportVM` takes the same STATE the same way: fired off the FX thread it is published into the VM's own `stateChannel` (`FxDispatcher.ContinuousChannel<ChangeKind>`, whose drain re-reads `transport.getState()`; closed in `dispose()`) instead of `dispatcher.onFx`, which stays the FX-thread branch. `TransportVM.onCoreChange` dispatches on the kind through an identity if-chain, STATE and POSITION first — deliberately not an enum `switch`, whose synthetic `TransportVM$1.$SwitchMap$…` table has a class initialiser (an `int[]` allocation, a `values()` clone and the class-initialisation lock) that runs on whichever thread reaches the switch first: after a fresh JVM with Record pressed before any play or seek, that is the render thread at the fire. `CountInRecordStartListenerBytecodeSentinelTest` walks the bytecode of both listener bodies the render thread executes at the fire — `TransportVM.onCoreChange` and the coordinator's `countInObserver` lambda, rooted by its read of the `countInFireChannel` field — over the shared `RtPathBytecodeWalk` helper (also `ChannelVmRtPathBytecodeSentinelTest`'s): no allocation, no monitor, no toolkit entry, no switch map, no lambda, and the walk must have seen the channel publishes each body is built around. `onCountInFired` announces the take (COUNT_IN → RECORDING) once the schedule reads fired and the transport is RECORDING, and `endCountInObservation` removes the listener and closes the channel. While counting in, `TransportController.start`, `togglePlayPause` and `playWithPreRoll` return without touching the engine (`recordCoordinator.isCountingIn()`): a transport that rolled would park the schedule for good; seeks are refused too — `TransportController.refuseSeekWhileCountingIn()` guards `skipBack`/`skipForward`, and `MainController.seekToPosition` (the ruler click and the clip-gesture seeks) asks it first, with the status `SEEK_REFUSED_DURING_COUNT_IN` ("Cannot move the playhead during the count-in — stop first"); the rescued-take notification's "Review" action (`RecordCoordinator.rescuedTakeReview`, story 327) is a user seek too and asks the same gate before moving the transport to the rescued take's anchor, refused with the same status. Stop (`stopAudioTake`), Record pressed again (`toggleRecord` → `stop()`), a device loss (`onDeviceLost`) and an abort cancel through `endCountIn` → `AudioEngine.cancelCountIn(schedule)` and reconcile the verdict: `CANCELLED` discards the MIDI recorders (`discardMidiRecording` — a kept pickup note is removed from the clip again, no undo entry) and, for an audio take, stops the active pipeline through the ordinary path with the status "Count-in cancelled — no take was started"; `FIRED` means the render thread won — the take is announced as RECORDING and stopped as an ordinary recording, notes and audio kept, never reported as an abort. A MIDI-only count-in's end has a second look on both verdicts (`lookAgainAtTheEndedCountIn`): a render thread descheduled between its cancel check and its `fired` store can run the record start after the cancel reported a win, and one descheduled between its `fired` store and the transport's RECORDING store makes the FIRED verdict's `requestStop()` a no-op on a still-STOPPED transport. So `stopAudioTake` schedules `stopIfTheEndedCountInFiredAfterAll(schedule)` twice — once on the next FX turn (`postFx`) and once a block period of the schedule's stream later (`blockPeriodOf(schedule)` = `blockSize / sampleRate`, through `stillWritingDelay`, the FX timer the coordinator already uses) — which stops a transport found RECORDING with the coordinator IDLE, no pipeline, no schedule and no active recorders, and does nothing when the schedule never fired, a new take has started since, or the coordinator was retired.

MIDI: `startMidiRecording` creates each `MidiRecorder` with `setCountInDurationUs(schedule.countInDurationMicros())` and `setCountInDownbeat(schedule)` (`CountInSchedule implements CountInDownbeat`), and `anchorMidiRecording` sets the origin before the schedule is installed, so the window is anchored at the count-in's START — never to the first received message (the device-timestamp origin is placed at the receipt time of the first message and never moves the window). A note-on inside the predicted window is dropped entirely, so its note-off finds no active note; within `PICKUP_TOLERANCE_US = 20_000` of the window's end it is kept at column 0. From the first message after the fire, `countInWindowEndUs` measures bar 1 from `fireNanos` instead of the prediction, so no note played after the real downbeat is ever a count-in note. `Transport.isInputCaptureGated` was deliberately left without a consumer: pre/post-roll is story 134's surface. `Metronome.generateCountIn` has no production caller; `RecordingPipeline.generateCountInAudio` no longer exists.

### Punch

The three declared actions are real: `DawAction.SET_PUNCH_IN` (I), `SET_PUNCH_OUT` (O) and `TOGGLE_PUNCH` (Shift+P) are registered in `KeyboardShortcutController.buildActionHandlers` against `Host.onSetPunchIn/onSetPunchOut/onTogglePunch` (default no-ops); `MainController` routes them as `SetPunchInCommand`/`SetPunchOutCommand`/`TogglePunchCommand` to `TransportController.setPunchIn/setPunchOut/togglePunch`, which report on the status line and delegate to `CoreTransportIntentHandler`. The rules there: the point just set wins and the other point moves to keep at least `minPunchFrames()` = `2 × CaptureFlushService.PUNCH_CROSSFADE_SECONDS` (0.005 s each — both cosine ramps must fit inside the region) at the handler's PROJECT rate (960 frames at 96 kHz); points are never swapped; a punch-out closer than the minimum to frame 0 clamps the in-point to 0 and the out-point to the minimum length; a set with no region installs an ENABLED region; `togglePunch` with no region neither mutates nor announces (the controller's status line explains how to create one). `installPunch` writes `Transport.setPunchRegion`, which fires `Transport.ChangeKind.PUNCH` (feeding `TransportVM.punchRegionProperty`) and publishes `TransportEvent.PunchChanged(enabled, startFrames, endFrames, timestamp)` (daw-sdk).

`TimelineRuler`: loop gestures own the upper half of the ruler, punch gestures the lower half — the halves the handles are drawn in. `DragMode` gained `PUNCH_IN_HANDLE`, `PUNCH_OUT_HANDLE` and `DEFINING_PUNCH`; handles hit-test within `PUNCH_HANDLE_HIT_ZONE` (8 px), the half the pointer is in deciding which family is tested first; Shift-drag in the lower half defines an ENABLED region once the drag spans `CoreTransportIntentHandler.minPunchFrames(sampleRate)`, and a handle drag that would cross the other handle is refused. Ruler gestures write `transport.setPunchRegion` directly, as the loop gestures write `setLoopRegion`: they fire `ChangeKind.PUNCH` but no `PunchChanged` bus event — the same asymmetry the loop gestures have. `TimelineRuler.setSampleRate(project.getFormat().sampleRate())` is wired at creation (`ArrangementCanvasFactory`) and on project rebind (`MainController`), so punch frames draw at the rate they are in. Recording across the region is the unchanged flush-thread gate, pinned by the existing `RecordingPipelineTest.shouldApplySampleAccuratePunchBoundariesWithinOneBlock`, `shouldApplyCosineCrossfadeAtPunchBoundaries` and `shouldAutoPunchAcrossMultiplePassesWhileArmed`.

### Loop-record and takes

The toggle is `Transport.setLoopRecordEnabled`/`isLoopRecordEnabled`: `DawAction.TOGGLE_LOOP_RECORD` (Shift+L) → `Host.onToggleLoopRecord` → `ToggleLoopRecordCommand` → `TransportController.toggleLoopRecord` → `CoreTransportIntentHandler.toggleLoopRecord`, which flips the flag and publishes `TransportEvent.LoopRecordChanged`; the FXML `loopRecordButton` ("Loop Rec") is bound by `TransportControlBinder.bindLoopRecord`, so its `:active` pseudo-class follows `TransportVM.loopRecordProperty` and a click raises the command. `TransportController` refuses the toggle while a take is being prepared, counting in, recording or still being written ("Loop Record: cannot change while a take is in progress — stop first"), because `RecordCoordinator` hands `transport.isLoopRecordEnabled()` to `RecordingPipeline.setLoopRecord` once, before `prepare`. For the same reason `TransportController.toggleLoop` refuses while loop-record is enabled and a take is in flight (`recordCoordinator.isRecordingInFlight()`), with the status `LOOP_REFUSED_DURING_LOOP_RECORD_TAKE` ("Loop: cannot change while a loop-record take is in progress — stop first"): the take took "loop playback on" into its configuration once, and turning the loop off mid-take would stop the wraps that seal its lanes; a take that is not loop-recording leaves the loop toggle free. The flag alone does not make a loop take: when the pipeline builds its capture config, `loopRecordTake = loopRecord && transport.isLoopEnabled()` — loop-record with loop playback disabled is a plain take (`RecordingPipelineLoopRecordTest.loopRecordWithLoopPlaybackDisabledIsAPlainTake`).

Takes are one model. `TakeGroup`, `Take`, `FlattenTakesAction`, `Track.takeGroups`, `RecordingPipeline.getTakeGroups`, `CompManager` and `TakeComping.getCompRegionsForTake` are removed. The flush thread stacks each lap into `TrackCapture.lapClips()` (a wrap seals the lane and advances `completeLaps`; stories 323/324's rotation), and each lap is placed where its audio belongs on the timeline: lane 0 starts at the take's `compensatedStartBeat` (the record position), and at a wrap `CaptureFlushService.applyBlock` passes the wrapping block's header beat into `finalizeLoopLap(double)` → `TrackCapture.finalizeLane(buildTake, openNext, nextLaneHeaderBeat)`, which stamps the next lane's `laneStartBeat` = that header beat (the loop start plus the wrap's overshoot) minus `compensationBeats()`, floored at 0. `RecordingPipeline.completeStop` ingests each lap as a `TakeLane` named "Take N" (N continuing from the track's existing lane count) in `track.getTakeComping()`, keeping a partial final lap, after snapshotting the track's comp regions into `compSelectionBeforeIngestion` (`getCompSelectionBeforeIngestion()`) and then clearing every lane's solo (`buildClips`): a lane audition (Alt-click solo) is transient by design and ends with the new take, because a solo makes `compile()` play that lane whole and slice no region, so the take would otherwise publish no clip, no undo entry and no dirty project; the take's undo restores the selection, not the audition. The default selection is one `CompRegion` over the last COMPLETE lap (`completeLaps − 1`), or the lone partial lane when no wrap sealed one; `CompileCompAction(track).execute()` then compiles the comp onto the main lane, `getRecordedTakeLanes()` reports the lanes per track, and only the compiled clips that are slices of THIS take's laps (`isSliceOfAnyOf`, by segment paths) count as the take's recorded clips — a recompile also re-slices an earlier take's surviving regions. `TakeComping.compile()` produces file-referencing slices (`slice`: the take's segment paths, source offset, gain and audio array — nothing copied), and `CompileCompAction` removes exactly the clips the comp currently occupies (`getCompClips`/`setCompClips`) before adding the new ones. `RecordCoordinator`'s "Record Audio" undo entry is `RecordedTakeAction(pipeline)` (daw-core `recording`): undo removes a plain take's clip, or a loop take's lanes (`removeTakeLane`), restores the pre-ingestion selection and recompiles, so an earlier take's comp plays again as it did before Record was pressed; redo re-adds the lanes, reinstates the selection the take left and recompiles; its first `execute()` finds the take as the pipeline applied it and changes nothing. Lane persistence is story 334.

### Comping

`ArrangementCanvas` grows a track's slot by `laneCount × TAKE_LANE_HEIGHT` (40 px) while its comping is active (`takeLanesHeight`), resolves a pointer to a lane with `takeLaneIndexAtY` (−1 for the main lane) and draws the lanes under the main lane in `drawTakeLanes`. `ClipInteractionController.handleCompPress` (COMP tool, comping active): a press on a take lane begins a swipe in `CompToolHandler(track, undoManager)`, and the release ends it with `SetCompRegionAction`, which sets the region and recompiles at once, and whose undo restores the previous selection first and then recompiles; Alt-click on a lane solos it (`altClickLane`) and a click on the main lane clears the solo (`clickMainLane`) — both recompile as auditions through `CompileCompAction.execute()` directly, not through the undo manager. The main lane is never restored from a snapshot of clips: `CompileCompAction.execute()` and `undo()` both recompile from the LIVE comping state, removing whatever `comping.getCompClips()` holds now, so an audition between a swipe (or a take) and its undo cannot leave its clips orphaned or doubled. The comped clips on the main lane are what plays.

## Known limitations

- `Transport.isInputCaptureGated` still has no consumer; pre/post-roll gating is story 134's.
- `ArrangementCanvas.setSessionRateHz` and `setSamplesPerBeat` have no production caller.
- `Metronome.generateCountIn` is an orphan (no production caller).
- MIDI without a downbeat: bar 1 is measured from the predicted window end, so every note is early by the block phase, bounded by `blockSize / sampleRate + PICKUP_TOLERANCE_US` (`MidiRecorder.setCountInDurationUs` Javadoc); with the downbeat the phase cancels from the first message after the fire.
- A cancelled audio count-in stops the active pipeline through the ordinary path and publishes a take of no clips; the take directory and its sealed manifest stay on disk — nothing on that path removes them (the empty-directory removal belongs to `cancelPendingStart`, for a take still PREPARING).
- Play and seeks are refused, not queued, during a count-in (`TransportController.start`, `togglePlayPause`, `playWithPreRoll`, `refuseSeekWhileCountingIn` in `skipBack`/`skipForward`, `MainController.seekToPosition` and `RecordCoordinator.rescuedTakeReview`). `CoreTransportIntentHandler.skipBack/skipForward` themselves carry no count-in gate; the gate sits in the controller and the `MainController` seam in front of them.
- The count-in click bypasses `ClickOutput.mainMixEnabled()` and `Metronome.isClickEnabled()`, plays one click per beat (no subdivision clicks), and feeds no side output or cue bus (stories 135/136). Bar 1's downbeat, emitted from inside the count-in, is the one click that follows `Metronome.isClickEnabled()`: metronome off, the count-in ends without a downbeat click.
- The MIDI-only count-in end's second looks (`lookAgainAtTheEndedCountIn` → `stopIfTheEndedCountInFiredAfterAll`, on both verdicts) run on the next FX turn and one block period of the schedule's stream later; a render thread kept off-CPU for longer than a block period past both looks leaves the transport rolling in RECORDING with the coordinator IDLE and no recorder listening until the next Stop press, which recovers it (`wasRolling`, `requestStop`).
- `TransportController.toggleLoop` is the only gated loop edit: the ruler's loop-bound drags (`TimelineRuler` → `transport.setLoopRegion`) carry no count-in or loop-record-take gate, so a loop region can still be moved under a loop-record take in flight. The refusal keys on the live `Transport.isLoopRecordEnabled()` flag rather than on the in-flight take's frozen configuration: a take started with Loop Rec on but loop playback off is a plain take, yet the Loop button is still refused until it stops (harmless over-refusal).
- Alt-click lane auditions end with the next take on that track (`RecordingPipeline.buildClips` clears every lane's solo); undo of that take restores the earlier selection, never the audition.
- `TakeComping.compile()` slices lanes at the comp-region bounds with no boundary crossfade: adjacent slices from different lanes abut at the sample; the cosine crossfades belong to the punch gate only.
- A chord held from the count-in into bar 1 is dropped: a note-on inside the window is dropped entirely and its note-off ignored; nothing re-triggers it at bar 1.
- No visible beat countdown: the status line is the static "Count-in — N bars".
- Ruler-made punch and loop edits fire `ChangeKind` only and publish no bus event.
- Master latency that grows after the schedule was built (an insert added during the count-in) delays a click to its block's first frame — guarded, not dropped.
- A schedule is refused when the engine's opened format differs from it in block size or rate; a backend that hands out blocks of another size than it was opened with is not detected (`AudioEngine.scheduleCountIn` Javadoc).
- Lane solo/mute has no gesture beyond Alt-click (solo) and the main-lane click (clear).
- Lanes and comp selections are not persisted (story 334).
- `TransportEvent.PunchChanged` and `LoopRecordChanged` have no consumer in main source beyond their publishers; only tests observe them.
- The MIDI downbeat re-anchor is pinned in daw-core (`MidiRecorderTest.onceTheCountInFiresBarOneIsMeasuredFromTheFireNotFromThePredictedWindowEnd`, `CountInScheduleTest.theFireIsStampedOnTheMonotonicClockBeforeItIsPublishedAndTheScheduleIsTheRecordersDownbeat`), not through `RecordCoordinator`: there is no daw-app-level timing pin.
