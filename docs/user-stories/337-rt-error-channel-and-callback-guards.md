# RT-Safe Error Channel and Callback Guards

## Motivation

The two default streaming backends handle a render-path exception in the two worst possible ways, and every guard that does exist is a black hole:

- **PortAudio — the production default (`AudioBackendFactory.createDefault()` wired at `MainController.java:802`) — is one exception from JVM death.** The FFM upcall body calls `callback.process(...)` with no try/catch (`PortAudioBackend.java:448`). The callback target is `AudioEngine::processBlock`, registered raw at `AudioEngine.java:442` and `:519`, and it **throws `IllegalStateException` when `running` is false** (`AudioEngine.java:910-913`) — `stop()` flips `running` independently of stream teardown, so a stop racing an in-flight callback throws straight through the FFM upcall into the native frame. Any plugin or DSP `RuntimeException` in the render pipeline takes the same exit. An exception crossing an FFM upcall boundary kills the JVM — total loss of an unsaved session. The codebase already knows better one module over: the ASIO upcall wraps its body in a catch-everything guard precisely because the driver cannot recover from a Java stack unwind (`AsioBufferSwitchShim.java:364-371`).
- **JavaSound — the always-available fallback — dies silently and lies about it.** The render loop calls `currentCallback.process(...)` bare inside `while (streamActive)` (`JavaSoundBackend.java:265-275`) on an unwrapped virtual thread (`:155`). One DSP exception kills the thread; `streamActive` stays true, so the backend *reports* an active stream while producing silence forever. Nothing notices, restarts, or reports it.
- **The existing swallows are amnesiac.** The ASIO shim swallows `Throwable` in its upcall and drain publisher with no counter, health flag, or user signal (`AsioBufferSwitchShim.java:364-371`, `:515`), and `AudioWorkerPool` swallows every task `Throwable` with an empty catch (`AudioWorkerPool.java:216`) — a track whose inserts throw every block silently mixes a stale buffer, uncounted.
- **The fan-out choke points have no isolation.** `FxDispatcher.pulse()` (`FxDispatcher.java:443-461`) runs each keyed runnable (`:455`) and each continuous-channel drain (`:460`) bare — one persistently throwing consumer propagates onto the FX thread and starves the playhead, status cells, and every other channel, sixty times a second. `DefaultEventBus` does isolate subscriber throwables but routes them only to the invisible log (`DefaultEventBus.java:191`, `:352`).

For a studio engineer this means a single misbehaving plugin can end the session — either the whole application vanishes mid-take (PortAudio) or audio stops with the UI still claiming an active stream (JavaSound) — and lesser failures (a failing track render, a throwing meter consumer) degrade the session with zero trace. The book's principle §2.3 governs the fix: the RT thread records, it never surfaces — atomics and rings on the callback path, a drain on the FX pulse turning records into visible facts.

## Goals

- **PortAudio upcall guard.** Wrap the entire FFM upcall body — including buffer marshalling — in a catch-everything guard mirroring `AsioBufferSwitchShim.java:364-371`: on `Throwable`, zero the output block, record into the health record (failure code + counter bump), and return the stream-continue status. An exception must never cross into the native frame.
- **Engine stop-race fix.** `processBlock` on a stopped engine renders silence and returns — the `IllegalStateException` at `AudioEngine.java:910-913` stops being an exception path. A stop racing a live callback is normal teardown, not a fault: it produces no failure record and no surface (book §5.1 row 4 — claiming a fault that isn't one is also lying).
- **JavaSound per-iteration guard with honest exit.** Each loop iteration guards the callback invocation: one bad block zeroes output, records, and continues. Past a consecutive-failure threshold the loop exits *honestly* — stream marked inactive, plus a channel-B record the drain escalates to an "audio engine fault — restart?" surface. The thread never again dies with `streamActive` still true.
- **Counters behind the existing swallows.** The ASIO shim's upcall/drain `Throwable` swallows and `AudioWorkerPool`'s task catch each bump a named counter in the health record. The swallow was always RT-correct; the defect was the missing count.
- **The RT health record and error ring** (channel B of book §3.2): a small struct of atomics — per-category failure counters, last failure code, and a callback heartbeat timestamp (shared substrate for story 338's watchdog) — plus a fixed-size ring of recent failure descriptors, preallocated at stream open. Nothing on the RT side touches a `SubmissionPublisher`, a lock, or the logger.
- **The FX-pulse drain and escalation.** A drain on the `FxDispatcher` pulse reads the health record once per frame and converts deltas into facts: first failure of a fingerprint → WARNING toast; sustained failure → "audio engine fault — N callback errors" with a restart-engine action. Rate limiting and escalation follow book §6.2 (frequency raises prominence, not volume).
- **Pulse isolation.** `pulse()` wraps each keyed runnable and each continuous-channel drain in its own guard: log once per offender fingerprint, keep draining the siblings, route repeated offenders to the story-336 funnel. One throwing meter consumer never again starves the playhead.
- **Bus escalation.** `DefaultEventBus`'s existing per-subscriber isolation gains the same fingerprint counting, so a persistently failing subscriber becomes a visible fact instead of an invisible WARNING.

## Goals — Tests

- **RT purity gate (book §6.3 gate 3).** Extend the bytecode-sentinel idiom of the ASIO shim tests (`RealTimeSafeContractTest`): the callback-path guard classes and the health record must not reference `SubmissionPublisher`, `ReentrantLock`, logging, or collection iteration in RT methods — asserted for the PortAudio and JavaSound paths, not just ASIO.
- **PortAudio guard test:** injecting a throwing callback yields a zeroed output block, a counter delta, and the stream-continue status returned from the upcall — no `Throwable` escapes toward the native boundary.
- **Stop-race test:** a `stop()` racing an in-flight `processBlock` renders silence with no exception and **no failure record** — the not-a-fault row is part of the contract.
- **JavaSound guard test:** a throwing callback produces silence-and-continue with a counter delta; sustained consecutive failures make the loop exit honestly — `streamActive` false plus an escalation record — never active-and-silent. A transient failure (below threshold) leaves the stream running.
- **Worker-pool counter test:** a task that throws every block bumps the named counter each time; the drain aggregates the deltas and escalates past the sustained threshold instead of toasting per occurrence.
- **Pulse isolation test:** a keyed runnable and a continuous-channel drain that throw every frame do not prevent sibling channels from draining in the same frame; the offender is logged once per fingerprint; a persistent offender escalates to a visible fact.
- **Bus escalation test:** a persistently throwing subscriber becomes a surfaced fact at the threshold while other subscribers keep receiving events.
- **Drain escalation test:** first failure of a fingerprint surfaces a WARNING immediately; repeats within the window are counted silently; a repeat after the window re-surfaces carrying the accumulated count; sustained failure produces the persistent fault fact with a restart action.

## Note from Story 336

- **JavaFX stops reporting a failing pulse after 100 throws.** `FxDispatcher.pulse()` is the `handle` body of the dispatcher's single `AnimationTimer` (`FxDispatcher.java:712-718`), which `start()` registers once per session. JavaFX's `AbstractPrimaryTimer` (javafx-graphics 27, `AbstractPrimaryTimer.java:372-391`) counts the throwables that leave a registered timer's `handle`. It passes the first 100 for that timer (`FAILING_TIMER_THRESHOLD`, `:68`) to the FX thread's uncaught-exception handler. It then logs one WARNING on the JavaFX logger ("Too many exceptions thrown by …, ignoring further exceptions.") and drops every later one silently.
- **Every throwing pulse counts toward that cap.** A keyed runnable (`FxDispatcher.java:635`) or a channel drain (`:640`) that throws leaves `pulse()` at once, and a participant's throw is held back and rethrown at the end of the pulse (`:642-644`). So after 100 such pulses in a session, a pulse failure no longer reaches the story-336 FX handler at all: no log record, no toast. The pulse's current locators are `FxDispatcher.java:618-645`; this story's `:443-461` predates story 318's participants.
- **This story's pulse isolation therefore catches inside `pulse()`**, per keyed runnable, per channel drain and per participant, and reports from there. It must not rely on the timer to deliver a throw to the FX handler.
- **Until that guard lands, a pulse storm's tail reads as if the failure stopped.** A pulse storm that hits JavaFX's 100-throw cap stops reaching the story-336 FX handler. The story-336 funnel then writes the storm's tail, a history entry ending "… the last time at …" and its log line, which reads as if the failure stopped, when it was only no longer delivered. Once this story's per-runnable pulse guard lands, the tail is accurate on every path.
- **This story moves the render path's existing log-once sites to its RT channel.** Story 336's "Known limits" names this story as their owner. Among the sites are `EngineStreamPump`'s render loop (`renderLoop`) at `EngineStreamPump.java:363`, `:383` and `:407`, `PluginInvocationSupervisor`'s SEVERE record of an `Error` a supervised plugin throws (`PluginInvocationSupervisor.java:504`), and `RenderPipeline#renderBlock`'s once-only return-bus-cap notice (`RenderPipeline.java:805-813`), which is allow-listed in `RealTimeSafeContractTest` (`RealTimeSafeContractTest.java:873`). Since story 336, each of them formats a record and writes it to disk under the file handler's lock at its first fault, which can cost one extra dropout. When that write is the session's first write to the log file to fail, the same thread also runs story 336's write-failure notice, once per session: `LogSink`'s error manager takes its monitor and prints one line to standard error, the sink takes its own monitor, and `FailureFunnel.onSinkWriteFailure` takes `armLock` and, while the toasts are armed, formats a WARNING and posts it through `Platform.runLater`, which enters JavaFX's `Toolkit.class` monitor; moving the sites moves that notice off the render thread with them. The allow-list is asserted exactly, so the change that moves the `RenderPipeline` notice also removes its entry.
- **A render-path swallow that future story 443 leaves to this story.** `VelvetNoiseReverbProcessor`'s late-segment catch (`VelvetNoiseReverbProcessor.java:286`) discards a segment's failure on the render path, like the swallows this story's Goal "Counters behind the existing swallows" counts. Future story 443 names it as a render-path site its own route cannot report from, so this story's RT channel is its route.

## Resolution

No failure on the render path or in an FFM upcall is silent any more, none can cross into a native frame, and the engine no longer claims to play while its render drive renders nothing. Every method an FFM upcall stub binds catches everything and answers its ABI's safe value. A render thread never logs, locks or publishes a failure: it records it into its own lane of the engine's audio health record, and a drain on the FX pulse turns the counts into notices through story 336's funnel — a WARNING at once, repeats counted, an ERROR with an action when a failure is sustained, and an immediate reaction when the render drive halts. A stopped engine renders silence and records nothing. A pulse item or bus subscriber that throws no longer stops its siblings, and becomes a visible fact when it keeps failing. Every Goals — Tests bullet is met by the tests named below.

**The PortAudio upcall guard.** Since story 316 the PortAudio upcall enters `CallbackBackendAdapter.deviceCallback`, a ring hand-off, through `PortAudioBackend.CallbackInvoker.invoke`; on Windows the stub binds `invokeNarrowLong`, which delegates to `invoke`. `invoke` bumps its device heartbeat (`deviceCallbackPeriods++`) and computes `hostFrames` and `frames` with conditional expressions before its `try`. Inside it, the output segment is reinterpreted once and the old body runs unchanged in a private `render`. On any `Throwable` it calls `silenceAfterFault` in a nested catch-all — one bulk `fill((byte) 0)` of the host's extent, reusing the reinterpreted segment, never `framesPerBuffer`-based — then keeps `lastCallbackFault` and only then bumps `callbackFaults`, so a report that counts the fault carries it (ruling E82); it returns `PortAudioBindings.PA_CONTINUE` on every path (rulings E1–E3). `invokeNarrowLong` wraps its delegation in a catch-all that only returns `PA_CONTINUE`. The backend keeps the counters of closed streams in daw-sdk's shared `BackendCounterLedger` (ruling E90): the invoker's `counters` are attached at `createCallbackStub` and folded at close (`reportClampedOversizedPeriods`) and at a failed `openStream`, and the backend reports them, with an always-present device heartbeat, through `threadCounters()`. The invoker stays without `@RealTimeSafe` (`reinterpret` allocates) and is walked by gate 3 anyway. Tests: `CallbackInvokerTest.aThrowingCallbackSilencesTheHostExtentCountsTheFaultAndContinues` (the Goals — Tests PortAudio bullet), `aThrowingCallbackOnAShortHostPeriodZeroesOnlyTheHostExtent`, `anErrorFromTheCallbackNeverReachesTheNativeFrame`, `theNarrowEntryPointContinuesWhenTheCallbackThrows`, `aFailingOutputReinterpretIsCountedEvenWhenTheSilencingReinterpretFailsToo` and `aHealthyCallbackBeatsTheDeviceHeartbeatAndCountsNoFault`; `PortAudioBackendTest.threadCountersWithNoStreamAreZeroWithADeviceHeartbeatOfZero` and `retiringTheLiveInvokerKeepsItsCounts`.

**The ASIO upcall and its drain.** `AsioBufferSwitchShim.bufferSwitchUpcall` now carries `@RealTimeSafe`, is package-private, and is listed in `RealTimeSafeContractTest.RT_CALLBACK_BRIDGES` next to `bufferSwitch` (ruling E16). It bumps `deviceCallbackPeriods` before its `try`; on a fault it calls `silenceOutputHalf(bufferIndex)` in a nested catch-all, which bulk-zeroes every bound output segment of that half, then keeps `lastUpcallFault` and only then bumps `upcallFaults` (rulings E15 and E82). Before story 337 its catch only returned, so the half kept the previous cycle's samples. `publishDrained`, on `asio-input-drain`, keeps `lastPublishFault` and then counts the lost block in `publishDrops`. `AsioBackend` keeps the shim counters of closed streams in the shared `BackendCounterLedger` over `AsioBufferSwitchShim.counters()`, attached at open (`openWithInputWidth`) and folded in `rollbackOpen` and in `close()` (ruling E90), and reports upcall faults as callback faults, publish drops as lost input blocks and an always-present device heartbeat. Tests: `AsioBufferSwitchShimTest.aThrowingBufferSwitchSilencesTheOutputHalfAndCounts`, `aHealthyUpcallBeatsTheDeviceHeartbeatAndCountsNoFault`, `aPublishFailureOnTheDrainIsCounted`, `anAsioBackendWithNoStreamReportsZeroCountsAndAHeartbeatOfZero` and `countersReportTheShimsFaultsDropsAndHeartbeat`; the fold itself is `BackendCounterLedgerTest`'s (6).

**Backend threads and the pulled counters.** A backend's own threads keep single-writer `volatile` counters with a `volatile Throwable` for the last fault, and the engine pulls them (ruling E4). daw-sdk's new `record BackendThreadCounters` (`NONE`, `plus`) is returned by `AudioBackend.threadCounters()` and `NativeAudioBackend.threadCounters()`, whose defaults are `NONE`. `CallbackBackendAdapter.threadCounters()` sums its delegate's counters and its own: its `native-input-drain` now catches every throwable per block, keeps `lastInputFault`, then counts the lost block (`inputBlocksLost`) and continues. On Java Sound's `javax-sound-capture` thread a throw from `decode` or `publishInput` loses one counted block, its fault stored before its count, and the loop continues. A throw from `line.read`, a read that returns no data (0 or less) while the stream is live (ruling E83), or a `VirtualMachineError` ends the loop as an input halt through `haltCapture`: the fault is stored, then one `inputHalts` count, then the stream's input publisher is failed with that fault (`closeExceptionally`), so story 326's terminal-input path keeps the take rolling and flags that source's tracks (ruling E84). A read released by a close, a stop or an interrupt finds the stream no longer live (`captureStreamLive`) and records nothing, which is teardown (ruling E17). The halt's fault is an `AudioBackendException` whose message, at most 120 characters (`MAX_HALT_LINE_LENGTH`), reads `input from “<name>” stopped delivering audio`, or `the audio input stopped delivering audio` when the device has no name (`stoppedMessage`); a throwing read's throwable is its cause, and a `VirtualMachineError` is kept as the fault itself (ruling E85). The device-notification upcalls (`AsioFormatChangeShim.asioMessageUpcall`, `WasapiFormatChangeShim.queryInterfaceUpcall` and `onPropertyValueChangedUpcall`, `CoreAudioFormatChangeShim.listenerUpcall`) call `backend.noteDeviceNotificationFault(t)` in a nested catch-all, which stores the fault and then bumps an `AtomicLong` on `AsioBackend`, `WasapiBackend` and `CoreAudioBackend` (rulings E31 and E82). Every backend-owned writer stores its fault before its count, and `RealTimeSafeContractTest`'s invariant 14 pins that order (ruling E82). `AudioEngine` attaches the open backend's name and `threadCounters` to its health record when a stream opens, as the first statement inside `startOpenedStream`'s unwound region, and for a retained failed hop, after the hop is tracked (`attachBackendCounters`), and folds them in `clearOpenStream()` after the stream is forgotten (`detachBackendCounters`); the attach baselines the source, so a reopen never counts a backend's history twice. Every input device opened beside the stream — Java Sound's `openInput`, or a PortAudio `CallbackBackendAdapter` sibling — is attached right after its `openInput` returns (`attachInputCounters`) and folded in `closeAdditionalInputs()` once its close released (`detachInputCounters`): its callback faults and lost blocks are lost input blocks (`audio.input`), never `audio.callback`, its input halts stay input halts, and its device heartbeat is not the stream's (ruling E86). Both kinds of source share one SDK ledger (ruling E90) and are read through the record's guard. A report that throws anything but a `VirtualMachineError`, or is `null`, freezes its source at the last good report without its device heartbeat: from then until the source is closed it counts nothing more and calls the source no more, every total it had already given stays, and one WARNING names it — "The audio backend “<name>” failed to report its failure counters; until it is closed, its device-callback faults, lost input blocks, input stops, device notifications and device heartbeat are not counted", or for an input device "The input device “<name>” failed to report its failure counters; until it is closed, its lost input blocks, input stops and device notifications are not counted", with "reported no failure counters" for a `null` report and "An audio backend" or "An input device" when the name cannot be read. The stream opens, or stays open, on the backend the user chose (rulings E78, E95 and E96). A `VirtualMachineError` freezes the source the same way, writes no record and propagates: at a stream open it fails the start through the ordinary unwind, which closes the opened handle and rolls the engine start back; at a retained hop the hop stays tracked; at a close the stream is still forgotten. At an input device's close it costs the one call that met it — a Stop, a start, the halt's close, a provision change or a shutdown, the callers of `closeAdditionalInputs()`: that device is already closed and stays tracked, any open stream stays open, and the next call that closes the input devices folds the frozen device without calling its report and does with the stream what it would have done (`AudioEngine`'s `lifecycleLock` Javadoc). That next call closes the device a second time before the fold, which the SDK contract allows (`AudioBackend.close()`: "Closes any open stream and releases native resources. Idempotent."). `MockAudioBackend.setThreadCounters` lets engine tests drive the ledger. Tests: `CallbackBackendAdapterTest.aPublishFailureOnTheNativeInputDrainIsCountedAndTheDrainContinues` and `threadCountersSumTheDelegateAndTheDrain`; `JavaxSoundBackendTest.aFailingPublishLosesOneBlockAndTheCaptureContinues` and `aThrowingReadEndsTheCaptureWithOneHalt`, both rewritten in place, `aCloseMidReadRecordsNothing`, `aVirtualMachineErrorFromPublishEndsTheCaptureWithOneHalt`, `aReadThatReturnsNoDataOnAnOpenStreamEndsTheCaptureWithOneHalt` (a read of 0 and of -1), `aCloseThatReleasesTheReadWithNoDataRecordsNothing`, `aCaptureHaltFailsTheStreamsInputPublisher` (an empty and a throwing read), `anInputHaltsFaultNamesTheInputThatStoppedDelivering` and `aLongInputNameIsCutBeforeACharacterOutsideTheBasicPlaneNeverThroughIt`; one test each in `AsioFormatChangeShimTest`, `WasapiFormatChangeShimTest` and `CoreAudioFormatChangeShimTest`; `BackendThreadCountersTest`; `AudioEngineBackendCountersTest.theOpenBackendsCountersReachTheRecordLiveAndSurviveTheClose`, `reopeningTheSameBackendNeverCountsItsHistoryTwice`, `countsABackendReportedBeforeTheStreamOpenedAreItsHistoryNotNewFaults`, `aBackendWhoseCounterReportFailsStillOpensItsStreamAndCountsNothingOfItsOwn`, `anErrorFromTheCounterReportAtOpenClosesTheOpenedHandleAndRollsTheEngineBack`, `aRetainedFailedHopStaysTrackedWhenItsCounterReportThrowsAnError`, `aCloseWhoseCounterFoldFailsIsStillAClose`, `aCounterReportThatStartsThrowingAfterAGoodOpenNeverFailsAStopOrTheNextOpen`, `aCounterReportThatThrowsAnErrorOtherThanAVirtualMachineErrorStillOpensTheStream` and `aVirtualMachineErrorFromTheCounterReportAtTheCloseStillForgetsTheStreamAndTheNextStartOpens`; `MultichannelInputCaptureStory326Test.aSecondInputDevicesThreadCountersReachTheHealthRecordAsInputAndFoldWhenItCloses`, `aVirtualMachineErrorFromAnInputDevicesReportAtItsCloseCostsOnlyTheStopThatMetIt` and `aStartDirectlyAfterAStopThatMetAVirtualMachineErrorAtAnInputDevicesCloseOpens`.

**The stop race.** Both `AudioEngine.processBlock` overloads return `boolean` (ruling E6). On a stopped engine they write silence through the new `@RealTimeSafe private static renderStoppedSilence` — `[0, min(max(numFrames, 0), plane.length))` of every non-null output plane and all of the interleaved output — and return `false` before the tap snapshot, so no metering stamp is consumed and nothing is recorded. The render drive exits on that `false` with no record; a throw while the engine or the pump is no longer running is teardown and also exits quietly (ruling E7). `AudioEngineTest.shouldThrowWhenProcessingWhileNotRunning` is rewritten in place as `processingOnAStoppedEngineRendersSilenceAndRecordsNothing`, with `processingOnAStoppedEngineToleratesShortPlanesNullPlanesAndNegativeFrames` and `processingOnARunningEngineReportsTheBlockRendered` beside it, and `EngineStreamPumpTest.engineStoppingMidStreamExitsThePumpQuietly` now also asserts no record and no uncaught-handler record (the Goals — Tests stop-race bullet).

**The render drive's honest exit.** The Goals' "JavaSound loop" is today `EngineStreamPump.renderLoop`, the one render drive every push backend runs. Its thread is a `RenderThread` that carries a `LaneRole.RENDER_DRIVE` lane claimed from `engine.audioHealth()` when the pump is built; the lane is retired on a confirmed `stop()` or a start that never ran the thread, and its undrained descriptors stay readable until the drain's reading takes them (ruling E81). The drive catches `Throwable` throughout (ruling E9). A fault from `processBlock` while the engine runs — a `LinkageError`, an `AssertionError` or a smuggled checked throwable included — records `audio.render` with the current streak, sinks a block of silence and continues; one rendered block resets the streak. `haltThreshold(format)` consecutive faults (`max(8, ceil(sampleRate / bufferSize))`, one second of audio counted in frames), a `VirtualMachineError` or any other throwable that escapes the loop's own catches end the drive through `halt`: `running = false`, then one `audio.render.halted` record with the cause, the streak and the stream generation, so a reader that sees the record already reads the drive dead (ruling E60), touching no lock, stream state, transport or backend (rulings E8 and E10). `sink` and `awaitSinkCapacity` faults are recorded as `audio.sink` and `audio.pacing`, floor-paced, and never end the drive. The lane beats once per block after `sink` returns normally (ruling E5). The three log-once sites and their flags are gone (ruling E14); the pump's logger is left for its backstop handler, the stop warning, a failed subscription cancel and the capture stream's `onError`. `AudioEngine.isRenderDriveAlive()` is true only while the stream is `RUNNING` and its pump runs, and `startAudioOutputLocked` reaps a dead drive through the existing stop and reopens it, so Play is never wedged; when that stop cannot join the old pump, the start refuses with `AudioBackendException`, attributed to the requested endpoint like every other refusal of the start, instead of opening over the unclosed stream (ruling E61). **The health record.** daw-core's new package `core.audio.health` is exported only `to daw.app`, daw-core's first qualified export. `AudioEngine` holds one `AudioHealthRecord` for its whole life (`audioHealth()`, never null, never replaced, never reset; ruling E18). The record holds one `AudioHealthLane` per render thread, published as an immutable `LaneSet` by one volatile write, and the backend counters in daw-sdk's `BackendCounterLedger`, each foreign source behind the record's guard (rulings E78, E90 and E95); the package-private `BackendLedger` that held them before the code review round is superseded, referenced by nothing, and removed with this story's commit. A lane has one writer: `record` samples a descriptor into a 16-slot ring that drops the newest when full and counts it lost, keeps a per-category last failure in an `AtomicReferenceArray`, and publishes the category's count last, with a load and `lazySet` of its `AtomicLongArray` slot, so the count is the commit: a reader that sees it also finds the sample or its loss (rulings E19, E21, E22 and E79). The streaming categories may fill at most 12 of the 16 slots (`STREAMING_SLOTS`); `audio.automation`, `audio.config` and `audio.render.halted` may use all 16, and a streaming descriptor beyond 12 undrained ones is dropped and counted lost, one integer comparison on the render thread (ruling E80). The drain copies a slot, nulls its references and only then advances. Retiring a lane folds its counts, beats, lost descriptors and last failures into the record, so totals only grow, and keeps its undrained descriptors readable until a reading takes them; once drained it holds no reference. At most 32 undrained retired lanes are kept (`LaneSet.MAX_DRAINING`); beyond that the oldest is cleared (`clearSlots()`) and its descriptors are counted lost (ruling E81). `AudioHealthRecord.read`, the record's one drain-side reading, returns one `AudioHealthReading` (ruling E79): every lane count, with the lanes' last failures, the render-drive heartbeat, the render-drive epoch and the stream opens; then every sample, of the undrained retired lanes, oldest retired first, and then of the live lanes; then the lost-sample count; then one report of each attached counter source, whose counts the totals include. If a source is folded (a device closed or reopened) while those reports are being read, the reading drops them and reads the still-attached sources once more in the same frame, and uses only that second read (ruling E98). A fold, under the record's registry lock, reads its source's report once and then publishes the folded ledger with its fold count in one step under a second private monitor that guards only fields and is never held while a counter source runs or a record is logged; the reading never takes the registry lock. For each kind the backends count — callback faults, lost input blocks with input halts, device notifications, and input halts on their own — the reading quotes the fault of a source whose count of that kind grew, still open or closed since: for an input halt, grew since the previous reading; for the other three, grew most recently, as readings saw it (ruling E94); when several grew, the one attached last among those that kept a fault, and none when none of them kept one (ruling E99), each source ranking by the attachment under which its count grew (ruling E100). Every source whose count grew is marked seen by that reading, whether or not it was quoted; a closed source's growth that no reading saw counts in the reading whose totals first include it, with the fault of the report its close folded and no other source's; and a reading consumes every growth kept from closed sources, quoted or outranked (`publishFold`, `markGrowthSeen` and their one ordering, `precedes`). Real-time sites record with `AudioFailureCodes` int constants (13 categories); the drain side reads `AudioFailureCategory` (slugs `audio.callback` to `audio.device`, ruling E23). `RenderThread` is a daemon platform thread at `MAX_PRIORITY` that carries its lane; `RenderThread.recordOnCurrentThread` and the record's own `recordOnCurrentThread` record only on a render thread and answer `false` elsewhere (ruling E20). - **E59** — `AudioHealthRecord.renderDriveEpoch()` counts render drives *started*: one for every stream open and one for every resume of a paused stream, because each builds a fresh pump with its own lane. A resumed drive counts as ruling E41's "stream opened after the latch". The docs say "a render drive started after the latch (a reopened or resumed stream)". Amended by rulings E71 (a halt) and E87 (an input halt).
- **E60** — `EngineStreamPump.halt` clears `running` *before* it writes the terminal `audio.render.halted` record. The volatile store then happens-before the lane's release store, so any reader that sees the record also reads the drive as dead. A bytecode sentinel pins the order.
- **E61** — When Play's reap of a dead drive (ruling E10) cannot close the stream, because the old pump's bounded join timed out, `startAudioOutputLocked` throws `AudioBackendException`. It never opens over a stream that is still open with its RT clock claimed.
- **E62** — A Restart Audio Engine succeeds when `applyConfiguration` returns normally *and* one of these holds: no stream was open when the restart began, or a stream is open when it returns. Only a successful restart clears the engine-fault fact. A reopen that the controller swallowed (`DefaultAudioEngineController`: "Deliberately NOT rethrown") is not a success.
- **E63** — A latched engine-fault fact stays latched while a fault keeps occurring. That covers the restart-eligible categories and `audio.render`, and also every category whose fingerprint is latched. The fault-free second requires no delta in any of them.
- **E64** — Each first-occurrence and sustained notice states what is true for its own category. DSP, PLUGIN and AUTOMATION get unnamed first-occurrence sentences. WORKER, DSP (named and unnamed), MIDI and unnamed PLUGIN get sustained sentences of their own. `failure.audio.automation` stops naming the engine restart as the only trigger. An `audio.config` notice whose frame holds no sample uses a sentence with no count. The exact texts are ruling 2's copy table, now in `Messages.properties`.
- **E65** — When an occurrence is folded into another notice of the same frame (ruling E27's worker-into-render fold, and the render-into-halt fold of DEV-B2-5), it writes its own log record at its severity, without a toast. Every counted occurrence then appears in exactly one record or tail line, which is story 336's accounting invariant.
- **E66** — Only the halt frame's own attempt to close the halted stream may act on the record coordinator (`deferInputStreamStop()`). Later frames retry through a side-effect-free query (`isInputStreamStopDeferred()`), so a retry never restarts a failed input cleanup or repeats its ERROR toast. After that, only the user's Stop retries the cleanup.
- **E67** — The halt's Stop ends any post-roll at once (`TransportController.stopForEngineHalt()`), because no tail can play on a dead drive and the halt notice says "Playback was stopped."
- **E68** — One predicate says whether a take defers the input-stream stop: `RecordCoordinator.isInputStreamStopDeferred()`. `deferInputStreamStop()` returns `false` when the predicate answers `false`. Otherwise it only acts on what it found (finishing a written take, or starting the input cleanup) and returns `true`. The halt-close retry (ruling E66) and the Stop's deferral therefore cannot drift apart.

**Known limits.**
- A PortAudio host that returns from `Pa_CloseStream` while a callback still runs jumps into a freed stub: native, not guardable from Java.
- A `native-input-drain` or `javax-sound-capture` thread that outlives a timed-out join can briefly double-write its counter: at worst a lost increment, never a torn value.
- A channel consumer that is a JavaFX method reference and throws inside JavaFX has `FxDispatcher`'s drain as its first host frame, so two such consumers throwing the same exception class share one fingerprint; the log record's offender names each.
- One fingerprint per streaming category: two plugins failing in the same category share one notice; its log record lists every distinct sampled anchor, up to 16.
- A thread with no lane — an offline export, bounce or freeze — records nothing, and an offline render runs only on its own thread, never on the engine's worker pool, so its failures never enter the engine's record (ruling E75). Off a render thread the return-bus notice is one WARNING log record per pipeline (ruling E76); the CLAP insert's crash, the CLAP host's `CLAP_PROCESS_ERROR` and caught throwable and the Velvet reverb's failed late segment are logged (ruling E77); and the automation binder tries again a binding playback disabled and throws ruling E57's exception if it is rejected (ruling E74). The MIDI renderer stays silent there: no offline caller passes one (`OfflineStemRenderer` hands `renderOffline` a `null` renderer). A freeze or export whose CLAP plugin fails completes with that plugin's input passed through for each failed block, and from that block to the end of the render when the failure latches its CLAP insert (a throw the CLAP host does not catch itself), a latch the live insert keeps for playback too; and with no processing at all for the whole render when its CLAP insert was already latched. A failed Velvet late segment is missing from the rendered block. No notice appears on screen. The log can show a single "for this block" record for a render under 30 s in which every block failed, because the bound is wall-clock with no end-of-render count, and a render that starts within 30 s of that plugin's or reverb's last record can log nothing. How rare it is: a CLAP plugin that reports processing errors, a Java-side CLAP failure or a late-reverb task failure; native crashes end the application and are not this case. The way out: read the log after a freeze or export (Help ▸ Open Log Folder), and unfreeze and render again; a latched CLAP insert passes audio through until it is removed (Remove in its row's menu), because bypassing and un-bypassing it, undoing its removal and moving it all keep the same latched instance, and nothing in the application resets the latch. No route the application offers puts a CLAP insert on a track today — nothing it runs builds a CLAP host, the insert picker offers built-in effects and JAR plugins only, and a saved CLAP insert opens offline, passing audio through — so a CLAP latch cannot arise at the desk yet. Future story 454 puts the failures in the render's result. Preventing the return-bus overflow is future story 452.
- A worker that does not join, or an orphaned pump, keeps a live lane for the engine's life.
- `exports com.benesquivelmusic.daw.core.audio.health to daw.app` is daw-core's first qualified export; `AudioEngine.audioHealth()` returns a type that other modules cannot see.
- One-shot and halt records beyond the free slots of one frame (at least 4 of a lane's 16 are always kept for them) are still counted. A one-shot record is counted under the last named subject of its category in that frame, so one automation notice can name one parameter for several that stopped following automation, and under `category|unknown` only when none of that category was sampled; a halt keeps its reason through the lane's last failure (ruling E80, DD-31). Rarity: more one-shot or halt records in one lane within one drain frame than its free slots, which are at least 4, and all 16 when no streaming failure fills the ring, for example many automated parameters of one plugin failing in the same block. The way out is the automation notice's own: restarting the audio engine retries the disabled automation (that notice's button is Open Log Folder; Restart Audio Engine is offered by the audio notices a restart can cure, and by their entries under Window ▸ Toggle Notifications). When no notice offering Restart Audio Engine has been posted in the window's session, the engineer restarts the audio engine, and so retries the disabled automation, by changing an audio setting marked "Engine reconfigure" under Edit ▸ Audio Settings… and applying it. This works whether or not a stream is open. Restart Audio Engine as a menu command, reachable without a notice, is future story 460's.
- A bus sink that rethrew one shared exception instance on every failure would grow that instance's suppressed list; the production sink never throws.
- `AsioBackend`'s three ledger call sites (open, `rollbackOpen`, `close()`) have no unit test, because an open needs a native driver; the fold they call is the shared SDK ledger's, which `BackendCounterLedgerTest` tests (ruling E90).
- When the restart's record guard ends a take and that Stop closes the stream, the restart reopens nothing, so the engine-fault fact stays latched until a later Play's render drive beats for one fault-free second, or until a second Restart Audio Engine, which begins with no stream open and so succeeds when it returns normally (ruling E62).
- The `finally` around `AudioWorkerPool.runTasks`'s `remaining.decrementAndGet()` (ruling E27) is untested: its handler, the lane record, cannot throw — the health gate holds it to zero findings — so no test can tell the `finally` from a decrement after the catch.
- A CLAP host-callback fault (`pendingEventsSize`, `pendingEventsGet`, `ostreamWrite`, `istreamRead`) records no subject, because the callbacks are static, so its notice uses the unnamed plugin sentence (ruling E64); naming the plugin is future story 451's.
- If `asio-input-drain` outlives the shim close's bounded join, a block it loses after that join is counted nowhere.
- The halt's Stop asks `isRenderDriveHalted()` without the lifecycle lock, so while a stream is being opened on another thread and the halted drive is not yet reaped — a reopen that already holds the lock, or a take's start, which closes and reopens the stream on its `daw-record-input-check` thread — the halt still runs its Stop once (ruling E97). With a reopen, the notice's context sentence says what that Stop did, no stream is wrongly closed — the halt's close answers `LIFECYCLE_BUSY` and then finds the stream replaced — and Play starts the reopened stream. With a take's start, which needs the halt's frame between Record and that thread's close of the halted stream, the Stop also cancels the take being prepared, before it captured anything, and the notice's context sentence says only what that Stop did (ruling E101): "Playback was stopped." when Record was pressed with the transport playing, paused or in a post-roll tail, and none over a stopped transport, never the recording sentence; the halt's close stays owed while the take defers it and then finds the stream replaced; and the stream the take opened is closed again by the cancelled start's own cleanup, as after any Stop of a take being prepared, unless a graph instrument keeps it open. The way out is Record again, which answers "Record is unavailable until the last take has been finished" until that cleanup has ended.
- A close still owed for a halted stream can close a later stream only if that later stream's own drive has halted, which needs an immediate halt — a `VirtualMachineError`, or a throwable escaping the render loop — before the drain's first frame after that drive started (any such frame finds the stream no longer halted and clears the owed close), with the halt record landing between that frame's reading and its retry. The transport then rolls over silence, the halt notice has no context sentence, and the way out is Stop, then Play (ruling E97). A halt's close never closes a stream whose drive is running.
- The halt's close never waits for the lifecycle lock, but once it holds it, it runs the stream's stop and the device's close on the FX thread, as the user's Stop does: the window does not repaint, playhead and meters included, for as long as the driver takes to close; future story 455 owns it.
- A Java Sound capture line that stalls ends nothing and counts nothing: its read blocks with no native error, and Java Sound reports no device heartbeat, so detecting a stall needs a capture heartbeat for story 338's watchdog (its Note from Story 337). The engineer is left without any notice of the stopped input. The take keeps rolling, and that input's armed tracks get no audio from the stall on, with no flag or gap in `take.manifest`, no notice and no latched fact: the stream's own input records silence, because `EngineStreamPump.fillInputPlanes` zeroes the input planes on every block with no captured block, and an input opened beside the stream writes nothing more. Only the input meters show it, flat for the stream's own input and held at their last level for an input opened beside it. How often an unplug or a driver fault stalls the read instead of ending it is not known: it depends on the driver, and the owner's unplug check shows which one a given interface does. The way out: Stop, which closes the line (unless a graph instrument keeps the stream open) and releases or abandons the read without recording anything, then reconnect and Play; Record also closes and reopens the stream for its take. The silent stretch stays in the take, unflagged. Detection is story 338's capture heartbeat.
- A reading is not one cut across a device close or reopen that lands while it runs (future story 458 owns these three, and records a fourth that no caller in the application reaches: a replacing attach of the same device). (1) A close reads its device's report once and folds it (`AudioHealthRecord.fold`), so a reading whose own later report of that device counted more, and that completes before the close publishes, counts more than the close then keeps; the next reading's total of that kind is lower by the difference, and because the drain's baselines only rise, as many later failures of that kind as the difference, usually one, raise no notice (which device a notice names is not affected, because a fold keeps growth only beyond what readings saw). For an input stop that means no ERROR, no Restart offer and no latched fact; a take still flags that input's tracks in `take.manifest` and warns once per track, because the halt fails the input's publisher whatever the drain counts. Nothing at the desk restores the count sooner; it is used up by those failures. It needs a device close that runs on a thread other than the FX thread, such as Restart Audio Engine, Settings ▸ Apply, a take's start, a device loss or a format-change or device-return reopen, while a drain reading runs, and that device counting a failure in the microseconds between the close's read of its report and the fold's publication; the user's Stop of playback or of a rolling take closes on the FX thread, with the drain, and cannot cause it. (2) `read` takes the stream-open count and the render-drive epoch before its device reports, so a reopen landing in between, whose input stops at once, gives a reading that counts the new stream's input stop against the older stream-open count, and the latched input-stop fact can then clear after one fault-free second of the new stream's drive although no stream opened after the stop. It needs an input that stops within microseconds of a stream open on another thread, inside a reading; the ERROR with Restart still posts, and only the latched fact can clear while the input is dead (visible from story 338's cell on). (3) A device whose report failed answers the last report the guard kept of it, and of two reports read at once the guard keeps the newer one only when its sum of all counts is at least the kept one's (`GuardedCounterSource.get`), so one kind's count in the kept report can be lower than an earlier reading saw and that kind's total can go down, with the consequence of (1); it needs a backend whose counter report fails, which no shipped backend's does.
- No test reaches `ClapPluginHost.process`'s `CLAP_PROCESS_ERROR` off-lane log branch: it needs a native CLAP plugin. The caught-throwable branch beside it, of the same shape, is tested, and `OffLaneFailureLogTest` covers the helper.
- The three halt fences in `MainController` (`stopTransportForEngineHalt`, `closeStreamForEngineHalt`, `retryCloseStreamForEngineHalt`) and the retry's `LIFECYCLE_BUSY` answer in `TransportController.retryCloseStreamAfterEngineHalt` are pinned by `FailureSpineWiringSourceTest`'s source text, not by a behaviour test: no test FXML-loads `MainController`, and the tests that run its halt response on a `new MainController()` given its fields by reflection pass, by trace, with any one fence removed — in `FailureSpineStartupWiringTest` no open stream's drive has halted and the window has no transport controller, so the halt stops and closes nothing either way, and in `CountInRecordStartTest.aRealHaltDuringACountInShowsTheHaltNoticeWithNoContextSentence` the drive has halted, which every fence lets through; the engine side of the same fence has behaviour tests (`AudioEngineRenderDriveHaltTest`).
- Some take states of a halt are pinned only through a test of another state that takes the same branch of the halt's Stop, not by a test of their own (ruling E101): a take being prepared before its own stream opened, a window the existing test seams cannot hold, through the tests of a take whose new stream opened; a take being prepared over a paused transport through the tests of a take being prepared over playback; an audio take whose count-in fired before the Stop through the MIDI-only one; the tail after a MIDI-only take's Stop through the tail after a Stop of playback; and an unannounced take being finished through a take being written after its Stop. Only one test halts the render drive for real and reads the notice's whole text, for a MIDI-only take counting in (`CountInRecordStartTest.aRealHaltDuringACountInShowsTheHaltNoticeWithNoContextSentence`); every other state is shown at the halt's Stop on a real `RecordCoordinator`, and the ERROR and FATAL text for each of the three contexts that Stop answers by `FailureCopyTest`. The `DEVICE_LOST` clause of `RecordCoordinator.stopAudioTake()`'s report, which counts a take that is `DEVICE_LOST` while still holding an active pipeline as started, has no test, because no path reaches it: `onDeviceLost` enters `DEVICE_LOST` only from `RECORDING`, after it has cleared the pipeline.
- No single-threaded test can show that a fold publishes the growth it keeps for the next reading and the folded ledger in one step under the record's second monitor: the fix round's review moved the ledger's publication ahead of that step and `AudioHealthRecordTest` and `AudioEngineBackendCountersTest` stayed green. Seeing it needs a second thread whose reading loads the ledger and marks inside that window — a concurrent stress harness of `read` against the detach methods, or a pause hook inside the fold, which would be a production seam. The fold-against-reading interleavings are shown by trace and by deterministic single-threaded tests whose counter source runs the close from inside the reading's report call (`aSourceClosedWhileAReadingRunsIsCountedAndNamedByThatReading`, `lostBlocksOfASourceClosedWhileAReadingRunsAreCountedByThatReadingAndByNoLaterOne`) or reads the report inside the close's (`aClosedSourcesHaltIsNamedByTheReportItsCloseFoldedNotByAReportAnotherReaderKept`); no concurrent stress test ran.

**Accepted as built.** These are recorded so that nobody "fixes" them:
- The record is per engine and only the lanes are allocated, the render drive's per render-pump start (a stream open or a resume) and the workers' per engine start that builds a worker pool (rulings E18 and E59); the heartbeat is two counters, not a timestamp (ruling E5).
- `CallbackInvoker.invoke` and `invokeNarrowLong` stay without `@RealTimeSafe`, because `reinterpret` allocates; gate 3 walks them anyway. The common PortAudio fault allocates nothing beyond the thrown object.
- `sink` and pacing faults never halt the render drive (ruling E8): a capturing stream stays alive, and a dead output device is story 338's verdict.
- Restart Audio Engine is not offered for the render-pipeline categories (ruling E13).
- A one-off pulse failure, once an ERROR `ui.handler` toast, is log-only now (ruling E35).
- The no-argument `FxDispatcher` rethrows after the frame; the four non-root main sites (`DefaultAudioEngineController`, `RecordCoordinator`, `MixerView`, `ProjectLifecycleController`) keep it (ruling E32).
- The capture ring's overflow and truncation counts and the flush thread's write failures stay off the audio health record (ruling E47): story 339 owns their warning sink's visibility, story 338 the dropout counts during a take.
- The two `dawg-annotations-reflection` copies still differ in both directions: story 334 updated only the ignored `.claude` copy (consumers 2, 3, 5 and 6, the `ClassValue` and `publicLookup` rules), and story 336 only the tracked copy (the FFM-upcall list under the table, which names the daw-sdk shims' `buildUpcallStub`); story 337 made identical edits at the anchors it touched and did not re-sync the rest (ruling E51).
- A resume after a pause starts a new render drive, so it counts as a newer drive for clearing the engine-fault fact (ruling E59) — except a fact latched by an input halt, which a resume never clears, because it does not reopen the input (ruling E87).
- Story 128 and `docs/user-stories/README.md` are unchanged (rulings E53, E54).
- A halt seen after its stream was replaced shows the halt notice with no context sentence, and stops and closes nothing (rulings E70 and E72).
- Offline renders run their inserts on one core (ruling E75).
- A backend whose own failure report cannot be read is not counted until it is closed (rulings E78 and E96). While that backend or input device is open, a device-callback fault, a lost input block or a device notification of it raises no notice, and a stopped input of it no ERROR, no Restart offer and no latched fact; render-side failures still do. Besides the one counter-report WARNING log record, only a stopped input shows: it still fails its input publisher, which the engine logs at WARNING, and a take flags that input's tracks in `take.manifest` and warns once per track. No shipped backend's report fails; it takes a third-party or broken backend.
- A `VirtualMachineError` from an input device's report at its close costs the one call that met it — a Stop, a start, the halt's close, a provision change or a shutdown — and the next call that closes the input devices folds that device without calling its report (ruling E95).
- An input device's counters are attached after its `openInput` returns, so a capture halt in the moment between its open and its attach is absorbed into its baseline: a baseline of `NONE` would count twice the history of any backend whose `createInputBackend()` returns an instance that has counted before, and the stream's own attach has had the same shape since story 337. An input, whether the stream's own or one opened beside it, that stops in that moment raises no ERROR, no Restart offer and no latched fact: outside a take the engineer gets no notice that it stopped. A take still flags its tracks in `take.manifest` and warns once per track, because the halt fails the input's publisher. Rarity: only an input whose first read fails at once, before the attach that follows its open returns. The way out: flat input meters show it; Record reopens it with the take's stream, and Stop then Play reopens the stream's own input when that Stop closes the stream.
- A take keeps rolling when a capture source dies, its tracks flagged (ruling E84). Stop ends the take and keeps what was recorded. The input comes back only when the input devices are reopened: a take's start (Record) reopens every input its tracks use, and Stop (which closes the stream unless a graph instrument keeps it open) then Play, or Restart Audio Engine while the stream is open, reopens the stream's own input.
- The input halt reuses `failure.audio.fault.device` (ruling E85). The notice's device slot names the open stream's device. The input that stopped is named only in its reason (`input from “<name>” stopped delivering audio`).
- Two inputs that stop within one drain frame give one notice, quoting the fault of the one opened last. Each opening counts on its own: an input closed and reopened within that frame ranks by the opening that stopped, not by the reopen. An input that stopped without reporting a fault is passed over; the notice gives only the site reason (input-capture) when no input that stopped reported one. (Rulings E94, E99 and E100.) That case is rare: no shipped backend counts a failure without keeping its fault — a read of the code found each shipped writer storing a caught throwable, or a fault it built, before its count, and every caller of `noteDeviceNotificationFault` passing the throwable of a `catch (Throwable)` — so an input passed over this way needs a backend that breaks that contract.
- A drain frame reads each audio device's failure counters once; in the rare frame in which a device is closed or reopened at that moment, it reads the open devices once more and uses only that second read. (Ruling E98.)
- A processor with no declared name is named by its class name in words (ruling E89).
