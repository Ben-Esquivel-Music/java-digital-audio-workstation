# RT-Safe Capture Path

## Motivation

The engine's render block is annotated `@RealTimeSafe` (`AudioEngine.java:909`) and the repo polices real-time paths with a bytecode sentinel (`daw-core/src/test/.../annotation/RealTimeSafeContractTest.java`) — yet the capture path violates everything that contract stands for, on the device callback thread:

- `RenderPipeline` invokes `recordingCallback.onAudioCaptured` inline in the render block (`RenderPipeline.java:495-497`), reaching `RecordingSession.recordAudioData`, which **doubles** the capture array and copies the *entire take so far* whenever capacity runs out (`RecordingSession.java:210-217`). A 2-hour 48 kHz stereo take is ~2.8 GB resident with multi-hundred-MB copies on the deadline-bound callback — dropout risk grows with take length, so the longest, most valuable takes are the ones the capture path itself ruins.
- Segment-rotation bookkeeping allocates wall-clock objects per captured block (`RecordingSession.java:382-393`) and formats strings + iterates listeners at each rotation (`RecordingSession.java:395-405`) — all on the audio thread.
- Loop-take finalization runs *synchronously inside the callback* at every loop wrap: constructing a new session, taking a full-take trimmed copy, and building take/clip objects (`RecordingPipeline.java:895-964`, copy at `:921` via `RecordingSession.java:249-258`) — despite the pipeline's own comment that finalization I/O *"never runs on the audio callback thread"* (`RecordingPipeline.java:168-170`). The virtual-thread executor hand-off it gestures at is an explicit documented no-op (`RecordingPipeline.java:954-961`).

Capture state also crosses threads with no synchronization: `RecordingSession`'s `active`/`paused`/`capturedAudio`/`capturedSampleCount` are plain fields (`RecordingSession.java:47-48,68-70`) mutated by the audio thread while the FX thread calls `stop()` and `getCapturedAudio()` — a data race that can tear the buffer-grow copy or lose the take tail. The pipeline's `active` flag is a plain boolean read in `onAudioCaptured` (`RecordingPipeline.java:70`), and its `sessions`/`routedInputBuffers` maps are plain `LinkedHashMap`s (`RecordingPipeline.java:53-55`).

Finally, the pipeline records at a format the engine is not running. `applyConfiguration` sets the settings `AudioFormat` on the **engine only** (`DefaultAudioEngineController.java:351-357`), but `onRecord` constructs the `RecordingPipeline` with `project.getFormat()` (`TransportController.java:443-445`) — pinned at the project's creation-time `STUDIO_QUALITY` default of 96 kHz / 256 frames (`MainController.java:778`, `AudioFormat.java:17`) regardless of what the engine now streams at. Routed capture buffers are sized from the project format (`RecordingPipeline.java:226,236`) while `recordToSessions` copies the frame count the engine stream actually delivered (`RecordingPipeline.java:782`) — any settings buffer size above the project's overruns the array **on the audio callback**, which the unguarded PortAudio upcall (`PortAudioBackend.java:432-448`; `FAILURE_SURFACING_DESIGN_BOOK.md` §1.7) turns into JVM death. A sample-rate mismatch corrupts every recorded clip's duration and position, computed from the project rate (`RecordingPipeline.java:300-302`).

The house already knows how to do this correctly: the ASIO bridge captures into preallocated lock-free `AudioBlockRing`s drained by a dedicated thread, with every allocation done at open time (`AsioBufferSwitchShim.java:99,161-162,223-224`). This story brings capture up to that standard on the seam story 323 builds.

## Goals

- Complete the book §5.1 RT-safety contract on the capture path: on the audio callback, capture does exactly bounded arithmetic, volatile scalar reads, and one bounded copy into preallocated memory — no allocation, no boxing, no locks, no string ops, no wall-clock objects, no listener iteration, no `SubmissionPublisher.offer` (the story-311 lesson), no file I/O.
- Delete the on-callback allocation/copy growth (`RecordingSession.java:210-217`), the on-callback rotation bookkeeping and listener iteration (`RecordingSession.java:382-405`), and retire the on-callback listener loop per the RT-safe observer rule (book §6.2).
- Size the `CaptureRing` at record-start from the engine's **live** format (book §4.2): slot payload = stream buffer frames × stream input channels; slot count covers ≥ 250 ms of audio and never fewer than 8 slots — following the `AudioBlockRing` sizing discipline. Overflow policy: the callback drops the *oldest unwritten block*, increments an atomic overflow counter, and the flush thread records a gap marker in the manifest; the callback never blocks and never silently overwrites (book §4.2).
- Replace the unbounded in-RAM `capturedAudio` copy with the bounded, decimated peak mirror of book §4.5 (min/max pairs per fixed frame bucket), maintained by the flush thread and published through an `FxDispatcher` continuous channel for live waveform drawing; post-stop playback loads clip audio from the sealed segments off the FX thread.
- Move loop-take finalization to the flush thread (book §4.6): wrap detection from slot-header beat positions (position decreased between consecutive blocks); on wrap, seal the lane's segments, append the take, and open pre-opened next-lane writers — giving the no-op executor hand-off (`RecordingPipeline.java:954-961`) its intended real body.
- Make the stop handoff a real fence (book §5.2 FINALIZING): deregister callback → drain ring → seal — fixing the `RecordingSession` plain-field races via the single-writer topology of book §2.3 (device callback writes ring slots; flush thread writes files/mirror/take model; FX thread writes coordination state only).
- The capture path stops reading racy transport fields mid-block by using slot-header snapshots stamped on the callback — the **record half** of the transport shared-state work. The transport's own volatile/seek-queue fix is story 315's scope (`AUDIO_ENGINE_WIRING_DESIGN_BOOK.md`).
- Derive all capture formats and per-block sizes per book §2.7: sample rate, channel count, and buffer size from the format the engine is *actually streaming*, captured at record-start; per-block sizes from the frame count the stream delivered — never `project.getFormat()`, never a captured constant. Where engine and project formats diverge, the divergence is **declared**: the clip records the take's true sample rate and beat math uses the true rate; surfacing rides the sample-rate-badge seam owned by story 342.
- Extend the `RealTimeSafeContractTest`-pattern bytecode sentinel over the capture-path classes so the §5.1 contract is enforced mechanically, not by review.

## Goals — Tests

- A `RealTimeSafeContractTest`-pattern bytecode sentinel over the capture-path classes asserts no allocation, boxing, locks, or string ops are reachable from the callback.
- A stress test records while the engine runs a larger buffer size than the project format: no array overrun, and the finalized clip length is correct.
- A stop-race test drives high-frequency start/stop cycles and asserts no take tail is ever torn or lost — the FINALIZING fence (deregister → drain → seal) is exercised under contention.
- A heap assertion test shows resident capture memory is flat over a long simulated take (the unbounded `capturedAudio` growth is gone; only the bounded mirror and ring remain).
- An overflow-policy test stalls the flush thread until the ring fills: the oldest block is dropped, the atomic overflow counter increments, and the manifest records a gap marker — the callback never blocks.
- A loop-wrap test asserts finalization work (session construction, trimmed copies, take/clip building) happens on the flush thread, lanes seal correctly at the wrap, and no finalization code is reachable from the callback (covered by the sentinel).
- A format-divergence test records at an engine sample rate different from the project's: the clip records the true rate and its duration/position math is correct at that rate.
- A mirror test asserts the published peak mirror is bounded and decimated (fixed bucket count) and rides the `FxDispatcher` continuous channel, never a callback-side listener.

## Technical Notes

- Implements **Stage 2 — RT-Safe Capture Path** of `docs/design/RECORDING_RELIABILITY_DESIGN_BOOK.md` (§8). Contracts bound: §5.1 (the RT table — the reviewer's law for this PR), §2.2/§2.3/§2.7 (principles), §4.2 (ring + overflow), §4.5 (mirror), §4.6 (loop rotation), §6.2 (observer rules).
- Files to touch: `RenderPipeline.java` (`:495-497` — the callback hand-off becomes a ring write), `RecordingSession.java` (growth, rotation bookkeeping, and listener loop retired; plain-field races removed by topology), `RecordingPipeline.java` (loop finalization to flush; buffer sizing from live format; `:70` active flag and `:53-55` maps re-homed per single-writer), `TransportController.java` (`:443-445` — pipeline construction takes the engine's live format, not `project.getFormat()`), plus the story-323 `CaptureRing`/`CaptureFlushService`.
- Seams to reuse: `AudioBlockRing` + `AsioBufferSwitchShim` drain-thread discipline (stories 311-312) as the proven local idiom; `RealTimeSafeContractTest` as the sentinel mechanism to extend; `FxDispatcher` continuous channels (story 289; `FxDispatcher.java:390`) for the mirror and elapsed-time facts; the RT-safe observer rule (volatile snapshot read once — never listener iteration on the callback).
- `SubmissionPublisher.offer` takes a `ReentrantLock` and is forbidden on the RT thread — publish into the ring or a preallocated structure and drain on the flush/FX side (story 311 finding; book §6.2).
- Engine/project divergence numbers verified: the project default is `AudioFormat.STUDIO_QUALITY` — 96 kHz / 256 frames (`AudioFormat.java:17`), set at project creation (`MainController.java:778`).
- Cross-refs: story **323** (prerequisite seam), **315** (transport-side synchronization), **342** (SRC badge surface), **337/338** (error/xrun surfacing), **132** (loop-record's landed RT compromise, fixed here).
- Research backing: SKILL `research-daw` §3, whose primary source (`docs/research/open-source-daw-tools.md` §3, Real-Time Audio Processing) asks for a lock-free audio thread — "no allocations or locks on the audio thread" — and "Ring buffers: For communication between audio thread and UI thread". The dedicated `capture-flush` drain thread is the book's own design (§2.3, §4.3), modeled on the `AsioBufferSwitchShim` + `AudioBlockRing` drain-thread discipline its Appendix B lists.

## Resolution

The capture path now does on the audio callback what book §5.1 allows and nothing else, and a bytecode sentinel denies everything else by default. The take's audio is no longer held in memory while it is recorded: it is on disk in its segments, a fixed-size peak mirror stands in for it while the take runs, and the clips of a stopped take get their audio by reading the sealed segments back, off the FX thread, before the take is published. The file and line references in the Motivation and Technical Notes above locate the code as it was before stories 323 and 324; they are left as written and no longer point at that code (`RenderPipeline` in particular is unchanged by this story — the ring write is in the new `CaptureCallback`, not in the render block).

**The callback — `CaptureCallback` (new, daw-core `core.recording`).** `RecordingPipeline.beginCapture()` constructs one per take and installs it with `AudioEngine.setRecordingCallback`. Everything the audio thread reads is a `final` field of that object — the take's `CaptureRing`, its `CaptureFlushService`, the array of armed graph-instrument tracks, the transport, the engine, the take's sample rate and the tempo the take was prepared at — so the audio thread reads no field of the pipeline, and a callback left over from an earlier take can only reach that take's ring. `onAudioCaptured` is `fillBlock` followed, in a `finally`, by `publishAndLeave`. `fillBlock` enters the ring's producer gate (`CaptureRing.enterProducer`), claims a slot (`claim`; `null` is a counted overflow and an immediate return), stamps the header — `Transport.getPositionInBeats()`, the start frame converted from that beat at the prepare-time tempo, the punch snapshot from one `Transport.getPunchRegion()` load, `Transport.isLoopEnabled()` — and copies the device block and each armed graph-instrument buffer into the slot. `publishAndLeave` publishes only if the gate is still open (`producerOpen`), wakes the flush thread (`CaptureFlushService.signal`) and leaves the gate (`exitProducer`). The callback does not call `Transport.getTempo()`: that reads the tempo map's list, and it stays without `@RealTimeSafe`.

**The ring — `CaptureRing`.** `RecordingPipeline.doPrepare()` allocates it from the format the pipeline was constructed with: slot frames `format.bufferSize()`, slot count `CaptureRing.slotCountFor(format.sampleRate(), format.bufferSize(), DEFAULT_HANDOFF_TOLERANCE)` — 250 ms of audio, never fewer than `MIN_SLOTS` (8), rounded up to a power of two. The ring gains the producer gate: two volatile words, `producerClosed` (written by the thread that ends the take, `closeProducer()`) and `producerPhase` (written only by the callback, odd while it is inside), and the flush thread's bounded wait `awaitProducerQuiescent(long)`. A delivered block longer than a slot keeps its first `slotFrames()` frames; the excess is stamped on the slot and counted (`noteTruncatedFrames`).

**The flush thread — `CaptureFlushService`, `TrackCapture`.** Before the final sweep of a stop the thread waits for a callback in flight to leave the gate (`awaitProducerQuiescence`, bounded by `PRODUCER_QUIESCENCE_BOUND`, four `PARK_BACKSTOP` periods = 200 ms). If the bound elapses it warns through the warning sink and sweeps and seals all the same; blocks published behind the sweep are recorded as one `gap=` line with a warning (`noteBlocksLeftBehind`, after the lanes have had their seal attempts). A truncated block is recorded as a truncation episode and in the manifest's `truncated-frames` total (`noteTruncation`). Each `TrackCapture` owns one `CapturePeakMirror`, fed with the frames its lane's session recorded; `publishPeaksIfDue` hands snapshots to the sink at most once per `PEAK_PUBLISH_INTERVAL` (33 ms) and once more when a lane is finalized.

**The session — `RecordingSession`.** The growing in-memory copy of the take is deleted: `capturedAudio`, `getCapturedAudio()`, `getCapturedSampleCount()` and `ensureMirrorCapacity` no longer exist, in main code of any module. The session has been driven by the flush thread since story 323, so its rotation and its listener calls already ran off the callback; the listener list itself stays, and `addListener`'s Javadoc states the thread ("the `capture-flush` thread once capture is running"). Two package-private seams serve the loop standby: `surrenderEmptySegment()` and `adoptAsNextSegment(SegmentWriter)`.

**The peak mirror — `CapturePeakMirror`, `CapturePeakSnapshot` (new, daw-core), `LiveCapturePeaks` (new, daw-app `ui.recording`).** The mirror is `BUCKETS` = 2048 minimum/maximum pairs in one array allocated at construction; a bucket covers `INITIAL_FRAMES_PER_BUCKET` = 256 frames until the buckets are full, then neighbours are merged in place and the frames per bucket double. The flush thread is its only writer and its only reader. `CapturePeakSnapshot` is the immutable copy handed to the sink installed with `RecordingPipeline.setPeakSnapshotSink`; with no sink installed no snapshot is built. In the app `TransportController.openCapturePeaks` opens a `LiveCapturePeaks` — one `FxDispatcher` continuous channel per armed audio track (`FxDispatcher.openContinuous`) — and installs `LiveCapturePeaks.publish` as the sink; the dispatcher's pulse delivers the newest snapshot of each track on the FX thread, where `latest(trackId)` returns it. Nothing draws from it yet.

**Loop record — `TrackCapture.prepareStandby`.** Wrap detection (the slot header's beat position decreased between consecutive blocks, `CaptureFlushService.applyBlock`) and lap finalization (`finalizeLoopLap`, `TrackCapture.finalizeLane`) have run on the flush thread since story 323. This story adds the pre-opened lane: in loop-record the flush thread keeps a standby session for lane + 1, its `.part` created and its header written away from the loop seam, and listed in the manifest; the wrap seals the lane, stacks the lap and swaps the standby in without opening a file. A lane that rotates takes over the standby's open, empty file, and another standby is prepared after the block. Whatever ends the take discards a standby no lap reached (`discardStandby`): its file is deleted and its entry removed. A standby is also discarded at a wrap when the sealed lane ended on an empty segment and so left the standby one index too far; if its empty file cannot be deleted there, the take goes on as it does when that delete fails at the stop — entry removed, session kept for a later retry, warning sent — and the next lane is opened one index past the file that stayed (`TrackCapture.finalizeLane`, `CaptureFlushService.finalizeLoopLap`).

**Stop and publication — `RecordingPipeline.requestStop`, `recordedSegmentPaths`, `completeStop(Function)`; `TransportController.finishWrittenTake`, `readRecordedAudio`, `publishWrittenTake`.** `requestStop()` closes the gate, removes the callback, clears the armed tracks' recording flags, stops the transport and asks the flush thread to seal; it does not wait for the callback in flight or for the flush thread (`Transport.stop()` keeps its own spin for a position advance in flight). When the flush thread has terminated, the FX turn `finishWrittenTake` asks the pipeline for the segment-path list of every clip the take will publish (`recordedSegmentPaths()`, no storage, no waiting) and hands `readRecordedAudio` — `SegmentFile.readFrames` per list — to the storage executor; `publishWrittenTake`, posted back to the FX thread, calls `completeStop(lookup)`, which attaches each clip's audio (`AudioClip.setAudioData`) before the clip is added to its track (`addClip`, `putTakeGroup`), every lap's clip included. `TransportController.isTakeBeingWritten()` stays true until that publishing turn.

**Format — `TransportController.onTakeDirectoryAllocated`, `RecordingPipeline.buildClips`, `TrackCapture.declaredRate`.** The app constructs the pipeline with `audioEngine.getFormat()`, not the project's format. Each recorded clip declares what was captured through `AudioClip.setSourceRateMetadata` — the rate and channel count its segment headers carry and the frames recorded — and the clip's duration, its start and the manifest's anchor are computed at that rate.

**The sentinel — `RealTimeSafeContractTest`.** An eighth invariant walks the bytecode reachable from `CaptureCallback.onAudioCaptured` across the capture-path classes and denies by default: every call is into a followed class, and walked, or is on an exact nine-entry allow-list of external members. The project skill `dawg-annotations-reflection` describes the tests.

### Binding decisions

- **Overflow drops the incoming block, not the oldest.** The Goals and the overflow test bullet above say "the oldest unwritten block" / "the oldest block is dropped". The code does the opposite, as story 323 landed it and as book §4.2 now records: `CaptureRing.claim()` returns `null` on a full ring, the overflow count advances and the callback returns. Overwriting the oldest slot is not safe with one producer and one consumer — the flush thread may be copying out of exactly that slot. The loss is one block per overflow either way, and it is recorded as a `gap=` line.
- **This story builds the stop fence, and it is a producer gate, not a callback handshake.** The Goals write the fence as "deregister callback → drain ring → seal". Removing the engine's callback does not stop a callback the audio thread has already loaded, so the order as landed is: close the gate, remove the callback, stop the transport (caller thread, no waiting for the callback or the flush thread); then, on the flush thread, a bounded 200 ms wait for the callback in flight, the final sweep, the seal. The gate is two volatile words and rests on a single callback thread. The block that straddles the stop is dropped whole, never torn; a block left behind a timed-out wait is recorded as a gap with a warning. Story 323's hand-off gave the handshake to story 325; story 325's own Non-Goals give the fence internals to this story, and that is what landed.
- **The callback uses a tempo snapshot taken when the take is prepared.** `RecordingPipeline.doPrepare()` reads `transport.getTempo()` once; the manifest's anchor frame and the callback's start frames use that value. The Goals speak of slot-header snapshots of transport fields; tempo is the one field that is not stamped per block, because reading it on the audio thread would read the tempo map's list.
- **One `CaptureCallback` object per take, with final fields.** No lambda, method reference or class nested in `RecordingPipeline` implements the callback; the sentinel pins that.
- **The clip declares its rate through `AudioClip.setSourceRateMetadata`.** No new field or type carries the divergence.
- **The pipeline keeps its `AudioFormat` constructor parameter; the app passes `audioEngine.getFormat()`.** Both constructors' Javadoc now state that it must be the engine's stream format. The Goals say "per-block sizes from the frame count the stream delivered … never a captured constant": slot frames are fixed when the take is prepared, and a longer delivered block is truncated, counted and recorded rather than overrunning.
- **The peak mirror is 2048 fixed min/max buckets, the flush thread its single writer, and its snapshots are pushed to a sink about every 33 ms.** The app's sink is one `FxDispatcher` continuous channel per armed track. The Goals say "for live waveform drawing": the feed exists and no renderer was built in this story.
- **Loop record uses a pre-opened standby lane that is listed in the manifest.** The standby holds no frames; a take that ends never leaves one sealed.
- **Recorded audio is loaded before the take is published.** The flush thread ends; an FX turn takes `recordedSegmentPaths()`; the storage executor reads the segments; an FX turn calls `completeStop(lookup)`, which attaches the audio before the clip reaches its track; then the take is published. `isTakeBeingWritten()` stays true through the read, so Record and the doors that replace the open project are refused until the take is on its tracks. The first implementation published the take at once and attached the audio on a later turn. That was rejected in review: between publication and attach, a freeze, bounce or export silently left the take out, and a clip derived from the recorded one (a split half, a duplicate) that was off its track when the audio arrived stayed without audio for the session. With the load first there is no such window.

### Known limitations and hand-offs

- **The declared rate is not saved (proposed for story 329).** `SourceRateMetadata` is set on the clip in memory; the project serializer and deserializer do not write or read it. The rate is still in every segment's header and in the manifest. Story 329's text does not yet mention it: its rehydrator would have to rebuild the declaration from the segment header, or the clip element would have to carry it.
- **Offline consumers assume the project rate (proposed for story 342).** Bounce, freeze, per-track export, stem export and embedded-media export treat a clip's samples as being at the project's rate; of the paths that render audio, only live playback (`RenderPipeline.resolveAudioData`) reads the declared rate. Story 342 owns the mismatch badge and the ruler's live rate; it does not state this.
- **An on-miss resample is reachable on the audio thread after an engine-rate change (no story owns it).** Recorded clips are now the first production clips that carry rate metadata, so `RenderPipeline.resolveAudioData` can convert a whole clip inline on the first block after the engine's rate has changed. Nothing pre-warms the conversion cache off the audio thread.
- **Nothing draws the live capture waveform (no story owns it).** `LiveCapturePeaks.latest(trackId)` is the feed; no renderer reads it.
- **A punch region's frames are read at the stream rate (proposed for story 328).** `RecordingPipeline.doPrepare()` converts `PunchRegion.startFrames()` with the pipeline's sample rate, and the flush thread compares the region's frames with start frames computed at that rate. A region whose frames were written against another rate is placed wrongly. Story 328 owns punch creation and the ruler's live-rate drawing; it does not state this conversion.
- **A clip of a take whose seal failed can declare more frames than its listed segments hold (story 323's hand-off to stories 325 and 332).** The clip declares every frame recorded; the unsealed `.part` is not in its segment list. Story 332's text does not mention a take recovery scan.
- **The read adds its time to the "finishing the take" period.** A take's clips appear only once its audio has been read back; until then Record and the doors that replace the open project are refused.
- **A clip whose read failed has no audio for the rest of the session.** The take is still published, the clip keeps its segment references, nothing is deleted and the user is told once, by one ERROR. Nothing reloads a clip from its segments within a session; reloading on project open is story 329's rehydrator. When the storage task fails as a whole, audio already read for earlier clips of that take is discarded and every clip is published without audio.
- **A read in flight when its controller is retired finishes the clip it is on, then stops.** Nothing of that take is published or attached.
- **The take's live peak channels are closed when its capture thread terminates,** on the `finishWrittenTake` turn, before the read — not at publication.
- **The status and refusal texts were reworded** so they stay true while the read runs: `TransportController.TAKE_FINISHING_MESSAGE`, `TAKE_STILL_WRITING_MESSAGE`, `RECORD_WHILE_WRITING_MESSAGE`, and in `ProjectLifecycleController` `PROJECT_CHANGE_WHILE_WRITING_MESSAGE` and `lateLoadRefusalMessage`. Earlier documents that quote the old texts are out of date on those strings.
- **A standby file that cannot be deleted, at a seal or at a loop wrap, is left as an unlisted, zero-frame `.part` (proposed for story 332).** Its manifest entry is removed, the warning sink is told, and a later abort retries the delete. At a seal the manifest stays sealed. At a wrap the take goes on recording, and the track's next lane is opened one index past the file, so the track's segment numbering skips two indices there: the one the sealed lane left free and the file's own. Book §3.4 has no row for this state; a recovery scan must treat an unlisted zero-frame `.part` in a sealed take as an orphan. The same delete failing when a rotating lane discards a standby that is not at its next index still ends the take as a write failure.
- **While a manifest write is failing, the manifest on disk can lag an adopted standby file.** When a rotating lane takes over the standby's file, the manifest is rewritten before the first frame lands in it; if that write fails, the file on disk is still named as the next lane's, or not at all, until a retry lands.
- **A standby lane's session fires its listeners' started and stopped callbacks without recording a frame** (`RecordingSession.surrenderEmptySegment`, `TrackCapture.discardStandby`). The pipeline adds no listener in production.
- **Peak mirror rules.** A sample that is not a number is left out of the fold; a frame with no number counts as silence, so a mono NaN frame contributes 0 to its bucket. Whatever a peak sink throws, an `Error` included, is contained in `TrackCapture.handOverPeaks`, logged once per track per take, and never ends a take.
- **`completeStop(lookup)` propagates what the lookup throws.** The clips published before it stay published and the finalisation has ended.
- **The gate's single-callback-thread precondition is documented, not enforced.** `CaptureRing`'s class note says what two overlapping callers would cause; nothing detects it.
- **Overflow, truncation and stop-fence warnings still degrade to logging** through the pipeline's warning sink, as the Non-Goals say (stories 337, 338). `RecordingPipeline.setWarningSink`'s Javadoc names story 339 as the one to inject the notification seam; story 339's text does not mention this sink (proposed for story 339).
- **Review items listed and not applied.** Each was raised in review, checked against the code as it stands, and left as it is:
  - `CaptureFlushService.finalizeLoopLap` sends the loop-wrap warning that ends "Recording continues." from a `finally` block. It is therefore also sent when the same `TrackCapture.finalizeLane` call, having failed to delete the standby's file, then fails to open the next lane; that failure reaches `applyBlock`'s `failAndSeal` and the take is sealed.
  - The catch at the loop seam in `TrackCapture.finalizeLane` (`catch (RuntimeException undeletable)` around `stopStandby`) treats any `RuntimeException` from stopping the standby — a listener that threw included — as a file that could not be deleted.
  - `TrackCapture`'s class note still says "indices are contiguous per track and rise with the lane", and the inline comment above the seam's `try` says "the lane is opened here at the index that is free". Neither sentence is qualified for the case in which the next lane is opened past a file that stayed; that case is described only further on in the class note and in the comment inside the `catch`.
  - `TransportController.finishWrittenTake` has no failure path if the storage executor throws synchronously when it is handed the read: the `CompletableFuture.supplyAsync(..., storageExecutor)` call is not guarded, so `publishWrittenTake` would never be posted and the take would stay "being written". The production executor starts one virtual thread per task and refuses none; only an executor installed with `setStorageExecutorForTest` could do it.
  - `RecordedAudioLoadsOffTheFxThreadContractTest.aControllerRetiredWhileTheTakeIsReadBackReadsNoFurtherAndPublishesAndAttachesNothing` arms one track and retires the controller before the held read runs, so it pins only the check `readRecordedAudio` makes before the first clip's list, not the check between two lists.
  - In `StopFenceTailIntegrityContractTest.everyTakeStoppedUnderALiveProducerSealsExactlyTheBlocksItPublished` only the 20 driven cycles widen the flush thread's wait (`setProducerQuiescenceBound`); the 40 undriven cycles run under the production `PRODUCER_QUIESCENCE_BOUND` of 200 ms while asserting no warning and no gap.
  - The structural walk of `CaptureMemoryFlatOverLongTakeContractTest` starts from the track captures, the ring and the flush service (`footprintOfTheCapture`), or from one session; it does not start from `RecordingPipeline` or `CaptureCallback`, and for a map it records the size and does not descend into the values.
  - `RecordingPipeline.completeStop(lookup)`: a lookup that throws ends `buildClips` in the middle of its loop over the armed tracks, so the tracks after the one being built get no clip (the item above on what the lookup throws states only that the earlier clips stay published); and the array the lookup returns is attached as it is (`AudioClip.setAudioData`), its channel count and length unchecked. The app's lookup is a map `get` and cannot throw.
