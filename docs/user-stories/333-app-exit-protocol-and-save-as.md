# The App-Exit Protocol: Close Guard, Save As, Lock Lifecycle

## Motivation

Quitting the application is a data-loss event. There is no exit protocol at all:

- **Nothing can veto a close.** The only primary-stage lifecycle hook is `setOnHidden` (`MainController.java:1007`) — it disposes view-models and timers *after* the window is gone and cannot veto anything. The only `setOnCloseRequest` in the app is on floating dock-panel stages (`MainController.java:3579`); `DawApplication`'s `WINDOW_HIDDEN` handler closes the event bus and dispatcher only (`DawApplication.java:98`).
- **The close sequence is never run.** `ProjectManager.closeProject()` — the final save, checkpoint-scheduler stop, and **lock release** (`ProjectManager.java:339-359`) — has zero production callers; only tests invoke it. Every real exit leaves the lock file behind, which feeds the crash-detection staleness heuristic garbage on the next launch.
- **No guard, no menu items.** `confirmDiscardUnsavedChanges` (`ProjectLifecycleController.java:813`) is invoked only from New/Open/Restore/Recover — never from any exit. The File menu (`MenuConstructionService.java:141-182`) contains no Exit item, no Close Project, and no project-level Save As.
- **The stolen-lock contract is documented and abandoned.** `LockStolenException`'s javadoc says the UI should prompt Save As (`LockStolenException.java:6-11`); the save path catches it as a generic `IOException` → "Save failed" toast (`ProjectLifecycleController.java:370-376`); `closeProject` swallows it assuming "the UI is expected to have already prompted Save As" (`ProjectManager.java:346-349`) — nothing does. The lock indicator even *tells the user* to "Use Save As to preserve your changes" (`LockStatusIndicator.java:110-111`) — an instruction to use a feature that does not exist.

For a studio engineer: closing the window at the end of a session silently discards every unsaved change, leaks the project lock, and — if another session stole the lock — the one documented escape hatch is a lie printed in the UI.

## Goals

- **An exit coordinator** (design book §4.8) owning the ordered §5.4 protocol, with the close request **consumed** until the protocol decides:
  1. **INTERCEPT** — primary-stage close-request handler consumed; protocol begins (never `setOnHidden` — that cannot veto).
  2. **GUARD** — dirty check (`ProjectVM.dirty` per the Control Synchronization book) → prompt: *Save and close* / *Discard and close* / *Cancel* (the veto point). **The take rule (story 323)** comes before the dirty check, because the capture-flush thread is a daemon that exit can end before the seal. The guard consults the transport for a recording still in flight (`TransportController.isRecordingInFlight()`) and for a take still being written to disk (`TransportController.isTakeBeingWritten()`, the FINALIZING state of `RECORDING_RELIABILITY_DESIGN_BOOK.md` §5.2) — the two checks `ProjectLifecycleController.confirmProjectMayClose()` makes for the in-app doors, which it refuses while either holds. A recording still in flight is stopped first — an audio take still being prepared counts as one, and a Stop cancels it (story 323, Copilot review round 5); after that Stop an audio take is still being written until a later FX turn publishes it, however fast its seal, and a cancelled start counts as being written until the removal of its files has run. A take still being written is either refused, with text worded for an exit — not `PROJECT_CHANGE_WHILE_WRITING_MESSAGE`, which speaks of the open project being replaced — or waited out, showing progress, until `isTakeBeingWritten()` is false (the FX turn that publishes the take has run: its clips, if any, published, or its failure reported; or the removal of a cancelled or failed start's files has run); only then does the guard make the unsaved-changes decision. Publishing a take marks the project dirty (story 323, Copilot review round 4), so a take published while the guard runs — on the turn after the Stop the guard made, or after the guard waited it out — reaches the unsaved-changes decision as an unsaved change. The prompt is `confirmDiscardUnsavedChanges()` reused or this story's own; nothing requires calling `confirmProjectMayClose()`. When the maturity rule below drops the prompt from this step, the take rule stays.
  3. **FLUSH** — the chosen save runs via the story-331 single canonical save (atomic, off the FX thread, progress in the Session Status Strip if > 500 ms).
  4. **SEAL** — the journal writes and fsyncs the story-332 session seal; the segment rotates.
  5. **RELEASE** — `closeProject()`: checkpoint scheduler stops, lock releases — its first production caller; the lock-file leak ends.
  6. **DISPOSE** — the existing `setOnHidden` work, now guaranteed to run last, never instead of the protocol.
  7. **HIDE** — the stage actually closes; the application exits. Each step publishes its outcome before the terminal state.
- **One protocol, every door**: the window [X], a new `File ▸ Exit`, a new `File ▸ Close Project`, the application-stop fallback, and workspace switch all route through the coordinator; input source is irrelevant past the intent boundary.
- **Project-level `File ▸ Save As`** lands — the command the lock indicator has been advertising.
- **Typed stolen-lock handling**: `LockStolenException` caught as itself, never as `IOException`; during save and during the exit FLUSH it drives a **blocking Save-As flow** (pre-filled sibling path) that preserves the work — never a transient toast, and `closeProject`'s "UI already prompted" assumption becomes true.
- **The maturity rule is carried in this story** (book §5.4, binding): `PROJECT_MANAGER_DESIGN_BOOK.md` §2.5/§8 reject the "Save changes?" modal in favour of autosave + undoable close — an end-state *conditional on trustworthy capture*. Today neither condition holds and the shipping behaviour is silent total loss, so the prompt ships first as the strictly better interim. Once story 332's default-on journal is field-proven healthy, step 2 yields to seal-and-close without interrogation, the prompt retained only for degraded cases (journal opted off, save failure, stolen lock). The prompt is scaffolding with a defined demolition condition; this paragraph is the record of that intent.
- **The protocol waits for story 331's two writers** (story 331, ruling M1). The exit coordinator waits for both the save writer and the checkpoint writer before RELEASE and HIDE, so story 331's `daw-exit-write-wait` shutdown hook finds nothing to wait for at these exits. It keeps that hook, its 30 s limit and its two log lines unchanged as the backstop for exits that bypass the coordinator: Ctrl+C, SIGTERM, `System.exit`, the OS ending the session, and the application-stop fallback after HIDE. It never runs its protocol from the hook.
- **SEAL waits for the journal and session close** (story 331, ruling M1). The journal-close and session-close threads in the hidden handler stop being fire-and-forget: SEAL waits for them before HIDE.
- **A way out of a save to a hung volume** (story 331, ruling M1 and ruling G's items for this story). An exit stuck behind a save to a hung volume offers a way to quit anyway, and says the save may not land. A door — New, Open, Import, Restore from Archive, a Hub or Welcome open, a snapshot restore — waiting behind such a save offers a way to stop waiting, which leaves the open project as it is.
- **One checkpoint writer per folder, and a `stop()` that does not hold the switch** (story 331, rulings G5 and J3). Today one serial checkpoint writer serves every project: while a write into project A's folder hangs, project B's seeding and checkpoints wait behind it, B's countdown gets no re-arm and each Ctrl+S in B waits 5 s for its checkpoint (J3), and `CheckpointManager.stop()`, called on the FX thread when a project is replaced, waits up to 5 s for the ended generation's jobs (G5). There is one serial checkpoint writer per checkpoint folder, keyed by the folder's identity rather than its path string (a mapped drive and its UNC path can name one folder): B never waits on A, and reopening the same folder queues behind its own write. `stop()`'s bounded wait then covers only a job that has claimed its write — a queued or unclaimed job can never write after the end — and the FX thread no longer waits in it.
- **Nothing of this session writes or deletes in a folder after its lock is released** (story 331's lock hand-off). Today three things can: a head save already past its last check when the project is closed or switched still finishes into that folder (`ProjectManager`'s class note); a prune delete decided just before `stop()`'s bound ran out may be issued after `stop()` returns (`CheckpointManager`'s class note); and `ProjectLockManager.heartbeat()`, which is not synchronized, can publish `.project.lock` again after `release()` deleted it — `release()` stops the heartbeat with `cancel(false)`, which does not wait for one already running — leaving a lock with a fresh `lastSeenAt` that this session then meets as a conflict when it reopens the folder. RELEASE comes only after each of these has finished.
- **A first save's location prompt is a pending switch** (story 331, ruling L4). Ctrl+S on a project never saved takes the open project (`ProjectLifecycleController.saveOpenProject`) before its location chooser opens, and a snapshot restore made while the chooser is open then has the replaced project saved into the new folder. The prompt counts as a pending switch, as story 331's door dialogs do, or the project is taken after it.
- **New and Open do their disk work off the FX thread** (story 331's known limit; Persistence Integrity book §6.1). `ProjectManager.createProject` — called on the FX thread by New and by a first save — creates the folder, writes the metadata file and takes the lock there, and the open path takes the lock and reads `project.daw` on the FX thread (`ProjectManager.openProject`, from `loadProjectFromPath`); both run on a worker.
- **Story 331's lock-loss outcome opens the Save-As flow** (story 331, ruling G13 #6). `ProjectManager.save` completes `SaveOutcome.Failed` with the `LockStolenException` as its cause, and `ProjectLifecycleController` shows `Save failed: the project was taken over by <user> on <host> (process <pid>) — nothing was written`, with no Retry; this story's blocking Save-As flow takes the place of that ERROR, on Ctrl+S and in the exit FLUSH.

## Goals — Tests

- **Close-guard test**: closing via [X] with unsaved changes shows the prompt; *Cancel* aborts (window stays open, project untouched); *Discard and close* exits without a save; *Save and close* produces exactly **one** atomic head write (the story-331 canonical save), then exits.
- **Lock-lifecycle test**: after a clean exit the lock file is gone and the journal is sealed — the next launch's recovery gate (story 332) classifies the project as clean and opens plainly.
- **One-protocol test**: `File ▸ Exit`, `File ▸ Close Project`, and the window close button all drive the same coordinator; the protocol's steps execute in §5.4 order exactly once, and `setOnHidden` disposal runs after RELEASE, never without the protocol having run.
- **Stolen-lock test**: steal the lock, then exit → the blocking Save-As flow appears with a pre-filled sibling path and preserves the work to the new location; no generic "Save failed" toast; the same typed path fires on a plain Ctrl+S under a stolen lock.
- **Menu-existence test**: `File ▸ Save As…`, `File ▸ Close Project`, and `File ▸ Exit` exist and land on live handlers (feeds Book 5's story-345 menu-truth conformance).
- **Veto test**: with the guard's *Cancel* chosen, no FLUSH/SEAL/RELEASE step has run — the session continues exactly as before the close request — except that a recording the take rule stopped stays stopped.
- **Take-at-exit test** (story 323 hand-off): with a take recording, and again with its Stop pending (the take still being written: its capture thread not terminated yet, or the FX turn that publishes it not run yet), each door of the one-protocol goal — the window [X], `File ▸ Exit`, `File ▸ Close Project`, the application-stop fallback and workspace switch — either runs no FLUSH, SEAL, RELEASE or HIDE step until the FX turn that publishes the take has run (`isTakeBeingWritten()` false), or is refused with text worded for an exit (the application-stop fallback, which runs once the stage has hidden and so can neither refuse nor hold off HIDE, runs no FLUSH, SEAL or RELEASE step until then); and a take the guard stopped or waited out is in `project.daw` after the FLUSH of *Save and close*.
- **Exit-after-save test** (story 331, ruling M1): Ctrl+S, then [X], and again via File ▸ Exit and File ▸ Close Project. `project.daw` equals that capture. Its post-save checkpoint was written, or the save writer's 5 s wait for it ran out (ruling J3). HIDE happens only after both. Past 500 ms the still-open window shows "◐ Saving project…". A failed save shows its ERROR in that window, and the exit does not proceed on its own (ruling G1 (3)).
- **Hung-save test** (story 331, ruling M1 and ruling G's items for this story): with a save held at its write, an exit offers a way to quit anyway that says the save may not land, and a door offers a way to stop waiting that leaves the open project as it is.
- **Per-folder writer test** (story 331, rulings G5 and J3): with a checkpoint write held in project A's folder, a switch to B returns without waiting on the FX thread; B's checkpoints are seeded, its countdown is armed and a Ctrl+S in B completes `Saved` naming its checkpoint while A's write is still held; reopening A queues behind A's write.
- **Lock hand-off test** (story 331's lock hand-off; rulings F9 and G5): with a head write held past its last check, a prune delete decided just before `stop()`'s bound, and a heartbeat held inside its write, a switch releases the old folder's lock only after all three have finished; afterwards no file in that folder changes and no `.project.lock` is left in it.
- **First-save prompt test** (story 331, ruling L4): Ctrl+S on a project never saved, then a snapshot restore while its location chooser is open: the replaced project is never written into the new folder.
- **Off-FX test** (story 331's known limit): New, a first save and File ▸ Open make no file-system call on the FX thread.

## Technical Notes

- Implements **Stage 5 — The App-Exit Protocol: Close Guard, Save As, Lock Lifecycle** of `docs/design/PERSISTENCE_INTEGRITY_DESIGN_BOOK.md` (§2.7 exit-is-a-protocol, §4.8 exit coordinator, §5.4 ordered protocol + maturity rule, §3.2 seal write side).
- Files: a new exit coordinator in `daw-app`; `MainController.java:1007` (`setOnHidden` stays dispose-only, sequenced after the protocol) and the primary stage gains its `setOnCloseRequest` (the floating-panel handler at `:3579` shows the existing idiom); `DawApplication.java:98` (application-stop fallback routes through the coordinator before bus/dispatcher teardown); `ProjectManager.java:339-359` (`closeProject` gains its first production caller) and `:346-349` (swallow assumption becomes true); `ProjectLifecycleController.java:813` (guard prompt reused), `:370-376` (typed `LockStolenException` handling replaces the generic catch); `MenuConstructionService.java:141-182` (three new File items); `LockStolenException.java:6-11` (the contract finally honoured); `LockStatusIndicator.java:110-111` (its instruction becomes true — and per book §7.3, fix its inline-hex token violation in passing while touching it).
- Story 323 hand-off (a take recording or still being written at exit): the GUARD step's take rule is binding; how the guard reads its two facts is not. `TransportController.isRecordingInFlight()` and `isTakeBeingWritten()` are package-private, and `ProjectLifecycleController` reads them through the checks `MainController` feeds it (`setRecordingInFlightCheck`, `setTakeBeingWrittenCheck`). `confirmProjectMayClose()` is the in-app doors' gate: it refuses while a recording is in flight (`PROJECT_CHANGE_WHILE_RECORDING_MESSAGE`), where the take rule above stops the recording instead, and while a take is being written (`PROJECT_CHANGE_WHILE_WRITING_MESSAGE`); neither message is worded for an exit, and the guard need not call it. A take still being written has not marked the project dirty; a take that published a clip has, as has a MIDI take that recorded a note (story 323, Copilot review round 4). Since story 323's Copilot review round 5, `isRecordingInFlight()` is also true while an audio take is being prepared (PREPARING: from Record until capture begins, while the take directory is allocated and the take's files are created), a Stop then cancels the take, and the cancelled start counts as being written (`isTakeBeingWritten()`) until the removal of its files has run, whether or not everything could be removed; and no Stop publishes its take at once — the take is published on a later FX turn, once its capture thread has terminated. `File ▸ Close Project` must also retire the outgoing `TransportController` — `MainController.createTransportController()` retires the controller it replaces (`TransportController.retire()`) — or do the equivalent, so that a take whose Stop is still pending is not published into the closed project when its capture thread terminates.
- Cross-refs: **story 331** (Stage 3 — the flush is its canonical save; strip progress affordance), **story 332** (Stage 4 — seal reader; clean exits also stop feeding `ProjectHealthScanner` phantom stale locks, sharpening its detection), **story 298** (journal machinery the SEAL step drives), **story 345** (Book 5 menu truth), **story 339** (Book 4 dialog conformance), `PROJECT_MANAGER_DESIGN_BOOK.md` §2.5/§8 (the reconciled end-state), `CONTROL_SYNCHRONIZATION_DESIGN_BOOK.md` (`ProjectVM.dirty` as the guard's input; §2.8 input-source irrelevance).
- Rejections bound here: book §9.9 (exit paths that bypass the protocol), §9.14 (swallowing a typed exception into its supertype's generic handler).
- Threading per book §6.1: the FX thread never blocks on the exit flush — the protocol shows progress rather than freezing; each step publishes its outcome before the terminal HIDE state so observers never see a half-closed world.

## Resolution

Quitting is no longer a data-loss event. Every close of the open project goes through one coordinator, `ExitCoordinator`, and one protocol of eight steps (`ExitStep`): INTERCEPT, GUARD, FLUSH, CLOSING_CHECKPOINT, SEAL, RELEASE, DISPOSE and HIDE. The window's close box and File ▸ Exit (Shortcut+Q) run it; File ▸ Close Project (Shortcut+Shift+W) runs it up to RELEASE and then installs a fresh Untitled project, with no DISPOSE and no HIDE, and the close-then-continue primitive closes as Close Project does, then installs the Untitled project without the Welcome window and hands its caller one outcome. The close box is consumed until the protocol decides. A recording is stopped only after a confirmation whose default keeps recording, a take still being written is waited out, and unsaved changes are asked about: Save and close, Discard and close, or Cancel. A clean exit saves through story 331's one canonical save, writes a closing checkpoint where the journal needs one, seals the journal, releases the lock once nothing of this session can still write in the folder, and only then disposes the window and ends JavaFX, so the next open is plain. An application stop that the protocol did not start runs the application-stop fallback, which asks nothing and never writes `project.daw` (ruling R4). File ▸ Save As… copies the open project into a new, self-contained folder and opens the copy in the same window. A lock another session took opens a blocking takeover dialog in place of story 331's ERROR. Every Goal is met as follows; the Verification maps each Goals — Tests bullet to its tests.

**The Goals.**

- **G1, INTERCEPT.** `ExitCoordinator.installOn(Stage)` adds a `WindowEvent.WINDOW_CLOSE_REQUEST` filter to the primary stage, which consumes the event and calls `request(new CloseDoor.WindowClose())`, and nothing else. `MainController.installPrimaryStage` installs it before `DawApplication` shows the stage, and the primary stage has no hidden handler.
- **G2, GUARD.** `ExitCoordinator.guard` applies the take rule first (ruling R1). A recording in flight — RECORDING, PREPARING, COUNT_IN or a live MIDI recorder (`TakeFacts`) — is stopped only after the “Recording in Progress” confirmation, and a take still being written is waited out; no door refuses for the take. Only then does `decideAfterTheWaits` read the unsaved changes and ask ruling R2's prompt through `ProjectClosePrompts.askBeforeClosing`.
- **G3, FLUSH.** `ExitCoordinator.flush` saves through `ProjectLifecycleController.saveBeforeClosing`, which runs `saveOpenProject` and `submitSave`, the path Ctrl+S takes: one atomic head write off the FX thread, with `◐ Saving project…` on the strip past 500 ms.
- **G4, SEAL.** Before SEAL, CLOSING_CHECKPOINT writes a closing checkpoint (`CheckpointOrigin.CLOSING`) where the journal needs one (ruling 1's closing checkpoint, ruling R3), and SEAL starts only once that checkpoint's marker has reached the journal. `ProjectFolderCloser.seal` then ends the journal on `daw-journal-seal` through `SessionJournalEnding`, which writes story 332's session seal and closes the session manifest, naming the segment the seal landed in after the marker's rotation.
- **G5, RELEASE.** `ProjectFolderCloser.release` calls `ProjectManager.closeProject()`, which no longer saves (ruling R9 splits the release from the save): it ends the generation's checkpoints and returns at once, and the lock file is deleted on `daw-lease-retire` once the work owed in the folder has ended. An exit waits for that release; Close Project does not (ruling 4 Q1).
- **G6, DISPOSE.** DISPOSE is `MainController.disposeWindowLifetime()`, which only the coordinator calls (`MainController.createExitCoordinator` hands it over): after RELEASE, or once Quit anyway has skipped the steps not yet begun. It hands the audio engine's stop to the `daw-engine-shutdown` thread, and HIDE waits for that stop at most 5 seconds (ruling 2 OQ-3).
- **G7, HIDE.** `ExitCoordinator.hide` publishes HIDE, marks the protocol complete and then runs the terminal exit, `Platform::exit`, its only call in the application. Every step publishes its outcome through the coordinator's `publish` before the terminal state, and Close Project publishes RELEASE before it installs the Untitled project.
- **G8, one protocol, every door.** File ▸ Exit and File ▸ Close Project — from the menu, the keyboard or the Command Palette — reach `ExitCoordinator.request` through one host method each, as the close box does through its filter. `Application.stop()` reaches `ExitCoordinator.applicationStopping()`, which runs the application-stop fallback when the protocol has not run (ruling R4). `closeOpenProjectThenContinue` is the workspace switch's primitive: Close Project's protocol, which hands its caller one outcome and runs no HIDE; it has no production caller yet (Known limits). No secondary window starts the exit (ruling R12 #14).
- **G9, project-level Save As.** File ▸ Save As… (`ProjectLifecycleController.onSaveProjectAs`, then `SaveAsFlow`) copies the open project into a new folder, pre-filled `<folder name> copy` beside the original (ruling R6). The copy becomes the open project in the same window, with its undo history, and the original is closed as Discard and close closes it (ruling R5).
- **G10, typed stolen-lock handling.** `LockStolenException` is caught as itself: from a save's `SaveOutcome.Failed` cause (`ProjectLifecycleController.reportSaveFailed`, before any toast) and in FLUSH (`ProjectLifecycleController.FlushResult.LockLost`). It opens ruling R7's blocking “Project Taken Over” dialog, whose default, Save As…, opens `SaveAsFlow` pre-filled `<folder name>-takeover-<yyyyMMdd-HHmmss>`. `closeProject()` saves nothing, so nothing is left to swallow. A save that meets the loss while a close is pending shows no dialog of its own (the takeover line below).
- **G11, the maturity rule.** The prompt ships unconditionally (ruling R11), and no code tests journal health to skip it. The demolition condition stays recorded in the Goals paragraph and in the Persistence Integrity book's §5.4; ruling R11 adds that it also needs story 387 and an Undo Close (Known limits).
- **G12, the protocol waits for both writers.** Before SEAL an exit waits for the saves queued before it (`ProjectLifecycleController.whenItsSavesHaveReported`) and for the open generation's checkpoint work (`ProjectManager.whenOpenGenerationIdle`); before RELEASE an exit's closer waits for every writer (`ProjectManager.whenWritersIdle`). Story 331's `daw-exit-write-wait` hook, its 30 seconds (`ProjectManager.EXIT_WRITE_WAIT`) and its two log lines stay unchanged as the backstop, and the hook runs no protocol.
- **G13, SEAL waits for the journal and the session.** The hidden handler and its fire-and-forget journal and session threads are gone. SEAL's journal end runs on its worker, RELEASE starts only from its end (`ProjectFolderCloser.journalEndFinished`), and the window's disposal does no journal or session work.
- **G14, a way out of a hung save.** An exit's closing surface (`ClosingProgressDialog`, past 500 ms) offers Don't quit; after the journal's detach the button is disabled for 10 seconds (the studio engineer's answer Q4), and it is not shown while the audio engine stops or, unless the exit upgraded a Close Project, once the release began. Once it has waited 10 seconds on disk work it adds a note on what is still being written — while the save has not finished, that the save may not land — and Quit anyway (`ExitCoordinator.quitAnyway`), which skips the steps not yet begun and leaves the lock, as after a crash (ruling R8). A door waiting behind a save shows, after 10 seconds, a WARNING with Stop waiting, which cancels the door and leaves the open project as it is (`ProjectLifecycleController.stopWaiting`). Close Project and the primitive offer Keep project open in place of Don't quit.
- **G15, one checkpoint writer per folder.** `CheckpointManager` keeps one serial writer per folder, keyed by the folder's identity (`FolderFingerprint`), so a local folder and its UNC name share one writer. `stop()` returns at once, with a stage that completes once the work already claimed has landed, and a queued job that no writer claimed never writes.
- **G16, nothing written after the release.** A lease is retired only after the saves queued before the close, a head write past its last check, the claimed checkpoint work (a prune's deletes among it) and the caller's own owed work have ended. `ProjectLockManager.heartbeat()` and `release()` share one monitor, so the release waits for a heartbeat inside its write, and nothing writes `.project.lock` again after its delete.
- **G17, the first save's location prompt.** A first save's chooser is a pending switch (`whileItsDialogIsOpen(SAVE_PROJECT_DOOR, …)`), and so is the creation of its folder off the FX thread (`PendingSwitch.CreatingFolder`). The project is captured only once the folder exists (`ProjectLifecycleController.saveIntoANewFolder`), so a snapshot restore meanwhile is refused and nothing of it is written into the new folder.
- **G18, New and Open off the FX thread.** `createProject` runs on `daw-project-create` for New and for a first save, and the gated open's `prepareOpen` reads and locks the project on a worker. Production always installs the recovery gate; the ungated branch, which only test fixtures reach, still opens on the FX thread (Known limits).
- **G19, story 331's lock-loss outcome.** For the open project the takeover dialog takes the place of the ERROR `Save failed: the project was taken over by <user> on <host> (process <pid>) — nothing was written`, on Ctrl+S and in the exit's FLUSH. The text stays in `saveFailureMessage` for a save of a project no longer open, as `Saving <folder> failed: …`.

**The Technical Notes' obligations.**

- **The lock indicator.** `LockStatusIndicator.applyStatus` sets the style classes `lock-held`, `lock-read-only` and `lock-stolen` over the role tokens `-ok`, `-warn`, `-danger` and `-text-on-accent`, with no `setStyle`. The stolen state's tooltip is `lock.tooltip.stolen`: “Another session has taken over this project's lock. Use File ▸ Save As… to keep your changes in a new project.” (ruling R7).
- **`LockStolenException`'s contract.** Its Javadoc now states the contract the code honours: the exception is caught as itself, and a blocking takeover dialog opens.
- **`closeProject()`'s first production caller.** The closer's RELEASE is one of its production callers, and it never saves, so there is nothing to swallow (ruling R9); a steal at FLUSH reaches ruling R7's dialog before RELEASE.
- **Close Project retires the outgoing `TransportController`.** Close Project installs its Untitled project through the window's rebuild (`installUntitledAfterClose`, `installFreshUntitledProject`, `MainController.handleProjectRebuild`), whose `createTransportController()` retires the controller it replaces. This is pinned by source only, because `MainController` is never FXML-loaded in tests (Known limits). GUARD waits the take out before RELEASE and the install, so a pending take is never published into the closed project.
- **Threading.** The FX thread never blocks on a close: every wait is a completion stage followed by a post, and the progress surface shows the step. The application stop's waits are one-shot nested event loops, or bounded waits off the FX thread on `daw-exit-fallback`. Each step's outcome is published before HIDE.
- **The rejections bound here.** §9.9: the terminal exit is the one `Platform::exit`, `DawApplication` has no `WINDOW_HIDDEN` handler, and secondary windows never start the exit. §9.14: `LockStolenException` is never caught by an `IOException` handler first.

**Corrections to the story text.** The Motivation records what the code did when the story began, and the Goals, Goals — Tests and Technical Notes record what it set out to do; they are kept as written. Where their wording is now false against the code, each line below gives what is true, by symbol rather than by line number:

1. Motivation, “Nothing can veto a close”: the close request is consumed (`ExitCoordinator.installOn`), and GUARD's Cancel ends the close with nothing changed but a recording the take rule stopped, which stays stopped.

What the rulings added beyond the Goals:

- **The take rule (ruling R1).** The close box, File ▸ Exit, Close Project and the primitive first ask “Recording in Progress”, with Stop the take and close, and Keep recording, which is the default and is what Escape and the dialog's close box mean. On consent the take is stopped and then waited out; past 500 ms the strip shows `◐ Finishing take…` and the closing surface opens with Don't quit (Keep project open for Close Project and the primitive), and never Quit anyway (ruling R12 #9). The application-stop fallback cannot ask: it stops the transport at once and waits for the take for at most 30 seconds.
- **The prompt (ruling R2).** “Unsaved Changes”, `Save the changes to “<name>” before closing?`, with Save and close (the default), Discard and close (set apart, never the default) and Cancel (Escape and the close box). Its content says what a discard leaves. A head failure that still stands puts `The last save failed (<cause>).` first, and a take that the close stopped or waited out, and that published a clip, adds `Your changes include the take you just recorded.` A project never saved offers Save and close…, which opens the first save's chooser; a read-only open says so in its header and content, and its Save and close… opens Save As pre-filled `<folder name> copy`. With no unsaved changes nothing is asked. While the close waits on disk work, until it ends or the window hides, every window that was showing is input-inert (`WindowInputFence`, rulings R2 and R12 #4), and playback is stopped before the capture.
- **The closing checkpoint (ruling 1; ruling R3).** One checkpoint of the live project, of origin `CLOSING`, captured on the FX thread after the decision and the take rule, with playback stopped. It is written when the journal is open and holds a record that no capture covers (trigger (i)), after a Discard whose revision is not yet checkpointed (ii), and by the fallback for unsaved changes (iii); never for a read-only open, a lost lock, a project with no folder, or when checkpoints are not running. Discard and close therefore seals the journal as usual, the next open is plain, and the discarded work stays in that checkpoint, logged at INFO as `Discarded changes of “<name>” were kept in checkpoint <file>.` A closing checkpoint that fails does not stop the exit.
- **The application-stop fallback (ruling R4; ruling 4 Q6).** When the exit protocol has not run, `Application.stop()` runs the fallback. It asks nothing, shows nothing of its own and never writes `project.daw`. Its steps:
  1. Stop the transport at once: a recording, which it cannot ask about (R1), and playback alike.
  2. Wait for the take (at most 30 seconds, ruling R1), then for the save writer and the checkpoint writer.
  3. FLUSH means the closing checkpoint only, under triggers (i) and (iii).
  4. SEAL only when nothing is unsaved; with unsaved changes the journal is drained and left unsealed, so the next open offers recovery from that closing checkpoint. When no journal is open for the project (journaling off, paused, or not yet started after a first save), the closing checkpoint is only kept, among the project's checkpoints, and the next open does not offer to recover those changes (L7b; category 1).
  5. RELEASE once the writers are idle.
  6. DISPOSE, then the event bus and the FX dispatcher are torn down, last.

  Every wait shares one 30-second deadline from the stop; past it the steps left are skipped, as after a crash. DISPOSE waits for the audio engine's stop at most 15 seconds (the studio engineer's stage-8 S1). A run the user had already decided keeps its decision's row and joins the steps it began; an undecided run is dropped (ruling 4 Q6.2). Its log is its only record (ruling 4 Q6.3, as the studio engineer's final rulings F5 and F4 amend L1 and L7b, and F2 adds L8c).
- **Save As (ruling R5).** The capture is taken on the FX thread when Save As starts; the plan, the free-space check, the copy and the publish run on a worker behind a modal progress dialog with a determinate bar and Cancel, and from the head's write on there is no Cancel. The copy holds a fresh render of `project.daw`, written last, at the current schema; `audio/` (but for takes still streaming, temps and `.part` files), `assets/` and `snapshots/` whole; and every other file the capture references, at the same relative path. Left out are `checkpoints/`, `journal/`, `sessions/`, `.project.lock` with its audit log `project.log`, a restored archive's header `archive.properties`, `archives/` — the folder the disk-usage view counts as the original's packaged archives — the head's backups (`project.daw.*.bak`), temps, and unknown top-level entries, whose number is logged at INFO. A new target is staged beside it and published by one rename; an existing empty folder is written into, `project.daw` last. Then the copy becomes the open project with its own lock, journal session, checkpoints and session manifest and an entry in Recent Projects, and the original is closed as Discard and close closes it, its `project.daw` left at its last save. A copy whose lock another session takes before it opens here opens as a project whose lock was taken over, with one ERROR (ruling 3 Q1). When the original's close is still running after 10 seconds, Continue opens the copy without a journal for this session (ruling 2 OQ-1). At a close (R2's read-only path, R7's Save As…) the copy is published and recorded in Recent Projects but not opened, and the close goes on.
- **The pre-fill (ruling R6).** The parent is the original's parent: `<folder name> copy`, or `<folder name>-takeover-<yyyyMMdd-HHmmss>` after a takeover, with the first free name (` 2`, ` 3`, …) when that name is taken. A project never saved is pre-filled with its name, sanitised for a folder, in the workspace root. When the original's parent cannot be written or does not answer within 2 seconds, the same pre-filled name is offered in the workspace root instead, and in the chooser's own starting folder when the workspace root fails that check too. An existing target that is not empty, and a target inside the project's own folder, are refused with a modal warning, and the chooser opens again (the studio engineer's answer Q6).
- **The takeover (ruling R7).** “Project Taken Over” names the holder, or says that the lock was removed. On Ctrl+S it offers Save As… (the default) and Not now (Escape); Not now leaves the project dirty with story 331's `⚠ Save failed · last saved HH:mm` and `⚠ Lock stolen`, and the next Ctrl+S asks again. At a close it offers Save As…, Quit without saving (Close without saving for Close Project) and Cancel (Escape); quitting without saving writes no head, checkpoint, seal or session manifest into the folder and leaves its lock to the other session (its journal still drains into this session's own segment there; Known limits).
  A save that meets a lock another session took while a close is pending shows no takeover dialog of its own: an interactive close meets the loss itself — at GUARD when it is already known, or at its FLUSH — in the takeover dialog whose Save As can run (ruling R7); after an exit's HIDE, or while the application-stop fallback runs, nothing asks (ruling 4 Q6.2 item 4). A project kept open shows the loss in its lock cell, and its next save asks again.
- **The hung-save escape (ruling R8).** An exit's surface is `Closing “<name>”`, with the step (`Finishing take…`, `Finishing <door>…`, `Saving project…`, `Writing checkpoint…`, `Closing journal…`, `Finishing disk writes…`, `Stopping audio…`) and Don't quit; from 10 seconds into a wait on disk work its note follows what is still running, and Quit anyway joins it (ruling 4 Q1). After the journal's detach the keep button is disabled for 10 seconds, and a keep after the detach leaves the project open with journaling paused until it is reopened (the studio engineer's answer Q4). The door's WARNING reads `Still saving “<name>” after 10 seconds — the disk may not be responding. <door> continues when the save finishes; stop waiting to keep the open project as it is.`
- **An exit after a failed save (ruling R9, as ruling 4 Q5 (vi) refines it).** When FLUSH, or a save queued before the close, failed and a head failure still stands once every queued save has reported, the close stops: story 331's ERROR shows in the live window, nothing is sealed or released, and the project stays dirty; the next close asks again, with `The last save failed (<cause>).` first. When a later save of the same project landed, the close goes on and logs at INFO `A save of “<name>” queued before the close failed, and a later one succeeded; the close goes on.` A lost lock and a read-only open have their own flows (R7, R2).
- **File ▸ Close Project (ruling R10).** After the close the window is as at launch: a fresh in-memory Untitled project, installed through the replacement New performs (`installFreshUntitledProject`), with the Welcome window over it once the run has ended. The transport is retired and recreated, the mixer is the Untitled default, the closed project's plug-ins are disposed and their editors closed, and the undo history and the meters are cleared; the audio engine and the device stay open.
  What stays: device settings and the theme. The dock layout and its named layouts belong to the project (DawProject.layoutJson) and reset to the built-in Default, as New resets them.
  Every door that replaces the open project clears the selection — the time range and the clip selection — when the window installs the new project (MainController.replacePluginProject), so no edit command acts on a track or clip of a project the window no longer shows (ruling R10, “Undo history and selection are cleared”).
  Close Project is enabled while a project folder is open, writable or read-only, or while the in-memory project has unsaved changes. On a pristine Untitled project the menu item is disabled, the Command Palette's entry says `Nothing to close — this project has never been saved and has no changes.` (ruling 2 OQ-2), and the shortcut does nothing (the studio engineer's stage-7 N1).
- **An exit while another switch runs (ruling R12 #8).** A door waiting for a save is replaced by the exit, which waits for the same save; an archive extraction or a session recovery is waited for under the closing surface.
  A switch an exit waited for (an archive restore, a session recovery) is not opened when it finishes: its work stays done, a WARNING says what was done and to open it later with File ▸ Open Project…, and the exit goes on.
- **An exit during an installation (the studio engineer's stage-7 ruling 1).**
  While a project is being installed, Ctrl+Q and the window's close box start the exit, which waits for the installation under the closing surface; the File menu is disabled with the rest of the window, and Close Project and Save As do nothing until the installation ends.

Two deviations from the rulings, both accepted:

- D15 (ruling 4 Q6.2 item 1, “closes its dialogs”): the application-stop fallback closes only the close's own surface; a prompt or a native file chooser that is up stays up, its answer fenced, because a native chooser cannot be closed from Java. Accepted as Resolution category 4 (the studio engineer's stage-8 N1).
- D16 (ruling 4 Q6.2 item 1, “a takeover Save As” among the joined decisions): the application-stop fallback does not join a close's own Save As — a takeover Save As, or a read-only open's Save and close… — whose chooser is open or whose copy is still running. That copy runs under the close's own pending switch and registers none, so the fallback neither waits for it nor stands down for it (no L11): it closes the original by the decision's row — a lost lock's or a read-only open's, no closing checkpoint — and logs L8's Save As variant (L8c). The end of the process may cut the copy and leave its staging folder. Accepted as Resolution categories 4 and 5; owner: the future story “the application-stop fallback for pending switches and open prompts” (story 398).

*An end of the application the protocol did not run*

- **Category 1, an end of JavaFX the protocol did not start.** An end of JavaFX that the exit protocol did not start — another caller ending JavaFX, or its last window closing some other way — asks nothing, shows nothing of its own and never writes project.daw: unsaved changes are kept in a closing checkpoint, which the next open offers to recover when the project's journal was open and only keeps when it was not (journaling off, paused, or not yet started after a first save). They are lost whenever no closing checkpoint can be written for them — for example under a lock another session took, in a read-only open or in a project never saved — unless a Save As chosen before the stop finished its copy first; and they are lost when the close is skipped at its 30-second bound, as after a crash. A window still up stays inert until the application ends. Owner: none (by ruling R4).
- **Category 2, an end of the process that bypasses JavaFX (ruling R12 #15).** An end of the process that does not pass through JavaFX — Task Manager's End task, a kill, or an OS session end that ends the process directly — runs neither the exit protocol nor the fallback; only the shutdown hook waits for the writers, when the JVM runs it. The next open offers recovery from the unsealed journal and meets the lock left behind (best effort). Owner: story 331's M1 limit.
- **Category 3, the audio engine's stop (ruling 2 OQ-3).** The process ends at most 15 seconds after the audio engine's stop began; a driver slower than that is cut, which leaves the device as after a crash, and the log says so. Owner: none; no story unless reported.
- **A driver that never returns.** A driver that never returns from its stream close holds up the ends of the render queue's workers, the plug-in supervisor, the backup scheduler and the disk scanner, which the end of the process cuts; the render queue's state was persisted before the stop. Owner: none; no story unless reported.
- **Category 4, prompts open at the stop.** A prompt or file chooser that a close had open when another caller ended JavaFX stays open until the application ends, and its answer decides nothing: the application-stop fallback closes the project its own way, without saving. A Save As chosen before the stop whose target is refused while the fallback waits asks again — its warning, then its chooser — and the application cannot end until that is answered; answered after the 30-second bound, the rest of the close is skipped, as after a crash. Owner: future story 398, the application-stop fallback for pending switches and open prompts.
- **Category 5, switches under way at the stop.** A switch still under way when another caller ends JavaFX — a Save As (a close's own Save As copy among them), an installation, an archive extraction, a session recovery or a first save's folder creation — is not waited for, and the end of the process cuts it, which may leave a folder partly written or still locked. While a Save As or an installation is replacing the open project, the application-stop fallback also closes nothing, as after a crash. A close's own Save As copy replaces nothing, so the fallback closes the original as it closes a project whose lock another session took or that is open read-only, and its log says the copy keeps the changes only if it finished. Owner: future story 398, whose scope is a bounded wait, on the one deadline, for a switch under way, as an exit's GUARD waits for one; a close's own Save As joined, with its outcome logged in place of L8c; prompts and choosers fenced or closed; and no modal opened inside `Application.stop()`'s waits.
- **A take sealed but never published** (the fallback with the toolkit gone, or its 30 s bound) stays unreferenced in `audio/`; TakeRecovery skips sealed takes. R4/R12 #10. Owner: future story 402, every take left unpublished on disk is offered at the next open.
