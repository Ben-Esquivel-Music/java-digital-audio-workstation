# The App-Exit Protocol: Close Guard, Save As, Lock Lifecycle

## Motivation

Quitting the application is a data-loss event. There is no exit protocol at all:

- **Nothing can veto a close.** The only primary-stage lifecycle hook is `setOnHidden` (`MainController.java:1007`) — it disposes view-models and timers *after* the window is gone and cannot veto anything. The only `setOnCloseRequest` in the app is on floating dock-panel stages (`MainController.java:3579`); `DawApplication`'s `WINDOW_HIDDEN` handler closes the event bus and dispatcher only (`DawApplication.java:98`).
- **The close sequence is never run.** `ProjectManager.closeProject()` — the final save, checkpoint-scheduler stop, and **lock release** (`ProjectManager.java:339-359`) — has zero production callers; only tests invoke it. Every real exit leaves the lock file behind, which feeds the crash-detection staleness heuristic garbage on the next launch.
- **No guard, no menu items.** `confirmDiscardUnsavedChanges` (`ProjectLifecycleController.java:813`) is invoked only from New/Open/Restore/Recover — never from any exit. The File menu (`MenuConstructionService.java:141-182`) contains no Exit item, no Close Project, and no project-level Save As.
- **The stolen-lock contract is documented and abandoned.** `LockStolenException`'s javadoc says the UI should prompt Save As (`LockStolenException.java:6-11`); the save path catches it as a generic `IOException` → "Save failed" toast (`ProjectLifecycleController.java:370-376`); `closeProject` swallows it assuming "the UI is expected to have already prompted Save As" (`ProjectManager.java:346-349`) — nothing does. The lock indicator even *tells the user* to "Use Save As to preserve your changes" (`LockStatusIndicator.java:110-111`) — an instruction to use a feature that does not exist.

For a studio engineer: closing the window at the end of a session silently discards every unsaved change, leaks the project lock, and — if another session stole the lock — the one documented escape hatch is a lie printed in the UI.

## Goals

- **An exit coordinator** (design book §4.8) owning the ordered §5.4 protocol, with the close request **consumed** until the protocol decides:
  1. **INTERCEPT** — primary-stage close-request handler consumed; protocol begins (never `setOnHidden` — that cannot veto).
  2. **GUARD** — dirty check (`ProjectVM.dirty` per the Control Synchronization book) → prompt: *Save and close* / *Discard and close* / *Cancel* (the veto point). **The take rule (story 323)** comes before the dirty check, because the capture-flush thread is a daemon that exit can end before the seal. The guard consults the transport for a recording still in flight (`TransportController.isRecordingInFlight()`) and for a take still being written to disk (`TransportController.isTakeBeingWritten()`, the FINALIZING state of `RECORDING_RELIABILITY_DESIGN_BOOK.md` §5.2) — the two checks `ProjectLifecycleController.confirmProjectMayClose()` makes for the in-app doors, which it refuses while either holds. A recording still in flight is stopped first — an audio take still being prepared counts as one, and a Stop cancels it (story 323, Copilot review round 5); after that Stop an audio take is still being written until a later FX turn publishes it, however fast its seal, and a cancelled start counts as being written until the removal of its files has run. A take still being written is either refused, with text worded for an exit — not `PROJECT_CHANGE_WHILE_WRITING_MESSAGE`, which speaks of the open project being replaced — or waited out, showing progress, until `isTakeBeingWritten()` is false (the FX turn that publishes the take has run: its clips, if any, published, or its failure reported; or the removal of a cancelled or failed start's files has run); only then does the guard make the unsaved-changes decision. Publishing a take marks the project dirty (story 323, Copilot review round 4), so a take published while the guard runs — on the turn after the Stop the guard made, or after the guard waited it out — reaches the unsaved-changes decision as an unsaved change. The prompt is `confirmDiscardUnsavedChanges()` reused or this story's own; nothing requires calling `confirmProjectMayClose()`. When the maturity rule below drops the prompt from this step, the take rule stays.
  3. **FLUSH** — the chosen save runs via the story-331 single canonical save (atomic, off the FX thread, progress in the Session Status Strip if > 500 ms).
  4. **SEAL** — the journal writes and fsyncs the story-332 session seal; the segment rotates.
  5. **RELEASE** — `closeProject()`: checkpoint scheduler stops, lock releases — its first production caller; the lock-file leak ends.
  6. **DISPOSE** — the existing `setOnHidden` work, now guaranteed to run last, never instead of the protocol.
  7. **HIDE** — the stage actually closes; the application exits. Each step publishes its outcome before the terminal state.
- **One protocol, every door**: the window [X], a new `File ▸ Exit`, a new `File ▸ Close Project`, the application-stop fallback, and workspace switch all route through the coordinator; input source is irrelevant past the intent boundary.
- **Project-level `File ▸ Save As`** lands — the command the lock indicator has been advertising.
- **Typed stolen-lock handling**: `LockStolenException` caught as itself, never as `IOException`; during save and during the exit FLUSH it drives a **blocking Save-As flow** (pre-filled sibling path) that preserves the work — never a transient toast, and `closeProject`'s "UI already prompted" assumption becomes true.
- **The maturity rule is carried in this story** (book §5.4, binding): `PROJECT_MANAGER_DESIGN_BOOK.md` §2.5/§8 reject the "Save changes?" modal in favour of autosave + undoable close — an end-state *conditional on trustworthy capture*. Today neither condition holds and the shipping behaviour is silent total loss, so the prompt ships first as the strictly better interim. Once story 332's default-on journal is field-proven healthy, step 2 yields to seal-and-close without interrogation, the prompt retained only for degraded cases (journal opted off, save failure, stolen lock). The prompt is scaffolding with a defined demolition condition; this paragraph is the record of that intent.
- **The protocol waits for story 331's two writers** (story 331, ruling M1). The exit coordinator waits for both the save writer and the checkpoint writer before RELEASE and HIDE, so story 331's `daw-exit-write-wait` shutdown hook finds nothing to wait for at these exits. It keeps that hook, its 30 s limit and its two log lines unchanged as the backstop for exits that bypass the coordinator: Ctrl+C, SIGTERM, `System.exit`, the OS ending the session, and the application-stop fallback after HIDE. It never runs its protocol from the hook.
- **SEAL waits for the journal and session close** (story 331, ruling M1). The journal-close and session-close threads in the hidden handler stop being fire-and-forget: SEAL waits for them before HIDE.
- **A way out of a save to a hung volume** (story 331, ruling M1 and ruling G's items for this story). An exit stuck behind a save to a hung volume offers a way to quit anyway, and says the save may not land. A door — New, Open, Import, Restore from Archive, a Hub or Welcome open, a snapshot restore — waiting behind such a save offers a way to stop waiting, which leaves the open project as it is.
- **One checkpoint writer per folder, and a `stop()` that does not hold the switch** (story 331, rulings G5 and J3). Today one serial checkpoint writer serves every project: while a write into project A's folder hangs, project B's seeding and checkpoints wait behind it, B's countdown gets no re-arm and each Ctrl+S in B waits 5 s for its checkpoint (J3), and `CheckpointManager.stop()`, called on the FX thread when a project is replaced, waits up to 5 s for the ended generation's jobs (G5). There is one serial checkpoint writer per checkpoint folder, keyed by the folder's identity rather than its path string (a mapped drive and its UNC path can name one folder): B never waits on A, and reopening the same folder queues behind its own write. `stop()`'s bounded wait then covers only a job that has claimed its write — a queued or unclaimed job can never write after the end — and the FX thread no longer waits in it.
- **Nothing of this session writes or deletes in a folder after its lock is released** (story 331's lock hand-off). Today three things can: a head save already past its last check when the project is closed or switched still finishes into that folder (`ProjectManager`'s class note); a prune delete decided just before `stop()`'s bound ran out may be issued after `stop()` returns (`CheckpointManager`'s class note); and `ProjectLockManager.heartbeat()`, which is not synchronized, can publish `.project.lock` again after `release()` deleted it — `release()` stops the heartbeat with `cancel(false)`, which does not wait for one already running — leaving a lock with a fresh `lastSeenAt` that this session then meets as a conflict when it reopens the folder. RELEASE comes only after each of these has finished.
- **A first save's location prompt is a pending switch** (story 331, ruling L4). Ctrl+S on a project never saved takes the open project (`ProjectLifecycleController.saveOpenProject`) before its location chooser opens, and a snapshot restore made while the chooser is open then has the replaced project saved into the new folder. The prompt counts as a pending switch, as story 331's door dialogs do, or the project is taken after it.
- **New and Open do their disk work off the FX thread** (story 331's known limit; Persistence Integrity book §6.1). `ProjectManager.createProject` — called on the FX thread by New and by a first save — creates the folder, writes the metadata file and takes the lock there, and the open path takes the lock and reads `project.daw` on the FX thread (`ProjectManager.openProject`, from `loadProjectFromPath`); both run on a worker.
- **Story 331's lock-loss outcome opens the Save-As flow** (story 331, ruling G13 #6). `ProjectManager.save` completes `SaveOutcome.Failed` with the `LockStolenException` as its cause, and `ProjectLifecycleController` shows `Save failed: the project was taken over by <user> on <host> (process <pid>) — nothing was written`, with no Retry; this story's blocking Save-As flow takes the place of that ERROR, on Ctrl+S and in the exit FLUSH.

## Goals — Tests

- **Close-guard test**: closing via [X] with unsaved changes shows the prompt; *Cancel* aborts (window stays open, project untouched); *Discard and close* exits without a save; *Save and close* produces exactly **one** atomic head write (the story-331 canonical save), then exits.
- **Lock-lifecycle test**: after a clean exit the lock file is gone and the journal is sealed — the next launch's recovery gate (story 332) classifies the project as clean and opens plainly.
- **One-protocol test**: `File ▸ Exit`, `File ▸ Close Project`, and the window close button all drive the same coordinator; the protocol's steps execute in §5.4 order exactly once, and `setOnHidden` disposal runs after RELEASE, never without the protocol having run.
- **Stolen-lock test**: steal the lock, then exit → the blocking Save-As flow appears with a pre-filled sibling path and preserves the work to the new location; no generic "Save failed" toast; the same typed path fires on a plain Ctrl+S under a stolen lock.
- **Menu-existence test**: `File ▸ Save As…`, `File ▸ Close Project`, and `File ▸ Exit` exist and land on live handlers (feeds Book 5's story-345 menu-truth conformance).
- **Veto test**: with the guard's *Cancel* chosen, no FLUSH/SEAL/RELEASE step has run — the session continues exactly as before the close request — except that a recording the take rule stopped stays stopped.
- **Take-at-exit test** (story 323 hand-off): with a take recording, and again with its Stop pending (the take still being written: its capture thread not terminated yet, or the FX turn that publishes it not run yet), each door of the one-protocol goal — the window [X], `File ▸ Exit`, `File ▸ Close Project`, the application-stop fallback and workspace switch — either runs no FLUSH, SEAL, RELEASE or HIDE step until the FX turn that publishes the take has run (`isTakeBeingWritten()` false), or is refused with text worded for an exit (the application-stop fallback, which runs once the stage has hidden and so can neither refuse nor hold off HIDE, runs no FLUSH, SEAL or RELEASE step until then); and a take the guard stopped or waited out is in `project.daw` after the FLUSH of *Save and close*.
- **Exit-after-save test** (story 331, ruling M1): Ctrl+S, then [X], and again via File ▸ Exit and File ▸ Close Project. `project.daw` equals that capture. Its post-save checkpoint was written, or the save writer's 5 s wait for it ran out (ruling J3). HIDE happens only after both. Past 500 ms the still-open window shows "◐ Saving project…". A failed save shows its ERROR in that window, and the exit does not proceed on its own (ruling G1 (3)).
- **Hung-save test** (story 331, ruling M1 and ruling G's items for this story): with a save held at its write, an exit offers a way to quit anyway that says the save may not land, and a door offers a way to stop waiting that leaves the open project as it is.
- **Per-folder writer test** (story 331, rulings G5 and J3): with a checkpoint write held in project A's folder, a switch to B returns without waiting on the FX thread; B's checkpoints are seeded, its countdown is armed and a Ctrl+S in B completes `Saved` naming its checkpoint while A's write is still held; reopening A queues behind A's write.
- **Lock hand-off test** (story 331's lock hand-off; rulings F9 and G5): with a head write held past its last check, a prune delete decided just before `stop()`'s bound, and a heartbeat held inside its write, a switch releases the old folder's lock only after all three have finished; afterwards no file in that folder changes and no `.project.lock` is left in it.
- **First-save prompt test** (story 331, ruling L4): Ctrl+S on a project never saved, then a snapshot restore while its location chooser is open: the replaced project is never written into the new folder.
- **Off-FX test** (story 331's known limit): New, a first save and File ▸ Open make no file-system call on the FX thread.

## Non-Goals

- **The single-save collapse and atomic-replace writer** — story 331 (prerequisite); the FLUSH step *is* that collapsed save, not a new one.
- **The recovery gate, seal reader, and journal default-on** — story 332; this story writes the seal at exit, 332 reads it at open.
- **Dirty-state tracking itself** — `ProjectVM.dirty` and the markDirty single source exist (story 294 / Control Synchronization book); the guard consumes them.
- **The end-state autosave-and-close UX** — deliberately deferred behind the maturity rule above until story 332 is field-proven; not built here.
- **Workspace-switch UX** — `PROJECT_MANAGER_DESIGN_BOOK.md` §4.4 territory; this story only provides the safe close primitive it reuses.
- **The menu-truth conformance harness and checked-state work** — Book 5 story 345 polices that every menu item lands, including the three added here.
- **Dialog-dismissibility conformance for the new prompts** — Book 4 story 339.

## Technical Notes

- Implements **Stage 5 — The App-Exit Protocol: Close Guard, Save As, Lock Lifecycle** of `docs/design/PERSISTENCE_INTEGRITY_DESIGN_BOOK.md` (§2.7 exit-is-a-protocol, §4.8 exit coordinator, §5.4 ordered protocol + maturity rule, §3.2 seal write side).
- Files: a new exit coordinator in `daw-app`; `MainController.java:1007` (`setOnHidden` stays dispose-only, sequenced after the protocol) and the primary stage gains its `setOnCloseRequest` (the floating-panel handler at `:3579` shows the existing idiom); `DawApplication.java:98` (application-stop fallback routes through the coordinator before bus/dispatcher teardown); `ProjectManager.java:339-359` (`closeProject` gains its first production caller) and `:346-349` (swallow assumption becomes true); `ProjectLifecycleController.java:813` (guard prompt reused), `:370-376` (typed `LockStolenException` handling replaces the generic catch); `MenuConstructionService.java:141-182` (three new File items); `LockStolenException.java:6-11` (the contract finally honoured); `LockStatusIndicator.java:110-111` (its instruction becomes true — and per book §7.3, fix its inline-hex token violation in passing while touching it).
- Story 323 hand-off (a take recording or still being written at exit): the GUARD step's take rule is binding; how the guard reads its two facts is not. `TransportController.isRecordingInFlight()` and `isTakeBeingWritten()` are package-private, and `ProjectLifecycleController` reads them through the checks `MainController` feeds it (`setRecordingInFlightCheck`, `setTakeBeingWrittenCheck`). `confirmProjectMayClose()` is the in-app doors' gate: it refuses while a recording is in flight (`PROJECT_CHANGE_WHILE_RECORDING_MESSAGE`), where the take rule above stops the recording instead, and while a take is being written (`PROJECT_CHANGE_WHILE_WRITING_MESSAGE`); neither message is worded for an exit, and the guard need not call it. A take still being written has not marked the project dirty; a take that published a clip has, as has a MIDI take that recorded a note (story 323, Copilot review round 4). Since story 323's Copilot review round 5, `isRecordingInFlight()` is also true while an audio take is being prepared (PREPARING: from Record until capture begins, while the take directory is allocated and the take's files are created), a Stop then cancels the take, and the cancelled start counts as being written (`isTakeBeingWritten()`) until the removal of its files has run, whether or not everything could be removed; and no Stop publishes its take at once — the take is published on a later FX turn, once its capture thread has terminated. `File ▸ Close Project` must also retire the outgoing `TransportController` — `MainController.createTransportController()` retires the controller it replaces (`TransportController.retire()`) — or do the equivalent, so that a take whose Stop is still pending is not published into the closed project when its capture thread terminates.
- Cross-refs: **story 331** (Stage 3 — the flush is its canonical save; strip progress affordance), **story 332** (Stage 4 — seal reader; clean exits also stop feeding `ProjectHealthScanner` phantom stale locks, sharpening its detection), **story 298** (journal machinery the SEAL step drives), **story 345** (Book 5 menu truth), **story 339** (Book 4 dialog conformance), `PROJECT_MANAGER_DESIGN_BOOK.md` §2.5/§8 (the reconciled end-state), `CONTROL_SYNCHRONIZATION_DESIGN_BOOK.md` (`ProjectVM.dirty` as the guard's input; §2.8 input-source irrelevance).
- Rejections bound here: book §9.9 (exit paths that bypass the protocol), §9.14 (swallowing a typed exception into its supertype's generic handler).
- Threading per book §6.1: the FX thread never blocks on the exit flush — the protocol shows progress rather than freezing; each step publishes its outcome before the terminal HIDE state so observers never see a half-closed world.
