# Atomic Saves and Autosave Snapshot Isolation

## Motivation

The write path can corrupt the very file it exists to protect, and the safety net around it fails silently:

- **`project.daw` is overwritten in place.** `writeDawProjectFile` truncates and rewrites the head with `Files.writeString` (`ProjectManager.java:493`; the metadata-only variant at `:527` is the same pattern). A crash or disk-full mid-write leaves a torn, unparsable project with no intact prior version. The codebase already contains the correct pattern — the crash-recovery path writes a `.tmp` sibling and atomically moves it into place (`ProjectLifecycleController.java:1368` onward) — but the *normal* save path, the one that runs hundreds of times per session, does not use it. Checkpoints share the bare-write pattern (`CheckpointManager.java:279`).
- **Autosave serializes the live model against concurrent edits, and fails silently.** The checkpoint data supplier serializes the **live** project (`MainController.java:829-836`) catching `IOException` only. `triggerCheckpoint` dispatches that supplier onto a virtual thread (`CheckpointManager.java:309`) while the FX thread keeps editing the model — and `DawProject.getTracks()` returns an unmodifiable view over the live mutable list (`DawProject.java:270-271`), so a track added mid-walk throws `ConcurrentModificationException`. `performCheckpoint` also catches only `IOException` (`CheckpointManager.java:288-290`), so the runtime exception escapes without calling `notifyFailed` — `ProjectOperationProgress.recordSaveFailed` never fires and the story-295 Session Status Strip keeps showing a healthy autosave. The failure mode is *silently lost checkpoints*, exactly when the user is editing most actively — which is when a checkpoint matters most.
- **One Ctrl+S: four serializations, two checkpoints, all on the FX thread.** The manual save path calls `saveDawProject` **and then** `saveProject` back-to-back (`ProjectLifecycleController.java:358-359`). Each performs a full serialize-and-write of `project.daw` *and* a synchronous `performCheckpoint` (`ProjectManager.java:317-332` and `:290-307`), which documents that it "runs the actual file I/O on the calling thread" (`CheckpointManager.java:256-262`) — here, the JavaFX application thread. Net effect per save: duplicate work, duplicate checkpoint files, and a UI freeze growing linearly with session size.
- **Checkpoint retention is amnesiac.** The checkpoint index is an in-memory list (`CheckpointManager.java:53`) that `start(...)` never seeds from the on-disk `checkpoints/` directory (`CheckpointManager.java:82-105`); `pruneOldCheckpoints` trims only that list (`:341-350`), so files from previous sessions are invisible to rotation and the directory grows without bound.

For a studio engineer: the save command can eat the project, the autosave that is supposed to catch that can die silently mid-session, and the disk fills up with checkpoints nothing ever prunes.

## Goals

- **Atomic-replace writer** (design book §4.1): one helper in `daw-core` persistence — write to a same-directory `.tmp` sibling → fsync → `ATOMIC_MOVE` over the destination → `REPLACE_EXISTING` fallback where the filesystem denies atomic moves — adopted by the head write, the metadata write, and the checkpoint write; the recovery writer (`ProjectLifecycleController.java:1368` onward) refactors onto the same helper so exactly one implementation exists. When the move fails — after both the atomic move and the `REPLACE_EXISTING` fallback — the helper deletes the temp sibling and rethrows the original exception, so a failed save leaves neither a partial target nor a stray `.tmp`. `ProjectArchiver` adopts the helper too: today `moveArchiveIntoPlace` (`ProjectArchiver.java` ~:865-873, called at ~:306) leaves `.<name>.dawz.tmp` behind when the final move fails. The same is true on `main`; severity is low, because a retry to the same name truncates and reuses the temp file.
- **Checkpoint snapshot isolation** (design book §4.2): the checkpoint supplier stops reading the live model. Capture an immutable representation on the FX thread (interim: the serializer walks on the FX thread only long enough to produce the document/string capture) and hand it to the virtual-thread writer for disk I/O. The worker never touches the live model; the FX thread never performs the disk write.
- **Contain `Throwable`, not `IOException`**: any capture or write failure reaches `notifyFailed` → `ProjectOperationProgress.recordSaveFailed` → the strip's Saved-cell warning state. A failed autosave the user can see is a nuisance; one they cannot see is the current bug.
- **Manual save collapses to one pass**: one capture → one atomic head write → at most one checkpoint, off the FX thread, with the strip's progress affordance for slow saves. The `saveDawProject`-then-`saveProject` double call is retired; one method becomes the single canonical save entry.
- **Checkpoint index seeds from disk**: `start(...)` enumerates the on-disk `checkpoints/` directory so pruning counts files across sessions and the on-disk cap actually holds.

## Goals — Tests

- **Crash-shaped atomicity test**: killing/failing the write between the temp-sibling write and the move leaves the prior `project.daw` intact and parsable; the same holds for a checkpoint write (a torn temp file never replaces a good checkpoint); and a failed move — atomic move and `REPLACE_EXISTING` fallback both failing, for the head, a checkpoint and the archive — leaves neither a partial target nor the temp sibling, and the original exception reaches the caller.
- **Concurrent-edit isolation test**: a mutation injected during capture (or a supplier throwing a `RuntimeException`) produces a *visible* failed checkpoint — `notifyFailed` fires and `recordSaveFailed` reaches the strip — never a silently swallowed `ConcurrentModificationException`; the scheduler keeps ticking afterwards.
- **Single-save test**: one manual save produces exactly one head write and at most one checkpoint file, and the FX thread performs no disk I/O (blocked only for the capture).
- **Cross-session retention test**: with a checkpoint cap of N, two consecutive app runs never leave more than N checkpoint files on disk (index seeded from the directory at start).
- **Archive isolation test**: an edit made while the archive worker runs does not change the archived document, because the worker serializes the FX-thread capture, never the live model.
- **Single-writer adoption test**: a source-scan (conformance-sentinel style) asserts no durable-file write in the persistence path bypasses the atomic-replace helper — no remaining bare `Files.writeString` over `project.daw`, metadata, or checkpoints.

## Technical Notes

- Implements **Stage 3 — Atomic Saves and Autosave Snapshot Isolation** of `docs/design/PERSISTENCE_INTEGRITY_DESIGN_BOOK.md` (§4.1 atomic-replace writer, §4.2 snapshot isolation + single-save collapse, §4.8 retention-index seeding, §5.2 write contract).
- Files: a new atomic-replace helper in the `daw-core` persistence package; `ProjectManager.java` (`:493`, `:527` bare writes; `:290-307`/`:317-332` save paths); `CheckpointManager.java` (`:279` write, `:288-290` catch widening, `:82-105` start-time disk seeding, `:341-350` pruning); `MainController.java:829-836` (supplier becomes capture-based); `ProjectLifecycleController.java:358-359` (double call collapses onto the canonical entry) and `:1368` onward (recovery writer refactors onto the shared helper).
- This is the reliability core **story 019 — Project Save, Load, and Auto-Save Reliability** always asked for. **Story 190**'s (landed) snapshot browser gains torn-checkpoint immunity immediately; **story 295**'s Session Status Strip is the failure surface every containment path reports into; **story 299**'s SPEC snapshot store binds to the shared writer.
- Threading per book §6.1: the FX thread *captures*; workers *serialize and write*; one writer per file; no persistence code in `daw-core` takes a JavaFX dependency.
- **Adjacent consumer — the project archive.** `ProjectLifecycleController.archiveInBackground` runs `ProjectArchiver.saveAsArchive` on a virtual thread, which serializes the **live** model off the FX thread (book §2.3). It falls under this story's snapshot-isolation rule (book §4.2: the FX thread captures, workers write): the archive worker consumes an FX-thread capture, never the live model. Until then, an edit that breaks the walk is reported as `Archive failed: <reason>`.
- Unblocks Stage 4 (story 332 — a journal is only as trustworthy as the checkpoints it replays onto), Stage 5 (story 333 — the exit save is this collapsed single save), and Stage 7 (story 335 — retention delivery needs the seeded index).
- Design principles bound here: §2.2 (every durable write is atomic or it is a hazard), §2.3 (serialization reads only quiescent state); rejections §9.1/§9.2/§9.8.

## Resolution

A save no longer rewrites `project.daw` in place, and the autosave that backs it up can no longer fail out of sight. Every durable write of the persistence path goes through one atomic-replace writer, so a crash, a full disk or a failed move leaves `project.daw`, a checkpoint or an archive as it was or whole and new, never torn. Ctrl+S on a project that already has its folder only captures it on the FX thread; one save writer then renders it once, writes the head once and writes at most one checkpoint from the same bytes, off the FX thread, and the strip shows `◐ Saving project…` only when that takes longer than 500 ms. Interims still block the FX thread. Among them, each a Known limit below, are `createProject` (New and a first save), the open path, `CheckpointManager.stop()`'s wait of up to 5 s when a project is replaced, the migration roll-back's file work up to its reload and `MigrationSuppression`'s write, and, as before story 331, the snapshot area's disk work that stays on the FX thread (the snapshot browser's, and a snapshot restore's or Compare's from the browser or the Session Manager dock). The archive dialog's preflight stays on the FX thread too (ruling G11, story 376). Autosave captures on the FX thread and writes on its own writer; any failure, an `Error` included, reaches the Session Status Strip as an amber checkpoint state that stays until a checkpoint is written or the project is replaced, and a failed Ctrl+S is never hidden by a later good autosave. The checkpoint index is seeded from `checkpoints/` at every writable open, so the cap holds across sessions. Every Goal is met as follows; the Verification maps each Goals — Tests bullet to its tests.

**Atomic-replace writer.** `AtomicFileWriter` in daw-core `persistence` is the one implementation: `writeString`, `write` (a streamed `Body`) and `copy`, either `Overwrite.REPLACE` or `Overwrite.NEVER`, which publishes only under a name nothing holds. Each write stages a temp sibling named `.<target name>.<16 lowercase hex>.tmp`, a new name per write, opened `CREATE_NEW, WRITE, NOFOLLOW_LINKS`; forces it (`force(true)`) and closes it; moves it with `ATOMIC_MOVE + REPLACE_EXISTING`, falling back to `REPLACE_EXISTING` alone on `AtomicMoveNotSupportedException`; and then makes a best-effort fsync of the folder. A refusal of the kind Windows gives transiently — an `AccessDeniedException` or a plain `FileSystemException` while an antivirus scanner, the indexer or a sync client holds the file — is retried three times, 130 ms in all, and never answered with the fallback, which on Windows deletes the target first. Any failure once the temp exists deletes it and rethrows the original exception unwrapped: after a failed fallback the fallback's, with the `AtomicMoveNotSupportedException` suppressed; a temp that cannot be deleted is attached as suppressed. In daw-core the head save and the metadata write (`ProjectManager.replaceProjectFile`), the migration and degraded-open backups (`writeSiblingBackup`, a `NEVER` copy), the checkpoints, the `.dawz` publish (`ProjectArchiver.write`; `moveArchiveIntoPlace` is gone) and `consolidateInPlace`'s copy, the named snapshots (`SnapshotStore`), the lock's takeover and heartbeat, the session manifest, `BackupRetentionPolicyStore` and `MigrationSuppression` write through it. In daw-app the recovered-file writer (`writeRecoveredProjectFile`, with its `project.daw.recovered.<stamp>.bak` backup), the archive restore's head write and the migration roll-back's copy do, so the recovery path's own temp-and-move code is gone and exactly one implementation exists on the persistence path. What stays outside is declared, each with its reason, in daw-core's single-writer sentinel: the append-only `ProjectLog`, the lock's `CREATE_NEW` acquisition, the journal segments, the archive restore's extraction into a staging directory and its directory publish, and the DAWproject interchange export (`DawProjectSessionExporter`, story 377); daw-app's sentinel declares nothing.

**Checkpoint snapshot isolation.** `CheckpointManager.setCaptureSource(Executor, CheckpointSource)` replaces the data supplier. A scheduled tick only posts the capture to the owner executor — in the application the FX thread, through `MainController.wireAutosave(..., this::postFx, ...)` — and never waits for it; at most one capture is pending, and a tick that comes while the previous one is still captured or written is dropped and re-arms. On the owner the source reads `DawProject.getEditRevision()` and whether the project is clean, and `capture()` walks the model into a `ProjectDocument` (`ProjectSerializer.capture`), returning a renderer. The checkpoint writer, one virtual thread started while jobs are queued, renders that document and writes it; it never reads the live model, and the owner never touches the disk. `ProjectDocument.toXml()` is byte for byte what `ProjectSerializer.serialize` writes. The archive follows the same rule: `ProjectArchiver.capture(DawProject, ArchiveOptions, List<ArchiveAssetDecision>)` runs on the FX thread in `archiveInBackground` and `write(ArchiveCapture, Path)` on the worker, so an edit made while the archive is written never reaches it; the `saveAsArchive` overloads are gone. File ▸ Create Checkpoint… captures and renders once on the FX thread, for the browser's in-memory entry, and hands the text to the checkpoint writer.

**Contain `Throwable`.** Every `Throwable` from a scheduled tick's capture, an owner that rejects it, the write guard, the render or the write is logged at SEVERE and reported exactly once — the SDK listener's `onCheckpointFailed` and `CheckpointEvent.Failed` — and the cadence keeps ticking. A Create Checkpoint whose capture or render throws never reaches `CheckpointManager`: both run on the FX thread, in one `try` in `SnapshotsController`, which logs either failure at WARNING, and the failure sets the strip's checkpoint failure state and shows the ERROR `Checkpoint failed: <cause>` (below), but reaches neither the SDK listener nor `CheckpointEvent.Failed`. A scheduled tick's capture failure that the checkpoint writer reaches after autosave was disabled is logged at FINE and reported to no listener (ruling H3). The text-summary fallback is gone: with no capture source a tick writes nothing, and an index is used only by a write, allocated after the render. A prune that fails, or a checkpoint that refuses deletion, is logged and never turns a written checkpoint into a failure. In daw-app `CheckpointStatusListener` turns those events into the strip's checkpoint state (see the deviation below). A checkpoint that fails, of any origin, sets `⚠ Checkpoint failed · last good HH:mm` (WARN), or `⚠ Checkpoint failed` when no good checkpoint is known. A scheduled or after-save checkpoint also counts toward a streak: the second failure in a row raises one WARNING, `Checkpoints are failing: <cause>. The last good checkpoint is from HH:mm.` (the date first when it is not today), or `Checkpoints are failing: <cause>. No earlier checkpoint of this project was found.`; later failures count quietly, and the next checkpoint written clears the state and ends the streak. A Create Checkpoint that fails shows `Checkpoint failed: <cause>` every time and does not count toward the streak. A manual save's capture that throws, an `Error` included, completes `SaveOutcome.Failed` with that throwable.

**Manual save collapses to one pass.** `ProjectManager.save(DawProject)` → `CompletableFuture<SaveOutcome>` is the one canonical save; `saveProject()` and `saveDawProject(DawProject)` are gone, and `closeProject()` uses it. `SaveOutcome` is sealed: `Saved(metadata, revision, Optional<Path> checkpoint)` or `Failed(cause, Optional<Path> safetyCheckpoint)`. The caller, the FX thread in the application, only stamps the metadata, reads the edit revision and captures. The save writer, one virtual thread started while saves are queued, then runs, in order: the generation fence (a capture of a project closed, abandoned or replaced since writes nothing); the lock check (`ProjectLockManager.verifyOurs()`); the render, once; the backup the open owes, a durable `NEVER` copy; the atomic head write; `DawProject.markCleanIfUnchanged(revision)`, so an edit made during the write keeps the project dirty; and, while the project is still the open one, the checkpoint of the same bytes (`CheckpointOrigin.AFTER_SAVE`), skipped when that revision is already checkpointed and waited for at most five seconds. One head write runs at a time with one waiting capture, which a newer capture of the same project replaces; the replaced capture's future completes with the newer one's outcome, so captures are written in the order they were taken. In daw-app `ProjectLifecycleController` hands the save to `ProjectManager.save` on the FX thread (`submitSave`) and follows its outcome through the `FxDispatcher`. A `Saved` sets the Saved cell to `✓ Saved HH:mm:ss` and flashes it once for 600 ms (`SessionStatusStrip.SAVED_FLASH_DURATION`; no flash under Reduce Motion), with no notification. A `Failed` sets the head failure, `⚠ Save failed · last saved HH:mm` (CRITICAL; `⚠ Save failed` alone where the cell would read `Not saved yet`), leaves the project dirty and shows an ERROR every time: `Save failed: <cause>. Your work is in checkpoint 014 (14:32).` when a safety checkpoint holds the rendered bytes, `Save failed: <cause>. A safety copy of your work is still being written.` or `Save failed: <cause>. No safety copy could be written.`; it offers Retry for an I/O failure only. A read-only project shows `Save failed: <cause>` alone. A lost lock reads `Save failed: the project was taken over by <user> on <host> (process <pid>) — nothing was written`, or, with no holder on disk, `Save failed: the project's lock was removed, so another session may have taken the project over — nothing was written`; neither a lost lock nor a read-only project offers Retry. A save that fails after another project replaced its own shows its ERROR as `Saving <folder> failed: …` and leaves the open project's strip as it is. `SLOW_SAVE_THRESHOLD` is 500 ms: a save still running then shows `◐ Saving project…` until it ends, decided on the FX thread from one FX-owned timer that also checks the project, so it is never left showing. The editor stays live and Save stays enabled; repeated presses coalesce.

**Checkpoint index seeds from disk.** `CheckpointManager.start(Path)` begins a checkpoint generation and queues seeding as the writer's first job; it does no disk I/O on its caller. Seeding lists `checkpoints/`, keeps only names `CheckpointFileName.parse` accepts (`checkpoint-<index>-<yyyyMMdd'T'HHmmss>.daw`, the index read as a `long`), orders them by the stamp in the name and then the index (`CheckpointFileName.ORDER`; never the file time), continues the index from the highest one on disk, and deletes the writer's own temps of checkpoint names — and only those — while the write guard passes, logging their count at INFO. Nothing is pruned at open. After each write the prune deletes until at most `maxCheckpoints` remain: the seeded checkpoints first, oldest first, then this generation's own, oldest written first, never the file it just wrote nor the one holding the last checkpointed revision. `CheckpointFileName` writes ASCII digits under every default locale and is shared by `RecoveryScanner` and `SessionManager`, so neither lists a temp or a near-miss name. The snapshot browser lists `checkpoints/` with its own glob, `{autosave*,checkpoint*,*.daw}` (`SnapshotBrowserService`): the temps' leading dot and `.tmp` suffix keep them out of it, but it still lists a near-miss name. A read-only open starts no checkpoints; every checkpoint write, and every temp delete at seeding, first asks the project lock (`ProjectLockManager.verifyHeld()`), and the prune runs only after such a write.

What the rulings added beyond the Goals:

- **The project as the user left it.** A head write or backup that fails after the render leaves the rendered bytes in a safety checkpoint (`CheckpointOrigin.SAFETY_COPY`, ruling G9), or names the checkpoint that already holds the revision; a failed safety copy is attached to the head's cause as suppressed, and none is written after a lost lock, past the fence or on a read-only open. The migration and degraded-open backups are durable no-overwrite copies taken before the head is replaced; a failed backup fails the save with `project.daw` untouched and the backup still owed (F10). Autosave skips a tick whose revision is already checkpointed (F4), and the first tick after a clean open skips when `project.daw` is byte-identical to the newest checkpoint on disk (G3); Create Checkpoint always writes (G8). With autosave disabled the generation still runs: a writable open still seeds, and Create Checkpoint and safety copies still write, while ticks and the after-save checkpoint do not (H3, J2).
- **Read-only files and permissions.** A replace keeps the existing file's POSIX permission bits (G10) and refuses a file the user made read-only before anything is staged, with an `AccessDeniedException` whose message is `<path>: the file is read-only or not writable; it was not replaced`; on Windows only the DOS read-only flag refuses (H2). The `.dawz` publish keeps that refusal, which on POSIX is a deliberate change: a read-only archive is refused before the pack, `Archive failed: <path>: the file is read-only or not writable; it was not replaced` (H1b). The session manifest and the lock replace with `ReplacePermission.DIRECTORY`, so a stale session or lock can still be taken over (H1a, H1c). Without `FOLLOW_LINK_TO_DAW_FILE` a target that is a symbolic link is asked about itself: on POSIX it is not refused, and on Windows only its own read-only flag refuses it (N3).
- **Links to `project.daw`.** The writers of an open project's `project.daw` — the head save, the metadata write, the recovered-file writer and the migration roll-back — pass `ReplaceOption.FOLLOW_LINK_TO_DAW_FILE` (M3): a `project.daw` that is a symbolic link to an existing regular `.daw` file stays a link, and that file is replaced, its temp beside it. Any other link — dangling, to a directory or to another file — is refused before anything is staged, with a `FileSystemException` whose message is `<path>: a symbolic link that does not lead to a .daw file; it was not replaced`. `AtomicFileWriter.followLinkToDawFile` is the one guard: the save's owed backup and the recovered-file writer's backup ask it before they copy anything, so neither copies through a link the guard refuses (one that does not lead to an existing regular `.daw` file), and a save's backup refused that way stays owed. A link to a read-only `.daw` file passes the guard, and its backup is copied before the replace refuses the file (Known limits; story 383). The archive restore's head write passes no option: it replaces the `project.daw` it has just extracted.
- **Temps of an archive.** The `.dawz` publish alone passes `ReplaceOption.DELETE_EARLIER_TEMPS` (M2): once the read-only refusal has passed, it deletes the temps that earlier, cut-off writes of the same file left beside it and logs `Deleted <n> temp file(s) that earlier, unfinished writes of <name> left in <folder>` at INFO.
- **Writes at exit.** The save writer and the checkpoint writer are daemon virtual threads, so `MainController.registerExitWriteWait` registers one JVM shutdown hook, a platform thread named `daw-exit-write-wait`, right after the project manager is built (M1). It only calls `ProjectManager.awaitWritesBeforeExit()`, which waits at most 30 s (`EXIT_WRITE_WAIT`) under one deadline, first for the saves and then for every job the checkpoint writer holds; it never waits on, or posts to, the FX thread. Its WARNING `Saves or checkpoints were still being written 30 s after the application began to exit; the application exits without them, and project.daw holds the last save that finished` reaches no handler, and its INFO `Waiting up to 30 s for the saves and checkpoints still being written before the application exits` usually does not, because the JDK's `LogManager` resets the handlers from a shutdown hook of its own (N1); story 336 gains the sink that keeps them.
- **Doors.** New, Open, Import, Restore from Archive, the Hub and Welcome opens and a snapshot restore wait, without blocking the FX thread, until the save writer has finished every save queued before them (`ProjectManager.whenSavesIdle()`), and then judge the close again: the take refusal first, then the unsaved-changes prompt (G1). Only one switch is pending at a time; another is refused with one rate-limited INFO: `Still saving — <door> continues when the save finishes.` (G2), `Still extracting the archive — Restore from Archive continues when the extraction finishes.` (K3), `Still recovering the session — Recover Session continues when the recovery finishes.` (L3), or `<door>'s file dialog is still open — finish or cancel it first.` (L4). New, Open and Import record their answer at judgment and ask again, `Do you want to save before continuing?`, when the project changed while their chooser was open (L4); a restored archive asks `The archive was restored to <destination>. Do you want to save before opening it?` when the project changed after Restore from Archive was answered (K3). A late switch that already did something and is refused shows a WARNING that is never rate-limited, `<what was done>; the project was not opened, because <switch> is replacing the open project — open it later with File ▸ Open Project…` (L3). Create Checkpoint on a project never saved, or open read-only, keeps the entry in memory and warns `Checkpoint kept in memory only, until the application closes: save the project to write checkpoints to disk.` or `Checkpoint kept in memory only, until the application closes: this project is open read-only, so no checkpoint is written to its folder.` (K2). A named snapshot copies exactly the bytes its own save wrote, queued behind that save with `runAfterQueuedSaves`, and only on `Saved` (K4, G13 #10).
- **The Saved cell and the countdown.** The Saved cell shows, in precedence order, `◐ Saving project…`, the head failure, the checkpoint failure, another operation (`◐ <name>`) and `✓ Saved HH:mm:ss` or `Not saved yet`; its severity is CRITICAL while a head failure stands and WARN while only a checkpoint failure does (G4). The amber and operation states also show the head save's time, `⚠ Checkpoint failed · last good 14:32 · saved 14:35:07` (L2). "Last good" is the newest checkpoint seeding found until the generation writes one, timed by the stamp in its name (K1). A time of another day carries its date, and "today" is a model fact the strip's 5 s poll publishes, so the cell gains the date within 5 s of midnight (L1). After a snapshot restore the cell shows the last head save that landed, not the time of a save that failed (`headSavedAt`). Only a re-arm of the checkpoint cadence writes the countdown (G13 #2): a snapshot restore keeps it, an open or New shows `No checkpoint scheduled` until its checkpoints are seeded and re-armed (M4), and a failed open's abandon ends it (`ProjectOperationProgress.checkpointsEnded()`, N2).

One deviation from the story's wording: a failed checkpoint does not call `ProjectOperationProgress.recordSaveFailed`. It sets its own checkpoint state, `recordCheckpointFailed`, shown amber as `⚠ Checkpoint failed · last good HH:mm`, separate from the head's `⚠ Save failed · last saved HH:mm` (rulings F6 and G4). One "last save succeeded" fact held both outcomes, so a later good autosave turned a failed Ctrl+S back into `✓ Saved`, and a failed checkpoint turned the cell red while `project.daw` was fine. While the close prompt and the dirty marker are about `project.daw`, "Saved" has to mean `project.daw`: red now means `project.daw` is behind what the user asked to save, and amber means `project.daw` is fine but checkpoints are failing. The concurrent-edit tests therefore assert the strip's checkpoint failure, and that the head state stays healthy.

Studio-engineer rulings this story applied:

- **F1** — The edit revision `DawProject.getEditRevision()` advances on every `markDirty()`, and a save marks the project clean only when it has not moved since the capture; a failed write never marks it clean.
- **F2** — Saves coalesce and are never refused: one head write at a time, one waiting capture the newest replaces, written in capture order; every checkpoint goes through one serial checkpoint writer.
- **F3** — A save's checkpoint is written after the head move from the bytes the head write wrote, skipped when that revision is already checkpointed, and restarts the countdown.
- **F4** — A tick whose revision is already checkpointed writes nothing, uses no index, reports no checkpoint written or failed, and re-arms the countdown (`CheckpointEvent.Rearmed` with `RearmReason.SKIPPED`).
- **F5** — The index is seeded at start and ordered by the stamp in the name and then the index, never by file time; nothing is pruned at open, only grammar names count, and seeding deletes only the writer's own checkpoint temps.
- **F6** — A failing autosave sets the strip's checkpoint state and raises one WARNING on the second failure in a row; a failed manual save shows an ERROR every time and leaves the project dirty; a checkpoint success never clears a head failure.
- **F7** — `◐ Saving project…` shows only for a save still running after 500 ms (its flash part was corrected by G4).
- **F8** — No capture, no file: the text-summary fallback is gone, and an index is used only by a write.
- **F9** — Each job carries its project's folder and generation: a write already running finishes into its own folder and tells no listener, a capture not yet taken is dropped, and a door waits for the head save without blocking the FX thread.
- **F10** — The migration or degraded-open backup is a durable no-overwrite copy taken before the head is replaced; a failed backup fails the save with `project.daw` untouched.
- **G1** — A door waits until the save writer has finished the saves queued before it, then runs the whole close judgment again, the take refusal first.
- **G2** — A second door while one waits is refused with one rate-limited INFO and is never queued.

Known limits:

- **Permissions (rulings G10, H2).** A replace keeps the POSIX permission bits, not the owner, the group, ACLs or DOS attributes. On local NTFS, a file whose ACL denies write but not delete, in a folder the user can write, is now replaced, where the in-place write refused it; that applies to the `project.daw` head and metadata and to `BackupRetentionPolicyStore` and `MigrationSuppression`, and afterwards the file has the folder's inherited ACL. Story 377, once a user reports it.
- **Retention order across restarts (ruling H4).** Across a restart the checkpoints already in `checkpoints/` are ordered by the stamps in their names again (ruling F5), which a clock step, a time-zone change or the hour repeated when daylight saving time ends can set apart from the order they were written in. The prune can then delete a more recent run's checkpoints before older or future-stamped ones, and the newest seeded checkpoint, which the Saved cell and the checkpoint-failure WARNING give as the last good checkpoint until a checkpoint is written, may not be the newest. Story 335 orders the prune and the newest seeded checkpoint by index, and story 332 orders recovery's newest checkpoint the same way, for the checkpoints a recorded fact shows the index can order; the others keep the stamp order until they are pruned (ruling O). The snapshot browser orders checkpoints by their file time, not their names: a time-zone change or daylight saving time does not reorder it, but a clock step does, within a run too. No story.
- **A read-only `.dawz` on POSIX (ruling H1b).** A read-only archive, or one another user owns, is no longer silently replaced: `Archive failed: <path>: the file is read-only or not writable; it was not replaced`. This is deliberate; no story changes it.
- **Checkpoints that refuse deletion (ruling J1).** `checkpoints/` holds the cap plus each checkpoint that refuses deletion, until a later prune deletes it. No story: later prunes in the same session retry these files, at most one per prune, and a retry deletes a file that can be deleted by then; after a restart or a re-open of the project they count toward the cap again and are pruned like any other checkpoint.
- **A stalled checkpoint write (ruling J3).** The save writer waits at most 5 s for its checkpoint. While a write into another project's folder hangs, the open project's seeding and checkpoints wait behind it and its countdown gets no re-arm, each Ctrl+S shows `✓ Saved` only about 5 s later, and a door waits up to 5 s for the save, with the window live, then up to 5 s more in `stop()`, with the window not responding. Story 333 (one checkpoint writer per folder).
- **A switch while the checkpoint writer is busy (ruling G5).** Replacing the project calls `CheckpointManager.stop()` on the FX thread. It waits at most 5 s, until the checkpoint writer holds no job of the ending project, and the window does not respond meanwhile. It does not wait at all when the writer holds no job of that project; otherwise it waits as long as the checkpoint job in progress takes — a write, the seeding at open, which lists `checkpoints/` and compares `project.daw` byte for byte with the newest checkpoint, or the first tick's same comparison — and the full 5 s while a checkpoint write hangs (ruling J3). Story 333 (a `stop()` that waits only for claimed writes).
- **A head write past its fence.** A head write already past its last check when the project is closed or switched still finishes into its own folder. Story 333 (the lock hand-off).
- **The FX thread still touches the disk** in `createProject` (a first save and New) and on the open path. `createProject` writes a metadata-only `project.daw` through the writer, so a first save and New each write `project.daw` twice: that file on the FX thread, then the head on the save writer. Story 333.
- **The migration roll-back's file work** runs on the FX thread — for example its search of the project folder for the newest backup, when the "Project Migrated" dialog starts it, and its copy through the writer (force, folder fsync and up to 130 ms of retries) — and so does `MigrationSuppression`'s write from that dialog. The reload after the copy is the open path, above. Story 373.
- **Other writers.** `DawLauncher` and `FloatingWindowStore` keep their own temp-and-move writers, without a force, and `DawProjectSessionExporter` writes its file in place. Story 377.
- **A replacement that fails early.** `createProject` and `openProject` stop the open project's checkpoints first; when a later step fails, that project stays current with no checkpoints and no safety copy, and Create Checkpoint shows `Checkpoint failed: Checkpoints are not running: no project directory is open for checkpoints`. The application never reaches this, because every door abandons the project first. Story 361 lifts it for the open, whose abandon then follows the parse; no story owns it for `createProject`.
- **Time zone (ruling L1).** After an OS time-zone change, times stay in the zone the application started in until it restarts. No story, unless a user reports it.
- **Strip colour tokens.** `-ssc-text`, `-ssc-warn` and `-ssc-critical` (story 295) still have no fallback in `status-strip-cell.css`, so outside a scene that loads `styles.css` the cell's text colours do not resolve; `SavedCellFlashTest` logs `Could not resolve '-ssc-text'`. No story.
- **A prune delete at `stop()`'s bound.** No delete is decided after `stop()` returns, but one decided just before its bound ran out may still be issued after it, like a write already under way. Story 333 (the lock hand-off).
- **Backups before a refused replace.** A recovered-file write refused by the read-only check leaves the `project.daw.recovered.<stamp>.bak` it took first, one more on every retry; a save of a read-only `project.daw`, or through a link to a read-only `.daw` file, that owed a migration or degraded-open backup leaves that backup and no longer owes it. A link repointed between the backup's link check and its copy is copied as it is then. Story 383.
- **A Create Checkpoint rotates out.** Its label (the user's text, or `Checkpoint HH:mm:ss`) lives only in the snapshot browser's in-memory entry; on disk it is an ordinary `checkpoint-<index>-<stamp>.daw`, which the prune deletes like any other checkpoint once newer ones fill the cap, and after a restart nothing marks it. Story 381.
- **No free-space guard.** Nothing checks free space before a save or a checkpoint, and a checkpoint that fails for lack of space is reported like any other failure, never retried elsewhere: a full disk fails the head write and usually its safety copy too (`No safety copy could be written.`). The Project Manager book's §6.2 disk-space guard designs the checkpoint side, a checkpoint write that fails with `ENOSPC` retried into a fallback workspace with a standing warning in the strip; nothing designs a check before a save. No story.
- **Snapshot work touches the disk on the FX thread.** What the snapshot browser and a snapshot restore or Compare, from the browser or the Session Manager dock, do with the disk runs on the FX thread, as before story 331, except work they hand to another thread, such as Create Checkpoint's file, which goes to the checkpoint writer, and the restored project's audio, which, as on an open, goes to decode threads. Among the work on the FX thread: the browser's refresh, which runs when the browser is opened and, once it has been, after Create Checkpoint, a named snapshot that was created, a snapshot restore, a project replacement and Purge old autosaves, and in which `SnapshotBrowserService.getEntries` lists `checkpoints/` and `snapshots/` and reads each listed file's attributes; the preview's read of the selected entry's file (`SnapshotBrowser.updatePreview`); Purge old autosaves' listing of `checkpoints/`; and a restore's or Compare's read of the entry's file (`SnapshotsController.loadFromEntry`, `SnapshotEntry.loadContent`) and, as it deserializes the entry, its checks that the audio clips' files and the reference tracks' files exist (`ProjectDeserializer`). An entry held in memory has no file to read. No story.
- **M1 (exit wait).**
  - An exit waits at most 30 s for the saves and checkpoints still being written. Past that, the JVM ends the writers: project.daw holds the last save that finished, whole, with the cut-off save's temp beside it until story 332.
  - OS logoff or shutdown is best effort and untested, because the OS can end the process before the JVM starts its shutdown. No story.
  - SIGKILL, End Task on a not-responding app, power loss and Runtime.halt: nothing runs at the exit itself, so there is no protection then beyond the atomic replace. Story 332 offers recovery at the next open: its journal is on by default, an unsealed journal with records after the last checkpoint marker presents the `RecoveryDialog`, and its recovery gate treats a complete head temp newer than project.daw as recovery evidence.
- **M1/N1.**
  - The exit wait's two log lines are not recorded. The JDK's LogManager resets every logging handler from its own shutdown hook as the exit begins. So the WARNING that the wait ran out is never printed, and the INFO that it waits usually isn't (measured on JDK 27: 0 of 9 and 4 of 19 real exits). Story 336.
  - In the packaged app no log sink exists at all until story 336.
  - An exit that abandons a save leaves no message, now or at the next launch. project.daw holds the last save that finished, and the temp of the save that was cut off stays beside it until story 332's recovery gate handles it.
  - Ctrl+C in a terminal: the process stays until the writes land or 30 s pass; usually nothing is printed. Story 336 writes the wait's lines to its log file, and story 333 keeps this wait for Ctrl+C.
- **M2.**
  - An archive's temps stay until the next archive to the same .dawz file; one whose file is never archived to again stays. No story.
  - Temps of project.daw (one per save cut off, any number) and of the project folder's other files stay until story 332's recovery gate removes them; a temp of an app settings file stays (no story).
- **M3.**
  - A save breaks a hard link: a hard-linked project.daw is replaced by a new file, and its other names keep the previous content. No story.
  - A project.daw link that does not lead to an existing regular .daw file is refused. Every save shows `Save failed: <path>/project.daw: a symbolic link that does not lead to a .daw file; it was not replaced. Your work is in checkpoint NNN (HH:mm).` and offers Retry. No story.
  - The temps of a write that follows a link sit beside the real file. Story 332 (its recovery gate handles them there).
  - Opening a project reads project.daw through any link. One that leads to a file that is not a .daw file is read like any project.daw: content that starts with an XML declaration or `<daw-project` is read as a project document, other UTF-8 text opens as an empty project, named "Untitled" unless the file has a `name=` line, and a file that is not UTF-8 fails to open. Every save of a project opened through such a link is refused. After a Recover whose write such a link refused, that is the 'last clean save' that opens. No story.
- **N2.**
  - A failed Open leaves the project on screen detached from its folder until story 361. That covers an unreadable, malformed or unmigratable project.daw, a missing one, and a cancelled lock prompt.
  - Its checkpoints stop, and the countdown reads "No checkpoint scheduled".
  - Create Checkpoint keeps its checkpoint in memory only (K2).
  - The next Save asks for a folder and creates a new project there.
  - The Saved cell keeps that project's last save, but a snapshot restore then shows "Not saved yet".
  - A checkpoint failure standing at the open stays, with no last good checkpoint. Its tooltip then says "No earlier checkpoint of this project was found.", although that project's folder holds checkpoints.
