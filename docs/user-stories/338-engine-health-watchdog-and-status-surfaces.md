# Engine Health: Watchdog, Xrun Counter, Clock and State Surfaces

## Motivation

An entire engine-health layer exists in the tree with zero production wiring — dropouts, stalls, and a dead audio engine are all invisible to the user:

- **No watchdog exists anywhere.** A grep for "watchdog" across all main source returns zero hits; the only heartbeat in the codebase guards the project lock file (`ProjectLockManager`), not the engine. Nothing detects "the callback has not run for N ms while the stream is nominally open" — which is exactly the observable signature of a dead PortAudio upcall, a silently-dead JavaSound loop, a stalled ASIO driver, and a physically unplugged interface alike.
- **Xruns are never detected, counted, or reported.** `XrunDetector` is constructed and rebuilt on every reconfigure, but there are zero production callers of `beginTick`/`recordTick`/`reportDropped`/`reportGraphOverload` — the render loop never reports timing into it. Its event stream is exposed (`DefaultAudioEngineController.java:466-467`) with no subscriber, and the story-123 `XrunCounterLabel`/`XrunLogDialog` exist only as a javadoc mention (`XrunDetector.java:105-111`). Worse, the detector's own publish path is not RT-safe: `recordTick` calls `SubmissionPublisher.offer(...)` inline on the caller thread (`XrunDetector.java:203-208`), whose `offer` acquires a `ReentrantLock` — the javadoc's claim that the audio thread "never blocks" (`:33-36`) is false, so it cannot simply be fed from the callback as it stands.
- **Engine state has no UI.** `setEngineState` offers every transition — RUNNING, RECONFIGURING, DEVICE_LOST, STOPPED — to a publisher (`DefaultAudioEngineController.java:661-672`, accessor `engineStateEvents()` at `:481-483`); grep finds no production subscriber. Transport silence never has a visible cause.
- **The clock-lock surface is finished and dead.** `ClockStatusIndicator` — a complete control with a notification hook and a recording-pause callback (`ClockStatusIndicator.java:105`) — is never instantiated in main source. The only `ClockLockEvent` publisher anywhere is the mock backend's test fixture (`MockAudioBackend.java:451`); the `AudioBackend` default is an empty publisher (`AudioBackend.java:568`) that no real backend overrides.

The studio-engineer consequence: a mid-take dropout leaves no evidence, a dead engine looks identical to a project that renders silence, and an external-clock rig losing lock records garbage with no warning — on the primary Windows + ASIO + multi-channel USB target where clocking and USB stalls are routine facts of life.

## Goals

- **Callback-heartbeat watchdog.** The story-337 render guards already bump a heartbeat timestamp in the RT health record (one wait-free atomic store). A low-priority daemon monitor — owned by the engine controller, rebuilt on reconfigure — checks the gap while a stream is nominally open; a gap exceeding a few buffer periods (scaled from the active format, with a floor for scheduling jitter) is a stall verdict that drives the **existing** reaction machinery: engine state → DEVICE_LOST, the controller's notification (visible via story 339's injected sink), and a restart offer. The watchdog *observes* the callback; it never runs on it. It is deliberately backend-agnostic — it detects PortAudio upcall death, JavaSound loop death, ASIO driver stalls, and device disappearance identically, including on backends offering no error callback at all.
- **XrunDetector publish side made RT-pure first.** Tick recording keeps only atomics on the caller thread; event *publication* moves off the hot path (drained by the same monitor/pulse machinery, or offered only from non-RT callers). The `:33-36` javadoc claim becomes true before anything feeds it.
- **Then feed it:** elapsed-time ticks recorded around the render body, dropped buffers reported from the story-337 guards, graph overloads from the worker pool's new failure counters.
- **Xrun counter surfaced:** the story-123 counter lands as a cell in the story-295 session status strip, with click-through to the xrun log dialog.
- **Engine-state cell:** a status-strip cell subscribes to `engineStateEvents()` via the dispatcher — RUNNING quiet, RECONFIGURING informational, DEVICE_LOST in the warning-accent token treatment (tokens, never raw hex). Transport silence permanently gains a visible cause.
- **Clock-lock surfaces live:** mount `ClockStatusIndicator` in the transport/status area bound to the active backend's `clockLockEvents()`, and implement the ASIO-side `ClockLockEvent` publisher in the shim (resync-request / sample-position-not-advancing detection) — so external-clock studios get the lost-lock warning and recording auto-pause the control was built for.

## Note from Story 336

- **The render pump's death is logged but never shown.** `EngineStreamPump` sets its own uncaught-exception handler on the `engine-render-pump` thread (`daw-core/.../audio/EngineStreamPump.java:209-213`). A per-thread handler pre-empts the process-wide default handler that story 336 installs. So when a throwable the render loop does not survive ends the pump (the loop survives `RuntimeException`s only), the only trace is that handler's SEVERE record, "engine-render-pump thread died; audio output is dead until the stream is stopped and reopened". Story 336's log sink now writes it to the log file, but it never reaches a toast or a status cell. For a live session it is the most important failure there is.
- **This story owns surfacing it.** Either the pump's death becomes an engine-health state transition that this story's surfaces show, or that handler delegates to `Thread.getDefaultUncaughtExceptionHandler()` after its log line, so story 336's funnel shows it. daw-core cannot reference daw-app, so the handler must not name the funnel. Test: an `Error` thrown on the render pump reaches a visible surface once, and the log file keeps the SEVERE record.

## Note from Story 337

- **The heartbeat is two counters, not one timestamp.** Story 337 built the heartbeat as two monotonic period counters (its ruling E5), and the watchdog samples them with its own monotonic clock. This story's Goal text that "the story-337 render guards already bump a heartbeat timestamp" is superseded by them.
  - **The render drive.** `EngineStreamPump.renderLoop` beats its lane once per block, after `backend.sink` returns normally, so a `sink` that throws does not beat. Read `AudioEngine.audioHealth().renderDriveBeats()`, monotonic across streams.
  - **The device callback.** PortAudio's `CallbackInvoker.invoke` and ASIO's `AsioBufferSwitchShim.bufferSwitchUpcall` count each period at entry, before their guard. Read `audioHealth().deviceCallbackPeriods()`, an `OptionalLong`: PortAudio and ASIO always report one, and it is empty for a backend with no device thread of its own (Java Sound, WASAPI, CoreAudio, JACK, and the Mock backend unless a test sets its counters), where the watchdog uses the render drive's beats instead.
  - **Why two.** A heartbeat that only the render drive stores keeps advancing through a PortAudio upcall death or an ASIO driver stall: `CallbackBackendAdapter.awaitSinkCapacity` returns at its timeout whether or not the device drained the ring, so the drive keeps cycling. Only the device-callback count stops.
  - `audioHealth().renderDriveEpoch()` counts the render drives claimed, one per render drive started (every stream open and every resume of a paused stream; story 337, ruling E59), and `AudioEngine.isRenderDriveAlive()` is true only while the stream is `RUNNING` and its pump runs. `AudioEngine.isRenderDriveHalted()` tells a halted drive from a paused or closed one: it is true only while the stream is `RUNNING` and its current pump has halted itself (story 337, ruling E69).
  - **An input device opened beside the stream has no heartbeat of the stream's.** Its counters count as input failures, and `deviceCallbackPeriods()` never includes it (story 337, ruling E86). A backend whose own counter report fails reads `deviceCallbackPeriods()` empty from then until it is closed (ruling E78), so the watchdog falls back to the render drive's beats there too.
  - **Java Sound needs a capture heartbeat.** A Java Sound capture line that stalls ends nothing and counts nothing: its read blocks with no native error, and the backend reports no device heartbeat. Detecting that stall needs a capture heartbeat this story's watchdog can read (story 337's Known limits). Until then a stalled line leaves unflagged silence in a take with no notice, which story 337's ruling E84 forbids ("never unflagged silence in a take"). So when this story's capture heartbeat declares a stall during a take, each armed track of that input is flagged in the take's `take.manifest` from the stall on and warned once, as for an input that stops, while the take keeps rolling and the other inputs' tracks keep recording. Verify it with a test whose capture read blocks mid-take without returning: once the stall is declared, that input's tracks are flagged in `take.manifest`, no other input's track is, and the take is still recording.
- **Treat a halted drive as handled, not as DEVICE_LOST.** When `processBlock` faults for one second of blocks in a row (`EngineStreamPump.haltThreshold`, at least 8), a `VirtualMachineError` reaches the render loop, or any other throwable escapes the loop's own catches (story 337, ruling E9), the drive stops and then writes one terminal `audio.render.halted` record, so a reader that sees the record already reads the drive dead (story 337, ruling E60). `isRenderDriveAlive()` then reads `false` while `isStreamOpen()` still reads `true`, and the window's `AudioHealthDrain` stops the transport, closes the stream once the take allows it, posts the halt notice with Restart Audio Engine (for a `VirtualMachineError`, the FATAL copy with Open Log Folder; story 337, ruling E13) and latches the engine-fault fact — the Stop and the close only while that stream's drive is still the halted one (`isRenderDriveHalted()`), the close through `AudioEngine.closeHaltedStream()`, which never waits for the lifecycle lock. A halt whose stream was already reaped, replaced, paused or closed stops and closes nothing and shows the halt notice without a context sentence (story 337, rulings E69 and E70). The render-drive heartbeat stops on purpose there, so the watchdog's stall verdict must first check `audioHealth().total(AudioFailureCategory.RENDER_HALTED)` or the latched fact.
- **The engine-fault fact is this story's cell to render.** `AudioHealthDrain.engineFaultProperty()` is a `ReadOnlyObjectProperty<Optional<EngineFault>>` read on the FX thread; `EngineFault` carries the category, the count, the first and last times and the action. The drain sets it at a sustained failure (three consecutive one-second buckets), a render-drive halt or an input halt, and clears it on a successful restart (story 337, ruling E62) or after one fault-free second of render-drive beats on a render drive started after the latch — a reopened or resumed stream (ruling E59) — with no delta in a restart-eligible category, `audio.render` or any latched category (ruling E63). A halt's fact clears on any render drive started after the halted one (ruling E71); an input halt's only on a drive on a stream opened after it, or a successful restart, never on a resume (ruling E87). The window hands its drain out through the package-private `MainController.audioHealthDrain()`. In story 337 the fact shows only as one ERROR toast and its history entry, with the action (ruling E41); book §3.4 rules out a new `EngineState` constant for it.
- **Restart Audio Engine is one method.** `public Thread MainController.restartAudioEngine()` applies the current settings through `audioEngineController.applyConfiguration(...)` on a virtual thread named `daw-audio-engine-restart`, then, when it succeeded — it returned normally and, if a stream was open when it began, one is open again — clears the fact on the FX thread (ruling E62); a declined record guard keeps the take and restarts nothing (ruling E12). The watchdog's restart offer can reuse it.
- **What the xrun feed can read.** The guards count failures, not dropped buffers: `audioHealth().total(...)` for `CALLBACK`, `SINK`, `PACING`, `INPUT` and `WORKER`, and `audioHealth().backendCounters()` for a backend's own counts. `audio.worker` counts worker tasks that threw, not graph overloads. The ring-overflow drop counters (`CallbackBackendAdapter.droppedOutputBlocks()` and `droppedInputBlocks()`, `EngineStreamPump.droppedInputBlocks()`) are unchanged, package-private and not in the record. `AudioHealthRecord.read`, the drain's one reading per frame, has exactly one consumer, the window's drain, so the watchdog and the xrun feed read totals and heartbeats only. Each single-fact reader (`total`, `backendCounters()`, `renderDriveBeats()`, `deviceCallbackPeriods()`) is one consistent cut of its own; a reader that combines several facts reads one cut of each, not one cut of all (story 337, rulings E79 and E82). Do not copy `XrunEventRingBuffer.poll`: it advances `head` before its caller reads the slot (`head.lazySet(h + 1); return slot;`), so the producer can reuse a slot still being read; the lanes copy a slot, null its references, then advance.
- **Take dropout counts stay this story's.** Story 337 did not put the capture ring's overflow and truncation counts on its channel (ruling E47): `CaptureRing`'s producer-only counters are read by the flush thread, which reports through `RecordingPipeline`'s warning sink. The Recording Reliability book gives dropout counters during a take to this story.
- **What is left of the Note from Story 336.** The pump now catches `Throwable` throughout (ruling E9): a render fault is counted, a sustained one or a `VirtualMachineError` is the halt above, and an outer catch-all turns anything else into the same halt, so the thread no longer dies by unwinding. Its per-thread uncaught-exception handler stays as a last-resort backstop, for a throwable the catch-all itself cannot handle, and that handler's SEVERE record ("engine-render-pump thread died; …") still reaches only the log file. Surfacing that backstop is still this story's.

## Resolution

A dead or stalled audio device is no longer silent. A device that stops calling back and a render drive that stops beating are declared lost on every backend, an unplugged interface among them when its driver stops calling back, within max(2 s, 8 buffer periods) of the last period (5 s while a stream is still starting), by a watchdog that only reads story 337's two heartbeat counters: the stream is closed through the same steps as a host-reported removal, a take in flight is sealed and rescued, the transport stops where the audio stopped, the input meters fall to the floor, the session status strip's new Engine cell reads "Device lost: <name>" in the warning accent, and the notice offers Reconnect, which reopens only the lost device. An input that stops delivering raises story 337's input-halt fault, and during a take its tracks are marked in `take.manifest` at the frame where it stopped and warned once while the take keeps recording. The strip's new Xruns cell counts observed gaps only and opens an xrun log that also lists late blocks, CPU-budget sheds and stalls; a take's dropouts show beside the count and stay after the take until Clear. The ASIO clock source shows beside the transport status, its lock measured from the driver's sample position and resync messages, so it can warn only of a lost clock that those reports show (ruling E147, a Known limit); an unlock warns and marks the take and never stops it. The render pump's last-resort death is a halt with one notice. Every Goal and every Goals — Tests bullet is answered below, by a named test or by the ruling that changed it ("**Goals and Goals — Tests, one by one.**"); the story 327 hardware proof is the owner's, written out under Verification.

**The ASIO driver messages, and a live defect fixed on the way.** `AsioFormatChangeShim`'s selector constants did not match the ASIO SDK's enum: at HEAD the resync request was 4, supports-time-info 5 and buffer-size change 7. A driver's supports-time-info message, which a driver may send while its buffers are created, therefore ran the buffer-size-change teardown, latched a driver reset and quiesced the stream at its open. The constants are now `kAsioBufferSizeChange = 4`, `kAsioResyncRequest = 5`, `kAsioLatenciesChanged = 6`, `kAsioSupportsTimeInfo = 7` and the new `kAsioOverload = 15` (1, 2 and 3 were right), pinned by `AsioFormatChangeShimTest.selectorConstantsMatchTheAsioSdkEnum`. `dispatch` answers an overload message with ASE_OK and counts it on the backend (`AsioBackend.noteDriverOverload`), and answers a resync request "supported" and counts it (`noteDriverResync`: the arrival time, then the count), never stopping or reopening the stream and never publishing a format-change request (rulings E37 and E38); a reset request and a real buffer-size change keep story 218's reopen. Tests: `AsioFormatChangeShimTest.resyncRequestIsCountedOncePerMessageAndPublishesNothing` and `overloadIsAnsweredCountedOnTheBackendAcrossShimsAndPublishesNothing`; `resyncRequestLeavesTheStreamingBridgeRunning` now asserts that nothing is announced; `resyncRequestSelectorEmitsClockSourceChange`, which pinned the overruled behaviour, is removed.

**What a backend counts.** daw-sdk's new `record BackendDropoutCounters(outputStarvedPeriods, outputDiscardedBlocks, driverOverloads, driverResyncs, inputBlocksDropped, reportsOutputStarvation)` (`NONE`, `plus`, negative counts refused) is returned by the new default `AudioBackend.dropoutCounters()`; its counts are monotonic for the backend object's life, a backend that rebuilds its bridge per open folding the old bridge's counts at close. On ASIO, `AsioBufferSwitchShim` keeps single-writer `volatile long` counters on the threads that already run there: a period that found the output ring empty, counted only once the bridge has played a rendered block; an input block the full capture ring refused; an output block the full output ring refused, once primed; and the older queued blocks a callback skipped to play the newest (`AudioBlockRing.drainLatestCountingInto`). On PortAudio, `CallbackBackendAdapter` counts starved periods in `deviceCallback` once primed, its rings' overflows and each block its drain loop's publisher dropped. `AudioBackendSupport` counts each input block a subscriber dropped once (amendment A3), which `AsioBackend`, `JavaxSoundBackend` and `MockAudioBackend` report. `AudioEngine.dropoutCounters()` reads the open stream's backend lock-free and answers `NONE` with no stream or when the backend's report throws. `AudioBackend.newestDriverResyncNanos()` (empty by default; `AsioBackend` overrides it) dates a resync at the driver message's arrival. Tests: the ten new tests of `AsioBufferSwitchShimTest`, among them `anEmptyRingAfterTheFirstPlayedBlockCountsOneStarvedPeriod`, `emptyCallbacksBeforeTheFirstRenderedBlockAreStartUpNotStarvation`, `aFullCaptureRingCountsEachBlockItLoses` and `olderBlocksACallbackSkipsToPlayTheNewestAreCounted`; `AsioBackendDropoutCountersTest` (4, through the backend's own open and close); `AudioBlockRingTest.theCountingDrainReportsEverySlotItConsumedAndPlaysTheNewest`; `CallbackBackendAdapterTest.emptyPeriodsCountAsStarvedOnlyAfterTheFirstPlayedBlock`, `aReopenStartsUnprimedAndACallbackWithoutARingCountsNothing`, `ringOverflowsReachTheDiscardedAndDroppedInputCounts` and `aBlockDroppedAtPublishJoinsTheDroppedInputBlocksOnce`; `AudioBackendSupportTest.inputBlocksDroppedCountsEachDroppedBlockOnce` and `aCloseRaceIsNotCountedAsADroppedBlock`; `BackendDropoutCountersTest` (4); `ClockSourceTest.mockDropoutCountersReportTheInputPublishersDrops`; `JavaxSoundBackendTest.dropoutCountersReportTheInputPublishersDrops`; and `AudioEngineBackendCountersTest.dropoutCountersAreTheOpenStreamsBackendsAndNoneWithoutAStream`.

**The xrun detector, real-time pure and fed.** `XrunDetector` is rewritten. `recordTick(long)` is its one real-time method, `@RealTimeSafe`: plain stores into single-writer `volatile long` fields, the overshoot before its count, with no allocation, logging, publisher, lambda or atomic read-modify-write, and it cannot throw. `reset()`, `beginTick()`, `Tick` and the injected clock are gone. `publishPending()` is `synchronized`, runs off the real-time thread and offers at most `MAX_EVENTS_PER_PUBLISH` (16) events per call, the counts staying exact; `reportDropped(count)` makes one offer per call; a closed publisher never makes a method throw; the borrowing constructors leave the publisher open at `close()`. The class Javadoc's claim that the render thread never blocks is now true. `EngineStreamPump.renderOneBlock` reads `System.nanoTime()` around `engine.processBlock(...)` and ticks only when it returned `true`; the pump takes the detector once at construction from `AudioEngine.setXrunDetector`. The controller owns one `SubmissionPublisher<XrunEvent>` that every detector borrows, so `AudioEngineController.xrunEvents()` survives every rebuild; both rebuild sites publish what is pending, swap the detector and hand the new one to the engine before the reopen. `RealTimeSafeContractTest.theRenderDriveLoopIsGuardClean` follows the drive into `XrunDetector` and must reach `recordTick`; its allow-list is still two entries and the class still documents fourteen invariants (invariant 10's wording, in both copies of the `dawg-annotations-reflection` skill too). Tests: `XrunDetectorTest` (10, rewritten in place: `onTimeBufferEmitsNoEvent`, `lateBufferEmitsBufferLateEvent`, `veryLateBufferEmitsBufferDroppedEvent`, `recordTickAssignsIncrementingFrameIndices` and `resetClearsAllCountersAndFrameIndex` are gone with the API they pinned), among them `ticksAreClassifiedAndCountedWithoutTouchingThePublisher` and `publishPendingOffersAtMostTheCapAndKeepsTheCountsExact`; `EngineStreamPumpTest.aRenderedBlockSlowerThanTwoPeriodsTicksTheEnginesDetectorAsDropped` (the real wiring) and `aFaultedBlockIsARenderFaultAndNeverATick`; `EngineReconfiguringStateTest.theXrunPublisherOutlivesEachDetectorRebuildAndTheEngineTicksTheNewDetector`.

**The pump's last-resort death.** `EngineStreamPump`'s per-thread uncaught-exception handler writes its SEVERE record ("engine-render-pump thread died; …") first, then calls the pump's own `halt(failure)` inside a catch-all, so the death is recorded as the drive's halt and story 337's drain gives it the halt treatment once: the transport stopped, the stream closed once the take allows it, the fact latched, the ERROR with Restart Audio Engine or, for a `VirtualMachineError`, the FATAL copy with Open Log Folder (ruling E33). Exactly one method is named `halt`, and main code never calls `getUncaughtExceptionHandler()`. Test: `EngineStreamPumpTest.aLastResortThreadDeathIsLoggedThenRecordedAsTheDrivesHalt` (one SEVERE record carrying the error, written before the `RENDER_HALTED` count moves; then the count 1, the error as last failure, the pump halted).

**The heartbeat watchdog and the engine health monitor.** `EngineHeartbeatWatchdog` (daw-app `ui`) is pure decision logic over a small probe and an injected clock; it owns no thread. Each tick samples epoch, alive, counters and inputs, alive, epoch, and a sample counts only when both alive reads are true and the epoch did not move. It watches the device-period count where the backend reports one and the render drive's beats otherwise (the Note from Story 337). The window is `windowFor` = max(2 s, 8 buffer periods) (`MIN_WINDOW_NANOS`, `WINDOW_PERIODS`), re-read from the engine's format at each re-baseline, and until the first advance in a render-drive epoch it is `startupAllowanceFor` = max(5 s, the window) (`MIN_STARTUP_ALLOWANCE_NANOS`; rulings E1 and E2); `allowForAClockSourceSwitch()` grants the same allowance after a clock-source switch the person sent (ruling E107). It re-baselines when the epoch changes, when the drive is not alive, when the watched kind changes, when a tick arrives later than twice its interval and when the controller refuses a verdict; one verdict per epoch is latched, and only when the controller accepts it. A paused or closed stream, a halted drive and a stream being closed are never judged (ruling E9). Inputs are judged per capture input (`CaptureInputSnapshot`): quiet time accrues only over ticks in which the render beats advanced, and the device periods too where the backend reports them, so a dead device is the stream's verdict, not an input stall; an input that delivered and then stayed quiet for the window is declared `STOPPED`, and one that delivered nothing within the start-up allowance while a recording capture is active is declared `NEVER_DELIVERED`, each handle once. `DefaultAudioEngineController` runs it on one single-thread daemon scheduler, "daw-engine-health-monitor", at normal priority and a 100 ms fixed delay (`ENGINE_HEALTH_TICK_MILLIS`), created only by `startEngineHealthMonitor()` (lock-free, idempotent, a no-op after a stop or a shutdown) and stopped by a flag and `shutdown()`, never `shutdownNow()`. One monitor serves the controller's life; a reconfigure does not rebuild it, the watchdog re-baselining on the new epoch instead. Each tick runs the watchdog, then the xrun feed, then `publishPending()`, inside a catch of `RuntimeException` and `VirtualMachineError` that logs and abandons that tick only. `MainController` starts the monitor right after the engine-state bridge subscribes and stops it in window disposal before the bridge is cancelled. **The ASIO clock-lock monitor.** daw-sdk's new package-private `AsioClockLockMonitor`, owned by `AsioBackend`, runs one platform daemon thread, "asio-clock-monitor", per open, polling every second (`POLL_INTERVAL`). It starts at the end of a successful open unless a driver reset is latched, is stopped by a flag, a generation bump and an unpark as the first statement of `close()`'s locked body, never by an interrupt (an interrupted caller of `AsioControlThread.call` would poison every later ASIO call), pauses for a driver reset and never takes the driver lifecycle lock. Each stream starts fresh (ruling E82): the source is read on the first tick, and a device with a single source or a source classified internal is never polled (ruling E60). A bad answer is "no clock" (-995), "not advancing" (-996) or an OK answer with an unchanged sample position, each counted only if the device periods advanced since the previous poll (rulings E29 and E59). The poll interval is the unit (ruling E106): an interval is bad if it holds a bad answer or a resync; an interval whose periods stood still, or whose poll only set a new position baseline with no resync, is not judged and breaks both runs (rulings E120, E121 and E140); two consecutive bad intervals unlock (`BAD_ANSWERS_TO_UNLOCK`), and three consecutive good ones relock an unlock of this measurement (`GOOD_ANSWERS_TO_RELOCK`). `AsioBackend.selectClockSource` calls `switchSent()` before its driver call and `switchAnswered(accepted)` after it on every exit; while a switch is pending every interval is a switch interval, and the window lasts two polls (`SWITCH_INTERVALS`) counted from the driver's answer, accepted or refused, during which resyncs are counted, logged and marked but judge nothing; only an accepted switch makes the source be read again (rulings E122, E137 and E138). A source that cannot be read keeps the lock state, judges nothing and is read again every ten intervals (`SOURCE_RETRY_INTERVALS`, ruling E80). While the driver's control panel is open nothing is sent to the driver, and the source is read again when it closes. The monitor publishes a level, `ClockLockStatus(device, sourceId, serial, lock, evidenceNanos)` with `Lock {NOT_MEASURABLE, CHECKING, LOCKED, UNLOCKED}`, read lock-free and without a driver call through `AudioBackend.clockLockStatus()`, `AudioEngine.openStreamClockLockStatus()` and `AudioEngineController.clockLockStatus()`. `ClockLockEvent` (now with `evidenceNanos` and a compatibility constructor; amendment A4) is still published on `AsioBackend.clockLockEvents()` and re-published by the controller's own publisher, but the badge does not subscribe. **The clock badge.** `ClockStatusIndicator` (899 lines) is mounted once, immediately before the transport status label (`MainController.mountClockStatusIndicator`, ruling E32), and installed by `installClockStatusIndicator` as a pulse participant whose stream-opened callback only asks for an early look; window disposal undoes both. **Known limits.**
- A halt that throws inside the pump's last-resort handler leaves only the handler's SEVERE record in the log.
- The loss reaction holds the controller's monitor across the pump's bounded join and the backend's close, as the host's removal path already did, and a driver whose close never returns holds it for as long.
- After a backend's own counter report fails (story 337, ruling E78) its device periods read empty, and the watchdog falls back to the render drive's beats, which keep cycling on PortAudio and ASIO: a device stall there is not detected while that backend stays open.
- A narrow race between the verdict's re-check and a Record start that begins at that moment: the Record start can open its stream just after the re-check, and the loss then closes that stream, perhaps a running one. The person sees the stall's notice with Reconnect and "Recording aborted — no take was started: …", and no take is made; the new stream's own announcement, delivered after the loss, then ends the loss with no stream open, so the Engine cell's "Device lost" goes at once and the notice's Reconnect does nothing. The next Play or Record opens the device as usual. Read in the code only; no test drives this race.
- A paused stream is not watched: an unplug while the stream is paused, or parked by a Reconnect, is noticed about 5 s after a later resume of that stream, the start-up allowance of a new render drive. A Play can resume it, and so can a Record that records no audio input (a MIDI-only take, for instance), and until the notice the transport then rolls over silence; a Record with audio inputs does not resume it: past its route checks it closes the paused stream and then tries to open a new one, as any open does. A Pause can pause the stream, but not while an instrument insert in the mixer keeps it running: then the stream is watched as during playback, and a device that stops calling back while the transport is paused or stopped is declared lost after the window, with no rolling over silence (rulings E2, E9, E150 and E163).
- The watchdog notices an unplug only when the driver stops calling back. - `CallbackBackendAdapter` forwards no clock facts of its delegate (no lock status and no clock-lock events), so the lock of a clock source behind it is never measured.
- A render drive wedged in a backend's write keeps the old stream from letting go: Reconnect then says "the previous audio stream has not shut down yet" until the write returns (`ReconnectAgainstOtherOpensTest.aReconnectWhileTheStalledStreamHasNotShutDownSaysSoAndALaterOneReopens`).
