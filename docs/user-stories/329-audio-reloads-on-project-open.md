# Audio Reloads on Project Open

## Motivation

Reopening a saved project restores metadata, not music. The deserializer rebuilds every `AudioClip` from name, position, duration, and the persisted source path only — `ProjectDeserializer.java:539` constructs the clip and never calls `setAudioData`; `AudioClip.setAudioData` (`AudioClip.java:327`) is called by importers, recording, and clip-edit actions, never by any load path. Both consumers of a clip's audio read the in-memory array: the render loop resolves `clip.getAudioData()` (`RenderPipeline.java:1069`) and **skips the clip entirely** when it is null or empty (`RenderPipeline.java:894-895`), and the arrangement waveform draws from the same array (`ClipOverlayRenderer.java:152`). A reopened project therefore *plays silence and renders empty clips* — every clip, every time, even when the source WAV is sitting right there on disk.

Worse, the deserializer already *knows* when sources are gone: it collects every missing path during load (`ProjectDeserializer.java:532`, `:535`) into an accessor (`ProjectDeserializer.java:133`) whose only callers are round-trip tests. The production open path (`ProjectLifecycleController.java:844`) never consults it and shows an unconditional "Opened project: …" `SUCCESS` notification (`ProjectLifecycleController.java:866`) for a project whose audio may be wholly gone.

For a studio engineer this breaks the single most basic promise a DAW makes: yesterday's session reopens today as a silent shell of clip outlines, with a green success toast on top. This is the loudest blocker in the whole persistence audit.

## Goals

- Implement the clip rehydrator (design book §4.3): after deserialization, every `AudioClip` that carries a source reference but no sample data is queued for rehydration on background virtual threads — decode the source file, populate the clip's audio data via `setAudioData`, and publish per-clip completion to the FX thread through the established `FxDispatcher` marshalling seam so waveforms appear as data lands.
- Playback readiness is a **per-clip** fact, not a whole-project gate: a 40-track project must not block its window (or the FX thread) behind 40 decodes. Rehydration is eager-but-async — lazy decode-on-first-read is explicitly rejected (§4.3) because the render pipeline's clip skip is silent, so a lazy miss during playback would reproduce the silent-clip symptom for the first bars.
- Surface the deserializer's already-collected missing-file list as a **missing-assets report**: one warning surface per open with count + paths and a relink affordance (locate file / locate folder / skip), mirroring the archive dialog's per-asset pattern; the report links the archive consolidation flow (story 189) as the recovery-of-last-resort, not duplicating it.
- The open notification becomes **outcome-qualified**: plain success only when every referenced asset resolved; otherwise "opened with N missing assets" (design book §5.3 step 8, rejection §9.11).
- Path semantics (design book §3.3): asset references inside `project.daw` normalise **project-relative** (forward-slash) on the next save; absolute paths remain accepted on read for backward compatibility; relinked paths are re-persisted project-relative when the asset lives under the project directory, and stay absolute when it does not (shared sample libraries).

## Goals — Tests

- **Round-trip playback test**: import audio → save → close → reopen → the clip's audio data is non-empty, the render pipeline no longer skips it, and the waveform renders identically to the pre-save state (the first row of the book's §5.1 round-trip contract goes green).
- **Missing-source test**: delete a clip's source file → reopen → the missing-assets report appears exactly once with the correct count and paths, and the open notification is qualified — never the unconditional `SUCCESS` toast.
- **Relink test**: relinking a missing asset restores its playback/waveform in the open session and re-persists the new reference project-relative on the next save.
- **No-FX-stall test**: opening a many-clip project performs no decode on the FX thread; per-clip completions arrive through the dispatcher seam (coalesced), and the window is interactive before rehydration completes.
- **Path-normalisation test**: a legacy absolute path pointing inside the project directory loads correctly and is rewritten project-relative on the next save; a reference outside the project directory stays absolute.

## Non-Goals

- Serializing state that is never written today (MIDI, tempo map, takes, plugin descriptors) — stories 330 and 334 own the write-side inventory.
- Making recorded audio exist durably under the project directory with project-relative segment paths — `RECORDING_RELIABILITY_DESIGN_BOOK.md` story 323 owns capture-to-disk; this story reloads whatever the write side persisted.
- Wiring the engine so reloaded audio is *heard* through the transport — `AUDIO_ENGINE_WIRING_DESIGN_BOOK.md` story 314.
- Waveform rendering correctness beyond "no longer empty" (source-offset truth after trim/split/slip) — `INTERACTION_COMPLETENESS_DESIGN_BOOK.md` story 342 consumes the data this story rehydrates.
- The archive consolidation flow itself — story 189 (landed); the relink surface links to it.
- Atomicity of the save that persists relinked paths — story 331.

## Resolution

Reopening a project now reloads its audio. `ProjectManager.openProject` turns the deserializer's missing-file list into the open's `MissingAssetsReport` (`MissingAssetsReport.atOpen`, read through `ProjectManager.getLastMissingAssets()`) without touching the disk, and resets it on create, close, abandon and a legacy metadata-only open. The core `ClipRehydrator` then starts one `RehydrationSession` covering every clip that has an openable source reference, no audio and no report row. Clips are grouped by `AssetReference` — a file, or a recorded take's whole ordered segment list — so each source is decoded once, and the sources under the playhead go first, then those ahead of it, then the rest. One job per source runs on the session's virtual threads, and `DecodeGate` admits the jobs strictly in ticket order under `max(1, min(4, processors − 2))` permits and a memory budget of a quarter of the heap: a source estimated above the budget waits until nothing else runs and then runs alone, one estimated above half the heap is not attempted (`TOO_LARGE`), an `OutOfMemoryError` inside a job is contained to that source as `TOO_LARGE`, and any other failure is contained to its source too. Workers only decode. A single file goes through the import's own decode and conversion to the project rate — `ReferenceFileLoader.read` and `ReferenceFileLoader.convertSampleRate` are now the one implementation the importer and the rehydrator share — so the reloaded audio is sample-identical to what the import held, with no `SourceRateMetadata`; a take is read with `SegmentFile.readFrames` at its capture rate, with the `SourceRateMetadata` the capture path attaches; an ADM BWF file is recognised from its RIFF chunk headers alone (`AdmBwfImporter.isAdmBwf` no longer reads the whole file) and parsed once into the import's bed and object audio (`AdmClipAudio.extract`). `RehydrationSession.apply` attaches on the FX thread: it walks the live project at that moment and gives every clip that still reads the source and has no audio the same array instance — so halves split before their audio landed still glue — sets a take's metadata before its array, never overwrites audio and never marks the project dirty. Loading is not an edit.

In the application, `OpenProjectAudio` owns the open project's audio on the FX thread. `ProjectLifecycleController.loadProjectFromPath(Path, OpenDoor)` parses, installs the project clean and calls `OpenProjectAudio.begin`, which starts the session and returns at once: no decode runs on the FX thread or holds the open, and the window is interactive while clips load. Each open has one FIFO completion queue and one keyed `FxDispatcher` drain. Decode threads only queue each outcome and, last, the run's end, then post `onFx` under the open's one key; the drain empties the queue on the FX thread, applies every outcome, adds the rows they produce to the live report, updates the status strip and repaints the arrangement once. That is how the Technical Notes' "per-clip coalescing keys" were realised: one key per fact — this open has completions — over a queue, so no completion is lost to the dispatcher's coalescing, the run's end never overtakes an outcome, and a pulse repaints at most once however many clips landed. Before any effect — an attach, a row, the strip, the announcement, the report, a repaint — the FX thread checks the open's generation and that its project is still the live project; the core's `cancel()` is only best-effort. A late completion of a project that was replaced, closed or torn down therefore does nothing, a `Review…` left in the notification history carries the open's number, never its project, and `ProjectLifecycleController.dispose()` retires the run from the window's teardown. A failure applying one completion is contained to it, and the progress, the run's end and the repaint still run; once the end has been taken, every source the session still owes — its outcome lost, or its apply failed — is settled (`RehydrationSession.settlePending`) as a `Can't read` row with the detail `loading did not complete` over its clips still without audio, so a run never stays loading. The open project's audio is retired only once the new project has parsed: an open that fails leaves the project on screen with its clips still loading, its report and its relink, while New Project, Import DAWproject Exchange and a Roll back that abandons the project retire it first.

Until a clip's audio lands, `ClipOverlayRenderer` draws a `Loading…` placeholder (a dashed line) in its body, and `Offline` (a hatch) for a clip that reads from a file, has no audio and that nothing is loading — missing, unreadable, too large or skipped. Both are clamped to the visible canvas, and a clip with no source reference keeps the plain body (`ClipAudioState`). The status strip shows the named operation `Loading audio — N of M` (sources applied of sources scheduled) until the run ends or is retired. A load that a migration Roll back re-entered stays quiet: `loadProjectFromPath` numbers its attempts, and the superseded outer call neither announces nor opens the journal and returns the inner load's result. The write-ahead journal opens only for the open that is still current, so a Roll back with no `.bak`, which abandons the project for an Untitled one, opens no journal for the folder it left.

Every door that installs a deserialized project — open, archive restore, journal replay, the recovered-write-failed and failed-replay fallbacks, a migration roll-back's reload and snapshot restore (`OpenDoor`) — shows exactly one announcement (`OpenAnnouncement`), made when the references have been classified found or missing and never waiting for decodes; the doors that used to post their own message pass their `OpenDoor` instead. With nothing missing or short it is the door's own message at its usual level: SUCCESS for `Opened project: Song`, INFO for a snapshot restore, ERROR for the two fallbacks. Otherwise it is qualified by distinct assets — a take is one asset, and split halves of one file are one — at WARNING (the fallbacks keep ERROR), with a `Review…` action when the report has rows, for example `Opened project: Song — 2 missing assets (3 clips silent), 1 asset shorter than its clips`. The silent-clip count is left out when it is zero, and the archive door puts the same clauses in its parentheses. Rows the run adds after the announcement — a source deleted after the open, or a file that does not decode, is too large, is shorter than its clips or selects no ADM bed or object — get at most one follow-up WARNING with `Review…` when the run ends, for example `1 asset could not be loaded as saved; 1 asset shorter than its clips`.

The report is `MissingAssetsDialog`, a non-modal `DawgDialog` owned by the main window. It is shown once per open, after the migration report, when the report has rows at announcement time, and is otherwise reached through `Review…`; every `Review…` and the File menu's `Relink Missing Assets…` item re-present the same instance, and retiring the open closes it. The menu item sits after `Restore from Archive…` (there is no Project menu), is enabled while any row remains, answers `No missing assets to relink` when nothing is left, and is the new action `DawAction.RELINK_MISSING_ASSETS`, with no default key. Each row is one asset and reason (a shorter ADM file whose clips partly select nothing has two rows): its label — `Missing`, `Can't read`, `Shorter than the clip`, `Needs re-import (ADM: object unknown)` or `Too large to load` — its detail, its path (the full path in a tooltip), how many clips hold it, naming the first six, and `Locate file…` and `Skip`. Above the rows sits `Locate folder…`; below them, in a Recovery section, an `Archive project…` link to story 189's consolidation flow, the recovery of last resort. Every row and control has accessible text, and Skip's says whether the asset's clips stay silent, keep playing as loaded, or how many of them stay silent. Skip hides the asset's rows for this session and changes nothing else: the clips keep their references, so a returning drive or a later relink still works, and the project stays clean.

Locate file opens in the project folder — for a take whose folder lies inside the project folder, in that folder or its nearest existing ancestor, and never at a path outside the project, so an offline share cannot stall the FX thread — and for a take it uses the picked file's folder and finds every segment there by name, all or none. Locate folder walks one chosen folder recursively off the FX thread (`MissingAssetSearch`), never following symbolic links or junctions, and can be cancelled (`Cancel search`). It matches file names ignoring case, prefers the candidate that shares the longest trailing path with the original reference, leaves a tie alone (`2 candidates — use Locate file…`), finds a take only whole and in its own take folder, and relinks every row it can (`Relinked 2 assets from <folder>`). The located file is decoded and checked on a worker (`AssetRelinker.prepare`): one that does not decode, a take with a segment missing from the folder or with segments that disagree, or a file above half the heap is refused on its row with the reason, and nothing changes. A candidate is applied on the FX thread by `AssetRelinker.apply` with the audio already decoded: every clip that holds the asset is re-pointed, gets the one array (for an ADM file, the array of its own bed or object; a clip whose name selects nothing in the located file is re-pointed without audio and becomes a silent clip of a `Needs re-import (ADM: object unknown)` row), replacing any audio it had, and has its sample-rate conversions invalidated, and the project is marked dirty. Relink is not an undo-stack entry — undoing it would silence the clips again — and the next save writes the new reference project-relative when it lies under the project folder and absolute outside it (`ProjectSerializer` through `ProjectPaths`). When a candidate needs consent the user gets one confirmation, `Use This File?` with the button `Use It`, which names the file and gives each reason that applies, in this order, then `Use it anyway?`: a take found outside its own take folder (`<picked take>/<track> is not this take's folder <take>/<track>.`, both named by their take and track folders), an ADM import's clips given a file without ADM metadata, and a file shorter than its clips use (`tone.wav holds 0.25 s; its clips use up to 1.00 s.`). Declining changes nothing. `SampleRateConversionCache` entries now remember the array they converted and convert again when the clip holds another array, so a relinked take is never served a conversion of its old audio.

Path semantics for clip references are the rule story 323 put in place (`ProjectPaths`): a reference under the project folder is saved project-relative, one outside it absolute, and a legacy absolute reference inside the folder reloads and is rewritten project-relative on the next save (`ClipReferencePathNormalizationTest`); a relinked reference follows the same rule. The other asset references in `project.daw`, which story 323's notes pointed at this story, are not under the rule yet: a reference track's `source-file` is written as held and, when relative, checked against the JVM's working directory (story 359), and a SoundFont assignment's path is written as held, with backslashes turned into forward slashes, and not checked on open.

ADM BWF clips get their own bed or object back by name: with every trailing ` (split)` removed, a clip's name must equal the parsed file's bed name (`Bed (<layout>)`) or the name of one of its objects (`Object <n>`). Clips that select the same bed or object of one file share one array, and a clip whose name selects nothing is never guessed: it stays silent under a `Needs re-import (ADM: object unknown)` row that says what the file has. An asset is an ADM import (`DecodedAudio.isAdmImport`) when the names of the clips that hold it, after every trailing ` (split)` is stripped, include at least two distinct names of ADM import form (`AdmClipAudio.hasImportNameForm`); clips with other names do not disqualify it. One distinct name is treated as a plain file, because a user may import a plain `Object 1.wav`. When such an asset's file decodes without ADM metadata, no clip gets it at open — each would play the same channels instead of its own bed or object — and every holder, whatever its name, is a silent clip of that row; a relink to such a file asks first and, once confirmed, attaches it as a plain file to every holder for this session. The first rule required every holder to have an ADM import form, on the studio-engineer's premise that nothing gives an ADM master's clips other names. Import DAWproject Exchange breaks that premise: it keeps each clip's name and file path exactly as the DAWproject file gives them (`DawProjectXmlParser.parseClip`, `SessionInterchangeController.addClipsToTrack`). Today the parser reads clips only from `Structure/Track/Lanes/Clips`, the layout this application's own export writes, and not from the `Arrangement` lanes where the published DAWproject format places them, so a file written by another program currently imports with no clips; the looser rule covers a file in this application's layout that was edited outside it today, and another program's files once the parser reads arrangement lanes (story 363). Under the first rule, such a session — an ADM import that came back with one of the master's clips renamed — would give the bed and every object clip the same channels of a master without ADM metadata, with no row. This story is what makes those clips load, so it adopts the studio-engineer's looser rule.

Import DAWproject Exchange never runs the ADM import. It creates the clips without audio, and after a save and reopen a clip on an ADM BWF file gets its bed or object by its name, exactly as above. A clip on a file that carries ADM metadata, whose name is not one of the file's import names (for example one multichannel clip renamed `Immersive Master` outside this application, or, once another program's file imports clips (story 363), so named by that program), stays silent under a `Needs re-import (ADM: object unknown)` row that lists what the file has. Relinking it to the same file cannot help, because the file is read as ADM from its own chunks and the application has no clip rename. Import Audio on the master, which makes its bed and object tracks, does. So does Locate file to a plain bounce, but only when that clip is the file's only clip. When the file's bed and object clips hold it too, Locate file re-points every one of them and asks the ADM question first. The rule judges clip names only. If the DAWproject file leaves fewer than two distinct ADM-form names on a master that has no ADM metadata, nothing marks its clips as an ADM import's, and every one of them plays the same channels of it. This is the same residual as an ADM import cut down to clips of one name. The import keeps an archive-relative path such as `audio/master.wav` as written and does not extract the archive, so after a save the path resolves under the new project folder and is `Missing` until relinked. Only a RIFF `.wav` file (not BW64 or RF64) with an `axml` chunk is read as ADM, and once another program's file imports clips (story 363), whether a copy that program packed into its archive still carries the master's `axml` chunk will depend on that program. This application's own DAWproject export writes each clip's name and path as held and puts no audio in the archive, so its ADM clips survive an export and a re-import into this application by their names alone.

The length check is the only check a reload allows, because nothing persisted records a clip's channel or frame count. A clip uses `(sourceOffsetBeats + durationBeats) × 60 / bpm` seconds of its source at the transport's tempo (`Transport.getTempo()`, the tempo `RenderPipeline` plays every audio clip at), and a source more than 10 ms shorter loads as it is under a `Shorter than the clip` row with the detail `holds X s; the clip spans Y s at the current tempo; loaded as it is` (two decimals). That row is relinkable but neither missing nor silent: its clips play, the announcement counts it as an asset shorter than its clips, and the render guard does not count its clips as silent. The label never claims the file changed (the enum constant keeps the name `CHANGED_ON_DISK`), because a file replaced by a shorter one and a song slowed after the import look the same. A renderer that follows the tempo map must replace this rule with one beat-to-source-frame function that it and the check both call.

`RenderReadinessGuard` is consulted before anything is rendered by a track's `Export as WAV` and by both freeze entry points (`TrackFreezeController.freezeTrack` and `freezeTracks`). While a clip on the rendered tracks is still loading it refuses with the WARNING `Audio is still loading (N of M) — try again when loading completes` (the counts are the whole project's). When clips on those tracks would render silent it asks once, titled `Missing Audio`: `1 clip has missing audio and will be silent. Export anyway?` (`Export Anyway`), or for a freeze `… will be silent in the frozen audio. The frozen audio stays silent until you unfreeze or freeze again, even after relinking. Freeze anyway?` (`Freeze Anyway`). With no current open it still asks about clips that read from a file and have no audio, such as the clips the DAWproject Exchange import creates. Of the other render paths the inventory found, AAF, bundle and ADM BWF export and render-in-place have no caller in the application, and the render queue's runner, built when the Render Queue window opens, never receives a job (nothing enqueues one) and its handlers are stubs, so no guard was added there. No application edit reads a clip's samples in a way that fails without them, so no edit guard was added either.

A defect present at the base commit was fixed on the way, because the open path runs through it. `MigrationReportDialog` could never close: its OK was `ButtonType.OK`, whose button data is `OK_DONE` rather than a cancel, and its result converter returned null, so after OK or a confirmed Roll back the dialog stayed up and the load that showed it never resumed. OK is now `MigrationReportDialog.OK_BUTTON_TYPE` (OK's text with `CANCEL_CLOSE` data, the default button): OK, Esc and the window's close button close the dialog with OK's meaning, a declined Roll back keeps it open, and a confirmed Roll back closes it. Its roll-back also ran inside the result converter, so the reload, with its own migration dialog, ran while the first dialog was still open; the converter now does its work once and only records a confirmed Roll back, which `showIfNeeded` runs once after `showAndWait()` returns.

It may also name the project track in a take confirmation, where two tracks of one take differ only by their track id. Relink decodes run outside the rehydration run's memory budget, although each is still refused above half the heap. Relinking to a file the run is still loading gives the relinked clips and the loaded ones two arrays, so Glue will not join them. The take wording `… segments cannot be read — the take is not loaded` has no producer: a take whose segments fail `SegmentFile.readFrames`' consistency check carries that method's own message.

Accepted as built. The Locate folder INFO counts only the relinks applied without a confirmation, since every confirmation names its file. A confirmed relink of an ADM import's clips to a plain file is not remembered, so the next open raises the row again and silences them; an object clip playing the whole program is never a deliverable state. A plain file whose clips carry two or more distinct ADM-form names — which a DAWproject Exchange import can produce (for example `Bed (30s)` and `Bed (60s)`), as can Locate file pointing two missing, differently named assets (for example `Object 1` and `Object 2`) at one file — is taken for an ADM import: its clips are silent under the ADM row until Locate file on the same file and `Use It`. The shorter row's detail does not add the tempo in BPM or say "the longest clip spans". A roll-back reload announces through the migration roll-back door, so after a Roll back of a recovered-write-failed or failed-replay open, that door's own message is not shown.

Known residuals. A `Shorter than the clip` row is judged when it is raised and is not judged again after a tempo change, so its "at the current tempo" can go stale, although the audio is right. A source whose decoded audio could not be applied is reported as `Can't read` with `loading did not complete`, although the file decoded. A recovered-write-failed or failed-replay open of a migrated project whose Roll back meets a corrupt `.bak` shows `Open failed: …` and then that door's `…the last clean save could not be opened either`, although the last clean save did open. A Roll back with no `.bak` returns success from the load: the user chose to discard the migration, and the SUCCESS `Discarded in-memory migration; the on-disk file is still the original (v…)` says what happened.

## Verification
