# MIDI and Transport Settings Round-Trip

## Motivation

The serializer and deserializer have drifted into asymmetry, and whole categories of work vanish between save and reopen:

- **MIDI notes and CC lanes are never saved.** Every track owns a `MidiClip` (`Track.java:91`) that the piano roll and MIDI recording write into, but the track serializer (`ProjectSerializer.java:268` onward) writes clips, soundfont assignment, automation, and the MIDI effect chain — never the `MidiClip`. The pair `serializeMidiClip`/`deserializeMidiClip` exists (`ProjectSerializer.java:1062`, `:1130`) with **only test callers**. All piano-roll work is lost on save, silently.
- **MIDI effect chains are written and never restored.** The serializer emits a full `midi-effect-chain` element per track (`ProjectSerializer.java:341-343`); the deserializer contains no handling for it at all. Write-only persistence: the bytes are on disk, the arpeggiator settings are gone on load.
- **Pre-roll / post-roll are written and never restored.** `buildTransport` writes the three pre/post-roll attributes (`ProjectSerializer.java:252-254`); no `pre-roll` token exists anywhere in the deserializer.

For a studio engineer, every MIDI arrangement session is unconditionally destroyed by the act of saving it — and the write-only elements are worse than nothing: they waste bytes, imply safety, and rot silently (design book §2.9). Nothing *fails* today when a serializer gains an element the deserializer never learns; that structural hole is what let these three bugs ship.

## Goals

- Each track's `MidiClip` (notes, velocities, channels, CC lanes with breakpoints) embeds as a child element in `project.daw`, promoting the already-written-and-tested `serializeMidiClip` / `deserializeMidiClip` pair from test-only utility to the production path (design book §4.6).
- The `midi-effect-chain` element gains its deserializer reader: per-track MIDI-effect chains (arpeggiator settings) restore on load.
- Pre-roll / post-roll restore joins the existing loop/punch parsing in the transport deserializer.
- The **write/read parity harness** (design book §4.4) lands in this story and retroactively pins the whole current schema:
  - A schema parity test derives the element/attribute names the serializer can emit and asserts the deserializer handles each (and vice versa for required elements), failing with the offending name.
  - A model round-trip test family: build a project exercising the book's §3.1 inventory rows, save, reopen, compare fact by fact; each new serialized fact adds its assertion in the same PR.
  - Both live in `daw-core` (JavaFX-free), following the repo's conformance-sentinel tradition: the test names the contract, the failure message names the drifted element.
- Schema additions ride the story-188 migration registry with a schema-version bump and pre-migration backup; old project files open unchanged with defaults for the absent elements.

## Goals — Tests

- **Parity harness is green — and demonstrably red on regression**: removing (or renaming) any deserializer reader for an emittable element (e.g. `midi-effect-chain`) fails the build with a message naming that element. The historical write-only elements of this story would have been build failures the day they were written.
- **MIDI round-trip**: piano-roll notes (pitch, velocity, channel, timing) and CC lanes survive save → close → reopen identically.
- **MIDI-effect-chain round-trip**: per-track chain contents and settings survive save → reopen.
- **Pre/post-roll round-trip**: pre-roll/post-roll configuration survives save → reopen; the §3.1 MIDI and transport rows flip to OK.
- **Pre/post-roll edits mark the project dirty**: once pre/post-roll is restored, a pre/post-roll edit that changes the stored value marks the project dirty and one that writes the value already stored does not — the rule set for loop and punch edits in the PR #984 fix round (Control Synchronization Design Book §5.2: dirty-only, no undo entry, dirty only when the stored value changes). Today `TransportController`'s pre/post-roll setters (`onTogglePreRoll`, `onTogglePostRoll` and the spinner listener's `applySpinnerChange`, each calling `Transport.setPreRollPostRoll`) do not mark it, which is left to this story because a reload drops the value anyway. The comparison matters: `syncPreRollControls` pushes the transport's value back into the spinners, whose listener then writes that same value again — the same only while every setter derives `enabled` from the bar counts (`newPre > 0 || current.postBars() > 0`, `preBars > 0 || postBars > 0`), whereas the file stores `pre-roll-enabled` separately, so a restored `(2, 0, false)` would be echoed as `(2, 0, true)`, a different value that would dirty a just-opened project and flip its flag.
- **Migration test**: a project file written before the version bump opens unchanged through the story-188 registry, with sensible defaults where the new elements are absent.

## Non-Goals

- The tempo map, take stacks / comp selections, and plugin-slot descriptors — story 334 (it extends this story's parity harness in the same PRs).
- Audio-data rehydration and the missing-assets report — story 329.
- Making the restored MIDI-effect chain audible/processed — existing **story 151** owns the arpeggiator's processing wire-up; this story restores the persisted settings only.
- Write atomicity, snapshot isolation, and the single-save collapse — story 331.
- MIDI clip editing parity in the arrangement (move/cut/copy/split) — `INTERACTION_COMPLETENESS_DESIGN_BOOK.md` story 346; savable MIDI is its precondition.
- Forward compatibility (new files opening in old builds) — the migration registry's version check refusing with a clear message is the accepted behaviour (book §6.3).

## Resolution

Saving now keeps each track's MIDI clip, its MIDI-effect chain and the transport's pre/post-roll, and the reader reads back everything the writer writes. The project format is schema version 2. The write/read parity harness pins the whole schema, so an item the serializer writes and the deserializer never reads now fails the build. Building the harness exposed a fourth write-only item, `track@id`: track ids were written but not restored, so every id-keyed mixer reference dangled after a reopen. The studio engineer ruled it Blocking and in scope, so track identity round-trips too. Every bullet of the Goals — Tests is met as follows.

**Parity harness is green — and demonstrably red on regression.** `ProjectSchemaParityContractTest` saves the `RoundTripInventoryProjects` family (the `"full"` project, four room-shape variants and a `"kernel-substituting master"` variant) and parses it. It then deserializes the very document that was written through `DomReadRecorder`, a test-only `java.lang.reflect.Proxy` view over the `org.w3c.dom` interfaces that records every read, via the deserializer's document seam `ProjectDeserializer.deserialize(Document, Path)`, so the migration registry runs through the view too. `XmlSchemaParity` judges every element, attribute and text by its element path (`track/midi-clip/notes/note`, never a bare name, because `point`, `parameter` and `channel` each appear in several places). Direction 1, `everyItemTheSerializerEmitsIsReadByTheDeserializer`, reports an unread item as `Write-only persistence (Persistence Integrity book §2.9, §9.3): …` with the item's path; no exemption type for write-only items exists. Direction 2, `everyNameTheDeserializerAsksForIsEmittedOrATolerableLegacyRead`, allows four reasoned reads, the master's and return buses' output-routing attributes; `noToleratedReadIsStale` checks those four. Source-derived guards (`PersistenceSourceScan`, unit-tested by `PersistenceSourceScanTest`) prove that the family emits every name literal the writer sources hold, that no writer or reader hides a name from that proof, and that the reader looks up no element nobody writes; the writer and reader files are pinned exactly (`theWriterAndReaderFilesAreExactlyTheDeclaredOnes`). The scan places code in a method by matching that method's braces, over the source with comments stripped and every string, char and text-block literal blanked, so a brace inside a literal is never counted, and it fails closed. A non-literal element write is a violation naming its line as `in no method the scan recognises` when it lies outside every recognised method's body — in a field-initializer lambda, an initializer block, a constructor, or a method whose declaration the pattern cannot read — and when it lies in a class body the scan recognises, nested inside the innermost recognised method but in none of that class's own recognised methods, so the code of such a class declared inside a builder is not credited to the builder. The scan recognises a local class, record, enum or interface by a `class`, `record`, `enum` or `interface` keyword followed by a name anywhere in the code that runs up to the brace from the previous `;`, `{` or `}` outside parentheses (so a record whose component's annotation has an array argument is one), and an anonymous class by an instance creation before its argument list that may be qualified by an enclosing instance (`this.new Maker`), carry explicit constructor type arguments (`new <String>Maker`) or carry type annotations (`new @Shared Maker`). `enclosingMethod`'s Javadoc claims no more than that: "The body of an anonymous class created in a shape `ANONYMOUS_CLASS_CREATION` does not read is read as the builder's own code", and `ANONYMOUS_CLASS_CREATION`'s Javadoc names two such shapes: type arguments before the last simple name of a qualified type (`new Outer<String>.Inner`), and an annotation whose arguments nest parentheses more than two deep. The keyword rule fails closed the other way: the block of a statement that names a variable `record` before another word (`if (record instanceof Element e) {…}`) is read as a class body. A constructor is never read as a method: it has no return type, and a modifier keyword is never taken for one, so `public Writer(…)` is not a method named `Writer`; a constructor declared as a builder is reported as a stale builder entry. A non-literal write inside a recognised method that is not a declared builder is a violation `outside a declared tag-parameter builder`, as is one inside a declared builder whose tag is not one of the builder's parameters; a tag-parameter builder used as a method reference is a violation of its own (`tag-parameter builder used as a method reference; call it with a literal tag`), because it would pass its tag out of the scan's sight. On the reader side, independently of that method parse, a file may hold no more `tagName` comparisons than lookup helpers it declares, so a second lookup helper cannot hide behind the declared one. `PersistenceSourceScanTest` names the line of each shape it covers: the field-initializer lambda (`aFieldInitializerLambdaThatCreatesAnElementOnItsTagNamesItsLine`); braces in a string, a char and a text-block literal inside a builder, which counted as code would leave the builder's body unclosed (`bracesInLiteralsInsideABuilderDoNotStretchItsBodyOverAFieldInitializer`); a one-line anonymous class and a one-line local class inside a builder (`aOneLineAnonymousClassInsideADeclaredBuilderNamesItsLine`, `aOneLineLocalClassInsideADeclaredBuilderNamesItsLine`), and four more one-line classes there, an anonymous class created as `this.new Maker()`, one created as `new @Shared Maker()`, one created as `new <String>Maker()`, and a local record whose component's annotation has an array argument (`aOneLineQualifiedAnnotatedOrGenericClassInsideADeclaredBuilderNamesItsLine`, one row each); a public constructor, undeclared and declared as a builder (`aConstructorThatCreatesAnElementOnItsTagNamesItsLine`); two helper declarations the pattern must read (`anAnnotatedTagParameterHelperAfterADeclaredBuilderNamesItsLine`, `aBoundedGenericTagParameterHelperAfterADeclaredBuilderNamesItsLine`); the method reference (`aBuilderUsedAsAMethodReferenceNamesItsLine`); and the second lookup helper (`aSecondLookupHelperAfterTheListHelperNamesItsLine`). An initializer block and a declaration the pattern cannot read have no test of their own. The red half is permanent: the `FaultInjection` cases of `hidingAnItemFromTheReaderNamesItInTheReport` hide one item per read idiom from the reader — `track/midi-effect-chain`, `midi-effect@plugin-id`, `transport@pre-roll-bars`, `@pre-roll-enabled`, `@punch-start-frames`, `track/midi-clip`, `midi-clip/notes/note`, `track@id` and `metadata/name#text` — and each must make the gate name exactly that item (plus the items read only because of it). `everyLegacyInputIsReadWhenPresentAndNeverWritten` pins the schema-1 names still read and no longer written (`send@mode` for channel and snapshot sends, `midi-effect@class`), and `StrictPerInstanceMode` proves the per-instance hook story 334 needs. The harness is green on the current tree.

**MIDI round-trip.** `ProjectSerializer.buildMidiClip` writes a `<midi-clip>` child of `<track>` whenever the clip has notes, has CC lanes or is locked, on any track type: the lock flag, the notes (`note-number`, `start-column`, `duration-columns`, `velocity`, `channel`) in file order, and each CC lane (`type`, `cc-number` for an `ARBITRARY_CC` lane only, `high-resolution`, `channel`, `height-ratio`) with its breakpoints. `ProjectDeserializer.parseMidiClip` fills the track's own `MidiClip` in place; the clip is final and owned by the track id, so the old string-based `serializeMidiClip` / `deserializeMidiClip` pair, which returned a new clip and threw on the first bad note, was retired and its tests moved to the production path. Nothing musical is clamped: a note, lane or event that is missing a value or that the model rejects is skipped and reported, and the rest of the clip loads (`unreadableMidiIsSkippedAndReportedWithoutRefusingTheProject`). Velocity 0 round-trips as 0. `ProjectSerializerMidiClipTest` (`roundTripsNotesAndCcLanes`, `roundTripPreservesEmptyClip`, `lockedClipWithoutNotesIsWritten`, `midiClipOnAnAudioTrackRoundTrips`, `midiClipAbsentFromAFileRestoresAnEmptyClip`) and `ProjectRoundTripInventoryTest.midiNotesAndCcLanes` cover it. A column is 0.25 transport beats in every producer and consumer, and saving columns makes that unit part of the format: `MidiColumnUnitContractTest` (daw-core: the renderer, the recorder, the keyboard processor, the MIDI file export's `COLUMNS_PER_QUARTER` and the slip edit, which now uses `MidiRecorder.BEATS_PER_COLUMN` instead of its own literal) and `MidiEditorColumnUnitContractTest` (daw-app: the piano roll) pin it with "schema-2 MIDI column = 0.25 beats; changing it requires a project migration". Piano-roll edits reach the `MidiClip`, and so the file, once story 355 commits them to it.

**MIDI-effect-chain round-trip.** `ProjectDeserializer.parseMidiEffectChain` restores the chain in file order. Each `<midi-effect>` is keyed by the plugin's stable `plugin-id` and resolved through a closed `switch` (`ArpeggiatorPlugin.PLUGIN_ID` → `parseArpeggiator`), never by loading a class named in the file. An unknown or missing `plugin-id` becomes an `UnresolvedMidiEffect` in the same position, a pass-through placeholder holding an immutable copy of the entry's attributes, which the next save writes back unchanged; its child elements or text are logged and dropped. An arpeggiator setting that is present but invalid is adjusted and reported: a finite value outside the plugin's range is clamped to it, and an unknown name or an unparseable or non-finite number takes the default, because `setGate` and `setSwing` let NaN through. `MidiEffectChainPersistenceTest` (`chainRoundTripsInOrderWithAnUnrecognisedEntryKeptAsSaved`, `invalidArpeggiatorSettingsAreAdjustedAndReported`, `absentArpeggiatorSettingsKeepThePluginDefaultsUnreported`, `entryWithoutPluginIdIsKeptAsAPlaceholderAndItsChildElementsAreDropped`, `schemaOneClassNameRestoresTheArpeggiatorThroughTheMigration`, `placeholderPassesMidiThroughAndIsNeverABuiltInPlugin`) and `ProjectRoundTripInventoryTest.midiEffectChain` cover it, and `SchemaV1ToV2MigrationTest.aClassNamedInTheFileIsNeverLoaded` proves that a class named in the file is never initialised. The chain is restored, not processed: story 151 owns its processing.

**Pre/post-roll round-trip.** `ProjectDeserializer.parseTransport` reads `pre-roll-bars`, `post-roll-bars` and `pre-roll-enabled` after the punch region, as three stored facts: no attribute gives `PreRollPostRoll.DISABLED`, a missing count is 0, a missing flag is false, and the flag is never re-derived from the counts, so `(2, 0, false)` and `(0, 0, true)` come back as stored. `parseRollBars` turns a negative or unparseable count into 0 and one above `PreRollPostRoll.MAX_BARS` (8) into 8, each with a WARNING only — a transport preference, not reported to the user. `MAX_BARS` is the one bound: the spinners offer 0 to it, and the record's constructor rejects a count above it as it rejects a negative one, so every storable value is one the controls can show. `PreRollPostRollPersistenceTest` (`storedValueRoundTripsExactly` over `(2, 0, false)`, `(0, 3, true)`, `(2, 4, true)`, `(0, 0, true)` and `(8, 8, false)`, `disabledWritesNoAttributesAndReadsBackDisabled`, `anAttributeOnItsOwnIsReadWithTheOthersDefaulted`, `badBarCountIsCorrectedAndLoggedButNotReported`), `ProjectRoundTripInventoryTest.preRollPostRoll` and `PreRollPostRollTest.shouldRejectABarCountAboveTheLargestOnEitherSide` (daw-sdk) cover it. The book's §3.1 rows for MIDI notes and CC lanes, MIDI-effect chains and pre/post-roll now read OK, owner 330.

**Pre/post-roll edits mark the project dirty.** All four controls go through one helper, `TransportController.commitPreRollPostRoll`: a value equal to the stored one only re-syncs the controls; a different one is set on the transport and marks the project dirty, with no undo entry and no bus event — the loop and punch rule (Control Synchronization Design Book §5.2, which now has a pre/post-roll row). The stored flag is no longer derived from the bar counts. A toggle works from what it shows: turning a side on uses its stored bar count, or 2 when it has none, and sets `enabled`, and an inert bar count on the other side is dropped rather than armed (so a click never changes whether the other side rolls); turning it off clears `enabled` and keeps the count, unless the other side rolls, in which case only that side's count goes to 0. A spinner edit changes only its side's count and keeps `enabled`, and both counts at 0 is `DISABLED`. The spinner listener reads the spinner's live value and returns when it equals the stored count, which is every value `syncPreRollControls` sets, so building the controls for a reopened `(2, 0, false)` leaves the transport and the clean project untouched. `PreRollPostRollControlsTest` covers the toggle and spinner tables from `(2, 0, false)` and five other starting values, `eachOfTheFourControlsMarksTheProjectDirtyWhenItChangesTheValue` (with an empty undo history), `aWriteOfTheStoredValueLeavesTheProjectClean` (a spinner set to its value, a typed identical value, a sync echo), `buildingTheControlsOverAnyStorableValueWritesNothingAndKeepsTheProjectClean` over all 162 storable values, and two reopen cases: a file whose count the reader bounded, and an inert pre-roll loaded from its file. `TransportControllerTest.createPreRollPostRollControlsShouldWireSpinnersToTransport` now expects `(5, 0, false)` after a spinner edit from `DISABLED`, and `(5, 0, true)` after a Pre-Roll click.

**Migration test.** `MigrationRegistry.CURRENT_VERSION` is 2. The one registered step, `MidiEffectPluginIdMigration`, is `ProjectMigration.formatOnly(1, "add per-track MIDI clips; key MIDI effects by id", …)`: it rewrites the arpeggiator's schema-1 `class` name to its `plugin-id` through a one-entry, exact-match table, leaves any other class name alone (the reader keeps that entry as a placeholder), and leaves schema-1 pre-roll attributes and chains in place for the new readers. `ProjectMigration` and `MigrationReport.AppliedMigration` carry a `changesAuthoredContent` flag (`step(...)` defaults it to true), and `MigrationReport.changesAuthoredContent()` gates the "Project Migrated" dialog in `MigrationReportDialog.showIfNeeded` and `ProjectLifecycleController.maybeShowMigrationReport`: a format-only migration opens without the dialog but is still a migration — `wasMigrated()` is true and the first save writes the `project.daw.v1.<stamp>.bak` backup, which the migration history and the hub's migrated badge then list. `SchemaV1ToV2MigrationTest` (the golden DOM-in/DOM-out step, an older shape, the deserializer over both v1 shapes with pre-roll restored and an empty MIDI clip, `firstSaveBacksUpTheSchemaOneFileOnceAndWritesVersionTwo`, `aNewerSchemaIsRefused`), `MigrationRegistryTest`, `MigrationReportDialogTest.showIfNeededReturnsFalseForAReportWhoseStepsAreAllFormatOnly` and `FormatOnlyMigrationOpensWithoutTheDialogTest` (a real v1 file through `loadProjectFromPath`: no dialog, one plain SUCCESS) cover it. `docs/project-migrations.md` gains a Schema Version History.

Track identity is restored in every door that deserializes a project. `Track(UUID, String, TrackType)` stores the id it is given; `ProjectDeserializer.restoreTrackId` restores a valid `track@id` in canonical form before `DawProject.addTrack`, so the channel id and the MIDI clip's owner follow it. A missing, malformed or duplicate id gets a fresh one with a WARNING, and the first track in document order keeps a repeated id, so two tracks never share a channel. Cue sends, VCA members, channel links and bed routings resolve only to tracks restored from the same file. A reference that does not resolve — a track the file does not hold, a malformed id, a channel linked to itself, or a repeat of an earlier assignment — is removed and reported, and its container is kept. The writer writes a reference only to a track it writes, so a deleted track's references, which the model keeps for undo, are not saved. Three derived duplicates are no longer written: `mixer/master@name`, `channels/channel@name` (a rename left it stale) and `send@mode`, which is still read when `tap` is absent. `TrackIdentityPersistenceTest`, `MixerTrackReferencePersistenceTest` (cue sends render the same mix, a −6 dB VCA keeps its members' composite volume, links resolve, dangling and repeated references are removed and reported while every track is present, and a deleted track's references come back with undo), `DerivedMixerAttributesPersistenceTest` and `TakeRecordedAfterAReopenCarriesTheSavedTrackIdTest` (a take recorded after a reopen names its track by the saved id in the take folder and the manifest) cover it.

The open reports what it could not read as written. The deserializer collects `UnreadProjectItem`s — skipped MIDI notes, CC lanes and CC events, adjusted arpeggiator settings, unrecognised MIDI effects and removed mixer assignments (`ProjectDeserializer.getUnreadItems`, `ProjectManager.getLastUnreadItems`, `ArchivedProject.unreadItems`, `RecoveryResult.unreadItems`, and the snapshot door's own read). Each item is logged once at WARNING in the form `<where>: <what> — <reason>[; saved as <snippet>][, at transport beat <b>]`: the track by its 1-based number and its name, items numbered from 1, the saved note, lane or event quoted in the writer's attribute order, and every string from the file quoted by `UnreadProjectItem.logText`, so a file can neither split nor forge a log line. `logText`'s Javadoc states the rule's scope: the WARNINGs `ProjectDeserializer` and `AnalyzerInsertPersistence` write while a file is read; a log line written by any other class is not covered. The lines that are logged only, which are not items, use the same location prefix (`Track <n> '<name>'`, or `Mixer <container>` for a mixer strip or container; the transport's lines start `Transport <attribute>`), numbering from 1 and `logText` quoting, and each says in its own words what was wrong and what the open did about it, with no saved snippet or beat:

- A repeated or malformed track id: `Track 2 'B': id 00000000-0000-0000-0000-00000000000a is already used by Track 1 'A'; a new id is used`, `Track 2 'Keys': id 'not-a-uuid' is not a UUID; a new id is used`.
- An unusable CC-lane height ratio: `Track 1 'Keys': CC lane 2 height-ratio '-2' is not a positive number; 1.0 is used`.
- A placeholder's dropped text, logged before the placeholder's own item line: `Track 1 'Keys': MIDI effect 1 has text no writer produces; it is dropped`.
- An analyzer setting the reader cannot use, named by the insert's strip and its position among the strip's saved `<insert>` elements (an insert that is skipped keeps its number), with the value as saved and never a parse exception's message: `Track 2 'Vox': insert 2 analyzer com.benesquivelmusic.daw.spectrum-analyzer window-type 'FLAT_TOP' is not a window type; the analyzer's saved settings are not applied and its defaults are used`. An unusable analyzer setting is not an unread item and arms no backup.

The first save writes it as `project.daw.degraded.<UTC stamp>[-n].bak` before overwriting `project.daw`, through the one `writeSiblingBackup` writer the migration backup also uses, and logs its path at INFO; the announcement does not mention it. An open that is also a migration writes one backup, the `v<from>` one, whose INFO line says it also keeps what this save drops. An unrecognised MIDI effect kept with its attributes, a missing track id, a non-canonical UUID, a missing asset, a CC lane's height ratio, a malformed pre/post-roll value and an analyzer setting the reader cannot use — a meter view preference, like the height ratio — arm nothing. The `degraded` tag never starts with `v` and a digit, so the Migration History view, the hub's health scan and the roll-back never take the backup for a migration. `DegradedOpenBackupTest` (the byte-equal backup, one backup per load, the per-kind table, whose `an unusable analyzer setting` row writes no backup, the combined case, the INFO lines, a file deleted while open, `createProject` clearing the debt), `MigrationHistoryViewTest.scanProjectDirectoryListsNoBackupOfADegradedOpen` and `HealthScanOffFxThreadTest.scanBlockingDoesNotTakeTheBackupOfADegradedOpenForAMigration` cover it; the rules are in `docs/project-migrations.md`, "The Degraded-Open Backup", and the design book's §6.3.

An adjacent defect was fixed in scope because the new mixer tests could not pass honestly without it. Copy Track put the copy right after the original in the track list but appended its mixer channel at the end. The engine pairs tracks and channels by position, so from that moment every later track played through its neighbour's strip — fader, pan, mute, inserts, sends and VCA — and the file saved them scrambled. The studio engineer ruled it Blocking. `Mixer.addChannel(int, MixerChannel)` inserts with one list change, and `DawProject.duplicateTrack` puts the copy's channel right after the original's channel. `DawProject`'s class Javadoc now states the invariant — channel order equals track order, for a track whose id is not already in the project — and names the four mutators that keep it. `DawProjectTest.shouldInsertDuplicateAfterOriginal`, four `MixerTest` cases for the indexed add, `ChannelOrderMatchesTrackOrderTest` (duplicates of the first, a middle and the last track, every edit and its undo, a seeded 400-step sweep, a move after a duplicate, and a live `Mixer.mixDown` in which a muted track's strip stays on that track) and `DuplicatedTrackMixerRoundTripTest.everyStripStaysOnItsOwnTrackAfterDuplicatingSaveAndReopen` cover it.

Studio-engineer rulings this story applied:

- **F1** — `pre-roll-enabled` is a stored fact independent of the bar counts; the controls display, toggle and edit by the rules above, and the reader clamps a bad count with a WARNING only.
- **F2** — pre/post-roll edits are dirty-only: marked only when the stored value changes, no undo entry, no bus event, through one commit helper.
- **F3** — the MIDI-effect chain restores in order; an unknown entry is a pass-through placeholder in place, and bad arpeggiator values are coerced and reported; never a reflective load.
- **F4** — every MIDI clip fact round-trips exactly; an invalid note, lane or event is skipped and reported, never clamped; the 0.25-beat column is fixed and pinned.
- **F5** — schema 1 → 2 is a recorded migration without the modal dialog, and the first save still writes the `.bak`.
- **F6** — MIDI is saved on any track type, the playhead position joins the round-trip family, and the harness keys on element paths.
- **R1** — track ids are restored on every load, references resolve by restored id, unresolvable ones are dropped and reported, and the writer filters references to unwritten tracks (Blocking, in scope).
- **R2** — `master@name`, `channel@name` and `send@mode` stop being written (`send@mode` stays a legacy read); `insert@name` and `return-bus@name` stay because they are read.
- **R3** — MIDI effects are keyed by `plugin-id`; the schema-1 class name is rewritten by the 1→2 migration, not by the reader.
- **R4** — the open report is one sentence of count-only clauses after the audio clauses; each item gets one WARNING naming its track or mixer container.
- **Q1** — a degraded open whose next save drops content gets a one-time `degraded` backup, or shares the migration backup; the archive door carries its own counts.
- **Q2** — Duplicate Track's channel order is fixed here (Blocking, a live misroute); the copy's default strip and Copy Track's redo are future work.
- **Q3** — the default return bus's removal and return-bus identity are deferred to one future story; the §3.1 row says PARTIAL.
- **Q4** — the mixer clause is neutral (`N mixer assignments removed`), covering self-links and repeats, which arm the backup like every removed assignment.
- **Q5** — the WARNING line names the track by number and name, numbers items from 1, quotes the saved snippet in the writer's order with the transport beat, and quotes all file text through one helper.
- **Q6** — the backup's INFO line gives no count; it says why the backup exists and points to the open's WARNING lines.
- **Q7** — `PreRollPostRoll` rejects a count above `MAX_BARS`, the one bound the controls and the reader share.
- **Q8** — an unreadable or NaN VCA gain opens at 0 dB, and a repeated VCA group id is skipped and backed up; the general unchecked-exception path is story 361's.
- **D1, D2** — analyzer settings are meter view preferences, like a CC lane's height ratio: an unusable one is logged only, never counted and arms no backup; its WARNING names the strip and the insert. Keeping the usable settings beside it is story 367's.
