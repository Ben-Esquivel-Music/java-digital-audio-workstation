# Migration Robustness: Roll Back, Archive Restore and an Honest Migration State

## Motivation

Story 330 registered the first real migration (schema 1 → 2, format-only: recorded, but opened without the "Project Migrated" dialog). Every existing project is now a migrated project on its first open, which exposes five pre-existing weaknesses of the story-188 machinery, found by story 330's migration audit and checked again in the current tree:

- **A1 — Roll back from Migration History destroys work with no way back.** A row's `Roll back` button (`MigrationHistoryView`) fires its event, and `ProjectLifecycleController.showMigrationHistory` calls `rollbackMigration(projectDir, report, backup)`, which copies the chosen `.bak` over `project.daw` with `REPLACE_EXISTING` (`ProjectLifecycleController.java:1456-1459`) and reloads. It keeps no copy of the file it overwrites and offers no Undo, so one click discards everything saved since the migration — all MIDI work included, now that MIDI is saved. Nor does it ask about unsaved work: it does not pass `confirmProjectMayClose`, whose Javadoc says so ("Recover and a migration roll-back, which do not pass it, refuse a recording in flight and a take being written on their own"), so the reload drops every unsaved edit without a word. With no backup to copy, it discards the in-memory project instead (`resetProjectState()`, then a new `DawProject("Untitled Project", …)`), unsaved edits included. That branch is reached from the "Project Migrated" dialog's own `Roll back…`, which asks for confirmation and runs right after the open (the dialog is modal, so no edit comes first), and from a history row whose backup file is no longer a regular file when the button is pressed. Story 299, which built the row, ruled against a modal here: "creating a snapshot and rolling back to a backup (which itself leaves the backup intact) do not need a modal — they surface Undo where reversible" (its Goals, after Project Manager design book §2.5). The book's rule is "A modern long‑form tool prefers **undoable** over **confirmable**", and "Confirmation dialogs are reserved for **irreversible** actions". Story 299 left `rollbackMigration` itself unchanged (its Non-Goals), so the Undo it names was never built. The row's Roll back also runs for a project that is not open: Migration History opens from any Project Hub card (`buildProjectHub` → `ProjectHubView.fireAction`; the hub disables it only for a card with no folder or an archive). For such a folder, the copy branch overwrites its `project.daw` before its lock is checked (`ProjectManager.openProject` takes the lock in the reload that follows) and replaces the open project without its close gate, and the no-backup branch abandons the open project, which is unrelated. On the stale-row path, today's message "the on-disk file is still the original (v<n>)" is normally false: the save that wrote the row's backup then replaced that file.
- **A2 — A failed archive restore hangs its progress dialog.** The restore worker `ProjectLifecycleController.restoreArchive` catches only `IOException`. `ProjectArchiver.openArchive` rethrows any `RuntimeException` (`ProjectArchiver.java:393-397`) — a `MigrationException` for an archive of a newer schema, or any other unchecked exception the deserializer throws — which escapes the virtual thread. The `finished` callback never runs, so the "Restoring archive…" dialog and the status strip's operation stay up, and no error is shown.
- **A5 — The status strip offers a backup that does not exist.** `MainController` sets the strip's backup version whenever the open's `MigrationReport.wasMigrated()` (`MainController.java:929-939`), and `SessionStatusStripSkin` shows `· backup v<n> available`. The backup is written only by the first save, so on the first open of every existing project the strip names a file that is not there.
- **A6 — The hub's migrated badge never goes away.** `ProjectHealthScanner` gives a project `HealthBadge.MIGRATED` (`⚠ migrated v1→v2` on the card, `ProjectCardSkin`) whenever a `project.daw.v<n>.….bak` exists, and nothing ever prunes migration backups. After story 330 every project saved once carries a permanent warning for an additive format change.
- **A7 — Three doors migrate without a record.** Journal replay, snapshot restore and archive restore deserialize, and so migrate, without reading the migration report (`JournalReplayer`, `SnapshotsController`, `ProjectArchiver`). Archive restore re-serializes the project at the current version before opening it, and journal recovery keeps its own `project.daw.recovered.<stamp>.bak`, which the history and the hub do not match. Each door keeps its source, so no data is lost, but the migration appears nowhere.

For an engineer, migration is the moment a session is most at risk: the one destructive action (A1) must be undoable, a failed restore (A2) must say so, and the state the screen reports (A5, A6, A7) must be true.

## Goals

- **Roll back keeps everything it replaces and offers Undo.** Roll back from Migration History, and the Project Migrated dialog's `Roll back…` when it finds a `v<from>` backup, keep the current `project.daw` as a sibling `project.daw.pre-rollback.<stamp>.bak` before they copy the chosen backup over it (the dialog keeps its confirmation; the backup it finds may be older than the file the open just read). When the project has unsaved changes, Roll back also writes the project as it stands in memory, as Save writes it, to a second sibling, `project.daw.pre-rollback-unsaved.<stamp>.bak`. It then reloads and surfaces **Undo**, which makes `project.daw` the unsaved copy when there is one, else the pre-roll-back copy, and reloads it: unsaved work comes back (saved, as the Project Manager design book's §2.5 "it autosaves and shows an **Undo Close** toast" leaves a closed project), and the file that was on disk is kept either way — after a degraded open, when no save has run since that open, it is the only holder of what the reader skipped. Undo is the same operation aimed at that copy, so it also keeps what it overwrites, and like Roll back it is refused while a recording is in flight or a take is being written. Neither deletes or renames a file, and neither writes a `project.daw.v<n>.*.bak`: only the first save after a migrating open writes that name, so a `v<n>` backup always holds schema `<n>`. From Migration History there is no modal: the §2.5 form, which story 299 chose for this action.
- **Roll back acts only where Save could write.** This holds for both entry points, Migration History and the Project Migrated dialog's `Roll back…`. Roll back overwrites `project.daw`, so the folder must be the open project's, opened read-write (a save refuses a read-only open and checks the lock first). Migration History opened from a Project Hub card for any other folder keeps Diff and disables Roll back, with a visible line in the view: "Open this project to roll it back." (for the open project opened read-only: "This project is open read-only."). The check is repeated when Roll back or Undo is pressed, since the history window stays open while another project is opened. On a read-only open the Project Migrated dialog's `Roll back…` is refused the same way, with a backup or without. A row whose backup is no longer a regular file when it is pressed has nothing to roll back to. In each case Roll back shows one WARNING and changes nothing on disk or in memory.
- **The Project Migrated dialog's `Roll back…` with no backup keeps its behaviour on a read-write open.** It runs right after the open, before any edit can be made, while `project.daw` is still the file the open just read, so it discards the in-memory project and writes nothing; its confirmation and its message that the file on disk is still the original stay, and the message is true there.
- **Every restore failure ends the restore.** The archive restore worker closes its dialog and operation and shows one ERROR for any exception, checked or not.
- **The strip is true.** Before the first save it says that the first save will keep a backup of version `v<n>`; once the backup exists it says `backup v<n> available`.
- **The badge means something.** The studio engineer rules, before implementation, what the hub shows for a project that was migrated and saved: for example, a format-only migration not badged once saved, the badge cleared after the user confirms, or migration backups pruned after a retention period.
- **The other doors are recorded or say why not.** The studio engineer rules whether a migration through journal replay, snapshot restore or archive restore appears in Migration History; the implementation follows the ruling and the doors' Javadoc says what they do.
- **Roll back and the dialog's suppression write leave the FX thread** (story 331's known limit; Persistence Integrity book §6.1). Since story 331 both write through `AtomicFileWriter`, which forces the data, fsyncs the folder and may pause up to 130 ms retrying a refused move, and both still run on the FX thread: `ProjectLifecycleController.rollBackNow` copies the chosen backup over `project.daw` there ("FX thread, as before story 331 — the copy blocks on storage there until story 373 moves it off"), after `rollbackMigration` has looked up the newest backup with `findNewestBackup`, a directory listing, there too; and the Project Migrated dialog's result converter calls `MigrationSuppression.suppress` when "Don't show again for this project" is ticked. Roll back's file work — the backup lookup, the copies this story adds and the copy over `project.daw` — and the suppression write run on a worker, and their outcomes come back to the FX thread through the `FxDispatcher`.

## Acceptance Criteria

1. Roll back from Migration History shows no confirmation; the Project Migrated dialog's `Roll back…` keeps its confirmation. Before either copies a backup over `project.daw` (a history row's, or the `v<from>` backup the dialog finds), it keeps that file as `project.daw.pre-rollback.<stamp>.bak` and, when the project is dirty, writes the project as it stands in memory to `project.daw.pre-rollback-unsaved.<stamp>.bak`; then it reloads and surfaces Undo. Undo makes `project.daw` byte-identical to the unsaved copy when there is one, else to the pre-roll-back copy, and reloads it, keeping what it overwrites by the same rule; like Roll back, it is refused while a recording is in flight or a take is being written. Neither Roll back nor Undo deletes or renames a file or writes a `project.daw.v<n>.*.bak`, and Migration History, the hub scan and `findNewestBackup` take neither copy for a migration backup. For a folder that is not the open project, or one open read-only, Migration History's Roll back is disabled with a visible reason; pressed anyway, or for a row whose backup has gone, it shows one WARNING and changes nothing on disk or in memory, and so does the Project Migrated dialog's `Roll back…` on a read-only open. On a read-write open, the Project Migrated dialog's Roll back with no backup discards the in-memory project and writes nothing.
2. An archive whose project is of a newer schema, and one whose deserialization throws an unchecked exception, close the restore dialog and the operation and show one ERROR.
3. After opening a schema-1 file and before saving, the strip does not say `backup v1 available`; after the first save it does.
4. The hub badge follows the studio engineer's ruling; a degraded-open backup (`project.daw.degraded.*.bak`) and a roll-back copy (`project.daw.pre-rollback*.bak`) still never count as a migration.
5. The three doors behave as ruled, and each is covered by a test.
6. Roll back — from Migration History and from the Project Migrated dialog — and the dialog's "Don't show again for this project" write make no file-system call on the FX thread (story 331).

## Goals — Tests

These tests are binding acceptance criteria. They run headless, and none of them assumes a non-Windows environment.

- **Roll back**: open a migrated project, save, then Roll back from Migration History: no dialog is shown, `project.daw.pre-rollback.*.bak` is byte-equal to the saved `project.daw`, no `project.daw.pre-rollback-unsaved.*.bak` exists, and `project.daw` equals the chosen `.bak`; Undo then makes `project.daw` byte-identical to the copy the Roll back wrote and reloads it. Open a migrated project, save, edit without saving, Roll back, then Undo: the edit is present and the `project.daw.pre-rollback.*.bak` the Roll back wrote is byte-equal to the saved `project.daw`. Roll back, edit, then Undo: a `project.daw.pre-rollback-unsaved.*.bak` holds that edit. Degraded open: a folder holding a schema-2 `project.daw` with a CC lane type this build does not know beside a `project.daw.v1.<stamp>.bak`; open it, edit without saving, Roll back on the `v1` row, then Undo: the edit is present and the `project.daw.pre-rollback.*.bak` the Roll back wrote is byte-equal to the fixture's `project.daw`, lane included. After each case, `MigrationHistoryView.scanProjectDirectory` lists only the `v1` backups and the hub scan gives the same badge as before the Roll back.
- **Roll back refused**: (a) open project A and edit it, then open Migration History for folder B, which holds a `v1` backup: B's rows show Roll back disabled and the view says why; firing a row's roll-back request anyway shows one WARNING, A's edit is still in memory, and no file in A's or B's folder is written or changed. (b) The same for project A opened read-only, on A's own rows. (c) Open a migrated project, save, open Migration History, delete the row's `.bak`, edit, then press Roll back: one WARNING, `project.daw` unchanged, the edit still in memory, no file written.
- **Dialog roll-back with a backup**: a folder holding a schema-1 `project.daw` beside an older, different `project.daw.v1.<stamp>.bak`; open it and drive the Project Migrated dialog's roll-back (`rollbackMigration(projectDir, report)`): `project.daw.pre-rollback.*.bak` is byte-equal to the file the open read and `project.daw` equals the backup; on a read-only open it shows one WARNING and changes nothing on disk or in memory.
- **Dialog roll-back with no backup**: open a schema-1 file and, with no `v1` backup, drive the Project Migrated dialog's roll-back (`rollbackMigration(projectDir, report)`): `project.daw` is byte-unchanged and no file is added, compared with the fixture (the abandon deletes the `.project.lock` the open wrote), and an Untitled project replaces the open one.
- **Archive failure**: drive `restoreArchive` with an archive holding a `version="3"` project; the `finished` callback runs once and one ERROR is shown.
- **Strip**: open a schema-1 file; the strip's text names no available backup until the first save writes it.
- **Badge**: the hub scan over a migrated-and-saved project gives the ruled badge.
- **Doors**: replay a schema-1 checkpoint, restore a schema-1 snapshot and a schema-1 archive; each matches the ruling for Migration History.
- **Off the FX thread** (story 331): with `ProjectLifecycleController.setFileWriter` given an `AtomicFileWriter` whose `Mover` records its thread, a Roll back from Migration History and one from the dialog publish only off the FX thread, and the FX thread returns before the copy is published; ticking "Don't show again for this project" writes `.migration-report-suppressed` off the FX thread.

## Non-Goals

- A3, the lock that a failed open leaks (story 361).
- Forward compatibility: a newer file is still refused (story 330, design book §6.3).

## Technical Notes

- Code locators: `MigrationHistoryView` (row `Roll back`, `requestRollback`), `ProjectLifecycleController` (`showMigrationHistory`, `rollbackMigration`, `confirmProjectMayClose`, `findNewestBackup`, `restoreArchive`, the journal recovery backup), `ProjectArchiver.openArchive`, `MigrationException`, `MainController` (status-strip schema feed), `SessionStatusStripSkin`, `ProjectHealthScanner`, `HealthBadge`, `ProjectCardSkin`, `JournalReplayer`, `SnapshotsController`, `ProjectManager` (`PendingBackup`, `writeSiblingBackup`).
- Roll back's folder check: compare the folder with the open project's by `Files.isSameFile`, not by path string (a Recent path can differ in form from the open path on Windows), and read `ProjectManager.isReadOnly()`. Code locators: `ProjectLifecycleController.buildProjectHub` (`setOnMigrationHistory`), `ProjectHubView.fireAction`.
- Roll back's copies: name both as `writeSiblingBackup` does (UTC `yyyyMMdd-HHmmss`, `-<n>` on a collision, never overwriting a file), with the tag as the first segment, which must not start with `v` and a digit (the rule `PendingBackup.DEGRADED_TAG`'s Javadoc states). `ProjectHealthScanner.BACKUP_PATTERN` accepts anything after `v<n>.` and `findNewestBackup` takes any name that starts `project.daw.v<n>.` and ends `.bak`, so a tempting `project.daw.v1.pre-rollback.<stamp>.bak` would badge the card and be taken for the migration backup. The `rollbackMigration` Javadoc's "the original file on disk has not been overwritten yet" is true only on the dialog path once stale rows refuse; correct it there. After an Undo there are two `project.daw.pre-rollback.*.bak` files, and tests must not order these copies by name: `<stamp>-1.bak` sorts before `<stamp>.bak`.
- Found in story 330's migration audit (adjacent findings A1, A2, A5, A6 and A7); A6's badge and A7's history are product questions for the studio engineer.
- Design references: Persistence Integrity design book §6.3; Project Manager design book §2.5 (undoable over confirmable; confirmations only for irreversible actions); `docs/project-migrations.md`.
- Cross-refs: story 188 (migration registry), story 247 (migration report dialog), story 299 (Migration History and its Roll back; its §2.5 goal names the Undo this story builds), story 330 (the 1→2 step, the degraded-open backup), story 361 (failed opens).
