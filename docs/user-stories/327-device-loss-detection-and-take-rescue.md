# Device-Loss Detection and Take Rescue, Live

## Motivation

Story 214 landed a complete device-loss reaction chain: `onDeviceRemoved` stops the engine, flushes the `IncompleteTakeStore`, enters `DEVICE_LOST`, and notifies (`DefaultAudioEngineController.java:676-708`); `onDeviceArrived` reopens and resumes (`:711`). None of it can run in production (book §1.7):

- The **only** publisher of `DeviceRemoved`/`DeviceArrived` in main source is the mock backend's test fixture (`MockAudioBackend.java:190-192`). The live PortAudio/JavaSound path emits no device events, nothing polls stream health, and the OS-level device-change hooks are no-op stubs.
- `captureRecordingFrames` — the only feeder of `IncompleteTakeStore` — has exactly one caller, a test (`DefaultAudioEngineController.java:652-654`; `DefaultAudioEngineControllerTest.java:196`). Its javadoc's claim that *"production wiring … calls this from the audio callback"* is false, so the rescue flush at `:699` always flushes an empty store.
- Production constructs the controller via the 2-arg constructor (`MainController.java:806`), which injects a **no-op notification sink** and roots the take store at the OS temp directory (`DefaultAudioEngineController.java:148-152`) — even if events fired, *"Audio device disconnected"* goes nowhere and the rescue WAV lands outside the project.
- `EngineState` promises a *"Reconnecting…"* transport indicator in its javadoc (`EngineState.java:8-9`); no production class subscribes to `engineStateEvents()` (the accessor at `DefaultAudioEngineController.java:481-483`; `AudioEngineController.java:320` and `DefaultAudioEngineController.java:481` are the only references).

The irony the book calls out: `IncompleteTakeStore` is the one class in the whole capture path that actually knows how to write a WAV file (`IncompleteTakeStore.java:130-155`) — and it is never fed. For a studio engineer, a USB cable snagged mid-take is today an *undetected total loss*: the performer keeps playing to a dead rig, no indicator changes, and nothing was on disk to salvage. USB interfaces get unplugged; a recorder that only works when hardware never fails does not meet the session invariant (book §2.1, §2.8).

## Goals

- **Device-loss detection is live in production**: the capture path consumes real detection feeds, in the book's preference order (§5.5) — backend device events (ASIO, live once story 316 opens the backend in production) first; the OS device-change watcher and the callback-heartbeat watchdog (Book 4 story 338) for event-less backends. This story consumes those signals; it does not implement watchers (book §6.3).
- **The §5.5 rescue sequence runs end-to-end** on `DeviceRemoved` (or a watchdog-declared stall) while RECORDING, each step completing regardless of later-step failure: ring drains → all active segments sealed, manifest marked `sealed-by: device-loss` → rescued take registered → state → DEVICE_LOST, REC indicator off, status strip shows the cause → notification names the device, says "take preserved", and offers review.
- **`IncompleteTakeStore` is repurposed as the rescued-take registry** (book §2.9): project-rooted, fed by the flush service's seal path — rescue *is* the ordinary seal applied early, never a second in-RAM copy of the audio. The never-called `captureRecordingFrames` RAM feeder (`DefaultAudioEngineController.java:652`) is retired, and the OS-temp rooting of the production constructor (`:148-152`) goes with it.
- **Reconnect is user-driven and identity-matched**: `DeviceArrived` matching the lost device's identity offers resume with the armed set preserved — recording never restarts itself (book §5.2/§5.5). The reopen path keeps existing story 218's reset-ordering discipline.
- **DEVICE_LOST is visible** per book §6.5: the record-state machine feeds the `EngineState` bridge and the status strip so the promised *"Reconnecting…"* indicator becomes real (the strip cell itself is Book 4 story 338's scope; the record-state feed is this story's). *(As landed: the transport status label reads "Device lost" with the `status-device-lost` style class — not "Reconnecting…"; the strip cell is story 338's. See Resolution.)*
- **The same rescue grammar recovers crash orphans**: a `.part` segment plus an unsealed manifest reconstructs a playable RESCUED take registered for review (book §4.7) — one rescue grammar for unplug, crash, and power loss. (Invoking the scan on every project-open path is story 332's scope.)

## Goals — Tests

- **End-to-end rescue test** (mock backend event fixture): publish `DeviceRemoved` mid-take — within the detection window the take is sealed on disk under the project, the rescued take is registered in the project-rooted `IncompleteTakeStore`, a notification names the device and offers review, the status strip shows the loss, and the REC indicator is off.
- **Hardware proof** (manual, primary platform): yank the ASIO-capable multi-channel USB interface mid-take on Windows — same observable sequence; replugging offers resume. Automated tests must not assume a non-Windows environment.
- **Identity-match test**: a *different* device arriving does not trigger reopen — state stays DEVICE_LOST and the remediation notification repeats (book §5.2 "Device returned" row).
- **No-auto-restart test**: after a matching `DeviceArrived` and successful reopen, the machine returns to IDLE with the armed set preserved; recording resumes only on an explicit user action.
- **Crash-grammar test**: a simulated crash leaving a `.part` segment and an unsealed manifest reconstructs a playable RESCUED take (sample count derived from file length per book §3.4) registered with the store.
- **Registry-role test**: `IncompleteTakeStore` is fed only by the flush service's seal path; `captureRecordingFrames` no longer exists (or has zero callers pending deletion is not acceptable — the method is removed and its test migrated); the store's root is inside the project directory, never OS temp.
- **Step-independence test**: a failure injected at the notification step still leaves the take sealed and registered (each §5.5 step completes regardless of later-step failure).

## Resolution

Device loss is now an input of the record state machine. The engine controller's existing reaction chain (story 214) keeps its job — detect the loss of the device of the open stream, stop the engine, enter `EngineState.DEVICE_LOST`, reopen on the matching return — and story 327 gives it the two things book §1.7 found missing: a consumer (`EngineStateBridge` → `TransportController.onEngineState` → `RecordCoordinator.onDeviceLost`/`onLostDeviceReturned`, all on the FX thread) and a subject (the take on disk, sealed by the pipeline's ordinary stop with reason `DEVICE_LOSS`). There is no second copy of the audio: `IncompleteTakeStore` is the registry of takes sealed by failure, and the same seal, replayed from the bytes on disk by `TakeRecovery`, recovers a crash. Each decision below names the code as it is on disk.

### Detection feed and the bridge

`DefaultAudioEngineController` is still the detector. `onDeviceRemoved` is gated on an open stream and on the identity it watches (`getWatchedDevice()`), stops the output and the engine, enters `DEVICE_LOST` and notifies *"Audio device disconnected — playback paused"* — the playback case; when a take was recording, the coordinator's rescue message follows it (both are shown — Known limitations, "Two toasts"). `onDeviceArrived` reopens only for a matching arrival and ends `STOPPED` with the existing *"Audio device reconnected — review recovered take and re-arm transport"*. New in this story: an arrival while `DEVICE_LOST` that is **not** the lost device repeats the remediation once per arrival — *"Audio device `<lost>` is still disconnected — `<arrived>` arrived, but it is not the lost device; playback stays paused"* — and reopens nothing (book §5.2 "Device returned", guard failure). Since the fix round, `EngineState.DEVICE_LOST` ends when *any* stream opens: the stream-open seam `DefaultAudioEngineController.onStreamOpened` — which also re-binds the device-event watch to the rung that won — publishes `STOPPED` through `setEngineState` when the state was DEVICE_LOST, so a loss on the new stream is published again instead of being deduplicated away, and `onDeviceArrived`'s DEVICE_LOST gate, and with it the "still disconnected" remediation, closes once another stream has opened (`DefaultAudioEngineControllerTest.aStreamOpeningEndsDeviceLostSoASecondLossIsPublishedAndNoRemediationNamesTheNewWatch`). `onDeviceArrived`'s own reopen fires that seam inside its `startAudioOutput()`, so its `STOPPED` is published from there, before the pause, and its later `setEngineState(STOPPED)` deduplicates. The identity predicate is unchanged in behaviour and, since fix round r2, shared: the package-private static `DefaultAudioEngineController.sameDevice(DeviceId, DeviceId)` — `DeviceId.equals`, else equality of the friendly name alone (Known limitations) — is what `onDeviceRemoved`, `onDeviceArrived`, both format-change paths and `RecordCoordinator.onLostDeviceReturned` test. `setEngineState` is `synchronized` since the same round: every caller but `runFormatChangeReopen`'s catch already held the controller's monitor, and the publisher's `offer` takes only its own lock, so the only edge added, [controller monitor → publisher lock], ends at a leaf and closes no cycle (the lock-order note on `controlPanelLock`).

The bridge is `EngineStateBridge`, a package-private `Flow.Subscriber<EngineState>` that `MainController.initialize()` builds right after the controller and subscribes to `engineStateEvents()` before the default streaming provision can open the first stream (the controller's constructor publishes no state, so nothing is missed). It requests `Long.MAX_VALUE`, never blocks (`setEngineState` offers with a drop handler), posts every state through `FxDispatcher.runOnFx` to whatever `TransportController` is current at delivery, and is cancelled in the window-teardown chain before the engine is torn down. `TransportController.onEngineState(EngineState, Optional<DeviceId>)` latches the loss: `DEVICE_LOST` sets `deviceLost` and calls `recordCoordinator.onDeviceLost(device)`; the lost device's return is the first `STOPPED` or `RUNNING` delivered after that **with the engine's stream open** (`audioEngine.isStreamOpen()`, read on the FX thread at delivery), which clears the latch and calls `recordCoordinator.onLostDeviceReturned(device)` — the coordinator ignores it in any state but DEVICE_LOST. A `STOPPED` delivered with the stream closed (a failed reopen; `refuseFormatChangeReopen`) and a `RECONFIGURING` only keep the latch (`TheLostDevicesReturnIsAReopenedStateWithTheStreamOpenTest`: a closed-stream `STOPPED` after `RECONFIGURING` leaves the rescue where it is; the same with the stream open, and a `RUNNING` with the stream open, are the return). The producers of an open-stream `STOPPED` or `RUNNING` while the coordinator is DEVICE_LOST are `onDeviceArrived` (the lost device: it reopens and parks the stream, and the stream-open seam `onStreamOpened` publishes the `STOPPED` from inside its `startAudioOutput()`) and `onStreamOpened` for any open the controller did not drive. Play and Record are refused while DEVICE_LOST; the instrument-audio open of `MainController.pluginGraphChanged` — an unguarded `startAudioOutput()` on a virtual thread when an instrument insert is added — is not, and is legitimate while the interface is unplugged: it walks the provision ladder, opens whatever rung it yields, and the seam re-points the watch to that rung and publishes `STOPPED`, so the device delivered with it is whichever rung opened — another device while the interface is unplugged, in which case the coordinator identity-matches it and reads the mismatch as the loss ending on another device (below; `TheLossEndingOnAnotherDeviceIsNotTheLostDevicesReturnTest`); the lost device itself if it is physically back and the ladder, which honours the configured `DeviceId`, lands on it, in which case it is the return. A `FormatChangeRequested` while DEVICE_LOST publishes `RECONFIGURING` and then a closed-stream `STOPPED` — `performFormatChangeReopen` restores only a stream that was open (`wasOpen`), and the loss closed it — and is ignored. A Settings apply never reaches a DEVICE_LOST coordinator: `requestConfigurationChange` leaves DEVICE_LOST through FINALIZING and settles to IDLE before the apply's permit is granted, so `applyConfiguration`'s `STOPPED` — published with the stream closed after a loss, since it too restores only what was open — meets an IDLE coordinator (`ASettingsApplyLeavesDeviceLostThroughFinalizingTest`, which delivers that `STOPPED` with the stream open, the stronger case, and sees no INFO and no seek). A controller that watches no device reports `TransportController.UNKNOWN_DEVICE` (`DeviceId("unknown", "Unknown audio device")`).

No producer was added (Non-Goals). In main source the only publishers of `DeviceRemoved`/`DeviceArrived` are `MockAudioBackend.simulateDeviceRemoved`/`simulateDeviceArrived`; `AsioBackend`, `WasapiBackend` and `CoreAudioBackend` publish `FormatChangeRequested` only (story 218's path). The consumer chain is wired in production; what feeds it on hardware is story 338's watchdog or a backend's native events (Known limitations).

One production defect in `daw-sdk` was exposed by the reconnect tests and fixed: `AudioBackendSupport.close()` completed the backend's device-event publisher together with the stream's input publisher, so the loss — which closes the stream on its way into `DEVICE_LOST` — completed the very feed the return had to arrive on, and no `AudioBackendSupport`-based backend (Mock, ASIO, WASAPI, CoreAudio, JACK, Java Sound) could ever deliver `DeviceArrived` after a loss. `close()` now completes only the input-block publisher; the device-event publisher lives as long as the support does (`MockAudioBackendTest.deviceEventsOutliveTheStreamCloseAndAReopen`).

### Engine controller changes

`IncompleteTakeStore` is gone from `DefaultAudioEngineController`: the field, the constructor parameters, `captureRecordingFrames`, `getIncompleteTakeStore`, both `flushIfNotEmpty` calls (`onDeviceRemoved` and step 3 of `performFormatChangeReopen`) and the `java.io.tmpdir` rooting. The 2-arg constructor `(AudioEngine, Runnable)` — whose only remaining job was the `NotificationManager.noop()` default book §6.3 forbids — is deleted; the constructors are `(AudioEngine, Runnable, NotificationManager)` and `(…, AudioBackendSelector)`. `MainController` passes a toast-backed sink of the track-budget sink's shape, `message -> postFx(() -> { if (notificationBar != null) notificationBar.show(NotificationLevel.WARNING, message); })` — the null check inside the posted runnable: `postFx` always posts (`FxDispatcher.runOnFx` is an unconditional `Platform.runLater`, a bare `runLater` before the dispatcher exists), and the sink is built inside `initialize()`, which also builds the bar, so no posted runnable runs before the bar exists and nothing is dropped on the calling thread; tests pass `NotificationManager.noop()` explicitly or a recording sink.

### The record-state machine

`RecordCoordinator` gained two FX-thread entry points, both ignored by a retired coordinator (its take was handed to `reportTakeOfAReplacedProject`):

- **`onDeviceLost(DeviceId)`.** RECORDING with an audio pipeline: the rescue first — `lostDevice` and `rescuedTakePipeline` remembered, `recordingPipeline = null`, `requestTakeRescue(pipeline)` = `pipeline.requestStop(TakeManifest.SealedBy.DEVICE_LOSS)` with the same one-retry as a Stop, `publishWhenWritten` (the existing deferred publication on a later FX turn) and the still-writing warning as for a Stop — and only then, each through `rescueStep` (its own `try`; a failure is logged at WARNING naming the step and the steps after it still run): `transition(DEVICE_LOST)` (the `recording` property turns false, so REC goes off), the status *"Audio device lost — `<device>`; saving the take"*, the `DawIcon.WARNING` glyph, the MIDI recorders of a mixed take stopped as the Stop path stops them, and `TransportController.finishDeviceLossStop(wasRolling, stoppedAtFrames)` — the Stop tail (the `Stopped` announce if the transport was rolling and is now stopped; the idle stream stop, unless a stream is OPEN (`audioEngine.isStreamOpen()`: RUNNING or PAUSED) — on that turn it can only be a post-loss reopen, since the loss closed the stream before publishing; see "The fast re-plug race" under Known limitations; status; Record-button reset; no post-roll). A UI step that throws therefore never skips the seal (`DeviceLossRescueStepIndependenceTest.theRescueIsRequestedBeforeTheStateBecomesDeviceLost` samples, at the DEVICE_LOST change, a pipeline already inactive and a take already being written). `stopAudioTake()` takes its DEVICE_LOST exit only while no pipeline is active (`recordingPipeline == null || !recordingPipeline.isActive()`); a DEVICE_LOST that somehow held an active pipeline — no path does today — falls through to the ordinary stop, so the machine can never hold an active pipeline with no exit. RECORDING with only MIDI recorders: there is no audio to rescue and the engine that drove the transport is stopped, so the take is stopped through the ordinary Stop (the controller's own notification covers the loss). PREPARING: `cancelPendingStart()`, `ABORTED`, MIDI stopped, transport stopped, ERROR *"Recording aborted — no take was started: audio device `<device>` was lost while the take was being prepared"*; it settles to IDLE as failed starts do (book §3.2 has no arrow from PREPARING to DEVICE_LOST). Any other state changes nothing. COUNT_IN is never observable to a posted event — `announceRecordingStarted` passes through it in one call — so no branch exists for it.
- **`onLostDeviceReturned(DeviceId)`.** Only while DEVICE_LOST, and identity-matched (fix round r2) with the controller's own predicate, `DefaultAudioEngineController.sameDevice`: `lostDeviceReturned = true` either way; when the device delivered with the state is the lost one (or none was remembered), the transport is seeked to the rescued take's start anchor — `RecordingPipeline.getRecordingStartBeat()`, the manifest's `start-beat`, which only the next `prepare()` replaces — and the INFO is *"`<device>` reconnected. Tracks are still armed; press Record to continue."*; when it is another device (the instrument-audio open above), nothing is seeked — the playhead belongs to whatever opened that stream — and the INFO is `lossEndedOnAnotherDeviceMessage`: *"Audio is now on `<device>`; `<lost device>` did not return. Tracks are still armed; press Record to continue."*; then `settle()` (`TheLossEndingOnAnotherDeviceIsNotTheLostDevicesReturnTest`: the mismatch settles to IDLE with the position unchanged, `recordAvailable` true and the armed set kept; a device matching by name alone is the return, with the seek). Nothing on either path disarms a track.
- **`settle()`** leaves DEVICE_LOST for IDLE only when `lostDeviceReturned` and nothing is pending (book §5.2: settlement alone cannot clear it). Pressing Stop while DEVICE_LOST (`TransportController.stop()` routes its not-rolling, nothing-in-flight branch to `stopAudioTake()` instead of the double-stop rewind) and a configuration request while DEVICE_LOST both leave through FINALIZING and settle to IDLE once the rescued take's publication has ended, the configuration being reserved then. Record and Play are refused while DEVICE_LOST with one WARNING shape, built by `RecordCoordinator.unavailableWhileDeviceLostMessage(action, device)` and shown by `refuseWhileDeviceLost` (log; status bar with the warning glyph; WARNING toast): *"Record is unavailable — audio device `<device>` is still disconnected; reconnect it, press Stop, or choose another device in Audio Settings"* from `onRecord` (`refreshRecordAvailability` keeps `recordAvailable` false in DEVICE_LOST, so the button is disabled and the refusal answers the command path), and *"Playback is unavailable — …"* from `TransportController.start()` and `playWithPreRoll()`, before the engine is touched — otherwise the provision ladder could open a fallback rung and roll the transport under a status that says "Device lost". A rescue whose seal failed (`stopSealFailure` present) goes through the existing `reportTakeFinalizationFailure`: DEVICE_LOST → ABORTED → IDLE, the ERROR of `stopSealFailedMessage`, no "saved" wording, nothing registered.
- **Publication of a rescued take** (`completeWrittenTake`): the completion first; then, for a rescue whose every lane sealed (`pipeline == rescuedTakePipeline && lostDevice != null && stopSealOutcome.of(pipeline).isEmpty()`), the take is registered with the registry (`registerSealedRescue(pipeline, clipCount, sealedSegments)` → `rescuedTakeRegistration`, whose default is `registerRescuedTake(RescuedTake)` → production `IncompleteTakeStore.register`, try/caught) **before any report** — a rescued take is on disk whatever follows; then the clips, undo entry and dirty mark (`publishRecordedTake`) and the report. When the audio could not be read back (`unloadedReport`) or a MIDI recorder of a mixed take failed to close (`midiStopFailure`), the ERROR leads with `rescuedTakeMessage` — *"`<device>` disconnected during recording. The take was saved up to the dropout: …"* — instead of *"Recording stopped — …"*, joined to the failure by `joinedReport` (the head's terminal period is dropped before the `"; "`, so no report reads `".;"`), and the state goes DEVICE_LOST → ABORTED → IDLE as for any finalization failure, the registration kept (`DeviceLossRescueStepIndependenceTest.aRescueWhoseAudioCannotBeReadBackIsStillRegisteredAndReportedAsADeviceLoss`). Otherwise `showRescuedTake`: status *"Audio device lost — `<device>`; take preserved"*, and the WARNING (not ERROR: nothing failed on our side) *"`<device>` disconnected during recording. The take was saved up to the dropout: N clip(s) on M track(s)."* — with no clip, *"`<device>` disconnected during recording; nothing had reached disk yet."* — shown with the action label **Review** (`rescuedTakeNotification`, production `notificationBar.show(WARNING, message, "Review", action)`). Review sets the status to *"Rescued take: audio/takes/`<dir>` — mm:ss.t recorded"* (the longest clip at the transport's tempo at publication) and, while the transport is STOPPED or PAUSED (a paused playhead is not playing), seeks it to the take's start anchor; over a rolling transport it never moves the playhead (`…EngineBridgeTest.reviewOverARollingTransportSetsTheStatusButDoesNotSeek`). Review seeks only; nothing selects the rescued clips (Known limitations). N is the number of clips the completion returned — one per track; a loop take's laps live inside the track's take group — and M the number of tracks with a recorded clip. `finalizationFailureReport` cannot call a device-loss rescue a failure: it reads only `earlySeal()` — which never completes for a requested stop — and `stopSealFailure()` — empty when every lane sealed, whatever reason the stop was requested with (`DeviceLossSealContractTest`).
- **Visibility.** `TransportController.updateStatus()` renders the record state when it is DEVICE_LOST: text *"Device lost"*, style class `status-device-lost` (`styles.css`, `-fx-text-fill: -warn`, the theme's warning token) and the `DawIcon.WARNING` glyph, in place of the transport-state branch. The §6.5 strip cell is story 338's and binds to the same `stateProperty()`/`statusProperty()`.

### The rescue window, numerically

The coordinator's one-shot stop does no storage I/O and never waits (`RecordingLifecycleCallerThreadSentinelTest` walks both `requestStop` forms). `CaptureFlushService.requestStop(reason)` sets the stop flag and wakes the flush thread at once; the thread's dry-ring park is in any case bounded by `PARK_BACKSTOP` = 50 ms. It ends its drain loop at the next pass boundary, waits at most `PRODUCER_QUIESCENCE_BOUND` = 4 × 50 ms = 200 ms for a callback still inside the ring's producer gate (the pipeline closed the gate before the request), drains the ring — sized for at least `CaptureRing.DEFAULT_HANDOFF_TOLERANCE` = 250 ms of audio at the stream format — seals every active writer (force, header patch, atomic rename) and writes the final manifest (up to `MANIFEST_WRITE_ATTEMPTS` = 5 attempts; the segments are sealed regardless). The live rescue therefore keeps every block the callback delivered before the gate closed, less what book §4.2 already drops (an overflowing block; the block that straddles the stop). The 5-second force cadence (`SegmentWriter.DEFAULT_FORCE_CADENCE`, `RecordingPipeline`'s default) bounds only what a crash or power loss — which the live rescue never reaches and the recovery scan handles — can take from a take: the frames since the last force.

### The rescued-take registry

`IncompleteTakeStore` keeps its name (the book and stories 332/334/339 reference it) and has a new body: `IncompleteTakeStore(Path projectDirectory)`, `projectDirectory()`, `record RescuedTake(Path takeDirectory, TakeManifest.SealedBy reason, Optional<String> deviceName, Instant registeredAt, int clipCount, int sealedSegmentCount)` — compact constructor refusing nulls, any reason but `DEVICE_LOSS`/`CRASH_RECOVERY`, a relative path and negative counts — `register(RescuedTake)` (`IllegalArgumentException` unless the take directory's parent is exactly `<project>/audio/takes`, absolute and normalized: a take in the OS temporary directory or in another project is never a take of this one), `rescuedTakes()` (unmodifiable snapshot, registration order), `latest()`, `isEmpty()`, and `registerRecoveredTakes(Path audioDirectory)` (refuses another project's audio directory; runs `TakeRecovery.scan` over `<audio>/takes` and registers each result with reason `CRASH_RECOVERY`, `clipCount` = distinct track ids of its playable segments, `sealedSegmentCount` = their number, no device name — a take whose every remaining file was unrecoverable, or whose only streaming entry was an empty standby `.part` the scan deleted, is registered with zero of each so the user is told it is there). Backed by a `CopyOnWriteArrayList`; any thread. `RecordCoordinator` owns one per project, created lazily by `rescuedTakeStore()` from `projectDirectory()` (empty for an unsaved project; an audio take is refused without a directory, so a rescue always has one). Nothing in main source calls `registerRecoveredTakes` yet — story 332 is to invoke it on every project-open path.

### Manifest, flush service, pipeline (`daw-core`)

`TakeManifest.SealedBy` gained `DEVICE_LOSS("device-loss")` and `CRASH_RECOVERY("crash-recovery")`, and the manifest an optional scalar `sealed-at=<ISO-8601 instant>`: written by every seal since this story (`CaptureFlushService.sealAll` stamps `Instant.now()` — no wall clock is injected anywhere in the service; its only clock is the monotonic `nanoClock` — and `TakeRecovery` stamps its own), refused by the builder and the parser on a streaming take, absent in a sealed manifest older than this story and read as `Optional.empty()`; `MANIFEST_VERSION` stays 1. `sealAll` is otherwise unchanged: `first == STOP && !sealFailed` is the only `sealed` outcome, so a `DEVICE_LOSS` request with every lane sealed lands as `aborted`/`device-loss` (book §3.4 RESCUED) and one with a lane that threw as `aborted`/`write-failure` with `stopSealFailure` recorded, exactly as for a Stop. `RecordingPipeline.requestStop(TakeManifest.SealedBy)` accepts `STOP` and `DEVICE_LOSS` only (`IllegalArgumentException` otherwise — the pipeline never writes `CRASH_RECOVERY`, and the flush thread's own reasons are its to raise); `requestStop()` delegates with `STOP`; a repeated request keeps the first reason, because the service records the reason of the first stop request it receives. The start anchor is the existing public `getRecordingStartBeat()`, whose Javadoc now states that it outlives the take. `SegmentWriter.patchSizeFields(FileChannel, long)` is the extracted package-private header patch that `seal()` and the scan share (`SegmentWriterTest.patchSizeFieldsWritesTheHeaderSealWrites`). Nothing on the callback changed; `RealTimeSafeContractTest` is green.

### The crash grammar

`TakeRecovery.scan(Path takesDirectory)` and `TakeRecovery.recover(Path takeDirectory)` (`core.recording`, exported) implement book §4.7. A take directory is a candidate when its `take.manifest` parses and either reads `seal-status=streaming` or lists a segment entry still in state `streaming` — whether that entry's `.part` exists, its `.wav` exists, or neither does. A sealed or aborted manifest whose every entry is sealed is not a candidate, even when an unlisted `.part` lies in a track directory (a standby the live seal could not delete): `recover` returns empty, logs the orphan at WARNING once per scan and leaves it untouched, so a healthy take is never registered as recovered (`TakeRecoveryTest.aSealedTakeWithAnUnlistedOrphanPartIsNotACandidate`); a second scan returns nothing for a recovered take; a directory with `.part` files but no manifest is logged and skipped, since the manifest is the only record of the format and the anchor. For every streaming entry whose `.part` exists and holds frames: frames = ⌊(length − 44) / bytesPerFrame⌋ (a torn trailing frame is dropped), with the manifest's bit depth, the track entry's channel count and the header sample rate cross-checked against the file's header (`SegmentFile.describe`); the file is truncated to whole frames, its sizes patched with `SegmentWriter.patchSizeFields`, forced, atomically renamed to `.wav`, and the entry replaced by `entry.sealed(frames)` — byte-identical to a writer-sealed segment (`theRecoveredHeaderIsByteIdenticalToTheWritersOwnSeal`). A `.part` whose header agrees with the manifest but holds no whole frame — the 44-byte header a loop-record standby or a fresh rotation tail leaves — is deleted and its entry removed from the manifest (`TakeManifest.Builder.removeSegment`), as the live seal discards an empty tail (`RecordingSession.discardEmptyTail` → `CaptureFlushService`'s `onSegmentDiscarded` → `manifest.removeSegment`): neither sealed nor reported, so `playableSegments()` and the registry's `sealedSegmentCount` exclude it; a take whose only streaming entry was such a standby recovers with no segment and a manifest reading `aborted`/`crash-recovery` with `sealed-at` and no `segment=` line (`anEmptyStandbyPartIsDeletedAndItsEntryDropped`, `aTakeWhoseOnlyStreamingEntryWasAnEmptyStandbyIsRecoveredWithNoSegments`); an empty `.part` whose delete fails is reported and its entry kept, so the next scan retries. A streaming entry whose `.part` is gone but whose `.wav` exists is marked sealed from the `.wav`'s data size — which is also how the next scan records a segment renamed by a scan whose manifest write then failed (`aRenameTheManifestNeverRecordedIsRecordedByTheNextScan`). A `.part` shorter than the header, one whose header disagrees with the manifest, one holding more data than a segment may (`SegmentWriter.MAX_DATA_BYTES`), one whose sealed sibling already exists, one of a track the manifest does not list, a segment with neither file, and — under a candidate — a `.part` the manifest does not list (the manifest write lagged the open; `segment-NNN.wav` encodes the index but not the lane, so no entry can be derived for it) are reported in `RecoveredTake.unrecoverable()` and left byte-for-byte untouched, never deleted. When the manifest was streaming or any entry changed (sealed or discarded), it is rewritten atomically with `seal-status=aborted` and `sealed-at` now; the reason is `crash-recovery` only for a take that was still streaming — a take the flush thread had already aborted keeps the reason it found (`write-failure`, `device-loss`, …) and the `sealed-at` it found — the scan stamps its own instant only for a take it ended itself, or for one that had none (`aLeftoverPartUnderAnAbortedManifestIsSealedAndTheFoundReasonIsKept`, fix round r2) — so the audit trail of why and when the take ended survives the scan. `RecoveredTake(takeDirectory, manifest, sealedSegments, unrecoverable)` carries `playableSegments()`. The result is playable: `SegmentFile.readFrames` returns exactly the declared frames. No throwable escapes `scan` for one take: every `Unrecoverable` reason and log line goes through `reasonOf`, which substitutes the exception's simple class name for a null or blank message (`ClosedChannelException` → `"ClosedChannelException"`; `anExceptionWithoutAMessageIsReportedByItsClassName`), and the per-take catch is `IOException | RuntimeException` — logged at WARNING, the take skipped, the next take scanned (`aRuntimeFailureInOneTakeDoesNotAbortTheScanOfTheNext`, through the package-private `setRecoverFaultForTest` seam: no cross-platform on-disk shape reaches a `RuntimeException` any more — `TakeManifest.parse` wraps its `IllegalArgumentException`s into `IOException`, and the one that did, `patchSizeFields` on a `.part` over `MAX_DATA_BYTES`, is now refused with an `IOException` naming the file).

## Known limitations

- **Identity is matched by name when `DeviceId` differs (follow-up story 352).** `DefaultAudioEngineController.sameDevice` accepts `DeviceId.equals` and otherwise equality of the friendly name across backends; the coordinator's return tests the same predicate (fix round r2), so its mismatch path cannot tell two identical interfaces apart either. Two identical interfaces whose names carry no serial are indistinguishable: after the loss of one, the other's arrival (or re-enumeration) reopens the engine on it, the coordinator reports the lost device as returned and seeks to the rescued take's anchor. `docs/user-stories/352-stable-audio-device-identity.md` owns a stable hardware key (backend + VID/PID/serial) with an ambiguous name-only match staying DEVICE_LOST.
- **No shipped backend publishes `DeviceRemoved`/`DeviceArrived`.** Only `MockAudioBackend` does; `AsioBackend`, `WasapiBackend` and `CoreAudioBackend` publish `FormatChangeRequested` only (story 218's path). A yanked USB interface therefore produces no event on the primary platform until story 338's callback-heartbeat watchdog or OS device watcher declares the loss into the same `EngineState.DEVICE_LOST` — the story's Non-Goals anticipated this: detection degrades to the mock-fixture test path. The hardware proof is manual and pending that feed.
- **Unlisted `.part` orphans are reported or logged, never recovered.** Under a candidate take (a streaming manifest, or a listed entry still streaming) a `.part` the manifest does not list is reported in `unrecoverable()` and left untouched; under a sealed or aborted take whose every entry is sealed it earns one WARNING log line per scan and the take is not a recovered take — it is never registered. A take directory with `.part` files but no manifest is logged and skipped. A take whose manifest was already `aborted` (a Stop whose lane rename failed; a device-loss rescue with a lane that threw) and still holds a `.part` is recovered with its original reason and its original `sealed-at` kept (`write-failure`, `device-loss`, …; the scan stamps its own `sealed-at` only for a take that was still streaming, or one that had none); the registry still records it as `CRASH_RECOVERY` — `RescuedTake` admits only `DEVICE_LOSS` and `CRASH_RECOVERY` — so the registry reason means "came from the scan" while the manifest carries the audit reason.
- **Review seeks only, and only while the playhead is not playing.** The notification's Review action sets the status text and, while the transport is STOPPED or PAUSED (a paused playhead is not playing), seeks it to the take's start anchor; over a rolling transport it only sets the text. It does not select the rescued clips (no selection seam exists in `TransportController`/`RecordCoordinator`, and none was plumbed through `MainController`).
- **Two toasts per loss and per return, every controller message at WARNING.** In production the controller's sink and the coordinator share one `NotificationBar`: a loss during a take shows the controller's *"Audio device disconnected — playback paused"* and then the coordinator's rescue WARNING; the return shows the controller's *"Audio device reconnected — review recovered take and re-arm transport"* and the coordinator's INFO *"`<device>` reconnected. Tracks are still armed; press Record to continue."* (when the loss ends on another device, `onDeviceArrived` did not run, so no "reconnected" toast precedes the coordinator's *"Audio is now on `<device>`; `<lost>` did not return. …"*). Nothing suppresses the controller's message when a take was in flight (the controller has no record-state fact) and `MainController`'s sink does no string matching; every controller message — including *"Audio engine reconfigured"* — rides at WARNING. Notification levels, deduplication and rate limiting are story 339's app-wide injection (Non-Goals).
- **Pending feeds and callers.** Story 338's watchdog is the only planned path to a hardware-declared loss; story 332 is the only planned caller of `IncompleteTakeStore.registerRecoveredTakes` (no production caller exists). Story 334 owns persisting rescued takes in the project file; the registry is in-memory and per project.
- **Which engine states reach a DEVICE_LOST coordinator.** The return is the first `STOPPED` or `RUNNING` delivered with the stream open, identity-matched by the coordinator. Its producers are `onDeviceArrived` (the lost device, by `sameDevice`: reopen, park, `STOPPED` from the stream-open seam) and `onStreamOpened` for an open the controller did not drive — Play and Record are refused while DEVICE_LOST, so that is the instrument-audio open of `MainController.pluginGraphChanged` (not gated: auditioning an instrument while the interface is unplugged is legitimate), whose rung is whichever the ladder opened — another device while the interface is unplugged, which the coordinator reads as the loss ending elsewhere (no seek; the "did not return" INFO; IDLE with the armed set kept), or the lost device itself if it is physically back and the ladder, which honours the configured `DeviceId`, lands on it, which is the return. A `FormatChangeRequested` while DEVICE_LOST publishes `RECONFIGURING` and then a closed-stream `STOPPED` (`performFormatChangeReopen` restores only a stream that was open; the loss closed it), which is ignored and keeps the latch, as is any `STOPPED` with the stream closed (a failed or refused reopen). A Settings apply never reaches a DEVICE_LOST coordinator — `requestConfigurationChange` leaves DEVICE_LOST through FINALIZING and settles to IDLE before the apply's permit is granted (`ASettingsApplyLeavesDeviceLostThroughFinalizingTest`); after a loss the apply restores nothing (`wasOpen` false) and publishes its `STOPPED` with the stream closed.
- **A rescue whose seal failed is not registered** and is reported through the existing ERROR path (DEVICE_LOST → ABORTED → IDLE). A rescue whose every lane sealed but whose audio could not be read back, or whose MIDI recorder failed to close, *is* registered and takes the same ERROR path with the device-loss wording.
- **A MIDI-only take's device loss is an ordinary Stop and a PREPARING loss an ordinary failed start**; neither has a dedicated test.
- **The still-writing warning is reused unchanged for a rescue**: its log line says "after its Stop".
- **The fast re-plug race.** When the device returns before the loss's FX turn has run, `onDeviceArrived` reopens and parks the stream on the device-event thread; `finishDeviceLossStop` leaves any stream it finds OPEN alone (`isStreamOpen()`, RUNNING or PAUSED — fix round r2; it used to test PAUSED and so closed a stream caught between `startAudioOutput()` and `pauseAudioOutput()`), so the `STOPPED` that follows arrives with the stream open and is the return; the controller's *"reconnected"* toast precedes the coordinator's rescue WARNING and its INFO, and nothing is stranded. What remains is the open call itself: `AudioEngine.startAudioOutput()` sets the open state inside its lifecycle lock, so a stop tail that reads `isStreamOpen()` while that open is still in progress sees it closed, waits for the lock in `stopAudioOutput()` and closes the fresh stream; the seam's `STOPPED` then arrives with the stream closed and is ignored, the engine is `STOPPED`, and the coordinator stays DEVICE_LOST — Play and Record refused — until Stop or a Settings apply; a later `DeviceArrived` of the device reopens nothing, because the engine is no longer `DEVICE_LOST`, and the user opens it again by Play after the Stop or in Audio Settings. Not pinned — no fixture controls the interleaving.
- **Loop-record counts in the rescue message.** `clipCount` is one clip per track (a loop take's laps live inside the track's `TakeGroup`; only the active lap is a clip on the lane), so a four-lap loop take reads *"1 clip on 1 track"*, and `trackCount` equals it in practice. The recorded length in the Review status is computed once, at publication, at the transport's tempo then. Accepted and documented, not changed.
- **`EngineState.DEVICE_LOST` ends on any stream open, including one the controller did not drive.** After a Stop that left the record state IDLE, a Play or Record opens whatever rung the provision ladder yields; the watch is re-pointed to it, the engine state becomes `STOPPED`, and a loss of that device is a new loss, published and rescued. Play and Record are refused only while the *record* state is DEVICE_LOST.
- **Once another stream has opened, a later `DeviceArrived` of the original device reopens nothing and says nothing.** `onDeviceArrived` returns at once unless the engine state is `DEVICE_LOST`, and any stream open ends that state — including the instrument-audio open that ended the loss on another device. The user selects the original interface again in Audio Settings (the provision ladder honours the configured `DeviceId`, so after a Stop the next Play may open it too).
- **A second Stop while the rescued take is still being written is the double-stop rewind.** The first Stop while DEVICE_LOST leaves through FINALIZING (`stopAudioTake`), and a take being written does not count as in flight (`isRecordingInFlight()`), so a second Stop over the stopped transport is the ordinary double-stop gesture: the playhead returns to zero when `Transport.isReturnToStartOnStop()` says so. The rescued clips stay anchored where the take started, and the Review action restores the anchor.
- **A loss during playback with no take in flight leaves the transport model PLAYING over the closed stream until Stop.** Pre-existing — story 214's chain: `onDeviceRemoved` stops the output and the engine, no engine or controller close path writes the transport model's state, and `onDeviceLost` changes nothing when no take is in flight. The controller's *"Audio device disconnected — playback paused"* toast covers it; the next Stop stops the model.
- **`sealed-at` of a scan-healed, already-aborted take is the flush thread's instant.** `TakeRecovery` stamps its own `sealed-at` only for a take that was still streaming, or one that had none; a take the flush thread had aborted and that still held a `.part` keeps the instant the flush thread wrote, although the scan sealed the leftover segment later — the manifest dates the end of the take, not the heal.
- **Javadoc outside this story's original files was brought in line in the fix round**: `EngineState` (the class note says the transport status shows the loss; `DEVICE_LOST` says an in-flight take is rescued on disk by the record coordinator and that any stream opening ends the state; "automatically reopen" stays — it is true), `AudioEngineController` (the bridge is named; the coordinator rescues the take), `DefaultAudioEngineController.onDeviceArrived` (why the subscription outlives the close), `AudioBackendSupport` (the device-event publisher is never completed and is collected with the support; subscribers that must stop cancel). The transport status reads *"Device lost"*; the strip cell is story 338's. Fix round r2 put the producer enumeration above into `TransportController.onEngineState`, `finishDeviceLossStop` and the `deviceLost` latch (a superset of "the coordinator is DEVICE_LOST": it may stay set after a closed-stream `STOPPED` or after Stop or a Settings apply left DEVICE_LOST — harmless, since `onLostDeviceReturned` ignores every state but DEVICE_LOST and a new `DEVICE_LOST` re-latches), `EngineStateBridge` and `RecordCoordinator.onLostDeviceReturned`.
- **The seal of a rescue reads `aborted`, not `sealed`.** `SealStatus.SEALED` is reserved for a Stop whose every lane sealed; a device-loss take with every lane sealed is `aborted`/`device-loss`, per book §3.4's RESCUED row — readers must not treat `aborted` as "nothing playable".
- **`sealed-at` is absent in manifests sealed before this story** and reads as empty; `MANIFEST_VERSION` is unchanged.
- **Research citation softened.** The Technical Notes cite "`research-daw` §3 — hot-plug robustness and never-block-the-callback discipline on device teardown"; the skill's lesson 3 is *Real-Time Audio Processing — lock-free audio thread, ring buffers, fixed-size blocks, priority scheduling*. The architecture lesson it means is the lock-free audio thread and the never-block-the-callback discipline, which this story keeps (detection on the device-event thread, rescue on the FX and flush threads, nothing new on the callback); the skill says nothing about hot-plug as such.
- **One unexplained timing outlier** in the implementation runs: `DeviceLossRescuesTheTakeThroughTheEngineBridgeTest` took 20.44 s in the first run after the SDK fix and 1.0–2.6 s in every later run; no product wait on the paths involved has a constant of that size.
